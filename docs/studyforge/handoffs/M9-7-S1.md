## How the practices were made

- **Shape.** Each practice is a LeetCode/CodeSignal-style Java task. It has:
  - a statement that keeps every example the page has;
  - a starter that compiles and throws `UnsupportedOperationException`;
  - JUnit 5 + AssertJ tests, one test method per case;
  - the pilot's workspace `pom.xml`: the course's versions, with Byte Buddy 1.17.5 pinned in `dependencyManagement`.
  - Run is `mvn -o -q -f <ws>/pom.xml compile`, and Submit is `... test`.
- **Cases.** Each practice has one main case, the ask, and 1 to 4 edge cases. Each edge case has its own planted wrong solution, which passes the ask and fails that edge.
- **Density.** Code-heavy, at the pilot's density: 4 to 6 practices per page, plus one short quiz (1 to 2 questions) set with `Page.quiz`. Order comes from `Page.order`, not from name prefixes.
  - 1.3.3 and 1.5.4 carry 3 practices each. 1.3.3 is a one-idea page, pass-by-value. Most of 1.5.4 repeats 1.2.5 and 1.5.3, which already practise it.
- **Authorship.** A scripted author drafted each exercise through `author_corpus`. The drafts and the driver are in scratch and are not committed. Everything they produced is in the bundles.
- **Proof before the real pass.** Every module was first run as a dry pass in a scratch clone of this branch, with live runner gates. The worktree pass then re-ran every gate live. Every exercise shipped on its first attempt there: no shortfall, no bare page, no missing excuse.
- **Quiz readers.** Every Q1, Q2 and Q3 reading was taken by a separate agent. No question was judged by its author.
  - Q1: two agents per question, each given the page and the unkeyed question.
  - Q2: `Q2_PROMPT` verbatim, answered from the question alone (`page_free`).
  - Q3: one agent per wrong option, quoting the passage that rules it out.
  - It took four rounds:
    - **r1** covered all 33 questions. Q1: both readers picked the key on 33 of 33. Q3 ruled out 66 of 66 wrong options. Q2 found a giveaway in 5 questions.
    - **r2** re-read the 5 reworded questions. Four held. `q-arrow` still echoed the stem's words.
    - **r3**: `q-arrow`'s new option c was not ruled out by the page.
    - **r4**: `q-arrow` holds on Q1, Q2 and Q3.
  - Each round re-read only the questions whose wording changed. Every reading is recorded in the quiz's own `gates.json`.

## Findings

- **F1. 1.2.5 links no test file.** The other 17 pages link their test, but `README_1.2.5.md` does not. I declared the module's `SwitchExpressionTest.java` its grader by reading the tree. The skill cannot find it from the page.
- **F2. Quizzes without readings spend the attempt budget.** A quiz gated before its independent readings exist fails Q1 and Q2 on every attempt, and uses up `ATTEMPTS`. Nothing in the skill separates "gate the code now" from "gate the quiz once readings exist". I worked around it with dry passes in scratch clones, and took the readings between them.
- **F3. There is no per-exercise prove harness.** The only way to see whether one draft clears G1 to G5 is to run a whole pass over its module. Proving took scratch clones, a dry-run judge and a flock around each clone.
- **F4. Changing a shipped exercise needs a delete in the corpus.** A fixed draft on an unchanged page is silently reused (R10), so the fix never takes effect. The skill's remedy is to remove the unit's directory from the corpus, which conflicts with an office's "delete only under scratch" rule. I resolved it through a scratch clone and a fast-forward (above). The skill could offer a way to supersede a unit named on purpose.
- **F5. Q2 keeps finding stem echoes.** Five of 33 questions were refused on r1, and `q-arrow` needed four rounds. The cue each time was a word the key shared with the stem ("body", "run", "case") or a key that broke the options' template. Author-side self-review missed these every time. A quick automated check for key/stem word overlap would save rounds.
- **F6. A reader wrote to scratch.** The r1 Q3 agent copied pages into the scratchpad to read them, then deleted the copies. Later rounds told readers to copy nothing, and none did. This is a process note: no page or answer was altered.
- **F7. Load.** Gate runs took about 2 s on an idle host and 25 to 33 s at a load average of 150 to 220, while the other offices ran. Nothing failed from load, but the whole pass took about 30 minutes.
