  16. Check yourself: singletons

The partner's payment API allows 100 calls a minute per API key. The service keeps the budget in PartnerQuota, a singleton, so that every thread draws from one counter. Last Tuesday the partner throttled the key for an hour: its logs show 200 calls in one minute, all from one process. Somewhere in that process a second PartnerQuota existed, although its constructor is private.

A hand-written singleton can be copied in three ways, and none of the usual forms closes all three. The examples use this quota (all outputs are from Java 21):

A Private Constructor Stops new, and Nothing Else

Spend this minute's budget, then call the private constructor through reflection:

private is checked by the compiler and by the access check that setAccessible(true) switches off. Whoever holds the copy has another 100 calls. DI containers and JSON mappers that build objects reflectively make the same call.

The defence is a constructor that refuses to run twice: it reads the instance field, which must already be set when anyone else calls it.

Reflection against each, the lazy one before anything has called getInstance() (the guard's exception arrives as the cause of an InvocationTargetException):

newInstance initializes GuardedQuota first, and class initialization builds INSTANCE, so the reflective call finds the field set and fails. The lazy field is still null when reflection comes first, so the copy gets through, and getInstance() builds another. A guard on a boolean flag lets a reflection-first copy through too, after which getInstance() throws; and reflection can reset the flag. It can't reset a static final field: Field.set on INSTANCE threw IllegalAccessException: Can not set static final GuardedQuota field GuardedQuota.INSTANCE to null value.

Named modules refuse `setAccessible`. If the singleton's package is in a named module that doesn't opens it, setAccessible(true) from another module throws InaccessibleObjectException, as it does for JDK classes (unit Public, private, protected, and default access modifiers). On the class path nothing stops it.

Deserialization Makes a Second Instance Without Running the Constructor

The quota is Serializable because it travels in a cached session. It has the guard from above, and its constructor prints a line. We take 60 calls, write INSTANCE to an ObjectOutputStream, take 40 more, and read the bytes back:

The constructor ran once, during class initialization. Deserialization never calls it: it allocates the object, runs the no-arg constructor of the first superclass that isn't Serializable (here Object), and fills the fields from the stream. The guard never runs, and the copy resumes with the 40 calls it had when it was written.

When a serializable class declares readResolve, readObject returns what that method returns instead of the object it just built:

The caller gets the live instance with the live count. Whatever the stream held is discarded with the object built from it, which is why left is transient here: there is no point writing state that is thrown away on arrival.

Each Class Loader Has Its Own Singleton, Enum Included

A static field belongs to a class, and a class is identified by its name and the loader that defined it. Two loaders that each define Quota from the same bytes have two classes, two static fields and two budgets. Application servers give each web application its own loader, and plugin hosts give each plugin one, so a library jar copied into two of them is loaded twice.

Public copies of Quota and of an enum QuotaEnum with the same counter are compiled into a directory, pluginJar, which is also on the application's class path. Two URLClassLoaders read it, each with the platform loader as parent, so neither can find the class through its parent, as in an isolated plugin host:

The enum gives no protection here: its constant is a static field like any other. The cast fails because the Quota named in the program's own source is the application loader's class, a third one.

Loaders delegate to their parent before defining a class themselves. With the application loader as parent, which has the directory on its class path, the class is defined once, whichever loader is asked:

So a singleton meant to be one per process lives in a jar that only the shared parent loads (the server's or the host's lib), and plugins must not ship their own copy. A host that loads plugin classes child-first, to let each plugin bring its own library versions, has to send the shared API packages to the parent explicitly.

The Holder Idiom Chooses When the Instance Is Built; Only the Enum Refuses Copies

One program applies the three attacks to five forms, reflection first, before anything has called getInstance(). Each form is Serializable and has a getInstance(). PlainQuota is the eager class with a private constructor, ResolvedQuota adds the guard and readResolve, HolderQuota keeps its instance in a nested class, GuardedHolderQuota is that holder with the same two additions, and EnumQuota is a one-constant enum:

The holder idiom answers when and how safely the instance is built. The nested class is initialized on the first getInstance(), under the JVM's class-initialization lock, so it is lazy and needs no volatile (unit Synchronization and memory consistency, which also shows why double-checked locking needs one). By itself it protects against none of the three attacks. GuardedHolderQuota's guard holds even when reflection comes first: the guard's read of Holder.INSTANCE starts the holder's initialization, which builds the real instance (the inner constructor call sees null), and the reflective call then finds the field set and throws.

The enum refuses both copies with no code: Constructor.newInstance rejects enum classes, and an enum is serialized as its name and read back with valueOf (unit Use Cases and Examples runs both). An enum can't extend a class, and its constant is built as soon as anything initializes the enum, such as a call to values(). Every form here except a lazy synchronized field builds its instance in a static initializer, and one that throws leaves the class unusable for as long as its class loader lives (unit Proper synchronization to ensure memory visibility). A constructor that calls a remote service belongs in none of them.

A Static Singleton Carries One Test's State Into the Next

A PartnerClient that looks up the quota itself has two tests. Each passes when run alone (JUnit 5.10.2, methods run in name order):

Every test in one JVM shares the static instance, so the first test spent the budget the second one needed. Which test fails depends on the order. The usual patch, a resetForTesting() method called from @BeforeEach, works only while every test class remembers to call it and while tests run one at a time: with JUnit's parallel execution on, two tests share the instance while both are running.

The fix is to stop looking the instance up. PartnerQuota becomes an ordinary class with a constructor, PartnerClient takes it as a constructor parameter (unit Dependency Inversion Principle (DIP)), and main builds the one instance and hands it to everyone who needs it:

Each test now builds new PartnerClient(new PartnerQuota(100)), and the same two tests pass together and alone. No static field exists for reflection, serialization or a second loader to duplicate, and a test that wants an exhausted quota builds one with a limit of 0. Another new PartnerQuota(100) in production code compiles, though, and only review catches it. A DI container's singleton scope is the same arrangement, with the container as main.

Summary

  • A private constructor stops `new`, and nothing else. Reflection calls it; a guard that reads the static final instance field refuses the second call, one that reads a lazily set field doesn't.
  • Deserialization builds a second instance without running the constructor. readResolve returning the instance gives callers the live object and discards the state that was written.
  • Each class loader has its own singleton, enum included. One per process means one shared parent loader and no copy of the class in any child.
  • The holder idiom decides when the instance is built; only the enum refuses copies without extra code. No form survives a second loader, and every static form makes a failing constructor fatal for its class.
  • A static singleton carries one test's state into the next. Build the one instance in main and pass it through constructors; tests then build their own.

Challenges

  1. A singleton is in a library that two web applications on one Tomcat both bundle. Moving the jar to Tomcat's shared lib makes it one instance. What else changes for those applications, such as redeploying one without the other?
  2. Your codebase has 40 calls to Clock.getInstance(). Plan the move to a constructor-injected clock in steps that each leave the build green.
  3. A metrics registry is a singleton so that libraries with no access to main can register gauges. Is that a reason to keep it static? What does the JDK's ServiceLoader (unit Dependency Inversion Principle (DIP)) offer instead?

Design Note: One Instance Is a Decision of the Program, Not of the Class

The pattern puts two decisions in one class: that the program needs exactly one of something, and how everyone finds it. The first is usually right. The second, a static field reachable from anywhere, is the part that reflection, serialization and class loaders duplicate and that tests can't replace.

Moving the decision to main costs the guarantee and some plumbing: every class that needs the quota has to receive it. The enum keeps the guarantee and the global access, which suits a stateless strategy or a constant table. For anything with state that tests need to control, or that must stay one per process across class loaders, one instance built at the composition root is the form that none of the three copies can reach and every test can replace.

Problem statement


The product is sold for 25 concurrent seats, and SeatLicense counts them: one instance per process, reached through getInstance(). A seat audit found customers using more seats than they paid for, and two SeatLicense objects in one process on two occasions. The first appeared at start-up, when the plugin framework instantiated every class of the package through its private constructor before anything had called getInstance(). The second appeared after the session store wrote a user's session out and read it back.


Finish the two TODOs in src/main/java/practice/SeatLicense.java:


  • checkConstruction(), which the constructor runs every time, whoever calls it;
  • readResolve(), for a license that is read back from a session.


When you're done, neither the framework nor the session store can produce a second license, and a session read back counts against the live license, with the seats that are claimed now. About four lines in total.


The tests load the class afresh for each test, so each one starts in a process where nothing has used the license yet.
