A customer is refunded 45.00 EUR for order 7781. The next morning reconciliation finds the shop's account 45.00 richer and the customer's 45.00 poorer. The refund code compiled, its tests passed, and every field of the transfer it created held a valid value. Two arguments were in the wrong order.

A builder is for objects like that one: many parts, several of the same type, some optional. Every output below is from Java 21.

The transfer class grew one constructor per optional part, the telescoping style:

customer and shop are both String, so the swapped call matches the constructor exactly. The compiler checks types. A test that builds a transfer from its own literals and reads them back passes in either order. Nothing fails until the money is in the wrong account.

The telescope has a second cost. A memo without a currency would need Transfer(String, String, long, String memo), and that signature is taken:

So a caller who wants a memo passes every value before it, which is how a five-argument call with adjacent Strings comes about. Here is the same class with a builder: a private constructor that takes the builder, and one method per part.

The caller set a memo without passing a currency, which took its default. The builder doesn't make the compiler reject .from(customer); it puts the word from next to the value, where a reviewer reads it. Only distinct types, such as a PayerAccount and a PayeeAccount, turn the swap into a compile error. A record's canonical constructor is positional too (unit Limitations and use cases for records shows the same swap), and a static factory (unit Factory Method Pattern (creating objects without specifying the exact class)) names one way to create an object, not each part.

A transfer to its own account is a mistake, and someone adds the check to the to() setter so it fails as early as possible:

Three callers: two orders, and one forgotten part. attempt prints the transfer, or the exception.

When to() runs first, fromAccount is still null, and the check compares against nothing. A setter sees one part. A rule that relates two parts, or requires one, belongs in build(), the call that says the caller is done. The same checks, moved there:

The product's constructor is private and only build() calls it, so no path to a Transfer skips the checks. A setter may still reject a value that is wrong on its own, such as a negative amount, at once.

A Builder Used Again After build() Changes What It Built, Unless the Product Copies

Transfers now carry tags, which reconciliation matches on. The monthly payroll run sets the payer and a batch tag once, then reuses the builder for each employee. The builder collects tags in a list, and Transfer gets a tags() accessor:

We ran it three times, each with another version of the line in Transfer's constructor that keeps the tags, labelled in the output:

With the first two, the transfer to employee 17, built and perhaps already sent, changed when the builder was used for employee 18, and reconciliation now matches it to both. The builder's list keeps changing while the builder is used, and a product that holds a reference to it changes with it. Collections.unmodifiableList stops the product's readers from writing, but it is a view of the same list, so the builder's writes still show through. List.copyOf takes an unmodifiable copy of the builder's ArrayList. Unit Advantages of records over traditional classes shows the same leak through a record's list component.

The copy fixes the first transfer, and the second still carries E-17, because the builder keeps every tag it was given. To use a builder as a template, give it a copy() method and build each product from a copy, or create a new builder per product. A builder kept in a static field, a singleton in the sense of unit Singleton Pattern (ensuring a single instance), is reused by every thread that calls it.

java.net.http.HttpRequest is created through HttpRequest.newBuilder(), and building a request sends nothing, so it runs without a network. A payout client reuses one builder for two payouts, each with its own idempotency key:

The same two payouts, each built from copy() of template, a builder set up exactly like payouts:

The keys of each pair, then the method, URI, timeout and body length of request b:

The first request still has one key after the second was built: build() copies the builder's state into an immutable request, the fix of the previous section. The second request has two, because header() adds a value, and which one the payout API reads is up to that API. setHeader() replaces the value, but it still changes the shared builder. copy() returns a new builder with the template's state, and nothing done to the copy reaches the template.

The JDK's builder checks a part in its setter when the part alone can be wrong, and leaves only the missing URI to build(). Each of these four ran on its own, and only the first calls build():

StringBuilder is a growing character buffer with nothing to validate, despite the name (unit StringBuilder and StringBuffer).

Summary

  • Same-typed constructor arguments swap without an error. A builder names each part at the call site and lets optional parts take defaults; only distinct types make a swap fail to compile.
  • A builder checks the whole object in `build()`. A setter that checks one part against another depends on call order, and a missing part gets through as null. For a small type, a record's compact constructor does the same job.
  • A builder used again after `build()` changes what it built, unless the product copies. A read-only view still shows the builder's writes; List.copyOf doesn't. Reuse also carries every earlier part into the next product.
  • `HttpRequest.Builder` copies on `build()`, and `header()` adds. Start each request from copy() of a template.

Challenges

  1. Your Order has nine parts, four of them required. Compare a builder that takes the required ones in its constructor with one that checks them in build(). Which mistakes does each catch, and when?
  2. Sketch a builder whose build() can only be called after from() and to(), so the compiler rejects a missing part. What does each added required part cost?
  3. Find a builder in your codebase that is reused in a loop. Write the test that fails if the second product carries a part of the first.

Design Note: Why Java Has Builders and Not Named Arguments

Languages with named and default arguments let the caller name each argument and leave out the optional ones, which covers most of what builders and telescoping constructors are for. Java has neither, so the builder supplies both, at the price of a second class that mirrors the product's fields and must be kept in step with it: add a field to Transfer and forget the builder method, and nothing can set it. The GoF form adds a director that drives one sequence of steps over different builders to produce different representations. It is rare in Java code.
