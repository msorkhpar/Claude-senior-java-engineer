A metrics library ships public Tag(String name), and every service calls new Tag("region") on each request. A heap histogram of one service shows about a million Tag objects carrying three distinct names. The maintainers want one shared object per name. A constructor can't give them that: new always allocates, so the fix is a method in its place, and every call site in every service has to change.

Java has two things called a factory method: a static factory returns an instance in place of a constructor, and the GoF Factory Method is an overridable method that base-class code calls to create an object, so a subclass decides what gets created.

new Always Allocates; a Static Factory Can Hand Back an Object It Already Made

The library's fix keeps one instance per declared name and makes the constructor private:

A million calls with the three names, each built with new String(...) so that no two are the same string object, counting distinct objects:

Sharing is safe only because a Tag can't change: if one caller could rename a shared tag, every other caller would see it. Names that aren't declared get a fresh object and aren't remembered. A tag name can come from a request header, and a cache keyed by caller input grows with every new value until the heap is full.

The JDK made the same move for the wrappers. Integer.valueOf caches -128 to 127 (unit Primitive data types), and the constructor is now marked for removal:

The same program, run as is and then with -XX:AutoBoxCacheMax=1000:

The class files are the same; whether valueOf(1000) returns a shared object was decided when the JVM started. A constructor's result is fixed by the language; a factory's only by its javadoc, which for valueOf promises -128 to 127 and says it "may cache other values". Code that compares a factory's results with == relies on whatever the javadoc leaves open.

A Static Factory Picks the Class From Its Input, So the Class Can Change Without Callers Noticing

EnumSet.noneOf declares that it returns an EnumSet, an abstract class. Here it is called for an enum of 64 permissions and one of 65:

RegularEnumSet keeps the set in one long, one bit per constant, which caps it at 64. JumboEnumSet keeps a long[]. Both are package-private, so no caller can name either; the factory chooses by the enum's size, at every call. Once a 65th permission is deployed, every EnumSet of that enum is a JumboEnumSet, and no caller's source changes. Had EnumSet exposed new RegularEnumSet<>(Perm.class), each call site would be compiled against the 64-bit class, and adding a constant would mean editing all of them. List.of picks by size the same way (unit Creating objects and using constructors).

The price falls on code that looks at the class: a getClass() check, a cast to a concrete type or a serializer keyed by class name breaks when the factory picks another one. A factory promises its declared type, and the class behind it can change between inputs and between JDK releases.

A Constructor Can't Say How It Reads Its Arguments; a Factory's Name Can

BigDecimal has a constructor and a static factory that both take a double:

The constructor reads the exact binary value of the double, which is not 0.1 (unit Primitive data types). valueOf reads the double the way Double.toString prints it, which is the shortest decimal that reads back as the same double, so a double written as 0.1 prints as 0.1. A fee of 0.1 built with new is over a limit of 0.1, and a price of 2.675 rounded half-up comes out a cent short. Both readings have uses, and both take one double, so only one of them could be a constructor: constructors have no names of their own, so two with the same parameter list can't coexist (unit Creating objects and using constructors shows the compile error). For amounts, use the String constructor or valueOf(long, int); valueOf(double) is right only when the double came straight from a decimal literal.

The GoF Factory Method Is a Creation Hook That Base-Class Code Calls and a Subclass Overrides

A listener task waits in ServerSocket.accept(), and on shutdown we cancel its Future. Unit Stopping threads (interrupt() method and cooperative cancellation) showed that a platform thread in accept() isn't woken by interrupt(), so cancel(true) returns true and the worker stays where it is. Closing the socket would end the wait, but cancel belongs to the Future, and submit creates the Future by wrapping the task in a FutureTask (unit ExecutorService interface and implementations). It does that through a protected method, newTaskFor, which a subclass can override:

The listener is a Closing<String> whose close() closes its server socket. The caller's code is the same for both pools: Future<String> f = pool.submit(listener), then, once the listener is in accept(), f.cancel(true), shutdown() and a 500 ms awaitTermination:

The first pool's worker left accept() only when the program closed the socket itself after the wait; in the subclass, cancel closed it. submit, invokeAll and invokeAny are written once, in AbstractExecutorService, and call newTaskFor; the subclass changed the product without touching them or any caller. The base class owns the code that uses the object, and a subclass owns the choice of object, where a static factory makes that choice inside one method.

submit(Runnable) goes through the other overload, newTaskFor(Runnable, T). In a pool whose override of the Callable overload returns its own product for every task, submit(() -> "x") got that product and submit(() -> { }) a plain FutureTask. A subclass overrides every overload its callers can reach. A creation hook called from the base class's constructor runs before the subclass's fields are assigned (unit Class structure and components); newTaskFor runs at each submit, after construction.

Each Product Costs a Subclass, and the Hook Reaches Only Objects Built From It

The service gets its pools from Executors, and the next release moves the listeners to virtual threads. Each pool's class, and whether it is a ClosingExecutor (the column hook overridden):

Executors.newFixedThreadPool and newCachedThreadPool build a plain ThreadPoolExecutor, which calls its own newTaskFor, not the override. newVirtualThreadPerTaskExecutor() returns ThreadPerTaskExecutor, which doesn't extend AbstractExecutorService and has no newTaskFor at all. The listener code compiles against all of them unchanged. On the two ThreadPoolExecutors, cancel again leaves the worker in accept(). On virtual threads the worker ends anyway: Java 21 closes the socket on an interrupt there (unit Stopping threads (interrupt() method and cooperative cancellation)). But close() never runs, so any other cleanup in it is skipped.

The count grows too. A second product, say a task that carries the request id into its logs, is a second subclass with its own newTaskFor. A pool that needs both is a third that merges the two overrides, since a class extends one superclass.

The same JDK class shows the other choice. ThreadPoolExecutor makes its threads through a ThreadFactory passed to its constructor, and most Executors methods have an overload that takes one: Executors.newFixedThreadPool(4, Thread.ofPlatform().name("listener-", 0).factory()) names the threads with no subclass. It can't change the Future, which is Challenge 3. A factory passed in works with any creator that accepts it, and can be a lambda (unit Using lambda expressions with functional interfaces). It sees only what the creator hands it, where an override can use the subclass's fields. Keep the hook where the subclass exists for other reasons: every collection must supply its own iterator(), and AbstractCollection builds contains, remove and toString on it. Choosing an implementation from the class or module path is ServiceLoader (unit Dependency Inversion Principle (DIP)); one shared instance is unit Singleton Pattern (ensuring a single instance), and step-by-step construction is unit Builder Pattern (step-by-step object construction).

Summary

  • `new` always allocates; a static factory can hand back an object it already made. Share only immutable objects, never cache by caller input, and use == on the results only where the javadoc promises identity.
  • A static factory picks the class from its input. EnumSet switches from RegularEnumSet to JumboEnumSet at 65 constants with no caller changed; code that checks the class breaks.
  • A factory's name says how it reads its arguments. new BigDecimal(0.1) and BigDecimal.valueOf(0.1) take the same double and return different numbers.
  • The GoF factory method is a creation hook. submit calls newTaskFor, so one override changes the Future for every caller; every overload callers reach must be overridden.
  • Each product costs a subclass, and the hook reaches only objects of that subclass. Pools from Executors aren't your subclass, and the virtual-thread executor has no newTaskFor at all; a factory passed in reaches any creator that accepts it.

Design Note: Why the Hook and the Parameter Both Survive

GoF's Factory Method comes from the application frameworks of the early 1990s, where the framework's base class ran the algorithm and an application subclassed it to plug in its own objects. Before lambdas, passing a creation object meant an anonymous class, so a subclass hook cost about the same; newTaskFor dates from Java 6. Since Java 8 a creation function is cheap to pass, and newer JDK code takes one: Collectors.toCollection(Supplier), ThreadLocal.withInitial, Thread.Builder.factory(). The hook stays where the creator and the product change together, as a collection and its iterator do. Where the products vary on their own, a parameter saves a creator subclass per product.

Problem statement


Request handlers in the order service hand background work to RequestPool, and every log line the service writes is tagged with RequestPool.REQUEST_ID, the id of the request the current thread is serving. Lines written by pool tasks come out with no request id at all, so nobody can follow an order from its handler into the work it started. Handlers submit both Callables and Runnables, and housekeeping jobs, which serve no request, use execute(...). When the pool and its queue are full, the handler's own thread runs the task, and carries on serving its request afterwards.


Finish RequestPool in src/main/java/practice/RequestPool.java so that every task a handler submits logs under that handler's request id, and nothing else logs under it: not the housekeeping that runs on the same thread later, and not the handler, which keeps its own id. The handlers' code doesn't change. About fifteen lines in total.
