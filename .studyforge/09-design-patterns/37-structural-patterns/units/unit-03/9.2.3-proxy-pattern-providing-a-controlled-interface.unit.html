The order service wraps its inventory client in a retry proxy: one InvocationHandler that tries a call up to three times when it fails with IOException. Since the release, the warehouse logs show exactly one call per stock check, even during a network blip. The order code catches IOException and shows "unavailable", and it now fails those requests with java.lang.reflect.UndeclaredThrowableException, an exception nobody on the team throws.

A proxy implements the same interface as the object it stands for and controls how calls reach it. java.lang.reflect.Proxy builds one at run time, with one handler for every call.

One InvocationHandler Receives Every Call on Every Method of the Proxied Interfaces

Inventory has int stock(String sku) and void reserve(String sku, int qty), both declaring IOException. timed wraps it, and also a String seen as a CharSequence:

newProxyInstance generates a class ($Proxy0) implementing the listed interfaces. Each of its methods passes invoke the proxy, the Method and the arguments (null when there are none). The handler names no interface, so it works for any, the JDK's included. The first call to each method was slow because Method.invoke sets itself up on first use.

The proxy is not a subclass of the target: type.cast to the interface succeeds, a cast to WarehouseInventory throws ClassCastException, and Proxy refuses a class outright. Proxying a class takes a subclass generated as bytecode, which is what CGLIB (copied inside Spring) and Byte Buddy's subclassing do, and a final class such as String can't have one. Unit Dynamic Object Creation and Method Invocation covers Method and reflection itself.

Method.invoke Wraps Whatever the Target Throws, So the Handler Must Unwrap It

The retry handler from the opening compiles without a warning. Find why it never retries:

The order code calls stock through it and prints the result, or the exception and its cause chain, then how many calls reached the warehouse. WarehouseInventory(2) fails its first two calls with IOException("connection reset"), and a blank SKU fails with IllegalArgumentException:

Method.invoke wraps anything the target throws, checked or not, in InvocationTargetException. So e is never an IOException, and the first failure ends the loop. catch (IOException e) doesn't compile ("exception IOException is never thrown in body of corresponding try statement"), and catch (Exception e) is the quick way to silence the error. Two resets are absorbed. After five, the caller gets the last IOException, which stock declares, and its own catch shows "unavailable". The blank SKU is not retried and arrives as itself. The timing handler of the first section has the same flaw: every exception the warehouse throws through it reaches the caller wrapped twice.

A Checked Exception the Interface Method Doesn't Declare Reaches the Caller as UndeclaredThrowableException

invoke is declared throws Throwable, so the compiler lets a handler throw anything, and the proxy checks what comes out against the interface method. An unchecked exception, or a checked one the method declares, passes through unchanged. Any other checked exception is wrapped in UndeclaredThrowableException, a RuntimeException, because a caller compiled against int stock(String) throws IOException can't be handed a checked exception it was never told about. The leaked InvocationTargetException above was one. The retry library's own checked exception, thrown when it gives up, is another:

Every caller's catch (IOException e) is skipped, and in a web service the request fails with a server error instead of showing "unavailable". A handler throws the target's own exception, one the called method declares (method.getExceptionTypes() lists them), or an unchecked one. A retry library that wants a type of its own, and can't know what each interface declares, makes it a RuntimeException.

Summary

  • One handler receives every call on the proxied interfaces, for any interface but only interfaces: the proxy is no instance of the target's class, and a class needs a generated subclass.
  • `equals`, `hashCode` and `toString` reach the handler. Forwarding equals to a target with identity equals makes the proxy unequal to itself, so a list can't remove it; printing proxy inside the handler recurses until StackOverflowError.
  • `Method.invoke` wraps the target's exception in `InvocationTargetException`. A handler that doesn't unwrap it retries nothing and changes the type of every failure.
  • A checked exception the method doesn't declare becomes `UndeclaredThrowableException`, which skips the caller's catch. Throw what the method declares, or something unchecked.
  • A call on `this` bypasses the proxy. Calls that must be intercepted go through the proxy reference, which is why a self-call in Spring ignores the called method's @Transactional.

Challenges

  1. The retry proxy wraps an interface whose reserve is not idempotent. Which methods should it retry, and how would the handler know? Compare an annotation with a list of method names.
  2. Put the timing proxy and the retry proxy around the same Inventory, in both orders. What does the timing line measure in each, and which order do you want on a dashboard?
  3. A listener is wrapped and registered twice by mistake, as two proxies. With identity-based equals, can the second registration be detected? Design an equals that can, and say what it costs.

Design Note: Why the JDK Proxies Interfaces Only

Proxy arrived in Java 1.3. The class it generates extends java.lang.reflect.Proxy and implements the interfaces you list. Since it extends Proxy, it can't extend your class, and an interface has no state and no constructor, so the proxy only has to answer calls. A subclass-based proxy can't intercept final or private methods, carries the parent's fields unused, and must either run one of the parent's constructors or skip them, which takes a library such as Objenesis.

The JDK can wrap an object only for callers that depend on its interface, the dependency unit Dependency Inversion Principle (DIP) argues for on other grounds. Code that names the class can't be handed the proxy at all.
