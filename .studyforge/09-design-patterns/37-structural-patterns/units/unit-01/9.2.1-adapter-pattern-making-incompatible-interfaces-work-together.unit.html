The invoice service gets each order from a legacy pricing library as two arrays matched by index, String[] skus and Integer[] cents. A new footer shows the most expensive line:

Since the release, customers see SKU A-100 billed at 72.00. It costs 19.99, nobody changed a price, and the footer's number is right. Before reading on, work out what moved the prices.

An adapter makes an object you already have usable through an interface its class doesn't implement.

Arrays.asList Adapts an Array Without Copying It, So Sorting the List Reorders the Array

The invoice lines after the footer, then the same code copying first with new ArrayList<>(Arrays.asList(cents)):

Arrays.asList returns a List that reads and writes the array you passed. The sort rearranged cents, so every price now sits beside another SKU. The javadoc calls it "a fixed-size list backed by the specified array", and the backing works both ways:

That is the adapter: the same data behind a second interface, with no copy, which is why a caller who wanted a list of their own got someone else's array. The view keeps the array's size, so add and remove throw (unit Liskov Substitution Principle (LSP)).

The last line is the other trap. asList(T...) adapts arrays of objects only. Given an int[], T becomes int[] and you get a one-element list holding the array. It compiles, and contains(7) answers false. The JDK has no List<Integer> view of an int[].

Copy when the receiver must not see your later changes, or you must not see its changes: new ArrayList<>(...) if it may change the list, List.copyOf(...) if it may not.

InputStreamReader Adapts Bytes to Chars Through a Charset, and the One-Argument Constructor Takes the JVM's Default

A parser that takes a Reader can't read a socket's or a file's InputStream: one deals in bytes, the other in characters. InputStreamReader sits between them, and the charset is the table it translates with. One string's UTF-8 bytes, read four ways. drain reads a Reader to the end, perRead does new String(buf, 0, n, UTF_8) for each read(), and trickle wraps the bytes in a stream that returns at most 3 bytes per read, as a socket may:

The constructor without a charset uses the JVM's default: UTF-8 on Java 18 and later unless the JVM is started with another file.encoding (unit String creation and initialization has the history). The same jar reads the same bytes correctly on a laptop and turns ü into Ã¼ on a server whose start script sets windows-1252. Single-byte charsets like that one give almost every byte a character, and Latin-1 gives all 256 one, so each byte of ü became a wrong character rather than �. Nothing throws, so the broken names are stored. Pass the charset the data is in.

The per read line is why decoding needs an adapter that keeps state, not a new String per buffer. The arrow is three bytes in UTF-8, the reads cut it apart, and each piece decoded alone is malformed and becomes �. InputStreamReader holds the bytes of an unfinished character until the next read completes it, so it decoded the same trickle correctly.

When the bytes aren't in the charset you named, the adapter doesn't fail by default. Latin-1 bytes read as UTF-8, once through a Charset and once through UTF_8.newDecoder():

The Charset constructor replaced the malformed byte with U+FFFD. A decoder from newDecoder() reports it, so where a feed in the wrong charset must be rejected, pass a decoder.

Java Has Only Object Adapters When the Target Is a Class

The textbook class adapter extends the adaptee and implements the target, so it inherits the code it translates to. Trying that for bytes and characters:

Reader is an abstract class, and a Java class extends only one. When the target is a class, the adapter extends the target and holds the adaptee in a field, an object adapter. That is how InputStreamReader is built, and its trickle run above is that adapter working. When the target is an interface, a class adapter compiles but adapts only the instances it constructs itself, never System.in or the stream a socket hands you. It also exposes the adaptee's public methods, so callers can change its state behind the translation. An object adapter forwards to the object it holds, as the forwarding wrapper of unit Definition and purpose of Composition over Inheritance does, and for a single-method target a method reference is the whole adapter (unit Introduction to method references).

The other wrappers in this module keep the interface they wrap: a decorator adds behaviour behind it (unit Decorator Pattern (adding behavior dynamically)), and a proxy controls access to its calls (unit Proxy Pattern (providing a controlled interface)).

Summary

  • `Arrays.asList` is a view. Sorting or setting through it changes the array, and asList of an int[] is a one-element List<int[]>. Copy when the receiver needs a list of its own.
  • `InputStreamReader` decodes with a charset. Without one it takes the JVM's default. It keeps a split character between reads, and only a CharsetDecoder makes it reject bad bytes.
  • A callback adapter completes its future on every path. A forgotten error callback leaves join() waiting forever, and a synchronous throw must become a failed future. Stages attached early run on the legacy client's thread, so slow ones go to an executor.
  • When the target is a class, Java allows only an object adapter, and for an interface target it is still the only kind that adapts an object you were given.

Challenges

  1. A method returns Arrays.asList(internalArray) so that callers can't add to it. What can a caller still change? Choose between List.copyOf and Collections.unmodifiableList for the fix: which one copies on every call, and which one still shows later changes to the array?
  2. The legacy client calls onError and then, after an internal retry, onQuote for the same request. What does the fixed adapter's caller see, and is that the answer you want?
  3. A caller cancels the future the adapter returned, and the legacy request keeps running. What would the adapter need from the legacy API to stop it, and what can it do if there is nothing?

Design Note: Why Arrays.asList Is a View

The javadoc calls asList a "bridge between array-based and collection-based APIs", the counterpart of Collection.toArray(). A view makes the bridge cost one small object whatever the array's size, and lets list algorithms such as Collections.sort or Collections.reverse work on an array in place. A copy would have been safe to hand out and useless for that second job.

The price is aliasing that no type shows: a List<Integer> parameter doesn't say whether someone's array sits behind it. List.of, added in Java 9, took the other side: it copies the array and refuses nulls and every change.

Problem statement


The pricing service is moving to CompletableFuture, but its FX rates still come from a legacy client that takes a listener and answers later, on a thread of its own. A pricing request combines several rates with thenCombine and turns any failure into a "price unavailable" reply with exceptionally. Those requests must always get a reply: last quarter, a handler that waited on a rate nobody would ever deliver held its thread until the pool ran dry.


Rates declares the client's interfaces (don't change them) and RateUnavailableException. Finish rate(pair) in src/main/java/practice/Rates.java, so that it returns at once with a future that settles however the client's lookup ends: with the rate, or failed with a RateUnavailableException that carries the client's reason, or failed with whatever the client threw. Callers handle every failure through the future. About ten lines in total.
