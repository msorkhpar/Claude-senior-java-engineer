The order service tells other components about each placed order through a list of listeners: receipts, loyalty points, metrics. Last week the first order after every restart failed with ConcurrentModificationException, although it had been saved, and the client's retry saved it again. For two hours guests got no receipts, and the log had a loyalty error for every guest order. The admin console's heap grows by about a megabyte for each report screen anyone opens and closes.

Observer is a list of callbacks that a subject calls when something happens. Each of those failures comes from a decision the list makes: what it walks, what it does when a callback throws, how a callback leaves, and how long it keeps one.

A Listener That Unsubscribes During a Dispatch Changes the List Being Walked

After a restart, the first order earns a welcome coupon. The listener that sends it has no work left after that, so it unsubscribes itself:

With an ArrayList behind OrderEvents, what happens to the receipt and metrics listeners for the first order? Three runs publish o-1 and o-2: coupon registered first, coupon registered second, and coupon first on a CopyOnWriteArrayList:

With the coupon first, the loop's next step throws, the receipt and metrics listeners never hear about o-1, and the exception reaches the code that called publish after the order was saved. That caller reports a failure, and the client retries an order that exists. With the coupon second, nothing throws, and the metrics listener silently misses o-1: the list shrank under the iterator, which then took itself to be at the end. Unit Order of Operations in Concurrent Collections explains both outcomes from the iterator's counter and the copy-on-write snapshot.

A listener can't know where it sits in the list, so the subject must make leaving safe. A CopyOnWriteArrayList does: a dispatch walks the array it started with, so a listener removed during a dispatch still gets that event and none after it, and one added during it starts with the next. Copying the list at the start of publish does the same. Listener lists change rarely and are read on every event, the load a copy-on-write list is built for.

synchronized on publish is no substitute: the removal comes from the same thread, which already holds the lock, so the ArrayList still throws. It also calls every listener under the subject's lock, which unit Best practices for safe concurrent programming shows deadlocking once a listener takes a lock of its own.

One Listener's Exception Skips the Listeners After It and Reaches the Publisher

The loyalty listener throws for a guest order, which has no customer. It was registered before the receipt listener:

The receipt listener was never called, and placeOrder, which had saved the order, threw. The listeners don't know about each other, and the subject doesn't know what they do, so neither can decide that loyalty points matter more than receipts. A loop with no try decides it anyway: one failure ends the dispatch for every listener registered after it. The publisher then reports a failed order that succeeded, with the same retry as in the previous section.

A Listener Is Removed by the Reference It Was Added With, and a Second Lambda Is Another Object

unsubscribe ends in List.remove(Object), which looks for an element equals to its argument. A lambda or method reference doesn't override equals, so only the same object matches. Three removals that look right, and one that is:

Each evaluation of this::onOrder created a new object (a and b are two of them), so the dashboard's close() passes an object the list has never seen, and remove returns a false nobody checks. The dashboard looks as if it cleans up after itself.

Keep the reference in a field and pass that field to unsubscribe, or let the subject hand back something that removes the registration, so the caller can't pass the wrong object:

Each registration gets its own entry, so a handle removes exactly its own registration.

The Subject Keeps Every Listener, and Everything It Captures, Until It Is Removed

A report screen in the admin console subscribes this::refresh when it opens, to update its 1 MB of report data on each order, and its close() doesn't unsubscribe. We open and close 200 screens, keep a WeakReference to each, and call System.gc(). A weak reference is cleared once nothing else can reach its object, so the uncleared ones count the screens still held:

The subject outlives the screens. Its list holds each method reference, the reference holds its screen, and the screen holds its data, so nothing a closed screen owns can be collected, and every order still refreshes 200 screens nobody can see. The second run's close() removes the listener it kept in a field. In a heap dump this shows as a screen class whose instance count grows with each open, every instance reachable through the subject's list.

Holding listeners through weak references moves the failure rather than removing it. A lambda that captures a variable, registered in place, has no other reference, so the first collection clears it, and the listener stops without an error:

Pair each subscribe with the code that ends its owner, such as a screen's close(), and give that code something to close.

When a Subscriber Can't Keep Up, a Flow Publisher Makes the Producer Wait or Drop

Every dispatch so far runs the listeners on the publisher's thread, so a listener that takes 10 ms adds 10 ms to every order. Handing events to another thread moves that delay into a queue, and while orders arrive faster than the listener handles them, an unbounded queue grows until the heap runs out. java.util.concurrent.Flow (Java 9) lets a subscriber say how many items it can take, and SubmissionPublisher is the JDK's publisher for it. This subscriber spends 10 ms on each order and asks for one at a time, behind a buffer of 8:

One run publishes 100 orders with submit, another with offer and a handler that counts drops:

submit blocks while the buffer is full, so the producer runs at the subscriber's pace and nothing is lost. offer returns at once and hands what doesn't fit to the drop handler. Which one is a business decision: orders must not be dropped, while a price display can skip a tick. A subscriber whose onNext throws has its subscription cancelled and gets the exception through onError; in a run of ten items with two subscribers, the other one still received all ten.

Summary

  • A listener that unsubscribes during a dispatch changes the list being walked. On an ArrayList the dispatch throws or skips the next listener; a CopyOnWriteArrayList or a copy makes leaving safe.
  • One listener's exception skips the listeners after it and reaches the publisher. Catch and report around each call; PropertyChangeSupport doesn't.
  • A listener is removed by the reference it was added with. A second lambda or this::m is another object, so the removal silently does nothing; keep the reference or return a handle.
  • The subject keeps every listener, and what it captures, until it is removed. Unsubscribe when the owner closes; weak references lose listeners that nothing else holds.
  • A `Flow` publisher bounds what waits for a slow subscriber. submit waits, offer drops.

Challenges

  1. A listener unsubscribes another listener, not itself, during a dispatch. With a copy-on-write list, the other one still gets the current event. When does that matter, and how would you make the removal take effect at once?
  2. Your subject catches and logs every listener failure. One listener now fails on every event and fills the log. What should happen after its hundredth failure, and who decides?
  3. Measure a CopyOnWriteArrayList of 10,000 listeners that subscribe and leave at the rate users log in and out. At what churn does copying on every write cost more than the dispatches?

Design Note: Synchronous Dispatch Puts Every Listener's Cost on the Publisher

A listener list calls its listeners on the publisher's thread, inside the publisher's call. That keeps events in order and needs no threads, and it is why the failures of the first two sections reached the publisher: a listener's unsubscribing and its exception happen inside publish. Moving dispatch to another thread separates them, and raises the questions Flow answers: how much to buffer, and what to do when the buffer is full.

The JDK's first answer, java.util.Observable, has been deprecated since Java 9. Its javadoc calls its event model "quite limited", says the order of its notifications is unspecified, and points to java.beans, the concurrent collections and the Flow API instead.

Since it shipped, two things happened: on the day it was installed first, the build event failed and no plug-in after it heard that build; on a server where it was installed second, the dashboard silently lost one build.

Problem statement


This practice continues the previous one: BuildEvents.publish already walks the plug-ins safely when one of them unsubscribes itself, and now hands each build to each plug-in through deliver(listener, buildId).


Plug-ins are written by other teams. Last night the artifact-cleaner plug-in threw on every build because an agent's disk was full. Every plug-in registered after it stopped hearing about builds, and the code that calls publish at the end of a build marked green builds as failed. Nobody running the server could tell which plug-in was at fault.


BuildEvents now takes an onPluginFailure handler in its constructor. Finish deliver(listener, buildId) in src/main/java/practice/BuildEvents.java so that a plug-in that throws costs no other plug-in its build, never makes publish fail, and is reported to that handler with the build id and the exception it threw. About five lines in total.
