The release-notes editor gained a "Sort lines" button, with undo like every other edit. Within a week support has three tickets with the same story: the user sorted, pressed Ctrl+Z, and the document went blank. The sort command's undo is one line, and it passed review.

The Command pattern turns a request into an object that holds what to do, to which receiver, and with which arguments. An object can wait in a queue, go into a log, run again after a failure, and keep what it needs to undo itself. The blank document comes from the last of these.

A Command Is a Request Held as an Object, So It Can Be Queued, Logged and Run Again

A warehouse service queues stock adjustments and writes each one to an audit log before applying it; each adjustment is a record:

The same two adjustments go through the queue once as records, then once as lambdas:

Both queues did the work. A lambda is enough when all you do is run it, but its arguments sit in its body or in captured variables that nothing outside can read, so the audit log names a generated class. A lambda has no equals of its own, so two identical adjustments are two different objects, and a queue can't drop a duplicate. A Runnable also has only run(), while a record or class can add undo(). When a command must be logged, compared, stored or reversed, make it a record or a class whose fields are its arguments.

The JDK's commands are Runnable and Callable: ExecutorService.submit accepts them and runs them later, on a thread it chooses (units ExecutorService interface and implementations and Callable and Future for returning results). A strategy (unit Strategy Pattern (switching between algorithms at runtime)) also packages behaviour, but its caller hands it the data on every call; a listener (unit Observer Pattern (loose coupling for event handling)) is called by a subject when something happens. A command already carries its receiver and arguments, and someone else decides when it runs.

Undo Restores What the Command Saved, So It Must Save a Copy Taken When It Runs

Some commands undo by the inverse operation: an insert is undone by deleting what it inserted. A sort has no inverse, so the command saves the order from before. Here is the editor's sort, with the receiver it works on. Work out what undo puts back before reading the output.

The editor appends three lines, each through an AppendLine command pushed on a Deque<Command> history, then runs the sort, pops it and undoes it:

doc.lines() at (1) returns the document's own list, not a copy. before is a second name for that list, so the sort reordered "the state before" as well. At (2) undo passes the document its own list: clear() empties it, and addAll then has nothing to add. A receiver that assigned the field instead (lines = newLines) would have kept the sorted order, and undo would have seemed to do nothing. Either way the command saved a reference to the state, not the state.

The fix is one line in execute():

Take it in `execute()`, not in the constructor. A command built now may run later, from a queue or inside a group of commands. In the same program, a sort built after two appends and executed after the third saved [zeta, alpha], so its undo deleted mu.

Copy every mutable level. List.copyOf copies the list, which is enough because String is immutable. A Map<String, List<String>> copied with new HashMap<>(map) shares its inner lists: in the run, clearing one live list emptied it in the "copy" too. Copy each list as well, or keep immutable values in the receiver so that one copy goes all the way down.

A snapshot costs one copy of the state per command on the stack. That is why editors use the inverse where one exists, and cap the history.

A Command That Timed Out May Still Have Run, So a Blind Retry Runs It Twice

The checkout service charges a card through a payment client. Charge is a record of a key, an account and an amount in cents. The client submits each attempt as a Callable to its executor, waits 200 ms for the reply, and retries. On the payment side, the money moves before the reply is sent, and the first reply is held up on the way back (replies counts replies; network is a latch the program releases after the client's loop):

The first attempt didn't fail: the money had moved and its reply was still on the way. A TimeoutException from get says only that the caller stopped waiting. After a timeout the request may never have arrived, may have been applied with the reply lost, or may still be in progress, and the caller can't tell which. The retry sends the charge as if it were new, and the customer pays 80.00 for a 40.00 order. Cancelling the timed-out Future doesn't undo anything: cancel(true) interrupts a local thread (unit Stopping threads (interrupt() method and cooperative cancellation)), and the remote side may already have applied the charge.

An Idempotency Key Created With the Command Makes the Retry Safe

A command is idempotent when running it twice has the effect of running it once. "Set the price to 9.99" is idempotent; "charge 40.00" is not. A charge becomes safe to retry when the command carries a key, created once with the command, and the receiver keeps the result of every key it has applied, here in a ConcurrentHashMap called receipts:

First the same client sends to this version; then a client builds a new Charge inside the loop, so each attempt gets a new key:

With one key, the retry found the first attempt's result: one charge, and the caller gets r-1, the receipt the lost reply carried. The receiver returns the stored result rather than an error, because whoever retries is the one who never saw the first answer.

With a key per attempt, the service saw two different charges. The key names the request, not the attempt: it is created where the intent is (the click on "Pay"), and every retry sends the same command object. Deduplicating by content instead, same account and same amount, fails the other way: a customer who really buys two 40.00 items in a minute is charged once.

The javadoc of ConcurrentHashMap.computeIfAbsent says the function is applied at most once per key, so two attempts that arrive together can't both charge. A containsKey check followed by put gives no such guarantee. If the function throws, nothing is stored and the next attempt runs it again, so an apply that fails after the money moved still charges twice. In production the key store must outlive the process, typically a table with a unique constraint on the key.

Summary

  • A command is a request held as an object, so it can be queued, logged, compared and run again. A lambda runs, but can't be read, compared or undone; Runnable and Callable are the JDK's commands.
  • Undo restores what the command saved. Save a copy, not a reference, take it in execute(), and copy every mutable level.
  • A timeout doesn't mean the command failed. It may have run, so a blind retry can run it twice.
  • An idempotency key created with the command makes a retry safe, when the receiver stores the result per key and returns it again.

Challenges

  1. Your editor keeps 200 undo steps of a 5 MB document. Compare snapshots, inverse operations, and a snapshot every 20 commands with inverses in between: memory, undo time, and what breaks when an inverse is wrong.
  2. How long must the payment service keep idempotency keys? What happens to a retry that arrives after its key was purged, and who should choose the window?
  3. "Set the price to 9.99" is retried after a lost reply, and another admin changed the price in between. Is the command still idempotent in the way that matters? What would you add to it?

Design Note: Commands Are Not Events

A log of commands can rebuild state by running them again, and some systems do this. The commands then run their validation and side effects a second time: the replay of a Charge asks the bank for money again, unless every command is idempotent and its keys survive. Event sourcing logs events instead: "charged 40.00, receipt r-1" is a fact that already happened, and replaying it only updates state. The cost is a second type for each operation, a command that may be refused and an event that records what was accepted.

Since archiving shipped, the bug reports say that undoing an archive sometimes empties the whole board, sometimes brings the columns back without their cards, and sometimes loses a card that was added just before the archive ran from the board's queue of pending edits.

  • execute(): archive the column;
  • undo(): put the board back as it was just before execute() ran.


The archive is kept sorted, so the order a column's cards had can't be read back from it. When you're done, undoing one archive, or several in turn, gives back every column with its cards in their order, and the archive as it was. About eight lines in total.
