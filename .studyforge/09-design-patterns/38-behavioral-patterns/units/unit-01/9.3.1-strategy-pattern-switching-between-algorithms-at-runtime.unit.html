The checkout service prices each cart through a pricing policy whose name comes from config: pricing.policy=bulk. In one month it had two incidents. After the request thread pool was enlarged, a few customers a day were charged a total mixed from their cart and someone else's. Then a deploy with pricing.policy=Bulk started, passed its health check, and failed at the first checkout 40 minutes later. Neither change has a line that looks wrong in review.

A strategy is an object the caller hands in to do one step of its work, so the caller doesn't decide how that step is done. All output is from Java 21.

A Lambda Strategy Has No Name; an Enum Strategy Has One, and One Instance per JVM

The interface has one method, so any lambda from a cart to a long is a policy. The same bulk rule, 10 % off a cart of ten units or more, written once as a lambda and once as an enum constant:

Both price the cart the same. The lambda's toString() is a generated class name that can change between runs, so a log line, a metric tag or an incident timeline can't say which policy priced a cart, and turning a config string into a lambda needs a table you write. The enum constant prints its name, valueOf turns a config string into the constant, and values() lists every choice for an error message.

Its set is closed: no code outside the enum can add a constant. A constant can't take parameters per use, so a 12 % bulk rate for one tenant and 8 % for another needs a class or a lambda that captures the rate. And each constant is a single object per class loader, which in practice means one for the whole JVM. Use the enum for a fixed set of named policies that carry no settings, and a lambda or a small record for policies built from configuration.

When the set of policies is fixed and the questions you ask about them keep growing, the alternative is a sealed interface of records with one switch per question (unit Open/Closed Principle (OCP)).

  1. Concept check

    Check yourself: strategies

    • An enum strategy is closed to other modules, can't take parameters per use, and each constant is one object for the whole JVM, so a policy with settings is a record, a class or a capturing lambda.
    • A lambda strategy's toString() is a generated class name, so logs can't say which strategy ran, and mapping a config string to a lambda needs a table you write; an enum constant prints its name and valueOf reads it from config.

A Strategy Object Is Shared, So a Field in It Is Shared State

One policy object prices every cart: an enum constant, a static final lambda or a singleton bean is one instance serving every request thread. The bulk policy was refactored into helper steps that pass their running totals through two fields:

Every unit test passes, because a test prices one cart at a time. Eight threads now price 200,000 carts each through one instance, and we count totals that differ from a single-threaded calculation: for this class, for the same class with both fields volatile, and for this version, which keeps the running totals in a value each call owns:

One thread resets sum while another is halfway through its cart, and the second thread's discount is computed on a mix of both carts: between one cart in 140 and one in 175 over four runs. volatile made it far worse. It forces every read and write of sum and units to memory, so each += picks up the other threads' partial totals, and it doesn't make += atomic. The plain fields probably went wrong less often because the JIT kept them in registers for part of each call, which nothing promises. synchronized on totalCents would be correct, and every checkout in the service would then queue for one lock.

The policy needs nothing from one call to the next, so it should hold no fields. A strategy that does need state across calls, such as a round-robin counter, holds it in an atomic type (unit Data races and how to prevent them) and says so in its javadoc.

  1. Coding practice

    Let one shipping policy quote for every request thread

    • One strategy instance serves every thread, so fields that carry per-call values between its steps mix concurrent calls; keeping those values in locals or a value the call owns fixes it.
    • Making the shared fields volatile doesn't stop the race and made it far more frequent; synchronized makes it correct but makes every caller queue behind one lock, including behind a slow call.

The JDK's Comparator Is a Strategy, and the Sort Trusts Its Contract


List.sort, TreeMap, PriorityQueue and Collections.max take a Comparator and don't validate it. The order history sorts orders by creation time, a long of epoch milliseconds, with a comparator that looks equivalent to comparingLong:



First three orders created on day 0 (A-1), day 20 (A-2) and day 30 (A-3), in two input orders; then five random sets of 1,000 orders spread over a year, counting neighbours left out of order:



Thirty days are 2,592,000,000 ms, which doesn't fit an int. The cast keeps the low 32 bits and flips the sign, so the comparator reports day 30 as earlier than day 0, and whether the sort ever asks about that pair depends on the input order. Tests with one day's orders never get 24.8 days apart, and pass. On a year of orders the comparator says a < b, b < c and c < a for some triples, and List.sort assumes that never happens. Four times it returned a scrambled list without a word; once its merge step ran into the contradiction and threw. Which of the two you get depends on the input, so one customer's history page throws and another's is silently misordered.


Long.compare, Integer.compare and the comparingLong/comparingInt factories can't overflow. Unit Using lambda expressions with functional interfaces covers reversed() on a comparator chain, and unit String comparison (equals() vs. ==) a TreeSet that treats a 0 from its comparator as "duplicate": there too, the collection acts on whatever the comparator answers.

Resolve a Strategy's Name When the Service Starts, Not When It First Runs


The policies sit in a Map<String, PricingPolicy>, and config names one. Three versions of the checkout service are each started with pricing.policy=Bulk. The first looks the name up on each checkout:



The second resolves it in the constructor with POLICIES.getOrDefault(name, STANDARD), where STANDARD is the standard policy as a lambda. The third resolves it in the constructor and refuses a name it doesn't know:




The lazy service passed its health check, so the deploy reached every node, and the typo surfaced at the first checkout as an exception that names neither the key nor the value. The fallback is worse: it never fails, and every bulk order is charged the standard 5400 instead of 4860 until finance notices. The eager service refuses to start, the deploy stops on the first node, and the message tells the operator what to type.


A default belongs to a key that is absent, never to a value that is wrong, so getOrDefault belongs on config, never on POLICIES. An enum's valueOf("Bulk") called in the constructor fails the same way, with No enum constant ValueOf.Policy.Bulk (ValueOf is the demo class), which lists none of the names that would work.

Summary


  • A lambda strategy has no name; an enum constant has one. The enum gives valueOf and values() for config and logs, and gives up parameters, extension by other modules, and separate instances.
  • A strategy object is shared, so its fields are shared state. Keep per-call values in locals or a value the call owns; volatile makes the race more frequent, and synchronized makes every caller queue.
  • A caller trusts its strategy's contract. A comparator that subtracts overflows, and List.sort returns a wrong order or throws, depending on the input.
  • Resolve a strategy name at start-up. A lookup at first use fails after the deploy, and a fallback for an unknown name never fails at all.

Design Note: What the Interface Can't Say


Strategy buys pluggability: the checkout prices carts with policies written after it, and the sort orders types it has never seen. The price is that the caller's assumptions about the strategy live outside the type system. PricingPolicy and Comparator each declare one method signature, and nothing in a signature says "safe to call from many threads at once" or "a consistent total order". javac accepts a policy with fields and a comparator that overflows, and the caller can't check either at run time. Those assumptions go in the interface's javadoc, and in tests that call the strategy the way the caller does: from many threads, and with values far apart.
