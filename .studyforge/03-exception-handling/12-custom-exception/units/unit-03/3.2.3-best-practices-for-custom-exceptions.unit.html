One payment fails at 14:02, and four things go wrong around it. The mobile app shows "Something went wrong" instead of "Top up your account". The API answers 500, which tells the client the server is broken. On-call gets three SEVERE alerts for one failure. And one log line holds the customer's email and full card number.

None of these is about writing the exception class (unit Creating custom exception classes) or throwing it (unit Throwing exceptions using the throw keyword). They are about how the module's exceptions are shaped and what the rest of the system does with them. The examples run on Java 21.

Take the module's BankAccount, with InvalidAmountException and InsufficientFundsException made unchecked: two unrelated subclasses of RuntimeException. An ATM was written against it:

The code compiled, and the new exception went past both catch blocks. In a web service, that is a 500 for an answer the module gave on purpose. Had the exceptions been checked and listed in throws, the ATM would have stopped compiling instead (unit Checked vs. unchecked exceptions shows that error).

The fix is one base class for the module, AccountException, which every specific exception, a leaf, extends. A nightly batch can catch only AccountException, while the ATM catches one leaf and the base: each caller picks its granularity.

The base also gives callers something narrower to catch than Exception. A caller that catches Exception or RuntimeException to be safe also catches the NullPointerException from a bug, and answers it with "rejected".

Throw IllegalArgumentException, IllegalStateException or UnsupportedOperationException When They Already Mean the Error

A cinema booking service is tempted to add SeatNotFoundException. Its web layer already has a handler, written long before the booking code:

Six failures go through it:

The new class turned a bad seat number into a 500 that pages on-call. The three standard exceptions have a meaning every Java developer shares, so handlers like this one already map them:

  • IllegalArgumentException: the argument is wrong whatever the object's state. Seat 0 never exists. The JDK's NumberFormatException is a subclass.
  • IllegalStateException: the argument is fine, but not now. Seat 4 exists, the booking is closed, and the same request may succeed later.
  • UnsupportedOperationException: this object never does that, like add on an unmodifiable list.

A closed booking reported as IllegalArgumentException answers 400, which tells the client to change a request that was right.

When you need your own type, to carry a field or to let one caller tell it apart, extend the standard exception that has its meaning: SeatOutOfRangeException extends IllegalArgumentException still gets its 400. Start a new branch, under the module's base, only for an error that belongs to your domain and that no standard exception describes, such as insufficient funds.

The second tried to add context and added the whole request. A record's toString() prints every component, so the email and card number are now everywhere the message goes: the log, the log aggregator, the ticket someone pastes it into, and any error page that echoes it. Removing them means finding every copy.

The third gives the value, the range with its bounds, and an identifier that leads to the rest. Objects.checkIndex(12, 10) gives the value and the bound too:

Write the range the way the code checks it, with each bound marked inclusive or exclusive: the reader of the log can't see the code. An identifier such as ch_7Q2, or a card's last four digits, points at the data without copying it. A password, a token, a full card number or personal data such as an email never goes in a message.

Log an Exception Where It Is Handled, Never Where It Is Rethrown

An order lookup has three layers: repository, service and controller. The lower two catch the failure, log it with java.util.logging and rethrow it, the service after wrapping it in OrderLookupException with the cause. The controller logs it and answers 503. The repository's catch:

Three SEVERE records and 24 lines for one failure, with connection reset three times. An alert on SEVERE fires three times, and whoever reads the log looks for three incidents. The last record holds it all: the wrapper keeps the original as its cause, and Caused by prints it.

When only the controller logs, the log is that last record alone, 9 lines. A layer with something to add puts it in the exception it throws, as the service's "could not load order 8812" does. The layer that decides what happens next (answers 503, retries, skips the record) logs, once, and passes the exception to log(level, message, e) so the stack trace is printed.

An API client needs to tell "insufficient funds" from "card expired". A leaf class pays off when a caller in the code catches it differently; for a client that only branches on the outcome, the payments module gives its base exception a code:

The message is written for the engineer reading the log, and it changes whenever someone improves it. The code is part of the API: the documentation lists it, and an existing code keeps its meaning, so renaming or removing one needs a new API version. New codes do appear, so a client needs a branch for a code it doesn't know yet. The response carries the code and not the message, which also keeps the values from the previous section away from clients.

Summary

  • One base exception per module lets each caller catch a leaf it treats specially and the base for the rest, so a new leaf needs no change in callers. A new unchecked leaf that callers catch only by name escapes them at run time.
  • Reuse `IllegalArgumentException`, `IllegalStateException` and `UnsupportedOperationException` when they mean the error, or extend them. Existing handlers already map them; a home-grown RuntimeException falls through to their fallback.
  • A message gives the bad value, the expected range and an identifier, never a whole request object, a password, a token, a card number or an email.
  • Log where the exception is handled. Logging and rethrowing prints the same stack trace once per layer.
  • Clients branch on an error code. An enum field mapped in a switch with no default survives rewording, and turns a new code into a compile error.

**What a change in the module does to an existing caller (runs on this page, Java 21; unit Checked vs. unchecked exceptions covers a checked exception added to throws):**

ChangeEffect
unchecked leaf added; the caller catches leaves by namethe new leaf escapes the handler
leaf added under a base the caller catcheshandled by the base's catch
enum constant added; mapped by a switch expression with no defaultthe mapping doesn't compile
message rewordedthe code is unchanged; text matching breaks

Challenges

  1. Your module's base exception is checked, and a team asks for it to be unchecked so they can call the module from a stream. What do callers lose and gain, and how would you migrate them? (Unit Checked vs. unchecked exceptions helps.)
  2. A third-party client library throws only RuntimeException, with different messages. Design the adapter that gives your callers a base exception and error codes.
  3. Find a log in your system where one failure produces more than one stack trace. Which layer keeps the log call, and what does each other layer add to the exception instead?

Design Note: Declare the Base, Document the Leaves

A throws clause is part of a method's contract, and callers compile against whatever it names. Naming each leaf gives the most precise contract, and turns every new failure into a change every caller must make. Naming the base gives up that precision for room to grow: the leaves move to @throws tags and to error codes, where adding one breaks no build but the one switch meant to catch it. The cost is that the compiler no longer tells a caller about a new leaf, and the base's handler takes it without anyone deciding. The switch over the codes puts one compile-time check back, in the one place that maps failures to responses.
