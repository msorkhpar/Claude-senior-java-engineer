A customer sends 250.00 from account A-1 to B-2x, a typo for B-2. The transfer API answers 500 Internal Server Error, and A-1 is 250.00 lighter. The same day, a request with a negative amount succeeds and moves money from the receiver to the sender.

Outputs are from Java 21, with classes compiled with -g so that exception messages name local variables.

Throw Where the Bad Value Arrives, Before Anything Changes

Two versions of the transfer, with amounts in cents:

Each call starts from A-1 = 100000 and B-2 = 0:

The late version did fail on the unknown account, with a NullPointerException that names the null variable (the default since Java 15). But it failed after the withdrawal, so the money was already gone. The negative amount failed nowhere, because withdraw and deposit accept a negative number; the transfer simply ran backwards.

A throw stops execution at that line, and control goes to the nearest enclosing matching catch, in this method or a caller. Whatever ran before it stays done. So a method checks its arguments and preconditions before its first change of state, and throws there. A throw placed after a change has to undo it, which a payment, an email or a row in another system often can't.

The early version also says what was wrong and with which value, which the caller can turn into a 400 instead of a 500. Objects.requireNonNull(id, "account id") is the short form of the null check: if id is null, it throws a NullPointerException with the message you give it.

The Compiler Knows a throw Ends the Block; It Doesn't Know Your Helper Always Throws

The operand of throw must be a Throwable: throw "negative quantity"; fails with incompatible types: String cannot be converted to Throwable. In return, the compiler knows that a throw never completes normally. A statement right after it in the same block is an unreachable statement error, and a switch expression arm can be default -> throw new IllegalArgumentException("unknown level: " + s); with no value.

That knowledge stops at the method boundary. A catalog moves its "unknown SKU" throw into a helper:

The compiler checks price against fail's signature, void, not against its body. The usual patch, return 0; after the call, ships a price of zero the day someone changes fail to log instead of throw. Make the helper return the exception, and keep the throw at the call site:

The first frame is the factory, because the trace is recorded when the exception is constructed, not when it is thrown (unit Handling exceptions with try/catch shows what that does to a shared, pre-built instance). The frame below it is the line that threw.

The operand is evaluated at run time, so it can be null. A class keeps a failure it found in a field and, later in main, throws it:

When no check failed, the caller gets an exception about the throw itself, not about any failure.

A Sneaky Throw Compiles, and Leaves Callers Unable to Name What It Throws

Called as throw sneaky(e); inside the lambda, it compiles with no throws anywhere. When a thrown type variable has nothing else to go on, Java infers RuntimeException for it. So the call declares nothing checked, and the erased cast lets the IOException itself out of the lambda. The caller tries catch (RuntimeException e), then catch (Exception e); then the same loader is called through a java.lang.reflect.Proxy of Supplier, the way an interface-based proxy calls it:

The IOException arrives where no signature says it can, and catch (RuntimeException e) let it pass. A caller that writes catch (IOException e) gets the same never thrown compile error as above, whatever its own method declares, so it must catch Exception and test the type. A dynamic proxy wraps a checked exception its interface doesn't declare in an UndeclaredThrowableException, so behind a proxy the real failure is a cause one level down.

Translate Exceptions at a Layer Boundary, and Keep the Cause

The account service reads from a JDBC store whose methods throw SQLException. Its callers, the web layer here, should not need to know about JDBC. Summary

  • Throw where the bad value arrives, before anything changes. A throw after a change leaves the change behind, and a value nothing checks may not fail at all.
  • The compiler knows a `throw` ends the block, not that a helper always throws. Have the helper return the exception and throw it at the call site. Throwing a null reference throws a NullPointerException.
  • A checked exception can't leave a `Function`. Wrap it in the lambda, and unwrap it before it leaves your method so callers can still catch the checked type.
  • A sneaky throw compiles and hides the checked type. Callers can't catch it by name, and a proxy turns it into UndeclaredThrowableException.
  • Translate at a layer boundary and keep the cause. Translate only the lower layer's exceptions, or your own become theirs.

Challenges

  1. Your service validates requests in a filter, then again in each method. Which checks belong where, and what happens when the two disagree?
  2. A stream pipeline runs in parallel and three elements fail with IOException. Which one does the caller see, and how would you report all three?
  3. Find a sneaky throw in a library you use. Which of your catch blocks would have to change if it became a declared checked exception?

Design Note: Why the Checked Exception Stops at the Lambda

Checked exceptions were designed for direct calls: the compiler reads each signature and makes the caller deal with what it lists. A lambda turns a call into a value that runs later, maybe on another thread, through an interface written long before your exception. java.util.function chose interfaces that declare nothing, so any lambda fits any stream. A checked exception then has to be wrapped, or hidden from the compiler, to get through. Either way the caller loses the one thing the checked exception gave it: a type it can catch by name. Unwrapping at your own boundary gives it back.
