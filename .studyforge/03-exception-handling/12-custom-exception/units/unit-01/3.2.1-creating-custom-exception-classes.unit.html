Meanwhile the node that retries failed batches logs java.io.NotSerializableException instead of the failure itself. A custom exception is a short class, and each of its lines decides what the person on call can see. The examples ran on Java 21.

The Class You Extend Decides Who Must Handle It

Extend Exception and the exception is checked: every method that lets it escape must declare it, or the code doesn't compile. Extend RuntimeException and it is unchecked: the compiler asks nothing.

Which to choose is a policy question (unit Checked vs. unchecked exceptions). One choice is wrong either way: extending Throwable (or Error) directly, to mark something as "more serious". A job runner usually has a safety net that logs a failed job and moves on to the next:

Three jobs, the second one over its quota; main catches whatever leaves runAll and prints "runner ended by":

QuotaExceeded is not an Exception, so the safety net, usually written as catch (Exception e), never sees it, and job 2 never runs. Error is reserved for problems a program shouldn't try to handle, such as OutOfMemoryError. A direct subclass of Throwable is also checked, so every interface it passes through must declare it, as Job does here.

A Wrapper Keeps the Original Failure Only If It Is Given the Cause

Throwable stores a detail message and a cause, the exception that led to this one. Exception and RuntimeException each have four public constructors for them, and a custom exception mirrors the ones its callers need:

The fourth, (), leaves both empty. Pause before the output: the ledger write fails with a SQLException, and the settlement code catches it and throws a SettlementException. What does the log show with each constructor?

The first is the 03:10 log line. Without a cause, the deadlock, its SQL state and the frames that led to it are gone, and nothing in the program can get them back. A class with only a message constructor forces every caller into that shape, so (message, cause) is the constructor never to leave out. The (cause) constructor keeps the chain but takes cause.toString() as its message, and the batch number is lost. Unit Throwing exceptions using the throw keyword covers throw and rethrowing from a catch.

A class without one can still attach a cause once, with initCause(cause), but every caller has to remember to (see the Reference).

Context Goes in Final Fields and in the Message

A handler that needs the order id should read it from a field, not parse it out of the message. Two versions of a payment exception, both with an orderId field and a getter; the second also puts its context in the message:

Logged as "checkout failed: " + e:

toString(), and with it the first line of a stack trace, prints the class name and the message. Your fields never appear unless you put them there. So the context goes in twice: in typed fields for code, and in the message for people. Build the message in the constructor and pass it to super rather than keeping a message field of your own, so that getMessage(), toString() and the stack trace agree. Keep the fields final with no setters: one exception object is caught, logged and rethrown by several layers, and none of them should be able to change what the next one reads.

Every Exception Is Serializable, So Its Fields Must Be Too

Throwable implements Serializable, so every exception class is serializable whether you meant it or not. Most exceptions are never serialized. The ones that are cross a JVM boundary through Java serialization: RMI, and some caches and job frameworks that ship a task's failure back to the caller. Here one exception holds the domain object, and a second holds only its id:

Each is written to an ObjectOutputStream and read back:

The first failure never arrives: the code shipping it gets a NotSerializableException about Order instead, which is what the retry node logged at 03:10. Marking the field transient silences the error, but a transient field isn't written and reading doesn't run the constructor, so it arrives as null. Keep ids, codes and amounts in exceptions, not connections, sessions or entities. The cause chain is serialized too, so a cause with such a field fails the same way.

The serialVersionUID matters on a rolling deploy, when the two sides run different releases. Without it, the version is computed from the class's shape, so adding a field changes it. Here release 1 of StockException writes one and release 2, with one more field, reads it, first without a declared serialVersionUID and then with one:

With private static final long serialVersionUID = 1L; in both releases, the new field reads as its default and the failure arrives. Throwable's own serialVersionUID covers only Throwable; each subclass needs its own. javac -Xlint:serial warns about a missing one, and about a field whose type isn't serializable.

An Exception Class Can't Be Generic

A RejectedException<T> that carries the rejected value as a T looks natural. The compiler refuses it:

A catch clause picks its handler by the exception's class at run time. After erasure, RejectedException<String> and RejectedException<Integer> are the same class, so catch (RejectedException<String> e) could never be checked. The rule also covers an inner (non-static) class declared inside a generic class, which is implicitly generic too; a static nested class compiles. Carry the value in a field of type Object or of a common supertype. A record can't be an exception either, because it already extends java.lang.Record.

Filling In the Stack Trace Is Most of the Cost; Skip It Only Where Nobody Reads the Trace

The stack trace is captured when the exception object is created: the constructor calls fillInStackTrace(), which walks the thread's stack. Some code throws exceptions as ordinary control flow, such as a rules engine where every rule that doesn't apply throws a miss and the engine tries the next. There the walk is paid on every miss, and nobody reads the trace.

Throwable has a protected four-argument constructor, (message, cause, enableSuppression, writableStackTrace), which Exception and RuntimeException pass on. With writableStackTrace = false no trace is captured. The older way overrides fillInStackTrace():

Summary

  • The superclass decides checked or unchecked. Extending Throwable or Error directly escapes every catch (Exception e) safety net.
  • `(message, cause)` is the constructor never to leave out. A wrapper without the cause loses the original exception and its frames for good.
  • Context goes in `final` fields and in the message. Logs print the message, not the fields.
  • Every exception is serializable. Keep its fields serializable, and declare a serialVersionUID so that the other release can still read it.
  • An exception class can't be generic, nor can an inner class of a generic class or a record be an exception.
  • A stack trace costs time that grows with stack depth. Switch it off only for exceptions that never leave the code that catches them, and only after profiling.

Challenges

  1. Your service's exceptions reach clients as JSON error bodies and reach the log. Which context belongs in the message, which only in fields, and which (a card number, an email address) in neither?
  2. A library throws an exception that holds a JDBC Connection in a field, and your job framework serializes failures. Where do you translate it, and what do you keep?
  3. Measure the stack depth at the point where one of your services throws its most common exception. Is the trace worth what it costs there?

Design Note: Why the Trace Is Taken in the Constructor

The JVM records the trace when the exception is created, not when it is thrown, so the trace points at the new, wherever the throw is (unit Throwing exceptions using the throw keyword). So every exception pays for its trace, whether anyone reads it or not, and a class that is created often pays most. Java 7 added the four-argument constructor so that such a class can opt out without overriding fillInStackTrace(). It is protected: the decision belongs to whoever writes the exception class, who knows whether the exception will ever reach a log, and not to the code that throws it. For almost every exception the default is the right choice, because a failure is rare and its trace is what tells you where it happened.

Problem statement


The nightly customer export runs on a fleet of worker JVMs. When an export fails, the job framework serializes the failure with Java serialization and sends it to the coordinator, which logs it and schedules a retry for that customer. Since the last release, the coordinator logs java.io.NotSerializableException where the failures used to be, and no failed export has been retried.


Workers and coordinators are upgraded on different days, so for a while a worker on one release talks to a coordinator on the other. The coordinators still run the previous release of ExportFailedException, which was declared with serialVersionUID = 1L and kept the customer's id in a String field named customerId. Customer comes from the CRM client library and you can't change it.
