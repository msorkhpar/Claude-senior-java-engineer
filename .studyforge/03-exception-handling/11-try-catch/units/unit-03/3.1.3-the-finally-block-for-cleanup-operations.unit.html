finally Runs on Every Way Out of try: return, break, continue or a Throw

This loop leaves its try five ways, counting the normal end:

The compiler copies the finally code onto every path out of the try: the normal end, each return, break and continue, and an exception of any type (javap -c shows five copies of the println in firstCsv).

Cleanup written anywhere else misses a path. A quote service counts calls in flight and refuses new ones at 200. If the decrement sits after the backend call, every failed call leaks one; add it to a catch (IOException e) as well, and every NullPointerException still leaks one. After an outage of a few minutes the gauge stays at 200 and the service refuses every request with nothing running. Unit Reentrant locks applies the same rule to unlock().

A return in finally Throws Away the Exception and the try's Result

The file was corrupt; the caller got 0 and no error, so its retry on IOException never ran. When finally ends with return, break, continue or a throw of its own, that ending replaces the try's: the pending exception or return value is dropped. javac warns only when the finally lint is on (-Xlint:finally or -Xlint):

  1. Coding practice

    Keep the quote service's in-flight gauge honest

    • finally runs on every way out of its try: normal end, return, break, continue and an exception of any type, so cleanup written after the block or in one catch misses paths.
    • A finally that ends with return (or break, continue or its own throw) discards the try's pending exception or return value.

finally Runs Only When the Thread Leaves try: exit, halt and a Killed JVM Skip It


Each case runs in its own JVM: a shutdown hook prints hook ran, and a thread sleeps inside a try whose finally prints finally ran:



finally runs when the thread leaves the try. System.exit and a SIGTERM start the JVM's shutdown: hooks run, then the JVM halts every thread where it is; per the Runtime javadoc, "finally clauses are not executed". When the last non-daemon thread ends, the same happens to daemon threads. halt and SIGKILL skip the hooks too. An interrupt is the one case here that runs finally: it ends the sleep with an exception, and the thread leaves try the ordinary way.


A lock file or temp file cleaned up only in finally is left behind by every deploy whose SIGTERM arrives while a thread is in that try. Cleanup that must survive shutdown goes in a shutdown hook that stops the work and waits for it (unit ExecutorService interface and implementations), and startup must cope with what a SIGKILL leaves.




    

  1.

    Check yourself: what finally guarantees

    • The value a return statement returns is evaluated before finally runs, so changing a primitive field or variable in finally doesn't change the result.

Summary


  • finally runs on every way out of try. Cleanup after the block, or in a catch, misses the paths it wasn't written for.
  • A return in finally discards the exception and the result. javac warns only with -Xlint:finally or -Xlint.
  • return fixes its value before finally runs. Reassigning the variable doesn't change the result; mutating the object it refers to does.
  • An exception from finally replaces the one in flight and ends the finally. Give each failing cleanup step its own try, attach its failure with addSuppressed, and release locks in an inner finally.
  • finally needs the thread to leave try. System.exit, SIGTERM, halt and SIGKILL skip it, and so does JVM exit for a daemon thread still in try.

Design Note: Why Cleanup Is a Block of Code


C++ releases a resource in a destructor that runs when its owning object goes out of scope. Java objects have no such moment, so Java put cleanup in the method that acquires the resource, as a block the compiler copies onto every exit path. The release sits next to the acquisition, but each caller rewrites it, in order, with nested handling for each failing step. Try-with-resources (unit try-with-resources statement) moved that code into the compiler for anything AutoCloseable; finally stays for what is not a resource object: a lock, a gauge, a flag.
