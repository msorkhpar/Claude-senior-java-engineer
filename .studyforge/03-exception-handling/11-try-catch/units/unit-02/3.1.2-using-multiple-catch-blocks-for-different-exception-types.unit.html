The checkout service charges cards through a payment gateway. When the gateway times out, the charge may or may not have gone through, so the timeout's catch block asks the gateway's status endpoint. During a gateway incident the status call failed too. Customers got an HTTP 500, although pay() has a catch (GatewayException e) right below.

The First Catch Clause That Matches Wins, So a Subclass Goes Above Its Superclass

Java tests the catch clauses from top to bottom and runs the first one whose type the exception is an instance of. A rates loader uses yesterday's file when today's is missing, retries a slow read, and fails on any other I/O error:

Position decides, not specificity as with overloads. Both specific types are IOExceptions, so with the IOException clause on top nothing could reach them, and javac rejects the order:

Only catch clauses get this check. The same order as an instanceof chain inside one catch (Exception e) compiles, and the yesterday's-file branch never runs:

An Exception Thrown in a Catch Block Leaves the Whole try Statement

The catch clauses of a try guard its try block, nothing else. The checkout:

The 503 is a GatewayException, but the statement chose its handler when charge() threw, and it chooses once. Had status() thrown a checked IOException, javac would have refused it as unreported, even with a catch (IOException e) below. An unchecked one compiles and propagates, and the customer gets a 500 for a charge that may have succeeded. A call in a handler that can fail needs its own try, which decides what that failure means: here, "payment pending".

A Multi-Catch Shares One Handler; Its Parameter Is Final and Typed as What the Types Share

catch (A | B e) runs one block for either type. Its alternatives must be unrelated, since a subclass alternative adds nothing:

The parameter is implicitly final (multi-catch parameter e may not be assigned). Its type is not "A or B" with the methods of both, but the closest supertype they share, their least upper bound. For IOException | SQLException that is Exception, and e.getSQLState() doesn't compile:

catch (Exception e) is not a shorter multi-catch: it also takes unchecked exceptions, so a bug's NullPointerException gets the I/O error's handling (unit Handling exceptions with try/catch).

Catching Exception to Rethrow It Keeps the Precise throws Clause

A cleanup block can catch Exception and still declare only the checked exceptions its try throws:

throw e on an effectively final catch parameter throws only the checked exceptions the try block can throw and that no earlier clause catches (JLS 11.2.2). Catching Exception is right here because nothing is swallowed: a bug's IllegalStateException is rolled back and rethrown too. Assign to e and the precision is gone:

Developers who expect that error everywhere declare throws Exception, which every caller must then handle. Others wrap the failure in a RuntimeException, and the caller's catch (SQLException e) that retries deadlocks never runs.

A Catch for a Checked Exception the Try Can't Throw Is an Error, Except for Exception and Throwable

javac knows which checked exceptions a try block can throw, from its throw statements and the throws clauses of what it calls. A refactor made readRates() read a cache and dropped its throws IOException:

Each multi-catch alternative is checked the same way. Exception and Throwable always pass, because they include unchecked exceptions, which any code can throw. After the same refactor a catch (Exception e) compiles silently, and its handler now takes only unchecked exceptions.

Summary

  • The first matching clause wins. javac checks that order for clauses, not for instanceof chains.
  • A catch block's own exception skips the clauses below it. A handler's risky call needs its own try.
  • A multi-catch takes unrelated types; its parameter is final and typed as their least upper bound.
  • Rethrowing an unchanged `catch (Exception e)` keeps the precise `throws` clause.
  • Catching a checked exception the try can't throw is an error; Exception hides a dead handler.

Reference

Which catch types compile (javac 21):

The clause catchesCompiles when
a checked exceptionthe try block can throw it, a subclass of it, or a superclass of it
an unchecked exception, Exception, Throwablealways, unless after a clause for its supertype
a type after a clause for its supertypenever
related types in one multi-catchnever

Challenges

  1. Find a catch (Exception e) in your code that handles rather than rethrows. Would a multi-catch of the checked types change behaviour?
  2. A timeout handler calls a second service. For each exception that call can throw, what should the method return?
  3. When is wrapping better than rethrowing e unchanged? What does the caller gain and lose?

Design Note: The Compiler Reads the Catch List as a Claim

javac checks each catch clause as a claim that this try can throw that exception, and multi-catch and an unchanged throw e keep the claim narrow without duplicated blocks or throws Exception. Unchecked exceptions, catch (Exception e) and instanceof chains claim nothing javac can test, so a refactor that changes what a try throws goes unnoticed there.

The warehouse books a shipping label for every parcel through the carrier's API. Addresses come from customers' typing, so the carrier sometimes rejects one, and ship(...) then hands the parcel to bookNormalized(...), which tries once more with the address cleaned up.


During last week's carrier incident, the packing stations showed a stack trace instead of the usual "retry later" for every parcel that had needed a second attempt. And a parcel whose address was wrong in both forms must go to the address-review queue, where a person fixes it; it must not come back every ten minutes.


ship(...) already books, and already answers a carrier failure on the first attempt. Finish the TODO in src/main/java/practice/LabelBooking.java:


  • bookNormalized(...): book the parcel with normalize(address) and return what ship(...) returns: "booked: " and the tracking number, "review: " and the carrier's reason when the address is rejected again, or "retry later: " and the message when the carrier fails.


ship(...) never throws a carrier failure at its caller. About six lines in total.
