A catch Clause Catches Its Type and Every Subtype

quantityNarrow is the same method with catch (NumberFormatException e):

catch (X e) takes an X or any subclass of X. The author meant "whatever parseInt throws", but every checked exception and every RuntimeException is an Exception, so the NullPointerException from the missing field became a valid-looking quantity. The narrow catch lets the bug through, and the first order fails loudly.

Around a sleep or a Future.get, catch (Exception) catches InterruptedException, whose throw has already cleared the interrupt flag, so code further up never learns the thread was asked to stop unless the catch restores it (unit Stopping threads (interrupt() method and cooperative cancellation)). StackOverflowError and OutOfMemoryError extend Error, not Exception, so catch (Exception) lets them pass. catch (Throwable) takes them, and the thread runs on with whatever half-finished update the error interrupted.

Catch the type you can handle, and let the rest reach code that reports it.

A New Exception Without the Cause Loses the Failure It Replaces

Two price-file loaders wrap the IOException; the second passes it as the cause:

Without the cause, the trace ends in our code: which file, and whether it was missing or unreadable, is gone. ... 1 more means the cause's remaining frames are the last frames of the enclosing exception's trace.

Copying e.getMessage() into the new message keeps neither type nor trace; an empty catch keeps nothing. Rethrowing the same object, throw e;, keeps everything. A task's exception reaches Future.get as the cause of an ExecutionException (unit Callable and Future for returning results).

An Exception Thrown in a catch Block Replaces the One Being Handled

The primary answers 401 Unauthorized and the mirror times out. The caller prints what reaches it:

Java doesn't link a new exception to the one being handled, which only the variable e refers to; when the catch block throws, e is dropped. On-call chases a network timeout while the real fault is an expired key. Attaching the first failure keeps both:

Suppressed, not cause: the timeout didn't happen because of the 401.

A throwing finally block replaces an exception the same way (unit The finally block for cleanup operations). Try-with-resources attaches the other way round: an exception from close() is suppressed into the body's (unit try-with-resources statement).

The Stack Trace Is Recorded Where the Exception Is Created, Not Where It Is Thrown

To save allocations, a catalog throws one shared instance for every unknown SKU:

A caller, checkout("BOOK-17"), calls price and prints what it catches:

Throwable's constructor calls fillInStackTrace(), which records the creating thread's stack; throw records nothing. <clinit> is the static initializer; neither checkout nor price appears. Calling fillInStackTrace() on the shared object before each throw walks the stack anyway, and overwrites the trace of an earlier failure still queued for the log. Create a new exception for each failure.

The JIT can drop traces too. HotSpot's OmitStackTraceInFastThrow, on by default, lets compiled code throw a preallocated exception for some exceptions the JVM raises itself. In our loop, after about 2,800 NullPointerExceptions from one line, the next had message=null and no frames; with -XX:-OmitStackTraceInFastThrow all 100,000 kept their traces.

Throwing Costs Microseconds, Mostly the Stack Trace; a try That Doesn't Throw Costs Nothing

We timed four parsers on 200,000 inputs, median of 7 rounds after warm-up, at the caller's depth and 100 frames deeper (the deep rows include the 100 calls to get there):

A try adds no instruction: javac writes an exception table that the JVM reads only when something is thrown, so valid input costs what checking first does. A throw cost about 0.3 µs, and over 2 µs with 100 more frames to record, because filling in the trace walks the stack. An exception built with writableStackTrace set to false (a protected four-argument constructor) cost close to checking first.

One machine, not JMH. A hand-written loop: across three runs the deep throw ranged from 2.1 to 2.7 µs. The ratios held in every run.

At 100 frames deep, a thousand bad rows a second cost under 3 ms of CPU, and a million would keep more than two cores busy. Use exceptions for what the caller can't expect, and a return value for an outcome it can.

Summary

  • A catch clause catches its type and every subtype. catch (Exception) turns bugs and interrupts into defaults.
  • A new exception without the cause loses the failure it replaces.
  • An exception thrown in a catch block replaces the one being handled. Attach the first with addSuppressed.
  • The stack trace is recorded at construction. A shared exception reports where it was made.
  • A throw costs microseconds, growing with stack depth. A try that doesn't throw costs nothing.

Challenges

  1. A batch job must skip bad records but stop on bugs. Where does each catch go, and how does it report what it skipped?
  2. A client library throws only RuntimeException, with the error in the message. How do you recover from one case?
  3. Profile a service that validates with exceptions. Is fillInStackTrace in the top ten?

Design Note: Why the Trace Is Taken at Construction

Recorded when the object is built, the trace travels with the exception: through a Future, inside a cause, into a later log. The price is a stack walk for every exception, read or not. A type that opts out, through the four-argument constructor or an overridden fillInStackTrace(), is cheap and leaves nothing to debug.
