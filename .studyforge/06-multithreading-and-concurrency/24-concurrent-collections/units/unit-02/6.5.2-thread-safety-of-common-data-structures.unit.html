The ops dashboard counts requests per endpoint and minute in a map that every request thread writes. It was a HashMap. After a week of low counts, someone wrapped it in Collections.synchronizedMap(...). The counts are still low, and the hourly export that walks the map now fails with ConcurrentModificationException.

Java has two ways to share a collection: a wrapper that locks each call, and the java.util.concurrent collections. Neither makes a sequence of your calls atomic. Every output below is from Java 21 on a 20-core machine.

A Plain HashMap Shared by Writers Loses Entries and Can Hang

Four threads put 25,000 keys each into one HashMap; raceFor returns how many are still running after 2,000 ms:

Five runs:

One thread alone keeps every distinct key, colliding or not, but different threads still share the map's table. When it fills, put moves every entry into a larger one, and threads that link entries or resize at the same time overwrite each other's work. Entries vanish without an error. The table is left in a shape that later calls fail on (ClassCastException from inside HashMap) or loop in: those threads were still inside put() two seconds later, each keeping a core busy, and a request thread caught there never answers. ArrayList, HashSet and the other mutable java.util collections break the same way, with lost elements and exceptions from inside the collection.

A Synchronized Wrapper Makes Each Call Atomic, Not a Sequence of Calls

The dashboard's counter, eight threads, 10,000 hits each over four endpoints:

and the same count in one call:

The wrapper locks each get and each put, and releases the lock between them. Two threads read 41, both write 42, and one hit is gone. This is the race of unit Monitors and synchronized blocks's flash sale, on a map. Moving to ConcurrentHashMap changes nothing while the code still makes two calls.

merge, compute, computeIfAbsent and putIfAbsent read and write in one call, and both maps run each of them atomically. Make every read-modify-write on a shared map one of those calls.

Walking a Wrapper Is Many Calls: Hold the Wrapper's Lock for the Whole Walk

A report walks a synchronizedList of 1,000 events 10,000 times while a writer adds the newest event and removes the oldest: once without a lock, once holding the list's lock, once over a CopyOnWriteArrayList:

A for-each loop calls iterator(), then hasNext() and next() per element, and the wrapper locks none of them: its iterator() hands back the ArrayList's own iterator, which notices the change and throws. Only the wrapper's one-call walks, forEach and removeIf, hold its lock. The wrapper's lock is the wrapper object itself, which is why synchronized (events) excludes every writer that goes through it. Locking anything else, such as this of the reporting class, excludes nobody.

The lock has a price: every writer waits for the whole walk. A thread that called add during a locked walk of 2,000,000 elements returned after 37 ms. For a long walk, copy the list (new ArrayList<>(events) copies through the wrapper's locked toArray()) and walk the copy. A map's copy (new HashMap<>(map)) walks the map, so it goes inside the block. Unit Order of Operations in Concurrent Collections shows what the iterators of the concurrent collections see instead of throwing.

A Thread-Safe Map Guards Its Entries, Not the Objects Stored in Them

A chat service keeps each room's messages in a ConcurrentHashMap<String, List<String>>. Eight threads post ten messages each into two rooms, in 1,000 rounds, in three ways:

How does the first lose messages when every list is synchronized? Two threads find no list and each creates one; the second put replaces the first list with the messages already in it. computeIfAbsent runs the factory at most once per missing key and gives every caller the same list.

The second creates the list once, then eight threads call add on one ArrayList; over the 1,000 rounds it threw ArrayIndexOutOfBoundsException from inside add ten times, ending that posting thread. The map's atomicity covers finding or creating the entry, and ends before add runs. A value that threads change after they get it is shared state of its own, and needs its own thread safety: a synchronized or concurrent collection, or an AtomicInteger. Removing an entry once its value is empty has the same gap: a thread that fetched the value before the removal adds to an object the map no longer holds. Do the removal and the add inside compute, so the entry and its value change together.

CopyOnWriteArrayList Copies the Whole Array on Every Write

Each write to a CopyOnWriteArrayList copies the array, changes the copy, and publishes it. Reads and walks use whichever array was current, with no lock. One thread, 100,000 adds, then 1,000 walks of the full list (the synchronized list walked under its lock):

The cost of an add grows with the list: the last one copied 99,999 elements. In return, a walk never waits and never throws (unit Order of Operations in Concurrent Collections shows what it sees).

That fits a list of listeners or routes, read on every event and changed at deploy time. An event buffer that grows on every request belongs in a synchronized list or a queue.

Summary

  • A plain `HashMap` or `ArrayList` shared by writers loses entries (even with distinct keys), and can throw or hang inside the collection.
  • A synchronized wrapper makes each call atomic, not a sequence. A read-modify-write is one call (merge, compute), on either map.
  • Walking a wrapper takes many calls. Hold the wrapper's own lock for the walk, and every writer waits for it.
  • A thread-safe map guards its entries, not their values. Create values with computeIfAbsent, and make a shared value thread-safe itself.
  • `CopyOnWriteArrayList` copies on every write. It suits lists read far more often than written.

Challenges

  1. The export must see one consistent minute of counts while 200 threads keep counting. Compare locking a wrapper for the export, copying under the lock, and swapping in a fresh map each minute. What does each cost the request threads?
  2. Replace the merge counter with computeIfAbsent(e, k -> new LongAdder()).increment() and measure both with 64 threads on one key. When is the difference worth a less obvious type?
  3. A listener registry gets one listener added per user session. At what size does CopyOnWriteArrayList stop being the right choice, and what do you use then?

Design Note: Why a ConcurrentHashMap Can't Be Locked From Outside

A synchronized wrapper locks on itself, so a caller can extend its atomicity: synchronized (map) around a check and a put makes them one step for every thread that also goes through the wrapper. The price is one lock for the whole map, so readers wait for writers and for each other.

ConcurrentHashMap gave up that lock to let threads work on different bins at once. Its methods never lock the map object, so synchronized (map) around a sequence excludes only code that does the same. What a caller can't build from outside, the map provides as single calls: merge, compute, computeIfAbsent, putIfAbsent, replace(key, old, new). A sequence that none of them expresses needs your own lock around every access to the map, and then the map's concurrency buys nothing.

The public API sells calls in packs. Billing tops a client up through grant, and every request thread calls tryUse before it serves a call. In last month's traffic spike two things went wrong: clients who bought a pack at the same moment as an automatic renewal got only one of the two, and clients with a single call left were served two or three calls for it.


The quotas already live in a ConcurrentHashMap. Finish the two TODOs in src/main/java/practice/Quotas.java:


  • grant(client, calls): add the calls to what the client has left;
  • tryUse(client): take one call if there is one, and say whether it did.


When you're done, every top-up counts however many arrive together, a client's last call is served once, and the quota never goes below zero. About eight lines in total.

Problem statement


The login service keeps the time each session was last seen in a Collections.synchronizedMap. Every request calls touch, so the map changes many times a second. Once a minute a sweeper removes the sessions that have expired, and on busy days it dies with ConcurrentModificationException, leaving stale sessions behind. The debug endpoint that dumps the sessions has a problem of its own: the dump it is writing out changes while it writes.


Finish the two TODOs in src/main/java/practice/SessionSweeper.java:


  • sweep(policy): remove every session the policy says has expired, and return their ids;
  • snapshot(): the sessions as they are now, in a map that later requests don't change.


When you're done, a sweep finishes however many requests arrive while it runs, a request that arrives during a sweep is kept, and a dump doesn't change once it is taken. About ten lines in total.


The tests send a request into the middle of a sweep, through the expiry policy, and check from the JVM's thread data whether the request had to wait for the sweep.

Problem statement


The search service indexes documents by word: a ConcurrentHashMap from each word to the set of documents that contain it. Indexing threads add and remove documents all day, while search threads look words up and walk the sets they get back. Support tickets say that a freshly published document sometimes can't be found by a word it plainly contains, and a search now and then fails with ConcurrentModificationException.


Finish the two TODOs in src/main/java/practice/WordIndex.java:


  • add(word, documentId): record the document under the word;
  • remove(word, documentId): take it off again, and drop the word once no document has it.


When you're done, no document is lost however the indexing threads interleave, including one added at the moment the word's last other document is removed, and a search can walk a word's documents while they change. About ten lines in total.


The tests make the threads interleave the same way on every run, through the map and the sets the index is given.
