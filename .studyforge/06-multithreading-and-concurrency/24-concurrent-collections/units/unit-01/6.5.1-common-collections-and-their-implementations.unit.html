The tenant-settings cache is a HashMap<String, String>, and a setting a tenant cleared is stored as null, so the cache can tell it from one never set. A reviewer asks for thread safety, and the change is one line: settings = new ConcurrentHashMap<>(settings). The next deploy fails at startup with a NullPointerException from that line.

Both classes implement Map, and the interface leaves null, order and cost to each implementation. Swapping one for another changes those promises along with the speed.

A Collection Costs What Its Structure Makes It Cost: ArrayList by Index, ArrayDeque at the Ends

The same call costs a different amount in each implementation, and in a loop the difference multiplies. An export sums 100,000 order amounts by index. Pause before the output: how much slower is the same loop over a LinkedList? The second measurement uses a list as a queue, taking from the front:

An ArrayList is an array: get(i) is one address computation. A LinkedList is a chain of nodes, and get(i) walks from the nearer end, so the loop makes about n²/4 hops: 2.5 billion here. LinkedList's constant-time insert needs a position you already hold, through a ListIterator; getting there is the same walk.

Taking from the front is the opposite case: remove(0) shifts every remaining element down by one. ArrayDeque is a circular array that only moves its head index, so poll() costs the same at any size.

Both loops are quadratic: ten times the rows makes them about a hundred times slower. The code that hits this rarely builds the list. It takes a List parameter, and one caller passes a LinkedList. Loop with for-each, which walks either list once, or check for the RandomAccess marker interface, which ArrayList implements and LinkedList doesn't. For a queue or a stack, use ArrayDeque.

A Hash Set Iterates in Hash Order, and the Order Changes as the Set Grows

A HashSet promises no order at all. An importer drops repeated airport codes with a HashSet and then writes the codes out:

A HashSet keeps its elements in a table of buckets chosen by hashCode(), and iterates by walking the table. For the same elements and table size the order is the same on every run, so it looks stable while the set is small. The default table has 16 buckets and doubles when it passes three-quarters full, 12 elements; then the elements are spread over twice as many buckets, and the same five codes come out in another order (unit Collection Capacity and Resizing explains the resize). A test written with five codes passes, and production, with fifteen, writes them in a different order.

When order matters, say which one: LinkedHashSet keeps the order of first insertion, and add of an element already there doesn't move it (Java 21's addFirst and addLast do). TreeSet and ConcurrentSkipListSet keep sorted order.

ConcurrentHashMap Refuses null, So That null from get Means Absent

ConcurrentHashMap throws on a null key or value, where HashMap stores it. The settings map from the start of the unit, and a few other collections (attempt runs a call and prints how it ended):

A HashMap returns null both for a key mapped to null and for a missing key, and containsKey tells them apart. In a map that other threads write, that takes two calls, and another thread can put or remove the key between them, so the two answers describe different moments. ConcurrentHashMap refuses null keys and values, which makes get returning null mean "absent" on its own. The skip-list collections and the concurrent queues refuse null for the same reason, and so does ArrayDeque, which isn't concurrent, through add and offer alike: poll() returning null must mean "empty". The copy-on-write classes and the synchronized wrappers accept it.

Storing null let the cache tell "the tenant cleared this" from "never set, use the default". The quick fix is to store "" for "cleared". Then a tenant whose order-number suffix really is empty reads back as cleared. A stand-in for null has to be a value no caller can store: a private object in a Map<String, Object>, or an Optional<String> value type.

CopyOnWriteArrayList Copies Its Array on Every Write, So Readers Iterate a Snapshot

A deploy event goes to a list of listeners. The first listener runs once: it removes itself, and the audit listener with it, while the event is being delivered:

Every write to a CopyOnWriteArrayList copies the array, changes the copy and swaps it in. An iterator keeps the array it started with, so it takes no lock, a writer never waits for it, it never throws ConcurrentModificationException, and it doesn't see a change made after it began. That is why audit heard the event after being removed: removal takes effect from the next event.

That fits a listener list, written a few times at startup and read on every event; unit Thread Safety of Common Data Structures measures what each write costs, and unit Order of Operations in Concurrent Collections shows how the iterator behaves.

A Sorted Set Answers Ranges Through Views Backed by the Set

A stock report lists the SKUs in a band. ConcurrentSkipListSet is the concurrent counterpart of TreeSet: sorted, a NavigableSet, with O(log n) expected cost. Is D-400 in the band below?

The two-argument subSet includes its lower bound and excludes its upper one, so adjacent bands don't overlap. The four-argument form sets each bound. b-250 sorts last because natural String order compares character codes, and lower case comes after upper case.

subSet, headSet and tailSet return live views, not copies. A view shows later changes to the set, writes through to it, and refuses an element outside its range. A report that returns the view and prints a total first and the lines later can print lines that don't add up to the total. A result that must stay as it was returns List.copyOf(view).

Summary

  • A collection costs what its structure makes it cost. get(i) on a LinkedList walks, and remove(0) on an ArrayList shifts; both turn a loop quadratic. Use ArrayDeque for queues.
  • A hash set iterates in hash order, which changes when the table resizes. Ask for the order you need with LinkedHashSet or a sorted set.
  • `ConcurrentHashMap` refuses `null`, as do the skip-list collections, the concurrent queues and ArrayDeque, so null from get or poll means absent or empty. A stand-in for null must be a value no caller can store.
  • `CopyOnWriteArrayList` copies on every write. Iteration takes no lock and walks a snapshot that ignores later changes; writes cost the whole array.
  • A sorted set's ranges are views, half-open by default, that follow the set.

Challenges

  1. A method takes a List<Row> and loops over it by index. You can't control what callers pass. Which change do you make, and how do you test that it worked?
  2. Your registry has 10,000 subscribers and gains one per second. Measure whether CopyOnWriteArrayList is still the right choice, and what you would replace it with.
  3. A report must list the distinct customer ids from today's events in a stable order. Compare LinkedHashSet, TreeSet and sorting a HashSet's contents: which order does each give, and which does the reader of the report expect?

Design Note: One Interface, Different Promises

The collection interfaces let a method accept any List or Map, and let a caller swap implementations without touching it. The cost is that a parameter typed Map tells you nothing about the promises this unit compared: whether null is allowed, what order iteration gives, what get costs, or whether another thread may write. Code that relies on one of those relies on something the type doesn't say, and the one-line swap from the start of the unit breaks it. Name the promise you depend on, in the type (SequencedSet, NavigableSet, ConcurrentMap) where one exists, and in the documentation where none does.

Problem statement

A collector that times out sends its whole batch again, so one event can reach the importer two or three times, each copy stamped with the time it was received. Auditors read the log top to bottom and expect each event once, in the order the events reached us.


AuditImport already writes a batch to the log. Finish firstOfEach(...) in src/main/java/practice/AuditImport.java: it returns each event of the batch once, as the first copy that arrived, in the order of first arrival, and leaves the batch it was given unchanged. About three lines.


Copies of an event are the same event when their ids are equal; nothing else about them has to match.
