A Probe That Reads the Array Behind a Collection

A collection's capacity is the length of the array behind it, and the API doesn't show it. Capacity.of reads the array by reflection, with the two --add-opens flags in its comment.

A HashMap Is Sized in Buckets, and It Doubles at Three-Quarters Full

Before you run it: a map created with new HashMap<>(100) gets 100 puts. Does its table change?

It does. HashMap's constructor takes a number of buckets (the table's length) and rounds it up to a power of two: 100 becomes 128. The map doubles the table as soon as its size goes above the threshold, capacity × load factor, and the default load factor is 0.75. A 128-bucket table holds 96 entries, and put 97 doubles it. The table is allocated on the first put, not in the constructor.

The opening problem is the same arithmetic: 900,000 rounds up to 1,048,576 buckets, whose threshold is 786,432. The rebuild resizes once, at put 786,433.

HashMap.newHashMap(n) (Java 19) takes the number of entries and picks a table that holds them. Before Java 19 the usual request was (int) (n / 0.75f) + 1, the pre-Java-19 formula, which also gives 256 for 100. new HashSet<>(n) and new LinkedHashMap<>(n) take buckets too, and so does the three-argument LinkedHashMap constructor that an access-ordered cache needs. Its factory, LinkedHashMap.newLinkedHashMap(n), takes no access-order argument, so there you compute the bucket count yourself.

A Resize Moves Every Entry in One put

Doubling keeps the average put cheap: the moves over a whole load add up to fewer than two per entry. The cost lands on one call. This loads the opening problem's SKUs, 900,000 distinct String keys in skus, and times every put:

Third round, after two to warm up, with a 3 GB young generation so that no collection runs during the load:

Most of the 23 ms between the totals is one put. It took 19 ms: it allocated a table of 2,097,152 buckets and moved 786,433 entries into it while the old table was still alive. Across runs that put took 19 to 29 ms. A resize doesn't call your hashCode() again (HashMap stores each key's hash; 1,000 puts through seven resizes made 1,000 calls); its cost is the walk over every entry.

So pre-sizing mainly removes a pause. Oversizing costs memory: HashMap.newHashMap(1_000_000) allocates 2,097,152 buckets on its first put, about 8 MB with compressed references (4 bytes each, the default below a 32 GB heap), even if only ten entries arrive.

ConcurrentHashMap Is Sized in Entries, and Its Load Factor Only Sizes the First Table

The stock cache is shared between request threads, so it's a ConcurrentHashMap, and someone copied the pre-Java-19 formula into it. The maps built for 100 get 200 puts; those built for 40 or 54 get 40:

new ConcurrentHashMap<>(100) is already sized for 100 entries: its javadoc says it sizes the table "to accommodate this many elements", the meaning newHashMap has. Passing it the formula, 54 for 40 entries, sizes for 54 entries and gets 128 buckets where 64 hold 40. Not every count crosses a power of two (100 and its 134 both give 256), so the waste shows on some maps and not others.

The load factor sizes only the first table: 100 entries at 0.5 asked for 200 buckets and got 256, but the next resize still came when the size reached three-quarters, put 192. That is one put earlier than HashMap's rule (the default map resizes at put 12, not 13). A load factor above 0.75 makes the first table smaller, and the map still resizes at three-quarters. In new ConcurrentHashMap<>(n, lf, concurrencyLevel) the last argument is a sizing hint as well: the initial capacity is raised to at least its value.

An ArrayList Grows by Half When Full, and Nothing Shrinks on Its Own

An ArrayList grows only when its array is full, to about one and a half times its length: new ArrayList<>() gets 10 slots on its first add, then 15, 22, 33. Each writer thread of a batching service reuses one list as its buffer, and one night a burst of a million records goes through it:

clear() nulls the slots so the records can be collected, and keeps the array. With compressed references, the empty buffer holds 4.9 MB for as long as the writer keeps the list, once per writer thread. trimToSize() gives it back but leaves 0 slots, and the next batch regrows from 1: 1, 2, 3, 4, 6,

  1. A buffer that should stay at its normal size after a burst is better replaced with a new list of that size. A HashMap doesn't shrink either: emptied of 100,000 sessions, it keeps 262,144 buckets, and clear() keeps them too.

Before adding a known number of elements one by one, ensureCapacity(minCapacity) grows the array once. Its argument is the total the list must hold, not the number to add: on a list that already holds 500 elements in 549 slots, ensureCapacity(500) does nothing.

CopyOnWriteArrayList keeps no spare capacity at all: every add copies the array into a new one exactly one longer (unit Thread Safety of Common Data Structures shows what that costs).

Summary

  • A `HashMap` is sized in buckets and doubles above three-quarters full. new HashMap<>(n) resizes before n entries for many n; HashMap.newHashMap(n) takes the entry count.
  • A resize moves every entry in one put. On a large map, pre-sizing removes a pause of tens of milliseconds, more than it speeds up the load.
  • `ConcurrentHashMap` is sized in entries, and its load factor only sizes the first table. The HashMap formula can oversize it, and every later resize comes at three-quarters full.
  • An `ArrayList` grows by half when full, and nothing shrinks on its own. clear() keeps the array, and an emptied HashMap keeps its table: trim the list, or replace either.

Challenges

  1. A map is filled once at startup and only read afterwards. Measure what a load factor of 1.0 instead of 0.75 saves in memory and costs in get time, with String keys.
  2. Your service builds one HashMap per request for a few dozen entries. Is pre-sizing worth a line of code there? Decide with a measurement.
  3. A cache's size swings between 1,000 and 1,000,000 entries over a day. Design how it gives back memory after a peak, and what each rebuild costs the requests in flight.

Design Note: Why HashMap's Constructor Takes a Bucket Count

HashMap picks a bucket with hash & (capacity - 1), which needs a power-of-two table, so its constructor asks for the thing it allocates. The number a caller actually knows is how many entries are coming, and turning it into a bucket count means dividing by the load factor first, a step that is easy to skip. Java 19 added newHashMap and a note on both constructors pointing to it, and left the constructors' meaning alone, likely because changing it would change the memory and the resize points of every existing new HashMap<>(n). The cost is that the same int means buckets in HashMap and entries in ConcurrentHashMap, two classes that often sit in the same service.

Problem statement


The catalogue import loads one batch of SKUs at a time, and the batch header says how many rows follow. A profile of an import shows time in HashMap.resize and ConcurrentHashMap.transfer on every batch, and a heap dump shows the stock cache's table twice the length of the price index's, for the same number of SKUs.


CatalogMaps builds three maps per batch. Finish its three factory methods in src/main/java/practice/CatalogMaps.java:


  • newPriceIndex(skus): filled once by the import thread, then only read;
  • newStockCache(skus): shared by the request threads;
  • newRecentTable(maxEntries): the table behind RecentLookups, a cache of the prices users looked up most recently, which drops the one used least recently when it is full.


When you're done, none of the three grows its table while a batch loads or while the cache evicts, and the stock cache's table is no longer than it needs to be. About three lines in total.

Problem statement


Each writer thread of the audit service collects records in a RecordBuffer and drains it to storage in batches of a few thousand. After an outage, a replay pushes hundreds of thousands of records through the same buffers. A week after the last outage, a heap dump shows every writer's buffer still holding an array of hundreds of thousands of slots, all of them empty. Decoding a frame, whose header gives its row count before the rows arrive one by one, also shows the buffer's array being copied while the rows go in.


Finish the two TODOs in src/main/java/practice/RecordBuffer.java:


  • prepareFor(incoming): called before a frame's rows are added;
  • drain(): hands back the records added since the last drain, in order, and leaves the buffer empty.


When you're done, a buffer drained after a replay keeps no more than NORMAL_BATCH slots, a normal batch neither reallocates the array nor grows it again, and a frame's rows go in without the array growing while they are added. About seven lines in total.


The tests read the buffer's array by reflection.
