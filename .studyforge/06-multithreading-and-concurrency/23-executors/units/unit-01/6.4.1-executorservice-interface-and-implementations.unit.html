The notification service sends its mail through Executors.newFixedThreadPool(8). During an incident the SMTP relay stops answering, and an hour later the service dies with OutOfMemoryError. The heap dump is dominated by one LinkedBlockingQueue. The first fix raised the pool to 8 core threads and 64 at most, and the next incident went the same way.

An ExecutorService takes tasks and runs them on threads it manages. Behind most factories in Executors is one class, ThreadPoolExecutor, and its rules for when to queue a task, when to start a thread and when to refuse decide what happens under load.

A Pool Queues Before It Grows: Threads Past the Core Start Only When the Queue Is Full

A ThreadPoolExecutor has a core size, a maximum size and a work queue. Here the core is 2, the maximum 4, and the queue holds 2. Each task holds its thread until release opens:

Pause before the output: when does the third thread start?

Not at task 3. Below the core size, every task gets a new thread. At the core size, a task goes into the queue. Only when the queue refuses it does the pool start a thread past the core, up to the maximum, and when that is reached too, the task is rejected. That order is why the first fix did nothing. Raising the maximum helps only if the queue can fill, and a LinkedBlockingQueue built without a capacity holds Integer.MAX_VALUE tasks:

With 10,000 tasks the pool stayed at 8 threads. newFixedThreadPool is built the same way, so when the relay stops answering, every new mail waits in memory. Here mailer is newFixedThreadPool(8), relayDown a latch that never opens, and the heap 256 MB (-Xmx256m):

The queue adds to every task's latency, too: a mail that waits behind 100,000 others is late even when it doesn't fail. The factories in Executors choose the queue's capacity for you (see the Reference).

A Full Pool Has to Refuse Work: Bound the Queue and Choose Who Pays

With a bounded queue, some task finds no room, and the pool's RejectedExecutionHandler decides what happens to it. Here a pool of one thread and a queue of 2 gets five tasks under each built-in policy; ran and refused record the outcome:

  • `AbortPolicy`, the default, throws RejectedExecutionException to the code that submitted. That code has to handle it: answer 503, or leave the message in its broker for a later retry. Uncaught, it fails whichever request arrived at the wrong moment.
  • `CallerRunsPolicy` runs the task on the submitting thread. While main ran tasks 4 and 5, it submitted nothing, so the producer slows to the pool's pace and, while the pool runs, nothing is lost. The cost falls on whatever else that thread does: if it accepts connections or reads from a broker, it stops doing that while it runs the task.
  • `DiscardPolicy` drops the new task, and `DiscardOldestPolicy` drops the oldest waiting one (here tasks 2 and 3) to make room. Neither tells anybody. Use them only for work nobody needs to know was lost, such as a periodic sample the next one replaces.

Under load, a pool with an unbounded queue never reaches its policy. That is why a production pool is usually built with new ThreadPoolExecutor(...): you choose a capacity and a policy, and a ThreadFactory that names the threads (unit Creating threads (Runnable interface and Thread class)).

execute() Hands a Task's Exception to the Thread; submit() Keeps It in the Future

execute(Runnable) comes from Executor, the one-method interface that ExecutorService extends. ThreadPoolExecutor's submit wraps the task in a FutureTask and returns it as a Future (unit Callable and Future for returning results). Both tasks here throw, on a pool with one thread:

The task run with execute() threw out of the worker's run(), so the exception ended that thread like any uncaught exception (unit Starting threads (start() method)): the default handler printed it, and the pool started pool-1-thread-2 to replace the worker. The submitted task threw inside FutureTask.run(), which caught the exception and stored it in the Future. Nothing was printed. Only get() shows that failure, wrapped in ExecutionException.

So submit() isn't the safer of the two. Code that submits and drops the Future, a common way to "run it in the background", loses every failure without a log line: the nightly settlement reports success, and three accounts were never settled.

afterExecute(task, thrown), which ThreadPoolExecutor calls on the worker after every task, misses it too (the stack trace on stderr is left out):

For the submitted task thrown is null, and task is the FutureTask, already done. A hook that reports every failure has to ask that Future for its outcome, and get() doesn't wait there; the afterExecute javadoc shows how, cancelled tasks included. Without such a hook, either the submitter keeps and reads the Future, or the task catches and reports its own failure.

shutdown() Stops Intake, Not Work: Wait for It With awaitTermination()

A fixed pool's threads, made by the default factory, are not daemons (unit Creating threads (Runnable interface and Thread class)), so a pool nobody shuts down keeps the JVM running. shutdown() is the first step. Here one task holds the pool's only thread and three wait:

shutdown() returned at once. It refused the new task and kept the four it had: the queued ones still ran. awaitTermination is what waits, and it returns false if its time runs out first.

A shutdown hook that calls pool.shutdown() and then closes the database connections breaks the queued tasks: they run after shutdown() returns, against closed connections. Close what the tasks use only after awaitTermination returns true. When it returns false, shutdownNow() interrupts the running tasks and hands back the queued ones (unit Stopping threads (interrupt() method and cooperative cancellation)), and a second awaitTermination gives the interrupted tasks time to end. The ExecutorService javadoc gives this two-step stop as its example.

Since Java 19 an ExecutorService is AutoCloseable, and close() is shutdown() plus waiting, with no time limit. A task that never ends holds it there:

Only an interrupt of the closing thread made close() call shutdownNow(). Try-with-resources fits a scope whose tasks are known to end, such as one batch of requests. A long-lived pool that must stop within a deploy's grace period gets the two-step stop with a timeout.

A Pool's Size Is Also a Limit on Concurrency, and Some Executors Have None

A thousand tasks each make one 20 ms database query, on three executors. inside counts the queries in flight and most keeps its peak; "threads made" is getLargestPoolSize(), the most threads alive at once:

The fixed pool kept the database at 10 queries, though nobody wrote 10 down as a limit for the database. newCachedThreadPool has no limit: it starts a platform thread whenever no idle one is waiting, and 549 were alive at once here (the count varies from run to run). newVirtualThreadPerTaskExecutor() starts a virtual thread per task, and all 1,000 queries ran together.

That is what virtual threads are for (unit Creating threads (Runnable interface and Thread class)): a virtual thread that waits gives its carrier thread back, so waiting costs almost nothing, and the number of tasks needs no pool to cap it. Replacing a fixed pool of 10 with virtual threads also removes the limit of 10 that the database or a vendor's API relied on. The database gets 1,000 queries at once, or the vendor answers 429. Limit what the downstream can take where the call is made, with a Semaphore of 10 permits around the query (unit Semaphores), and leave the executor unbounded.

Java 21 pins. In Java 21 a virtual thread that blocks inside synchronized keeps its carrier thread, so a JDBC driver that waits under a monitor costs a platform thread after all. JDK 24 removed that limitation (JEP 491).

Summary

  • A pool queues before it grows. Threads past the core start only when the queue is full, so with an unbounded queue the maximum is never used and waiting work grows in memory.
  • A bounded pool has to refuse. AbortPolicy throws to the submitter, CallerRunsPolicy makes the submitter do the work, and the two discard policies lose tasks silently.
  • `execute()` hands a failure to the thread, `submit()` keeps it in the `Future`. A dropped Future loses the failure, and afterExecute gets thrown == null for it.
  • `shutdown()` stops intake, not work. Queued tasks still run; wait with awaitTermination, then fall back to shutdownNow(). close() waits without a limit.
  • A pool's size limits concurrency. The cached pool and the virtual-thread executor have no limit, so bound the downstream call itself.

Challenges

  1. An API gateway hands requests to a pool with a bounded queue. Which policy would you choose, and what does the client see with each? What changes if the submitting thread is a Netty event loop?
  2. A pool of 8 threads runs tasks of about 50 ms. How long can a new task wait behind a full queue of 1,000? Choose a capacity for a 2-second latency budget.
  3. Measure a deploy: how long do shutdown() and awaitTermination take for a pool of 8 with 200 queued tasks, and how many tasks does shutdownNow() hand back after a 5-second grace?

Design Note: Why a Pool Queues Before It Grows

ThreadPoolExecutor could start threads up to the maximum first and queue only after that. Its javadoc states the opposite order without giving a reason. The likely one is cost: a platform thread has a native stack and a place in the OS scheduler, so a pool that queues absorbs a short burst with the threads it already has, and starts more only when the queue is full.

The price is that the maximum depends on the queue in a way the constructor doesn't show. With an unbounded queue the maximum does nothing; with a SynchronousQueue, as in the cached pool, the core does little, because every task without an idle thread gets a new one.

Problem statement


The document service reads the text out of every uploaded scan, a few seconds of OCR each. On a normal day three workers keep up. At the end of the month the accountants upload in bursts, and last month the service ran out of memory with forty thousand scans waiting.


The team's decision: three workers normally, and at most six scans waiting for one. When six are already waiting, the service may take on extra workers for the burst, five at most in total. A scan that arrives when all five are busy and six are waiting must not be lost or refused: the upload thread that brought it reads it itself, which slows that uploader down until the burst passes.

Problem statement


The invoice service takes invoice runs from a message broker and hands them to a worker pool. On a deploy the orchestrator gives the old process a grace period, then kills it. Two things go wrong today: runs that would have finished in a few seconds are cut off, and the runs that were waiting in the pool are simply lost, so customers miss their invoices until someone notices.


Write stop(pool, grace, unit) in src/main/java/practice/Drain.java, called by the deploy's shutdown hook:


  • work the pool already has, running or waiting, gets the grace period to finish, and stop returns only when it has finished or the grace period is over;
  • what is still running after the grace period is asked to stop, and gets one more grace period to do so; the runs that never started are returned, so the hook can put them back on the broker;
  • if the orchestrator interrupts the hook while stop waits, stop the pool at once, return what never started, and leave the hook's thread able to see that it was interrupted.


About twelve lines in total. The tests call stop on a thread of their own and use a pool with one worker.
