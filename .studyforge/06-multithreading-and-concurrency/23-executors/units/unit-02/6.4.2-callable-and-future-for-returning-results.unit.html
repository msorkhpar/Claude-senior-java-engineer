A price-comparison page asks four suppliers for a quote. Each request is a Callable submitted to a pool of eight threads, and the page waits for each Future with get(2, SECONDS), showing the cached price when a supplier is late. On Tuesday one supplier's API stopped answering without closing its connections. Within minutes every page view showed nothing but cached prices, from healthy suppliers too, and all eight threads were waiting on the one supplier that had stopped.

A Future carries a task's result, its failure and its cancellation back to the caller. Five rules decide what comes back, one per section.

The examples submit to pools from unit ExecutorService interface and implementations on Java 21, and most use this helper, a supplier that answers after a delay:

A Callable's Result and Its Exception Both Come Back Through get()

Callable<V>.call() returns a V and may throw any Exception, checked ones included; Runnable.run() can do neither. Here fetchQuote throws IOException because the supplier's API is down:

The pool catches whatever call() throws and stores it in the Future. get() then throws ExecutionException with the original as its cause, whatever its type, an Error included. The wrapper exists because get() must declare what it throws and can't know your task's checked exceptions. A catch (IOException e) around get() doesn't even compile; the handling has to look at getCause().

The second quote failed the same way and printed nothing: submit reports a failure only to whoever calls get(). (With execute, the failure reaches the thread's uncaught-exception handler instead, as unit ExecutorService interface and implementations shows.) isDone() is true whether the task succeeded, failed or was cancelled; state() (Java 19) tells them apart. A job that submits work and never reads the futures loses every failure this way.

get() throws one more checked exception, InterruptedException. It means the waiting thread was interrupted, not that the task failed: the task keeps running, and the caller handles the interrupt as in unit Stopping threads (interrupt() method and cooperative cancellation).

A Timed get() Ends the Wait, Not the Task

An untimed get() waits as long as the task takes, so a supplier that never answers makes it wait forever. get(timeout, unit) throws TimeoutException instead. Here a pool of one thread asks a supplier that hangs for two seconds, waits 100 ms for it, and then asks the next supplier. After the timeout the caller does nothing, calls cancel(false), or calls cancel(true):

With no cancel, the task kept the pool's only thread, and the next quote queued behind it for two seconds.

cancel(false) returns true, and from then on the Future is cancelled: isCancelled() is true and get() throws CancellationException. But on a task that has already started, cancel(false) only gives up the result. It doesn't touch the thread, which runs the task to the end. cancel(true) also interrupts the thread, and a task that responds to interrupts stops (unit Stopping threads (interrupt() method and cooperative cancellation)). Thread.sleep does, so the next quote was answered 10 ms after the timeout.

In the opening outage, each page view that timed out on the stuck supplier left a thread waiting on it. After eight such views the pool had no thread left, and quotes from healthy suppliers timed out in the queue. A fallback after a timeout needs the cancel(true) too.

Futures Read in Submission Order Wait for the Slowest; a CompletionService Hands Them Back as They Finish

Three suppliers answer in 300, 100 and 200 ms, on a pool of three threads. We read their futures in a loop, then submit them again through an ExecutorCompletionService around the same pool:

The tasks ran in parallel both times. The loop's first get() waited for the slowest supplier, and the quotes that were ready at 100 and 200 ms sat in their futures until then. A CompletionService puts each future on a queue when its task completes, so take() returns the next one to finish. The get() after it returns at once, or throws ExecutionException with the task's exception as its cause.

The batch still takes 300 ms, but a page that shows each quote as it arrives shows the first at 100 ms instead of 300, and a caller that needs any two quotes can stop after two.

invokeAll's Deadline Cancels the Stragglers, and Their get() Throws an Unchecked CancellationException

invokeAll(tasks) submits every task, waits until all are done and returns their futures in the order of the tasks. invokeAll(tasks, timeout, unit) waits at most that long for the whole batch, then cancels every task not yet done; the JDK's pools do it with an interrupt. Here three suppliers share 300 ms: one answers in 50 ms, one fails, one takes five seconds. The loop handles a failed quote:

The late supplier is still in the list, in its place, with a cancelled future. Its get() throws CancellationException, which is unchecked. The compiler made the loop handle ExecutionException and said nothing about this one, so the first late supplier ended the loop. In production that exception leaves the request handler, and the page loses the quotes it already had. Code that reads a future that can be cancelled catches CancellationException too.

Calling get(remaining, unit) on each future in turn waits just as long, but leaves the late task running unless you cancel it yourself; the timed invokeAll cancels it for you.

invokeAny Returns the First Success, Not the First to Finish

A hedged read sends the same query to three replicas and keeps the first answer. Replica 1 fails after 20 ms, replica 2 answers after 100 ms, replica 3 would take two seconds. invokeAny gets all three; a CompletionService written by hand keeps the first future to finish (replica 3 can't change its answer, so it is left out). A last call gives invokeAny two replicas that both fail:

invokeAny returns a value, not a future. It skipped the failure that finished first, returned the first successful result, and cancelled replica 3 as soon as it had one, here with an interrupt. The hand-written version returned replica 1's failure while a correct answer was 80 ms away. invokeAny throws ExecutionException only when every task fails, with one of their exceptions as the cause; which one is not specified, and in other runs it was replica 2's.

Summary

  • A task's result and its exception both come back through `get()`. The exception arrives wrapped in ExecutionException; a future nobody reads fails silently.
  • A timed `get()` ends the wait, not the task. After a timeout, cancel(true) frees the thread if the task responds to interrupts; cancel(false) only gives up the result.
  • Reading futures in submission order waits for the slowest. A CompletionService returns each one as it finishes.
  • `invokeAll` with a timeout cancels the late tasks and keeps their places. Their get() throws the unchecked CancellationException, which a loop must catch.
  • `invokeAny` returns the first success and cancels the rest. It fails only when every task fails.

Challenges

  1. The comparison page shows the cheapest of five quotes and must answer within 400 ms. Would you use a timed invokeAll or a CompletionService with a deadline? What does each show when two suppliers are late?
  2. A supplier's client blocks in a socket read that ignores interrupts (unit Stopping threads (interrupt() method and cooperative cancellation)), so cancel(true) after a timeout doesn't free the thread. How do you keep that supplier from filling the pool?
  3. A hedged read with invokeAny doubles the load on the replicas. When is that worth it, and how would you send the second request only when the first is slow?

Design Note: A Future Is Something You Wait On

Future (Java 5) is a pull model: the caller asks for the result and blocks until it is there. Everything above follows from that. The caller decides how long to wait, in what order to read and whether to read at all, and a result nobody pulls is lost, failure included.

CompletableFuture (Java 8) adds the push side: thenApply or exceptionally attach what happens next, and it runs when the result arrives, with no thread blocked in get(). Failures then travel through a chain of callbacks instead of up a stack, and a chain whose end nobody handles loses its failure the same way. With virtual threads (Java 21), a blocked get() parks a virtual thread rather than holding an operating-system thread, which makes the plain pull model affordable for many request handlers.
