The nightly risk report sums exposures over 8 million positions, and one thread takes too long. A colleague parallelised it: each range of rows submits its two halves to an Executors.newFixedThreadPool(8) and waits on their Futures. On the 50,000-row test file it worked. The first full night it never finished, and a thread dump showed all eight pool threads in FutureTask.get.

Splitting a job into halves, then halves of halves, is divide and conquer, and Java has a pool built for it: ForkJoinPool, with the task types RecursiveTask<V> and RecursiveAction.

A Task That Waits for Its Subtasks Deadlocks an Ordinary Pool; ForkJoinPool's join() Keeps Working

Here is the colleague's version. A range of 10,000 rows or fewer is summed in a loop; a larger one is split:

Before reading on: why does 50,000 rows work and 8,000,000 not?

Each range that splits holds a thread while it waits for its halves. 50,000 rows split three levels deep: 7 ranges wait, and the eighth thread runs the 8 small ranges one after another. 8,000,000 rows make 1,023 waiting ranges. The first eight take all eight threads, and the halves they wait for sit in the queue with no thread to run them. A bigger pool only moves the size at which it hangs: 64 threads sum 500,000 rows and still hang on 8,000,000. Any other job sharing the pool queues behind it for good.

The same split as a fork/join task:

Both versions run on 8 threads, with a 5-second limit on the fixed pool (ex/Deadlock.java, Java 21, 20 cores):

In a ForkJoinPool a waiting thread keeps working. Each worker keeps its own queue of tasks, and fork() puts a task on the current worker's queue and returns at once. join() on a task that isn't done runs that task itself if it is still queued, or helps run the work of the worker that took it. Only when neither is possible does the worker park, and the pool may then start a spare thread to keep its parallelism. A worker with an empty queue takes a task from the other end of another worker's queue. That is work-stealing, and it is how the left halves reach the other seven workers. Unit Parallelizing tasks with ForkJoinPool covers the pool itself.

Blocking still hurts. The javadoc says the pool keeps enough threads active while tasks wait to join others, and doesn't promise it when they block on I/O or locks. A blocked worker runs nothing else, as the last section shows.

    Check yourself: fork/join

    • In a ForkJoinPool, fork() queues a task on the current worker's queue, join() runs the awaited task or helps the worker that took it before it parks, and idle workers steal tasks from other workers' queues.
    • A task that submits its subtasks to a fixed pool and waits for them holds a thread while it waits, so a deep enough split leaves every thread waiting and the job never finishes; a bigger pool only moves the size at which it hangs.

Fork One Half, Compute the Other, Then Join

SumTask forks the left half, computes the right half, then joins the left. That order lets two workers run at once: while this thread works on the right half, the left half waits on its queue for another worker to steal.

Swap two lines, so the task joins the left half before it starts the right one:

Over 8 million rows with about 27 ns of arithmetic each, on ForkJoinPool(8) (ex/Shape.java, best of five runs):

Same tasks, same result, and the swapped order runs at the speed of one thread. Each task waits for its left half to finish before its right half starts, so at every level only one half is in progress. Because the answer is right, no test catches it; only a timing does.

compute() decides the task's type. A RecursiveTask<V> returns a value, and join() hands it back (unit Implementing RecursiveTask for results-bearing tasks). A RecursiveAction returns nothing and works in place, such as scaling every element of an array; it often runs both halves with invokeAll(left, right), which returns when both are done or one throws (unit Implementing RecursiveAction for resultless tasks). Both extend ForkJoinTask, which implements Future.

The Threshold Decides Whether Splitting Pays

Each task costs an object, a push on a queue, and often a steal. The threshold, the size at which a task stops splitting and runs a plain loop, decides how many tasks there are. The same run with other thresholds:

With a task per row the parallel version takes twice as long as the plain loop: 16 million tasks cost more than the arithmetic they wrap. With one task there is nothing to share. Between those the times are flat over four orders of magnitude. The threshold has to be large enough that a leaf's work outweighs the cost of a task, and small enough to give every worker several pieces. The ForkJoinTask javadoc puts a leaf at roughly 100 to 10,000 basic steps.

The middle is flat only because every row costs the same. When some rows cost a hundred times more than others, 8 leaves for 8 workers leave seven idle while one finishes. Unit Splitting and joining tasks for optimal performance covers choosing the threshold for uneven work.

    • The threshold decides how many tasks there are: a task per element costs more than the work it wraps, one task gives no parallelism, and a wide range in between performs alike when work is even.

The Common Pool Is Shared, So Blocking in It Delays Work You Didn't Write


ForkJoinPool.commonPool() is one pool per JVM, with availableProcessors() - 1 workers by default (19 on the 20-core machine here). Parallel streams run in it, and so do CompletableFuture.supplyAsync and the other ...Async methods called without an executor, and any ForkJoinTask forked outside a pool.


A nightly price export runs a parallel stream over 200 SKUs, and each element calls a rate service that answers in 300 ms. While it runs, another part of the service calls CompletableFuture.supplyAsync(() -> "quote") (ex/CommonPool.java):




The quote waited 800 ms behind someone else's network calls. The workers were asleep in the lookups, and the pool can't tell. The stream also ran lookups on Thread-0, the thread that started it.


A stream started from inside a task of another ForkJoinPool splits into that pool instead, because fork() queues to the pool the current task runs in. That is how the JDK's streams behave today, though the stream javadoc doesn't promise it:




Work that mostly waits fits better on virtual threads (unit Lightweight threads for high concurrency), and ForkJoinPool.ManagedBlocker lets a fork/join task block without losing a worker (unit Parallelizing tasks with ForkJoinPool). Since Java 19 a ForkJoinPool is AutoCloseable: close() shuts it down and waits for its tasks, and does nothing on the common pool.


Small machines differ. When the common pool's parallelism is below 2, CompletableFuture's async methods start a new thread per task instead (its javadoc). A container limited to two CPUs or fewer gets that behaviour.

Summary


  • A task that waits for its subtasks deadlocks an ordinary pool. A ForkJoinPool worker runs queued tasks while it waits in join(), and idle workers steal from busy ones.
  • Fork one half, compute the other, then join. Joining before computing runs at one thread's speed and still gives the right answer.
  • The threshold decides whether splitting pays. A task per element costs more than the work; one task gives no parallelism.
  • The common pool is shared by parallel streams, async CompletableFutures and tasks forked outside a pool. Blocking calls there delay all of them; give such work its own pool or executor.

Design Note: Why the Waiting Thread Does the Work


An ordinary pool runs each task from start to end on one thread, so a task that waits for another holds a thread until the other finishes. Fork/join tasks are written to wait for each other, so join() turns the waiting thread back into a worker. The price is in what a task may do. A worker runs whatever task it finds, and the pool counts only the waits it sees: joins and ManagedBlocker calls. A task that blocks on I/O or holds a lock takes its worker out of the pool unnoticed, which is why the ForkJoinTask javadoc says tasks should ideally avoid synchronized blocks and blocking I/O. The framework gives up generality for throughput on one kind of problem: CPU work that splits into independent pieces.
