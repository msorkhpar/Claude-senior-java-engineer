A Task Returns Its Part of the Answer; Tasks That Write into Shared State Lose It

The revenue report sums 4 million orders per region. Its first version has every leaf add into one map that all tasks share. Since it returns nothing, it is a RecursiveAction:

The second has each task return a map of its own, and the parent merges the two it gets back:

Before reading on: the leaves never touch the same order. What does the shared map add up to?

Three runs of each on ForkJoinPool(8) (ex/Shared.java, Java 21):

The leaves read different orders but write the same four entries. When two workers merge into one region at once, both read the old total and one sum overwrites the other: more than half the revenue is gone, a different amount each run. In run 2 a HashMap noticed another thread changing it mid-merge and threw. The second version shares nothing that changes. A leaf's map belongs to one thread until it returns, and join() hands it to the parent, so the merge needs no lock. join() returns only once that task's compute() has returned, which here is after it has joined its own halves.

Making the shared state thread-safe fixes the arithmetic but not the ownership. A ConcurrentHashMap or an AtomicLong held by the report object adds correctly, and then every report run on that object adds into the same field: the second run starts from the first one's total, and two runs at once mix their sums. A value returned from compute() belongs to one invocation.

The Parent Can Only Combine What Its Halves Return


The customer report counts the distinct customers among 2 million orders; there are 150,000 of them. Each leaf collects its customers in a HashSet. The first version returns the set's size, and the parent adds the two counts. The second returns the set itself, and the parent merges the two sets (ex/Distinct.java):




Every leaf's count is right, and their sum is wrong. A customer who ordered in both halves is counted once by each half, and the parent, holding two numbers, can't tell. With one task the answer is right, so a test on a small file passes.


The value a task returns must hold enough to combine with its sibling's, so that any split gives the answer one task would. Adding works for sums and row counts, and max works for maxima. A distinct count needs the sets. An average needs the sum and the count, not two averages. A median needs the values themselves: no weighting of two medians gives the median of both halves. The most frequent value needs every value's count, since the overall winner can come second in both halves. Choose that type first, then write compute().

A Subtask's Exception Reaches join() as a Copy, and Its Siblings Keep Running


The ledger import parses a million amounts, and row 600,123 says 12O0, with a letter O. Long.parseLong throws in some worker, and the caller catches the exception around pool.invoke(...). The program then follows the cause chain to its end, and counts the rows parsed after the failure happened (ex/Failure.java, second of three runs):



The class is right: as unit Parallelizing tasks with ForkJoinPool showed, join() and invoke() rethrow the task's own type. The object is not the one thrown. When the joining thread isn't the thread that failed, ForkJoinTask builds a new exception of the same class, so that the stack trace shows both threads, and keeps the original as its cause. It uses a public constructor taking a Throwable if the class has one, and otherwise the no-argument constructor. NumberFormatException has no Throwable constructor, so the copy has no message, and the log said null. A class that has one, such as IllegalStateException or the ConcurrentModificationException in the first section, gets the original's toString() as its message. Each thread the failure crossed added a copy: three here, four in another run. To report the failure, follow getCause() while it is the same class.


Nothing cancels a task's siblings, and the pool doesn't run a failed task again: it stays failed, and its exception goes to whoever joins it. The parent whose compute() threw never joined its forked half, which was still queued, so a worker ran it. cancel(true) wouldn't stop a running task either: in a RecursiveTask the argument has no effect, and no task is interrupted. When one failure makes the rest worthless, make the tasks check, for example a shared AtomicBoolean that a failing leaf sets and every compute() reads first (failed is null in the first run):




The rows still parsed belong to leaves that had started before the flag was set.

Splitting Shares the Work Among Workers; It Can't Remove Work the Recursion Repeats


Fibonacci is the textbook RecursiveTask: fib(n) forks fib(n - 1), computes fib(n - 2), and adds them. Below the cutoff a task calls the plain recursive method instead. fib(40) on ForkJoinPool(8), against one thread (ex/Fib.java, third of three runs):



With a task per call there are 331 million tasks, and the job is three times slower than one thread. With a cutoff it is about five times faster: eight workers sharing the same 331 million calls. The loop does 40 additions, each needing the two results before it, so it can't be split, and it doesn't need to be. The recursion computes fib(20) 10,946 times, because the two halves of a split overlap, and the workers can only share that waste. Before parallelising a recursion, check that its subproblems are independent.

    Concept check
    

    Check yourself: results of a RecursiveTask
    

      

    • cancel(true) on a RecursiveTask has the same effect as cancel(false): it marks a task that isn't done as cancelled and interrupts nothing, so a running task runs to its end.
      • 

    • Splitting shares work among workers but can't remove work a recursion repeats: recursive Fibonacci as tasks is at best the number of workers faster than one thread, and a task per call is slower than one thread, while a loop does a few additions.

  • A task returns its part of the answer. Leaves that write into a shared map lose updates, and a field made thread-safe still mixes the totals of two runs.
  • The parent can only combine what its halves return. Return what the combine needs (sets for a distinct count, sum and count for an average), or the answer changes with the threshold.
  • A subtask's exception reaches join() as a copy of the same class with the original as its cause, and the other subtasks keep running unless they check a flag.
  • Splitting shares work; it can't remove work the recursion repeats. Fork/join speeds up recursive Fibonacci by the number of workers at best, and a loop is far faster still.

  2. The ledger import should report every bad row, not only the first. Design the result type, and say what it costs in memory when half the file is bad.

Design Note: Why the Result Travels Through join()


A fork/join task is written so that two halves run with nothing in common: each gets its own range, builds its own value and hands it to one parent through join(), once per task. The price is allocation and a combine at every level. A tree of 2,000 tasks builds 2,000 partial maps or sets and merges each into another, and every merge of two sets walks one of them. When the combine gets that expensive, a concurrent structure that all leaves write to may be cheaper, as long as it belongs to one invocation and not to the object that runs it.
