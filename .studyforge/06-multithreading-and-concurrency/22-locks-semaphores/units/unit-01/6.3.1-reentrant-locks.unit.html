At 02:10 the stock service stops answering. The thread dump shows forty request threads WAITING for the same ReentrantLock, and the lock's toString() names its owner: [Locked by thread pool-1-thread-1]. That thread sits idle in its pool, in LinkedBlockingQueue.take(), and the log says nothing about it.

With synchronized (unit Monitors and synchronized blocks) this can't happen. ReentrantLock, from java.util.concurrent.locks, guards a critical section with the same memory visibility and adds a wait you can give up on, several conditions (wait sets) per lock, an optional fair queue, and methods that report who holds it. You write the locking and unlocking yourself, as method calls. Every output on this page comes from Java 21.

Nothing Releases a ReentrantLock but unlock(), So Unlock in finally

The stock service reserves like this:

A task on a one-thread pool asks for 5 mugs when 3 are left; the exception goes into a Future that nobody reads. Then we print the lock and the pool's thread, and another thread calls reserve for one mug. We repeat this with the body in a synchronized block, and last, a thread named nightly-import takes a lock and ends:

The lock stayed with the pool thread after its task ended, and every later reserve waits for an unlock() that will never run. Even the terminated nightly-import still owns its lock.

synchronized releases the monitor on every way out of the block, because the compiler writes the release. A ReentrantLock is an ordinary object that records an owner thread and a count, and nothing calls unlock() for you: not when an exception passes, not when the task ends, not when the thread dies. So the release goes in a finally:

lock() goes before the try, so that the finally runs only once the lock is held.

The Lock Counts Holds: One unlock() per lock(), by the Thread That Holds It

A price import locks once for the whole batch and calls apply for each line, which locks the same lock again:

The thread that holds the lock gets it again at once, and the lock counts how many times: that is what reentrant means. Without it, applyAll would wait forever for a lock it holds itself. The lock is free when the count is back to zero. synchronized is reentrant in the same way.

Spot the Problem: One Path Locks Twice

After each call, the caller's hold count and whether another thread can take the lock within a second:

The discounted path locks twice and unlocks once, so its thread keeps one hold for good and every other thread waits. A test that makes all its calls from one thread passes, because the owner can always relock. Pair each lock() with its own unlock() in a finally of the same method.

Only the thread that holds the lock can release it:

So a lock can't be taken on a request thread and released by a callback on another thread. A permit that one thread takes and another gives back is a semaphore (unit Semaphores).

lock() Waits Until It Gets the Lock; tryLock and lockInterruptibly Can Give Up

A thread called price-refresh holds the lock while it waits for a slow upstream service. Three threads ask for the lock in three ways, and each is interrupted while it waits:

Then the main thread tries without waiting, and with a budget of 200 ms:

("gone" means the thread has ended.) lock() waits as long as it takes, like entering synchronized; an interrupt only sets the flag (unit Stopping threads (interrupt() method and cooperative cancellation)), so a deploy that calls shutdownNow() can't move a thread out of it. lockInterruptibly() answers an interrupt with InterruptedException, without taking the lock. tryLock(time, unit) does the same, and also returns false when its time is up. tryLock() doesn't wait at all.

A request with a two-second budget uses a timed tryLock and answers "busy" when it doesn't get the lock. A worker that a shutdown must be able to stop uses lockInterruptibly(). lock() fits waits that are always short.

    Keep one bad partner file from stopping the points ledger

    • lockInterruptibly() and tryLock go before the try, so that a failed attempt never runs unlock(): inside it, IllegalMonitorStateException replaces InterruptedException, or an outer hold is silently lost.

A Condition Gives Up the Lock While It Waits, So Check Again After await()


A Condition is a wait set that belongs to a lock, like wait() and notify() on a monitor (unit Monitors and synchronized blocks), and one lock can have several. A print queue keeps one for printers waiting for a job and one for clerks waiting for room:



await() must be called with the lock held. It releases all of the thread's holds, not just one, parks the thread, and takes them all back before it returns. Here thread A awaits from a nested call while another thread tries to take the lock:



signal() wakes one thread waiting on that condition, signalAll() all of them. All three throw IllegalMonitorStateException in a thread that doesn't hold the lock.


Spot the Problem: if Around await()


A printer takes the next job like this:



printer-2 waits on an empty queue. A clerk puts invoice-118.pdf and signals. Before printer-2 has the lock back, printer-1 arrives and takes the job. The program forces that order, with if and then with while:



A signal says the state changed, not that it is what you wanted. Before the woken thread holds the lock again, any thread can take the lock and change the state, whatever the lock's fairness policy. The javadoc of Condition also allows a thread to wake with no signal at all, a spurious wakeup. With while, the woken thread checks again and goes back to waiting. With if, it carries on with null, and a printer sends that to the device.



Signal the Condition Its Waiters Wait On


put signals notEmpty and takeIf signals notFull, so each change wakes the side that can use it. Signal the other one and the waiter isn't woken. Here a job is added and notFull is signalled while a printer waits on notEmpty:



With a single condition for both sides, signal() can wake a clerk when a printer was needed; the clerk finds the queue still full and waits again, and the signal is lost. Two clerks and two printers sharing one condition, a queue of capacity one, 2,000 items per thread, twenty runs each:



A single condition works only with signalAll(), which wakes every waiter so that one of them can go on.

A Non-Fair Lock Lets a Newcomer Go First; a Fair Lock Queues, and Costs Throughput


A sync job holds the lock while it syncs a row, unlocks, and locks again for the next row, while a report thread waits in lock(). Three runs with the default lock, then three with new ReentrantLock(true):



Waking the parked report thread takes time, and the default, non-fair lock doesn't hold the lock for it: a thread that asks in the meantime, here the sync job, takes it at once. This barging is why the default is fast: the lock goes to a running thread instead of staying idle. A fair lock hands it to the thread that has waited longest, so every handover costs a wake-up; the fair count is 1 because the sync job's first relock waited for the report thread. Four threads taking the same lock in a tight loop for one second:



Other runs (not shown) ranged from about seven to more than thirty times fewer. With non-fair, a waiter has no bound on how many newcomers go first; behind threads that hold the lock for seconds and keep coming back, it can wait for minutes.


Keep the default, and keep the time the lock is held short. Use a fair lock when the wait of the unluckiest thread is what you are measured on. Even then, the untimed tryLock() takes a free lock while others wait, where tryLock(0, TimeUnit.SECONDS) respects the queue. One thread queued on a fair lock that was just released, a hundred times:



In the other 17 runs, the queued thread got the lock before tryLock() was called.




    

  1. 

    Concept check
    

    Check yourself: reentrant locks
    

      

    • await() releases every hold of the waiting thread and restores them before it returns.
      • 

    • Only the thread that holds a ReentrantLock can unlock it; unlock() from another thread throws IllegalMonitorStateException.
      •

A Read-Write Lock Lets Readers Share, but a Reader Can't Upgrade


A product catalog is read thousands of times for every change. A ReentrantReadWriteLock holds two locks: any number of threads can hold its read lock together, and its write lock excludes all other readers and writers. Two threads read while a writer tries:



Spot the Problem: Loading on a Miss


The catalog loads a missing entry when a read misses it:




The write lock waits until every reader has left, including the thread asking for it, so it waits forever, and nothing detects it. Other writers can't get in, and in this implementation neither can new readers that call readLock().lock() or a timed tryLock: a reader that arrives while a writer waits at the head of the queue waits behind it, so that a stream of readers can't shut a writer out. Here one miss stops the whole catalog.


There is no upgrade from read to write. Release the read lock, take the write lock, and look again before loading, because another thread may have loaded the entry in the gap. The other direction works: a thread that holds the write lock can take the read lock and then release the write lock, a downgrade with no gap for a writer:



A read-write lock pays off when reads are long or many and writes are rare. It does more bookkeeping than a plain lock, so for short reads, measure first.

Summary


  • Nothing releases a ReentrantLock but unlock(). Lock before the try, unlock in the finally.
  • The lock counts holds per thread. One unlock() per lock(); only the owner can unlock.
  • lock() waits through interrupts. A timed tryLock, its result checked, gives a budget; lockInterruptibly() lets a shutdown stop the waiter.
  • A Condition gives up the lock while it waits. Wait in a while loop, and signal the condition the right side waits on.
  • A non-fair lock lets newcomers go first. That is its throughput; a fair lock serves waiters in order at several times the cost.
  • A read-write lock lets readers share, but doesn't upgrade. Release the read lock before taking the write lock.

Design Note: Why Java Kept synchronized


Java 5 added ReentrantLock beside synchronized, because a block of the language can't offer a lock wait with a timeout, a lock wait that answers an interrupt, an unlock in a different method from the lock, several conditions per lock, or a choice of fairness. Each of those is a method call, and a forgotten call is a bug the compiler doesn't see; synchronized can't leak a monitor, unlock twice or be released by the wrong thread.


For a short critical section with none of those needs, synchronized is the safer choice and reads better. When you need one of them, use ReentrantLock, and write the release yourself in every method that locks.
