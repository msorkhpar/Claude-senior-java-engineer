synchronized Locks an Object, and Excludes Only Code That Locks the Same One

Every Java object has a monitor: a lock that one thread at a time can own. synchronized (x) { ... } takes x's monitor before the block runs, waiting while another thread owns it, and gives it back when the block ends. A synchronized instance method does the same with this, and a static synchronized method with the class's Class object. The keyword sits on the code, but the lock belongs to an object.

Each of 8 threads increments an order counter, static int ordersToday, 100,000 times. Which of these four versions reach 800,000?

ordersToday++ is three steps: read the field, add one, write it back. Two threads that read the same value both write the same result, and one order is gone.

The two middle versions lock and still lose increments. new Object() gives every increment a lock no other thread will ask for. The handler's synchronized method locks the handler, and every increment has a new one, while the static field is shared by every handler. Only the last version has all eight threads asking for the same object.

Choose the lock by the state it protects: one lock object per piece of shared state, and every access to that state goes through it, reads included. Releasing a monitor also makes everything the thread wrote before the release visible to the next thread that takes the same monitor; a read that skips the lock has no such guarantee (unit Volatile keyword).

A metrics exporter, someone else's code, receives the cache and exports it every minute:

A synchronized method locks this, and any code that holds a reference to the object can lock it too. The cache's latency now depends on code its author never sees, and if that code takes a second lock, on a lock order nobody planned. Only the class itself can take a lock that is a private field.

Lock a private final object, unless you mean outside code to share your lock, and then document it. Never lock an object other code can reach by accident: a string literal is interned, one object JVM-wide, so two unrelated classes that lock "lock" stall each other.

Each Synchronized Method Is Atomic; a Check Followed by an Act Is Not

Five runs, 500 units each:

Each call was atomic, but between available() returning and take(1) starting the buyer holds no lock. Several buyers saw the last unit as available, and each took it. Check and act in one hold of the lock, inside the class:

tryTake calls available() and take(), which lock the monitor the thread already owns. That works because a monitor is reentrant: it records its owner and a count, entering again adds one, leaving takes one off, and other threads can enter only when the count is back at zero. Without reentrancy, tryTake would wait for itself forever.

A service with 200 request threads can sell up to 199 units it doesn't have. A class shared between threads should offer the combined operation (tryTake, or putIfAbsent and compute on a ConcurrentHashMap) rather than leave callers to compose one from atomic parts.

The Monitor Is Released However the Block Exits, Half-Done Changes Included

A ledger moves money from checking to savings, and refuses amounts over a daily limit:

One thread calls moveToSavings(300, 200). When it has ended, another thread asks for the total:

The second thread got the lock, so the monitor was released when the exception left the method. That is guaranteed: a synchronized block is compiled with a handler that releases the monitor and rethrows, and the JVM releases a synchronized method's monitor however the method completes.

The release undoes nothing. The 300 left checking and never reached savings, and the next thread saw a ledger 300 short, with no error anywhere but the mover's exception.

Inside a synchronized block, make every check that can throw before the first write, here the limit check before checking -= amount. Where a write must come first, undo it in a catch before rethrowing.

Two Locks Taken in Opposite Orders Deadlock; One Order for Every Pair Prevents It

A transfer locks both accounts, so that no other thread sees the money in neither of them:

One thread moves 1 from a to b 100,000 times, another moves 1 from b to a 100,000 times. How many transfers complete?

Within the first second, transfer-0 held a and asked for b while transfer-1 held b and asked for a. A deadlock needs four things at once: locks that one thread at a time can hold, a thread that holds one while it waits for another, no way to take a lock from its holder, and a cycle of threads each waiting for the next. A monitor supplies the first and the third by design: entering synchronized has no timeout, and an interrupt doesn't end the wait. Hold-and-wait comes from nesting two blocks and goes away only with one coarser lock. Where two locks are needed, remove the cycle by taking them in the same order in every thread:

Both threads now ask for a first, and the one that gets it can always get b, because nobody holds b while waiting for a. The key that sets the order has to be fixed for the life of the object and different for every object: an id, not a balance that changes between two transfers, and not hashCode(), which two different objects may share.

The order must hold for every piece of code that takes two of these locks, not only transfer: an audit that locks the two accounts it compares in its own order deadlocks with the transfers just the same. A deadlock also spreads: every thread that next needs a or b queues behind it in BLOCKED until only a restart helps. Take a thread dump (jcmd <pid> Thread.print) first.

Threads Can Also Stop Making Progress Without Blocking

In a livelock, the threads keep running and reacting to each other, and none gets anywhere. With random back-off, a walker steps forward after a conflict only on a coin toss:

In starvation, one thread keeps losing the lock to the others. Nothing promises which waiting thread gets a monitor next, so a monitor can't prevent it. new ReentrantLock(true) (unit Reentrant locks) hands the lock to the longest waiter on lock().

wait() Belongs in a Loop Over Its Condition, and a Change Is Announced With notifyAll()

Unit Thread lifecycle and states showed that wait() releases the monitor while the thread waits, and that a notified thread is BLOCKED until it gets the monitor back. What does it find when it does? Two packers wait for orders, and one order arrives:

notifyAll() woke both packers, and each had to take the monitor back before returning from wait(). packer-1 got it first and took the order. packer-2 got it next and returned into code that assumed the queue wasn't empty (each prints after leaving the monitor, so the lines can come in either order). A return from wait() doesn't mean the condition is true, only that somebody notified, or the timeout ran out, or nothing happened at all: the javadoc of Object.wait warns of spurious wakeups and says to wait in a loop. With while (queue.isEmpty()) wait(); the second packer checks again and goes back to waiting:

The opposite mistake is to wake too few threads. Packers now wait for orders of their own region, next("EU") and next("US"), each in a loop over "is there an order for my region?". The EU packer starts waiting first, then the US packer, and a US order arrives, announced with notify() in one run and notifyAll() in the other:

notify() wakes one waiting thread, and its javadoc says the choice is arbitrary. Here it woke the EU packer, which found nothing for EU and waited again. The notification was spent, and the US order sits in the queue until some other order happens to wake the right packer. With notifyAll() both woke, both checked, and the US packer took its order.

notify() is enough only when every waiter waits for the same condition and any one of them can handle the change. Otherwise, and whenever you aren't sure, use notifyAll(): the cost is a few threads that wake up, check, and wait again. A waiting thread answers an interrupt with InterruptedException (unit Stopping threads (interrupt() method and cooperative cancellation)), so the loop needs no exit of its own for shutdown.

Summary

  • `synchronized` locks an object, and excludes only code that locks the same one. Use one private final lock per piece of state; a monitor others can reach lets them stall yours.
  • Each synchronized method is atomic; a check followed by an act is not. Check and act in one hold; reentrancy makes it easy to write.
  • The monitor is released however the block exits, half-done changes included. Check before the first write.
  • Hold the lock for the state, not for the slow call. Reserve, call, then settle; call listeners after the lock is released.
  • Two locks taken in opposite orders deadlock. One fixed, unique order for every place that takes two of the locks removes the cycle.
  • `wait()` belongs in a loop, and changes are announced with `notifyAll()`. A woken thread re-checks its condition; notify() can wake a thread that can't use the change.

  2. Find every place in a codebase you know that takes two locks at once. What order do they use, and how would you make sure the next change keeps it (a helper that takes both, a review rule, one coarser lock)?
  3. Run the order counter with ORDERS_LOCK, an AtomicInteger and a LongAdder, with 8 and with 64 threads. When does the lock stop being the right tool?

Design Note: Why Every Object Is a Lock

Java 1.0 gave every object a monitor: a lock and a single wait queue built into the object, with synchronized to take the lock and wait/notify to use the queue. Protecting a class became one keyword, and the lock can't leak, because the block structure releases it on every path.

The costs come from the same choice: anyone can lock your object, one wait queue makes notifyAll() wake every condition's waiters, and entering has no timeout, so a deadlock on monitors is permanent. Java 5 added java.util.concurrent.locks for those cases (unit Reentrant locks): a lock with a timeout, several conditions per lock, and an optional fair order. The monitor remains the simplest correct choice for a short critical section that doesn't block.
