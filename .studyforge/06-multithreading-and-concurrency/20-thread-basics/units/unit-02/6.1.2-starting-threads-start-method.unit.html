The nightly settlement report computes four regional totals, each on its own thread. One morning it said APAC had settled nothing. The job had exited with code 0; the only trace was a stack trace in its stderr:

The code that started the threads waited for them inside a try that caught runtime exceptions, and never saw the failure. start() hands the work to another thread and returns; the result, the failure and the news that the thread has finished come back only if the caller collects them.

The examples use two helpers: total(region), a few milliseconds of arithmetic returning a total in cents, and fetchTotal(region), which waits 200 ms like a call to a region's ledger service. Every output comes from Java 21.

start() Doesn't Wait for the New Thread to Do Anything

Four region threads are started and the totals printed on the next line:

start() makes the thread runnable and returns without waiting for run() to begin: the scheduler decides when the new thread gets a CPU. Reading the array before the joins is a race.

Nor does the new thread reliably get going first. This program counts the runs in which the worker appended w before the caller appended m:

Pinned to one core (taskset -c 0), the worker went first in about one run in seven. Nothing orders the two threads after start(); the order you measure belongs to the machine you measured on.

Virtual threads are daemon threads, and the JVM exits once only daemon threads are left (unit Creating threads (Runnable interface and Thread class)). Returning from main cancels nothing, but if no non-daemon thread is left, the JVM's exit ends the virtual thread wherever it is. The report is never written:

Results Come Back at join(): Start Every Worker, Then Join Every One

t.join() blocks the caller until t has terminated. Where the joins go decides whether the threads save any time. Four ledger calls of 200 ms, joined two ways:

The first loop runs the threads one after another, as slowly as no threads at all. The second has all four calls waiting at once and takes as long as the slowest. Joining in start order is fine: if the first thread is the slowest, the later joins return at once.

The plain Long[] was safe to print after the joins, with no volatile or lock, because threads see each other's writes in an agreed order only where a happens-before rule says so, and the memory-consistency rules of java.util.concurrent give two for threads:

  • "A call to start on a thread happens-before any action in the started thread": what the caller wrote before start() is there when run() begins.
  • "All actions in a thread happen-before any other thread successfully returns from a join on that thread": what the thread wrote is there when join() returns.

While both threads run, a plain field written by one and read by the other has no guarantee.

Spot the Problem: A Done Flag Instead of join()

Instead of joining, a reader waits for a flag the worker sets when done:

The main thread joined the worker and sees done = true. The reader never does; it spins at 100 % of a core. No rule connects the worker's write of done to the reader's reads, so the JIT compiler may read the field once and loop on that value forever, as it did here.

Wait for a thread's work with join(); a signal while it keeps running needs a volatile field (unit Volatile keyword) or a CountDownLatch. isAlive() is a hand-over too: by JLS 17.4.4, a thread that sees it return false also sees everything the finished thread wrote.

join(millis) Returns Without Saying Why, So Ask isAlive()


A plain join() on a ledger call that hangs waits forever; join(millis) bounds the wait:




join(300) returned the way it returns when the thread ends: no exception, no value. Ask isAlive() afterwards, or code reads APAC's empty slot and reports it as a total. Since Java 19, join(Duration) returns true only if the thread has terminated. Either way the thread is still working; only your wait stopped (unit Stopping threads (interrupt() method and cooperative cancellation) shows how to stop it).


join(0) waits forever. The javadoc: "A timeout of 0 means to wait forever." It bites code computing the time left on a deadline: 0.6 ms left rounds down to 0, and slow runs 400 ms:




On a hung thread, a shutdown waits forever exactly when its budget has run out. Once the deadline has passed, the negative remaining time makes join(millis) throw IllegalArgumentException. join(Duration) has neither edge: zero or a negative duration only checks whether the thread has terminated.


A thread that was never started looks finished. join(millis) "returns immediately, without waiting, if the thread has not been started":



isAlive() is false both before start() and after the end. A helper handed a Thread it didn't start can't tell which unless it checks for Thread.State.NEW (unit Thread lifecycle and states).

    Keep the health check inside its time budget

      • 

    • join(0) waits forever, including when a deadline's remaining time rounds down to 0 ms; join(Duration) with zero or less only checks.

An Exception Ends Only Its Own Thread: Hand the Failure Over


The report from the start, with APAC's exchange rate missing and the joins inside a try:




An exception travels up the stack of the thread that threw it, and a started thread's stack begins at Thread.run(). The caller's frames are on another stack, so no catch of the caller is in the way. When the exception leaves run(), the JVM hands it to the thread's UncaughtExceptionHandler (with none set, the default handler, or a stack trace on System.err). Then the thread terminates like any other: join() returned normally, the catch never ran, and APAC's slot kept its 0.


The thread has to hand the failure over like a result, written where the caller reads after join(): catch it at the top of the thread's work, or set a handler before start():




The handler runs on the failing thread while it is still alive, "when a thread is about to terminate due to an uncaught exception" (the javadoc). Its write is one of that thread's actions, so join() hands it over like the totals.


If you catch inside the thread instead, catch Throwable. An AssertionError or a StackOverflowError is not an Exception, and a catch (Exception e) lets it through to stderr.

A Thread Runs Once: Run the Work Again on a New Thread


A region thread has ended or died, and its work has to run again. The obvious call is start():




A Thread goes from NEW to TERMINATED once (unit Thread lifecycle and states), and start() is legal only in NEW. Thread doesn't give its Runnable back, so keep your own reference and create a new Thread for each run, with the old name for readable thread dumps.


A supervisor that calls start() on a dead consumer gets IllegalThreadStateException in its own thread and, unless it catches it, dies too; no consumer is restarted after that.


Nor is the thread's state the test for a dead worker. A consumer settles one payment and finds its queue empty:



It is parked in take(), alive. A supervisor that restarts every worker that isn't RUNNABLE starts another consumer on the same queue each time the queue runs dry. Ask isAlive() instead.




    

  1. 

    Coding practice
    

    Bring a dead consumer back, and only a dead one
    

      

    • Whether a worker has ended is a question for isAlive(); a worker waiting for work is WAITING or TIMED_WAITING and alive.
      • 

    • start() is legal only on a NEW thread; to run the work again, a new Thread is created for the same Runnable.
      •

Summary


  • start() doesn't wait for the new thread to do anything, and no order between the two threads holds.
  • Results come back at join(): start every worker, then join every one. start(), join() and an isAlive() that returns false are the hand-over points; a plain done flag is not.
  • join(millis) returns without saying why. Ask isAlive(), or use join(Duration). join(0) waits forever, and a never-started thread looks finished.
  • An exception ends only its own thread. Hand the failure over by catching Throwable in the thread or with an UncaughtExceptionHandler, and read it after join().
  • A Thread runs once. Restart work on a new Thread, and decide that the old one is dead with isAlive(), not with its state.


Reference


CallEffect (Java 21)
t.start()starts t and returns at once; IllegalThreadStateException unless t is NEW
t.join(millis)waits at most millis ms and returns nothing either way; 0 waits forever; a negative value throws IllegalArgumentException; returns at once if t was never started
t.join(Duration) (Java 19+)waits at most that long and returns true if t has terminated; zero or negative only checks; IllegalThreadStateException if t was never started
t.isAlive()true from start() until the thread terminates (after any uncaught-exception handler has run); false before start() too

Design Note: Why a Thread Hands Nothing Back


run() returns void and declares no checked exception, so the work has no typed way to return anything; where the result goes, how the failure travels and how long to wait are left to you. ExecutorService and Future (unit Callable and Future for returning results) package the three: get() returns the result, throws the failure wrapped in an ExecutionException, and takes a timeout.
