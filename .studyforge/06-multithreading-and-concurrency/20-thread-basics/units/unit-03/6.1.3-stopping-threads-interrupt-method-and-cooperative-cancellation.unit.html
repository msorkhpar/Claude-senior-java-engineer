Every rolling deploy of the metrics service takes 30 seconds too long, and once a week the orchestrator kills the process halfway through writing a file. The shutdown hook calls executor.shutdownNow(), then awaitTermination(30, SECONDS). A thread dump taken during those 30 seconds shows one pool thread in Thread.sleep, inside the loop that sends metrics, and the log has one new line: interrupted while waiting, will retry.

In Java a running thread can't be stopped from outside: it is asked to stop, and its own code decides.

A Tool That Asks a Thread to Stop

The examples run each job through this helper. It starts the job on a pool of its own, calls shutdownNow() once the job has done a little work, and reports whether the thread ended within a second and how much work the job did after the request.

shutdownNow() calls interrupt() on the thread running the job. The examples use import static java.lang.Thread.currentThread;, and every output is from Java 21.

Interrupting a Thread Sets a Flag, and Running Code Stops Only Where It Looks

A reindex job works through 20,000 documents. reindex(doc) is a few dozen microseconds of CPU work, with no waiting. We ask the job to stop a few documents in:

The first job processed every remaining document and ended only when it ran out of work. interrupt() doesn't stop anything: it sets a boolean on the target thread, the interrupt flag, and returns. The second job reads the flag before each document and stops within two documents.

Only the thread being stopped knows where it can stop without leaving half a result: between two documents, but not between writing a document and updating its index entry. That is why Java leaves the check to the code that runs.

Two other checks look equivalent and aren't:

`Thread.interrupted()` reads the flag and clears it. The inner loop saw the request, ended its batch and erased the request, so the outer loop's check found nothing, and 39 more batches ran. Thread.currentThread().isInterrupted() only reads. Use Thread.interrupted() only where the code acts on the request and ends the work, never in a check that code above you also relies on.

Your own cancellation field is invisible to the JDK. shutdownNow() and Future.cancel(true) set the interrupt flag, not your field. A field can sit beside the flag to carry a reason ("cancelled by the user"), but the loop must check the flag too.

A Blocking Call Answers by Throwing, and the Throw Clears the Flag

Most threads spend their time waiting: in sleep, wait, join, a queue's take. A parked thread can't check anything, so these methods check for it. When the thread is interrupted while blocked, or is already interrupted when it calls one, the method returns at once by throwing InterruptedException, and clears the flag. The exception is then the only record that anyone asked. The metrics sender from the start of the unit has this shape:

The thread spends most of each cycle in sleep, so that is where the interrupt lands. The exception clears the flag, the catch logs it, and the while reads false forever. In production, awaitTermination times out after 30 seconds and the orchestrator kills whatever is half-done.

The JDK clears the flag because the exception now carries the request; left set, the flag would make every later blocking call in the thread throw again. Only two things clear it: Thread.interrupted(), and a waiting method that throws. Code that never looks at the flag leaves it set, and the thread's next wait throws at once.

Spot the Problem: Restoring the Flag and Retrying Turns Every Wait into a Spin

The middle catch passes code review: it restores the flag, and the pool ended within a millisecond. What did it do in that millisecond?

It made the 97 remaining attempts back to back. With the flag set again, every following sleep threw at once, and the sender hammered the webhook as fast as the loop could turn. A loop bounded by time instead runs until its time is up. This one backs off 100 ms between tries for 250 ms, and is interrupted once:

That is one core at 100 % for a quarter of a second. Code that restores the flag must also stop, in one of two shapes:

  • Rethrow it. A method that can declare throws InterruptedException does, and doesn't catch it. A helper that sleeps or waits can't tell whether an interrupt means "shut down" or "the user pressed Cancel", so it lets the exception reach code that can.
  • Restore it and stop. Code that can't throw it, typically a task's run(), calls Thread.currentThread().interrupt() and returns. The flag tells whoever called run() that the task ended because it was asked to.

Wrapping it in an unchecked exception is neither shape. To its caller, this helper's interrupt looks like any other failure:

The retry treats "we were asked to stop" as "the fetch failed", and with the flag cleared the next fetch succeeds. If an interface forbids checked exceptions, restore the flag before wrapping, so the next check sees it.

The three Futures report the same thing. isCancelled() and isDone() describe the Future, not the thread: once cancel succeeds, get() throws CancellationException. What the thread does next is up to the task. The first two uploaded a file the user cancelled. The second even checked, but its catch had swallowed the interrupt. The user, told it was cancelled, starts it again, and now there are two.

cancel(true) interrupts the running task's thread. cancel(false) only keeps a queued task from starting. On a running export both return true, so after cancel(false) the caller loses the result and the thread carries on, uninterrupted.

When a side effect must not happen after a cancel, check right before it, and make sure nothing between the request and the check can swallow it.

Classic I/O Doesn't Hear an Interrupt: Close What It Waits On

Not every blocking call checks the flag. Here a platform thread waits in accept(); we interrupt it, then close the socket:

interrupt() only set the flag. The waiting methods of the earlier sections check the flag when woken, but a platform thread in a socket call is blocked in the operating system, and java.io gives the interrupt nothing to wake. Closing the socket from another thread makes the blocked call fail with an exception. So a component that owns a blocking stream stops by closing it, and its read loop treats that exception as the end of the work, not as a failure to report.

Virtual threads differ. On a virtual thread, Java 21 makes blocking socket operations interruptible: the interrupt closes the socket and the call throws. NIO channels (InterruptibleChannel) behave that way on any thread, with ClosedByInterruptException. In both cases the interrupt flag stays set.

Summary

  • `interrupt()` sets a flag; running code stops only where it checks. Thread.interrupted() clears the flag it reads.
  • A blocking call answers by throwing, and the throw clears the flag. A catch that logs and carries on leaves a loop that can't be stopped.
  • Whoever catches `InterruptedException` rethrows it, or restores it and stops. Restoring and carrying on turns every later wait into a busy loop.
  • `Future.cancel(true)` only asks. The task's own checks decide whether it stops before its side effect.
  • Classic I/O doesn't hear an interrupt. Close what the reader waits on, and treat the exception as a stop.

Challenges

These have no single answer. Try them with the Stops helper.

  1. A task copies rows from one database to another in transactions of 1,000 rows. Where do you check the flag, and what does a reader of the target database see if the check is in the wrong place?
  2. Your task calls a third-party client that swallows InterruptedException inside its retry loop. You can't change the client. How do you make your task stoppable, and what does it cost?
  3. Measure how long shutdownNow() plus awaitTermination takes for a pool of 50 tasks, each one of the shapes in this unit. Which one decides your deploy time?

Design Note: Why Java Has No Safe stop()

Java 1.0 had Thread.stop(), which threw an error into a thread wherever it was, releasing every monitor the thread held. A thread stopped between debiting one account and crediting another released the lock with the money gone from the first and never added to the second, and the next thread to take the lock saw that state as consistent. No code can defend against an exception that can appear between any two of its instructions, so the method was deprecated in Java 1.2 and, since Java 20, throws UnsupportedOperationException.

The price of cooperative cancellation is that it works only if every layer between the request and the work cooperates: one empty catch in a library three calls down, or a reader blocked in a socket that nobody closes, and the pool can't stop.

When a proxy is retired, the collector calls stop() on its tailer, and that call never returns: the collector's admin thread hangs until someone restarts it.
