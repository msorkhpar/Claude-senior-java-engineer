At 14:05 the checkout service stops answering. Its admin page counts the request pool's threads by state: 200 threads, 9 RUNNABLE, 191 WAITING, 0 BLOCKED. The runbook says that no BLOCKED threads means no lock contention and that WAITING threads are idle, so the on-call engineer restarts the service. The next afternoon it happens again.

All 191 threads were waiting for the same ReentrantLock around the price cache. Its holder was one of the 9 RUNNABLE threads, stuck in a socket read to a pricing service that had stopped answering.

A Tool That Shows What a Thread Dump Shows

Every example prints its threads through this helper. For each thread it prints what a thread dump would say (the state, the lock the thread waits for and that lock's holder) and the CPU time the thread used in the 200 ms before the snapshot, because the state alone doesn't say whether the thread is doing any work.

ThreadMXBean is what a JMX-based admin page reads. jcmd <pid> Thread.print prints the state and the lock as text, but names no owner for a thread waiting on a ReentrantLock. The examples also use daemon(name, body), which starts a named daemon thread whose body may throw; crunch(), a few microseconds of arithmetic; silentPricing(), a local server that accepts connections and never answers; and readPrice(pricing), which connects to it and reads. Every output is from Java 21.

RUNNABLE Means the JVM Isn't Holding the Thread Back, Not That It Is Using a CPU

One thread calls the silent pricing service, one computes a report, one sleeps between two retries. Which of them are RUNNABLE?

The thread waiting for an answer is RUNNABLE, like the one that used a whole core. A state records what the JVM is doing with the thread: when the JVM parks it, in sleep, a lock or wait, the state says so. A socket read waits inside the operating system, where the JVM has no say, so the thread stays RUNNABLE. The javadoc says a RUNNABLE thread "may be waiting for other resources from the operating system such as processor".

The processor is the other resource. On a machine with 20 hardware threads we start 40 threads that only compute, and print the first three:

All three are RUNNABLE, and in the 200 ms window each got between a third and a little over half of a core. Java has no "running" state: running, ready to run and stuck in a native call look the same.

So the 9 RUNNABLE threads on the admin page were not the 9 busiest. To see what a RUNNABLE thread is doing, read its top frame: a native socket method such as SocketDispatcher.read0, Net.poll (a read with a timeout) or Net.accept means it waits for the network. Or compare its CPU time in two dumps taken a few seconds apart; jcmd prints it as cpu= on each thread's first line.

Virtual threads differ. A virtual thread in the same socket call reports WAITING, or TIMED_WAITING when the socket has a read timeout, because it is parked and its carrier thread is freed. Neither ThreadMXBean nor jcmd <pid> Thread.print lists virtual threads; jcmd <pid> Thread.dump_to_file -format=json <file> does.

BLOCKED Means Waiting for a synchronized Monitor; a Thread Waiting for a ReentrantLock Is WAITING

The checkout incident at small scale: price-refresh takes the price cache's ReentrantLock, then calls the silent pricing service. Two requests want the lock, and a pool worker with no work waits in take().

No thread is BLOCKED. The same cache guarded by synchronized (priceMonitor) instead:

BLOCKED has one meaning: the thread is waiting to enter a synchronized block or method whose monitor another thread holds, or to re-enter one after wait() (next section). The monitor is built into the JVM. ReentrantLock, Semaphore, the blocking queues and CountDownLatch are Java code: to wait, they park the thread with LockSupport, and a parked thread is WAITING, or TIMED_WAITING if the park has a timeout. The state names the mechanism, not whether another thread is in the way.

request-1 is stuck and worker-7 is idle, in the same state. The difference is on the right: what each waits for, and who holds it. A thread dump shows the same:

To find a pile-up, ask whether a thread waits for something another thread holds. ThreadInfo.getLockOwnerName() answers that for a monitor and for a lock that records its owner, such as ReentrantLock. A Semaphore, a latch or a queue has no owner, so the owner is null, and the lock's class and the stack tell a stuck thread from an idle one.

An alert on the number of BLOCKED threads stayed at zero through the checkout incident, because the cache had moved from synchronized to ReentrantLock a release earlier. A dump taken before the restart would have shown 191 threads waiting for one lock held by price-refresh.

A Waiting Thread Keeps Every Lock but the One It Waits On

Spot the Problem: a Back-Off That Holds the Cache

When the pricing service fails, the cache backs off for a minute before trying again. Requests read prices through the same object:

price-refresh is sleeping in refreshWithSleep(), and two requests call price(...). What are the requests doing?

sleep gives up the processor, not the monitor: its javadoc says the thread "does not lose ownership of any monitors". The sleeping thread holds the cache for the whole minute, and every request that reads a price queues behind it. The same goes for a thread holding a lock while it waits for anything else: a socket, as in the checkout incident, a join(), a take() on another queue.

The exception is the lock a thread waits on. Object.wait(), called on an object whose monitor the thread holds, releases that monitor, and only that one, while it waits; Condition.await() does the same for its Lock. The back-off written with wait(60_000) on the cache:

price-refresh is in the same state as before but no longer owns the cache, so both requests got their price and finished. WAITING and TIMED_WAITING differ only in the timeout (wait() and wait(60_000), join() and join(60_000), park and parkNanos), and neither says whether the thread holds a lock. The dump shows held monitors as - locked <...> lines in the stack, but it prints one for a monitor released by wait() too (with - waiting on the same address above it), and it lists held ReentrantLocks only with jcmd <pid> Thread.print -l.

A Notified Thread Is BLOCKED Until It Gets the Monitor Back

A thread in wait() doesn't wake because a condition became true. It waits until another thread calls notify() or notifyAll() on the same object or interrupts it, or until its timeout runs out; the javadoc also allows a rare spurious wakeup. Setting a field it would check wakes nothing. Nor does a notified thread run at once:

wait() returns only once the thread owns the monitor again. After notify() the packer goes straight from WAITING to BLOCKED behind its notifier, until order-intake leaves its synchronized block. Meanwhile another thread can get in first and change what the packer was waiting for, which is why wait() belongs in a loop that checks its condition again (unit Monitors and synchronized blocks builds it).

getState() Is a Snapshot: Coordinate with join() or a Latch, Never by Polling a State

An indexing worker loads its configuration under a lock, then waits for jobs in take(). Startup has to know when the worker is ready, and someone writes the obvious check: wait until it is WAITING, as it is once it waits for jobs. This time config-reload holds the configuration lock when the worker starts:

The worker is WAITING for the configuration lock, not for jobs: WAITING says how a thread waits, never where. A state may also be gone a moment after you read it. We started a thread with an empty body and read its state straight after start(), 10,000 times:

That thread touches no lock of ours and was seen BLOCKED 6 times. Eight runs of the loop saw it BLOCKED between 0 and 124 times, and sometimes already TERMINATED: the JVM's own code blocks threads briefly. The javadoc of getState() says it is "designed for use in monitoring of the system state, not for synchronization control". A Thread.sleep(100) before the first job is no better: it guesses how long loading takes, and a reload that holds the lock longer makes the guess wrong.

The signal is something the worker does at the point it means: a latch counted down once the configuration is loaded (ready.countDown() above), and a bounded wait on it at startup:

For "the thread has finished", join() is the signal (unit Starting threads (start() method)). Only the two ends of the lifecycle hold for good: a thread is NEW until start() and never again, and once TERMINATED, whether run() returned or threw, it stays so.

With the state check or the sleep, start() returns while the worker still has no configuration, and startup carries on as if it had one: the service reports itself ready, and anything reading the worker's configuration in that window finds none. It happens only when a reload overlaps a start, which a test rarely does.

Summary

  • `RUNNABLE` means the JVM isn't holding the thread back. It covers running, waiting for a processor and waiting in a native call such as a socket read, so a RUNNABLE thread may be the stuck one. CPU time and the top frame tell them apart.
  • `BLOCKED` is only the `synchronized` monitor. A thread waiting for a ReentrantLock is WAITING, like an idle worker. What it waits for and who holds it decide whether it is stuck, and an alert on BLOCKED alone misses every pile-up on a ReentrantLock.
  • A waiting thread keeps every lock but the one it waits on. A sleep inside synchronized leaves every other caller BLOCKED for as long as it sleeps, and a notified waiter is BLOCKED until its notifier leaves.
  • `getState()` is a snapshot. WAITING doesn't say where, and states change between two reads. Signal readiness with a latch and completion with join().

Challenges

These have no single answer.

  1. Design the alert that would have fired at 14:05 in the checkout service. What does it count, from ThreadMXBean, and how does it keep quiet for a pool whose workers are all idle?
  2. Take three thread dumps five seconds apart from a service under load. Which differences between them tell you a thread is stuck, and which are just a busy system?
  3. Your service moves to virtual threads. Which of this unit's diagnoses still work, which tool do you use instead of jcmd Thread.print, and how would the checkout incident look there?
  4. Measure how much CPU a RUNNABLE thread gets as you add busy threads beyond the core count. At what point would a state count and a CPU graph disagree on a dashboard you know?

Design Note: Why Java Has No RUNNING State

An operating system's scheduler knows which thread is on a core and which is waiting for one, and Thread.State doesn't say. It describes a thread from the JVM's side: the javadoc calls them "virtual machine states which do not reflect any operating system thread states". The JVM knows when it parks a thread itself, in a monitor, in park, in sleep, so those states are exact. It doesn't decide which runnable thread gets a core, and it doesn't see inside a system call, so everything else is RUNNABLE.

That keeps the states the same on every operating system, and reading one asks nothing of it. The price is that a state count is never a measure of work: a state needs the lock, the owner and the CPU time beside it.

Problem statement


The payments service has an admin page that sorts the JVM's threads into three groups: active, idle, and stuck behind another thread. During the last incident it showed 0 stuck, while every payment request was waiting for one thread to finish, and on-call restarted the service without looking further. On a quiet night, it must not call the idle mailer workers stuck either.


The page reads a snapshot from ThreadMXBean.getThreadInfo(...), and ThreadTriage already counts and groups the threads. Finish the TODO in src/main/java/practice/ThreadTriage.java:


  • classify(ThreadInfo thread): which of the three activities this thread is in.


A thread is stuck behind another when it can't go on until another thread lets go of something it holds; stuckBehind then reports it under that thread's name. About three lines in total.


The tests start real threads, put each one somewhere (computing, in a lock, in a queue, in a sleep) and hand your method the snapshot ThreadMXBean takes of them.

Problem statement


The trading desk's monitoring page asks every market-data feed for its status() once a second. When a feed loses its connection, its own thread calls reconnect(), which backs off between attempts, for up to two minutes when the exchange is down. That is exactly when the desk most wants to see the feed's status, and it is when the monitoring threads stop getting answers. At shutdown, close() should make a reconnect give up, and today shutdown waits out the back-off.


QuoteFeed keeps its state under its own monitor, and reconnect(), status() and close() stay synchronized. Finish the two TODOs in src/main/java/practice/QuoteFeed.java:


  • pause(long millis): the back-off between two attempts, called from inside reconnect();
  • close(): closes the feed, and a reconnect that is backing off gives up at once.


When you're done, status() answers during a back-off of any length, and close() ends a back-off in progress. About seven lines in total.


The tests run reconnect() on a thread of its own, with back-offs of a few milliseconds and of two minutes.

Problem statement


The search service starts an IndexWorker at boot and sends it the first search terms as soon as start() returns. The worker can't index anything before it has loaded its synonym table. Usually that takes a few milliseconds, but when the configuration is being reloaded at the same moment, the loader has to wait for the configuration's lock, and on a cold cache it computes for seconds. On those boots the first terms meet a worker with no table.


IndexWorker already starts its thread, loads the table on it and indexes what it is sent. Finish the two TODOs in src/main/java/practice/IndexWorker.java:


  • signalReady(): called on the worker's thread once its table is loaded;
  • awaitReady(): called by start(), returns once the worker is ready to index.


When you're done, start() returns once the table is loaded, however long the loader takes and whatever it waits for. About four lines in total, a field included.


The tests hold the loader back, once behind a lock and once in a long computation, and check whether the table was loaded at the moment start() returned.
