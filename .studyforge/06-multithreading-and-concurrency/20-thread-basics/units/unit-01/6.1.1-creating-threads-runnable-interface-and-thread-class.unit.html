A command-line tool exports the day's orders to a file. To keep its progress bar moving, someone moved the export onto a thread of its own: new Thread(exporter).start(). Since then the tool sometimes never exits on the batch server, and a thread dump of a stuck run shows "Thread-3" in TIMED_WAITING, which could be any of its four background threads. Someone made the thread a daemon so the tool would exit, and now, on some nights, the export file is empty. Every output below is from Java 21.

A Thread Runs a Task: Write the Task as a Runnable, Not as a Thread

A Thread object is the handle for one thread of execution. The work it does is a Runnable, an interface with one method, void run(), so a lambda can go straight to the constructor:

The other way is to extend Thread and override run(). The two differ once the task runs on another thread.

Another team's nightly export was written years ago as a thread of its own (Thread.onSpinWait() stands in for one batch of work):

Someone moves it onto the service's pool. Thread implements Runnable, so this compiles. shutdownNow() stops the pool by interrupting its threads (unit Stopping threads (interrupt() method and cooperative cancellation)):

Which thread does the log line name, and does shutdownNow() stop the export?

The pool's thread calls job.run() as an ordinary method, so the code runs on pool-1-thread-1. Every method ExportJob inherited from Thread, though, describes the ExportJob object, which was never started and is still NEW. getName() names a thread that doesn't exist, and isInterrupted() reads a flag nobody sets: shutdownNow() interrupted pool-1-thread-1. The loop never ends, and since a pool's threads are not daemons, neither does the process: run without its final System.exit, it was still busy when killed after 5 s.

The same pool code with ExportTask, then the task on a named thread and on a virtual thread (the last section), each stopped with an interrupt:

The task runs unchanged wherever it is put, and code on its own thread today can be handed to a pool or a virtual thread later. Extend Thread only to change how the thread itself behaves, which application code almost never needs. Inside a task, ask Thread.currentThread(), never this.

A Runnable Has No Way Back: Return a Result or a Failure Through a Callable

run() returns void and declares no checked exceptions. Here a loader thread reads the orders into a list, and readOrders() fails:

The exception ended the loader thread. Nothing connects a thread's failure to the thread that started it: the JVM hands it to the failing thread's uncaught-exception handler, whose default prints it to standard error (unit Starting threads (start() method) sets your own). join() returned normally, because it waits for the thread to end, not to succeed, and main went on with an empty list: in the opening's tool, an empty export reported as a success.

Callable<V> (V call() throws Exception) returns a value and may throw any exception. A Thread runs only a Runnable, so wrap the Callable in a FutureTask, a Runnable for the thread and a Future the caller reads the outcome from:

get() waits for call() to finish, then returns its value or throws ExecutionException with the task's exception as its cause. Handle e.getCause(), the task's own failure, not the wrapper. In services the thread usually comes from an ExecutorService, whose submit wraps the task the same way (units ExecutorService interface and implementations and Callable and Future for returning results).

Name Every Thread Where You Create It

Four threads printed Thread.currentThread(): from new Thread(task), an Executors.newFixedThreadPool(2) pool, new Thread(task, "invoice-mailer") and Thread.ofVirtual():

Only invoice-mailer says what it does. Thread-0 and pool-1-thread-1 are generated, and a virtual thread has no name: getName() returns the empty string. In a thread dump the name is the only thing that ties a stack to a component.

So the code that creates a thread, and knows what it is for, names it. The constructor takes a name, and Thread.Builder counts for you. A builder also gives a ThreadFactory, the interface an ExecutorService calls to create each of its threads, so a named factory names a pool's threads:

name(prefix, start) appends a counter that the builder increments for each thread. A factory taken from the builder starts from a copy of the counter's current value, which is why both factories began at 3 and two threads are now called invoice-mailer-3. Take one factory per pool, each with its own prefix.

A Daemon Thread Doesn't Hold the JVM Open, and Exit Drops It Mid-Step

An exporter thread writes five orders, 100 ms apart, through a buffered writer, and main returns after 250 ms. log prints milliseconds since the start.

Run once with daemon false:

The process ended after 539 ms, and the file held all five orders and END: 44 bytes. Then with daemon true:

The process ended after 283 ms, and the file was empty: 0 bytes.

The JVM begins to shut down when the last started non-daemon thread ends. In the first run the exporter was one, so the JVM waited for it; the opening's tool hangs because one of its non-daemon threads never ends.

A daemon thread doesn't count. In the second run the JVM shut down as main returned, with the exporter in the middle of a sleep. The exporter wasn't interrupted and got no exception. Its finally never ran, so the writer was never closed, and the three orders in its buffer never reached the file. No error appeared anywhere.

setDaemon(true) lets the JVM abandon the thread's work between any two instructions, which suits a cache refresher. Work that must finish, such as a file or a commit, runs on a non-daemon thread whose owner waits for it (units Starting threads (start() method) and Stopping threads (interrupt() method and cooperative cancellation)).

Daemon status can't change while the thread is alive: setDaemon on a running thread throws.

A thread you don't mark is not necessarily non-daemon: a platform thread inherits the daemon status of the thread that creates it. These four were created on a daemon thread called housekeeping:

The two that didn't say became daemons, like their creator. The pool's thread didn't, because Executors.defaultThreadFactory() sets non-daemon explicitly. Code that creates threads for work that must finish says daemon(false) or setDaemon(false), so the answer doesn't depend on which thread calls it.

A Virtual Thread Is Cheap to Create and to Block, Not Faster at Computing

A platform thread, the kind every earlier example created, wraps an operating-system thread with its own native stack. A virtual thread is scheduled by the JVM onto a small pool of platform threads, its carriers, and in most cases releases its carrier while it is blocked.

This program starts one thread per task and waits for all of them: first tasks that each wait 1 s, as a call to a slow remote service would, then tasks that each compute about 50 ms of arithmetic.

The waiting tasks wait the same second either way, so on platform threads the extra 14 s went into handling 100,000 operating-system threads. The computing tasks took the same time either way: 20 logical CPUs do 20 tasks' arithmetic at a time, whatever kind of thread asks.

One virtual thread per blocking task (HTTP calls, database queries) replaces a pool sized to ration platform threads; work that keeps a core busy gains nothing. Unit Differences between virtual threads and platform threads covers what a virtual thread still costs.

A virtual thread is also always a daemon:

So virtual threads started from main hold nothing open: at exit they are dropped mid-step, like the daemon exporter. Code that starts virtual threads for work that must finish waits for them before it returns.

Summary

  • A thread runs a task; write the task as a `Runnable`. A Thread subclass run by a pool describes an unstarted object: wrong name, and shutdown can't stop it.
  • A `Runnable` has no way back. Its failure goes to standard error and join() returns normally; a FutureTask's get() returns a Callable's result or throws its failure as the cause of an ExecutionException.
  • Name every thread where you create it; generated names make a thread dump unreadable.
  • A daemon thread doesn't hold the JVM open, and exit drops it mid-step, with no finally. Daemon status is fixed at start() and, unless set, copied from the creating thread.
  • A virtual thread is cheap to create and to block, not faster at computing, and is always a daemon.

Challenges

  1. A library creates its background threads with new Thread(task), and your service creates the library's clients from a daemon housekeeping thread. Which of the library's threads are daemons, and how would you check in a running service without its source?
  2. The opening's export must finish its file even when the operator presses Ctrl-C. Which thread owns the file, who waits for it, and what does the operator see if the export takes three minutes?
  3. Your service makes 2,000 concurrent calls to a slow partner API, each waiting about 300 ms. Compare a fixed pool of 200 platform threads with one virtual thread per call: measure the time for a burst, and decide what keeps the partner from receiving all 2,000 calls at once.

Design Note: Why Thread Implements Runnable

In Java 1.0, Thread is both the handle for a thread and, since it implements Runnable, a task, which kept the first programs short and left this unit's first trap. Later libraries separate the two: executors (Java 5) take tasks and make threads in a ThreadFactory, and Thread.Builder (Java 21) describes a thread apart from its task. The original design can't change without breaking every Thread subclass, so the code that creates threads keeps them apart.

Problem statement


The billing service has a dozen thread pools, all created with Executors' default factory. Two things went wrong last month. During an incident, on-call took a thread dump and found 37 threads called pool-<N>-thread-<M>, and had to guess which pool belonged to which component. And after a routine restart, the audit log was missing its last entries: the audit pool is created lazily, on the first audit event, and that event is raised by the housekeeping thread, which is a daemon.


The team now creates every pool with a ServiceThreads factory, which knows the component's name and whether the component is background work that may be dropped at exit (a CPU sampler) or foreground work that must finish (audit, ledger). Finish the TODO in src/main/java/practice/ServiceThreads.java:


  • newThread(...): the thread a pool asks for.


When you're done, a thread dump shows audit-1, audit-2, ledger-1, ... (each component counting its own threads), and whether the JVM waits for a pool's threads at exit depends only on what the component declared, whichever thread happened to create the pool. About four lines in total.


The tests build real pools with the factory and also call it from a daemon thread.
