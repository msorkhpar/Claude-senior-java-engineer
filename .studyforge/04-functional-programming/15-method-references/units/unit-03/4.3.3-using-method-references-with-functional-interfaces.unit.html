The Interface's Parameter Types Choose the Overload; the Value at Run Time Doesn't

String.valueOf has nine overloads, among them valueOf(char[]) and valueOf(Object). Before reading the output, decide what each reference prints for the same array:

javac resolves String::valueOf like the call String.valueOf(x), with x typed char[] in one and Object in the other. That happens once, at compile time: javap -v shows one reference pointing at String.valueOf:([C)Ljava/lang/String; and the other at String.valueOf:(Ljava/lang/Object;)Ljava/lang/String;. From then on fromObject calls valueOf(Object) whatever it is given, and for an array that means toString(), the class name and a hash. A null goes the other way: valueOf(Object) writes "null", and valueOf(char[]) throws.

An export that keeps its column formatters as Function<Object, String> therefore writes [C@7f31245a into a token column, and a test suite whose tokens are all Strings never sees it.

javac searches in the same phases as for a call: first without boxing, then with it, then varargs. Math::max has int, long, float and double overloads:

No max(Integer, Integer) exists, so for BinaryOperator<Integer> javac allows unboxing, finds all four overloads applicable, and takes the most specific, max(int, int). The reference unboxes each argument before the call, so a null element throws a NullPointerException with no message. With abs the overload changes the answer: Integer.MIN_VALUE has no positive int, so abs(int) returns it unchanged, while abs(long) returns 2147483648.

For an unbound reference the interface's first parameter is the receiver, and it may be any subtype of the class before ::: Function<String, String> show = Object::toString compiles. The other way round fails, since an Object is not a String: Function<Object, Integer> length = String::length gives method length in class String cannot be applied to given types.

An Exact Reference Lets javac Pick submit(Callable); Overloading the Method Makes the Call Ambiguous

ExecutorService.submit is overloaded for Runnable and Callable<T>. A method that returns a value fits both, since a Runnable can drop the result. Which does each line choose?

refresh has one declaration, is not generic and takes no varargs, so javac knows the call this::refresh makes before it chooses between the submits. Such a reference is exact. Both fit, and the one whose method returns a value is more specific: the same preference unit Syntax and structure of lambda expressions showed for lambdas. clear returns void and fits only Runnable.

Now the price cache gets a second refresh:

Which refresh the reference names now depends on the target. The reference is inexact, and javac doesn't use it to choose the overload of submit: it only checks that some refresh takes as many arguments as each candidate's interface supplies. Both pass and neither is more specific, so the call is ambiguous. A single varargs method (int count(String... names)) or generic method (static <T> T none()) gave javac 21 the same error. Naming the target fixes one call site:

The lambda has no parameters, so its body can be checked against both overloads, and the value-returning one wins.

An Inexact Method Reference Leaves Inference Without the Types It Needs

Back to the opening. comparing is generic, <T, U> Comparator<T> comparing(Function<? super T, ? extends U>). Assigned straight to a Comparator<Customer>, it gets T from the target. With .reversed() called on its result it gets no target (unit Using lambda expressions with functional interfaces), and T must come from the argument. While displayName had one declaration, the reference told inference its types: the receiver is a Customer, the key a String. Once overloaded, it tells inference nothing. T becomes Object, and javac then reports the closest candidate it tried, displayName(Locale) with an Object argument.

String::toLowerCase, overloaded with toLowerCase(Locale), fails the same way:

comparing(String::length).reversed() compiles, because length has one declaration. Unit Using lambda expressions with functional interfaces's advice, use a method reference where a lambda can't infer its parameter, holds only for exact references. Each of these sorts Mei, Ade and Zora:

The first is the one to prefer: comparing gets its target from sort, and the order to reverse is the key's.

A Generic Method Needs Type Arguments When Nothing Else Gives Them

Collections::emptyList names one method, but its T is open until a target fixes it. In a chain, nothing does:

supplyAsync inferred a List<Object>, and thenApply can't turn it into a List<String>. Collections::<String>emptyList supplies the type argument, and the same chain compiles and yields [].

javac and the specification. As we read JLS 15.13.1, a generic method reference with explicit type arguments is exact. javac 21 still reports pool.submit(Collections::<String>emptyList) as ambiguous, like this::refresh; a cast to Callable<List<String>> compiles.

A Varargs Method Packs the Interface's Arguments, So an Array Becomes One Element

String.format(String, Object...) fits a BiFunction<String, Object, String>. No format(String, Object) exists, so javac reaches the varargs phase and compiles the reference to a synthetic lambda$ method (unit Introduction to method references) that calls String.format(t, x) with x typed Object, so x is packed into a new one-element array. A routing service renders shard names this way:

The direct call passes its Object[] as the varargs array. Through the reference the array arrives typed Object and is packed: the first %s gets the whole array, printed as [Ljava.lang.Object;@…, and the second finds nothing. Single values work, so the failure appears with the first message that carries two. With Object[] as the parameter type, the reference passes the array through.

A Method That Throws a Checked Exception Doesn't Fit Function

Files.readString(Path) declares throws IOException, and Function.apply declares nothing:

The rule is the one for a lambda's body, but a reference has no body to put a try in. Unit Throwing exceptions using the throw keyword gives the two ways out: a functional interface whose method declares the exception, which takes Files::readString as it is, or a lambda that wraps the exception and code at your boundary that unwraps it.

Summary

  • The interface's parameter types choose the overload, at compile time. String::valueOf as a Function<Object, String> prints [C@… for a char[]; Math::abs as an IntUnaryOperator leaves Integer.MIN_VALUE negative; a boxed target unboxes and throws on null.
  • An exact reference (one declaration, not generic, not varargs) lets javac pick `submit(Callable)`. Adding an overload makes every submit(this::m) ambiguous; a cast or a lambda fixes the call site.
  • An inexact reference leaves inference without the types it needs. comparing(m).reversed() breaks when m gains an overload; pass reverseOrder() to comparing, or give type arguments.
  • A varargs method packs the interface's arguments. An Object[] passed as Object becomes one element, and an int[] is never spread.
  • A checked exception doesn't fit `Function`. Use an interface that declares it, or wrap it in a lambda (unit Throwing exceptions using the throw keyword).

Challenges

  1. Pick a class in your codebase that other modules use through method references. Which of its methods could gain an overload without breaking a caller's build, and how would you find out before merging?
  2. Your API takes a Function<Object, String> formatter, and callers pass String::valueOf. Would you change the parameter type, add overloads for common types, or document it? What does each cost a caller?
  3. submit(this::refresh) and submit(() -> refresh()) both choose Callable today. Which one keeps compiling when refresh gains an overload, and which one would you write in a code base you don't control?

Design Note: Why javac Ignores an Overloaded Reference While It Picks an Overload

To choose an overload of submit, javac checks every argument against every candidate. For a reference to an overloaded method, that would mean resolving the reference again for each candidate's parameter types, and each resolution could pick a different method, while the candidate's own type variables would depend on that pick. javac leaves such a reference out of the choice and resolves it once, against the method chosen. The cost lands on callers: adding an overload doesn't break compiled ones (a Scheduler compiled against the old PriceCache still printed get() = 120 against the new one), but breaks them at their next compile.
