A method reference comes in four kinds: static (Integer::parseInt), bound (prefix::concat), unbound (String::length) and constructor (ArrayList::new). Each maps the functional interface's parameters onto a call in its own way. Unit Introduction to method references covers what all four share.

Class::method Is Static or Unbound, and the Method's Declaration Decides Which

Integer::parseInt and String::length look alike, and both fit a Function<String, Integer>:

parseInt is static, so the argument goes straight to it. length is an instance method with no parameters, so the argument becomes the receiver. With more parameters, the first becomes the receiver and the rest the arguments: as a Comparator<String>, compare(a, b) calls a.compareToIgnoreCase(b). An unbound reference to a fixed-arity method needs one more interface parameter than the method has.

Nothing in the text Class::method says which of the two it is. The compiler searches both ways: for a static method that takes all the interface's parameters, and for an instance method that takes all but the first. When both searches find one, it does not pick:

Integer has a static toString(int) that takes the Integer by unboxing, and the instance toString() that takes it as the receiver. Long::toString and Integer::hashCode fail the same way. Object::toString and String::valueOf compile, because each leaves only one search with a match, and so does the lambda i -> Integer.toString(i), an ordinary call with one argument. Unit Using method references with functional interfaces covers how overloads of one kind are chosen.

Through a Supertype, the Call Still Reaches the Override

The class before :: in an unbound reference can be a superclass or an interface of the receiver. With record Sku(String code, int qty) {}:

Object::toString printed the record's own toString, not Sku@ and a hash. The class before :: decides what compiles and what the interface's first parameter may be; the receiver's class decides which body runs, as for s.toString().

A Bound Reference Holds Its Receiver, and the Interface's Arguments Become the Method's

In expr::method, the expression supplies the receiver, so every parameter of the interface goes to the method. An invoice service tags ids with a prefix, then adds a region suffix the same way:

The second reference puts the suffix in front. A bound reference cannot make the incoming value the receiver: the receiver was fixed when the reference was created. When the value must be the receiver and something else the argument, write the lambda s -> s.concat(suffix). The same trap turns term::contains into "does the term contain this line?" when the filter meant "does this line contain the term?".

this:: Dispatches; super:: Is Fixed to the Parent's Body

In an instance method or constructor, this and super can stand before ::. Both bind the current object, but they call different bodies:

On a new EuroFormat(), parent().apply(1250) and own().apply(1250) give:

this::format behaves like this.format(c): it runs the override of whatever class the object is, including a subclass written later. super::format behaves like super.format(c): it always runs PriceFormat's body. It skips dynamic dispatch, as Iface.super::m does for an interface's default method, and it is how you pass the parent's version as a callback.

Class::new Picks Its Constructor From the Interface's Parameters

A constructor reference has no parameter list of its own. The interface's parameters are the constructor's arguments, so the target type chooses the constructor:

sized.apply(5) is an empty list with room for five elements, not a list holding 5. In the opening loop, with record Reading(String sensor, int celsius), computeIfAbsent takes a Function<? super K, ? extends V> and calls it with the key. With Integer keys, ArrayList::new resolves to ArrayList(int initialCapacity), and the temperature becomes the capacity:

Capacities 3 and 1 are legal; ArrayList(int) throws IllegalArgumentException for a negative one, so the first negative reading threw. Large positive keys fail another way: a map keyed by customer id reserves an array of that many slots for each new list, and one key of 40,000,000 ran out of memory with -Xmx64m. With String keys the line does not compile, since no ArrayList constructor takes a String. Write k -> new ArrayList<>() whenever the interface passes something the constructor should not see.

Arrays: String[]::new Tells toArray the Element Type

Type[]::new is a constructor reference that takes the length, an IntFunction<Type[]>. Its main use is Stream.toArray:

A Stream<String> does not know at run time that its elements are strings: the type argument is erased. Without a generator, toArray() can only allocate an Object[], and an array's class is fixed when it is created, so no cast turns it into a String[] later. String[]::new lets the stream allocate the right array.

The generator must produce an array of a reference type. int[]::new is a valid IntFunction<int[]>, but Stream.of(4, 9).toArray(int[]::new) does not compile (inference variable A has incompatible bounds). For a primitive array, convert with mapToInt(Integer::intValue) and call IntStream.toArray(), which needs no generator.

A Constructor Reference Makes a New Object per Call; a Bound Reference Reuses One

A dispatch screen turns parcel ids into slips, two ways:

Before reading on: how many StringBuilders does each line create?

StringBuilder::new names a constructor, so every call runs it: three ids, three builders. In new StringBuilder("slip ")::append, the new is the receiver expression of a bound reference. It runs once, when the reference is created (unit Introduction to method references), and every call appends to that one builder and returns it. The list holds the same object three times, so the screen shows slip A-7B-12C-3 three times, and code that appends a signature to one slip changes all three.

A bound reference to a mutable object is shared state. When each call needs its own object, create it inside the call: StringBuilder::new, or the lambda id -> new StringBuilder("slip ").append(id), which builds slip A-7, slip B-12 and slip C-3.

Summary

  • `Class::method` is static or unbound, and the method's declaration decides. Static passes every argument through; unbound makes the first argument the receiver. When both fit, javac reports an ambiguity instead of choosing. The call is virtual even when a supertype is named.
  • A bound reference holds its receiver. Each argument goes to the method, so suffix::concat prefixes. this::m dispatches to the override; super::m always runs the parent's body.
  • `Class::new` picks its constructor from the interface's parameters. computeIfAbsent(key, ArrayList::new) turns an Integer key into a capacity. String[]::new gives toArray its element type.
  • A constructor reference makes a new object per call; a bound reference reuses one. new StringBuilder()::append shares one builder across every call.

Design Note: Why :: Has No Parameter List

A method reference names a method and lets the target type say how to call it. Leaving out a parameter list keeps String::length and ArrayList::new short, and lets one spelling serve several shapes: ArrayList::new is a Supplier, a Function<Integer, …> and a Function<Collection, …>. The cost is that the line does not say which shape it has. javac turns the static-or-unbound question into an error when both fit, but it cannot tell an intended constructor from an accidental one, and computeIfAbsent(id, ArrayList::new) compiles. Where the choice matters, a lambda states the constructor and its arguments.
