A rate limiter reads its limit through an IntSupplier that is wired once, at startup. A reviewer shortened the wiring from () -> settings.limit() to settings::limit, with the comment "same thing, shorter". Since that change, an operator who reloads the settings sees the new limit, 250, in the log, and the limiter keeps allowing 100 requests a second. Nobody restarted anything. Where does the 100 come from?

A method reference behaves like a lambda that makes one call, and most of the time the shorter text means exactly the same thing. This unit is about the places where it doesn't. Every output below is from Java 21; long stack traces are cut to their first frames.

A Method Reference Is a Lambda That Makes One Call, and the Target Type Decides What the Call Means

String::length names a method without calling it. Like a lambda (unit Introduction to lambda expressions), it has no type of its own: the interface the context expects, its target type, supplies the parameters, and the compiler finds a call to length that fits them. As a Function<String, Integer> it is s -> s.length(); the kinds of reference and how each one maps the parameters are unit Types of method references (static, instance, constructor).

A leaderboard wants the best of three scores:

max takes a Comparator<Integer>, whose method is int compare(Integer, Integer). Integer.max(int, int) takes two ints and returns an int, so the reference compiles, without a warning. The comparator now is Integer.max: asked to compare 40 and 95, it answers 95, a positive number, which means "40 is greater". With positive scores every comparison says "the first is greater", so max returns whichever score came first.

The compiler checks that the call fits the interface's method: the number of parameters, their types after boxing, and the return type. It can't check that the method means what the interface's contract asks for, and a lambda is no safer: (a, b) -> Math.max(a, b) compiles too. The reference hides what the call does, though: a reader sees max(Integer::max) and assumes it finds the maximum.

The leaderboard passes any test whose best score comes first, which is common when test data is typed in sorted order.

A Bound Receiver Is Evaluated Once, When the Reference Is Created


settings::limit and () -> settings.limit() call the same method. They differ in when settings is read. In a reference with an expression before the :: (a bound reference), the expression is evaluated when the reference is created, and the result is kept. A lambda's body, receiver included, runs on every call. A counter that issues a new ticket on each next() shows when each one runs:




Creating the reference issued T-1, before anyone called get(), and every call returns that ticket. The lambda issued nothing until it was called, and then a new ticket per call.


The rate limiter has the same shape. settings is a volatile field that a reload replaces with a new Settings object:




The reference holds the object that was in the field at startup. The reload changed the field, not that object, so the limiter reads 100 for as long as the process runs. The lambda reads the field on each call. A lambda that reads a local copy instead, Settings s = settings; and then () -> s.limit(), is pinned just like the reference: what it captured is the object, not the field (unit Introduction to lambda expressions).


Neither is wrong in itself: a job that must report the settings it started with wants them pinned, and the limiter, which must follow reloads, wants the field read on every call.


A Null Receiver Fails Where the Reference Is Created


Because the receiver is evaluated at creation, a null one fails there. Here the settings are not loaded yet:




javac compiles a bound reference as Objects.requireNonNull(receiver) followed by the code that creates the object, so the exception comes from requireNonNull and carries no message. The line number is the only clue. The lambda was created without complaint and failed on its first call, with a message that names the field.


In the limiter, wiring settings::limit before the settings are loaded stops the service at startup with that bare exception. The lambda version starts, and fails on the first request if the load never happens. Failing at startup is usually better than failing on a request an hour later, after the load was quietly skipped.

javac Points Most Method References Straight at the Method, With No lambda$ Method in Between


Unit Introduction to lambda expressions showed that a lambda's body becomes a private method, lambda$main$0, and the lambda itself an invokedynamic whose bootstrap method, LambdaMetafactory.metafactory, builds an object that calls that method. A method reference already names a method, so javac usually passes that one instead. This class has three plain references, one lambda, and three references of kinds that need help:




The second listing is the method handle each invokedynamic hands to LambdaMetafactory. String::length, prefix::concat and ArrayList::new point at String.length, String.concat and the constructor directly. The lambda gets lambda$wire$0, and so do the three that need an adapter:


  • String::format is format(String, Object...). Called through BiFunction, the second argument must be wrapped in an Object[], and lambda$wire$1 does that.
  • int[]::new has no method to point at: creating an array is a bytecode instruction.
  • super::toString must call Object.toString without virtual dispatch, which only code inside Refs may do.


A bound receiver needs no adapter. prefix is checked with requireNonNull and passed as an argument of the invokedynamic, and the function object it returns holds it, the way a lambda holds a captured value. Performance is not a reason to pick either form: both are an invokedynamic and a small hidden class, and an adapter adds one call to a small private method.


A Stack Trace Through a Method Reference Has No Frame of Its Own


The missing lambda$ method shows in stack traces. A list of codes holds a null, and a stream maps each code to its length, once with a reference and once with a lambda. show runs the code and prints the exception and its first frames:




The reference's NPE was thrown in the metafactory's hidden class, before String.length was entered, and the JVM leaves hidden frames out of stack traces. So the top frame is the stream's, no frame names our code, and the NPE has no message: the JVM computes that message from the method that threw, and here that method is hidden. The lambda's trace starts at lambda$main$1, line 12, with the message.


When the referenced method is our own, it is in the trace, and the reference adds nothing between it and the stream. parse(code) is Integer.parseInt(code.substring(1)), and here map(Traces::parse) and map(s -> parse(s)) fail on the code "Bx" (in a List.of, hence the other spliterator):



Neither trace gives the line where the reference was written. In a pipeline with five map(SomeType::method) steps, a bare NPE from a reference to a JDK method still tells you which step failed if you count: each map stage calls the next one's accept, so a failure in the third step sits on three ReferencePipeline$3$1.accept frames. It doesn't tell you the line, or what was null.


Hidden frames. -XX:+UnlockDiagnosticVMOptions -XX:+ShowHiddenFrames puts the generated frame back (Traces$$Lambda/0x….apply(Unknown Source)), and the NPE gets its message again. It is a diagnostic option for a debugging session.

A Lambda Reads Better When the Call Needs Swapped Arguments, a Constant, or a Chain


A method reference passes the interface's parameters to one method, in order. When the call needs anything else, the reference form needs a helper, and the helper moves the logic away from the call site:



String::startsWith alone does not fit a Predicate<String>: it needs a prefix that the predicate's one parameter doesn't supply.



The helpers make the reader jump to learn that one swaps its arguments, one checks a prefix and one walks two getters; the lambda says it in place. A named method is worth it when the logic has a name in the domain, is reused, or needs its own test (unit Best practices and readability considerations). For descending order, Comparator.reverseOrder() beats both. Prefer the reference for a straight pass-through (map(Order::customer), forEach(System.out::println)), and the lambda when the call has to rearrange, add or chain anything.


Summary


  • A method reference is a lambda that makes one call; the target type decides what it means. javac checks the call's shape, not its sense: max(Integer::max) compiles and returns the first element.
  • A bound receiver is evaluated once, when the reference is created. settings::limit keeps the old settings after a reload, and a null receiver throws a message-less NPE at creation; () -> settings.limit() reads the field on every call and fails only when called.
  • javac points most method references straight at the method. Of the forms above, only varargs, array constructors and super:: got a lambda$ adapter; a bound receiver is passed as a captured argument.
  • A stack trace through a method reference has no frame of its own. A reference to a JDK method that meets a null element gives a trace with no line of ours and no NPE message.
  • A lambda reads better when the call swaps arguments, adds a constant or chains calls. Use the reference for a straight pass-through.

  3. Integer::max compiles as a Comparator<Integer>. Find two other JDK methods that fit Comparator or Predicate by shape and mean something else. Would a code review catch them?


Design Note: Why a Bound Reference Evaluates Its Receiver Early


The Java Language Specification (section 15.13.3) has the receiver evaluated when the method reference expression is evaluated, and a null result throws there. Re-evaluating it on every call would make expr::m a lambda in all but syntax, and counter.next()::m would run next() once per call, hidden behind text that looks like a name. Early evaluation makes a bound reference a value: an object paired with one of its methods, fixed when made, like a lambda's captured variables.


This is the bug in the opening. Two spellings that look interchangeable read the receiver at different times, and a reviewer or an automated refactoring that shortens a lambda to a reference can change when a value is read without changing anything else on the line.
