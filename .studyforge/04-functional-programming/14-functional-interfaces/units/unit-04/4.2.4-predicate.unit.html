The seat-reservation service releases expired holds every night. Its for-each loop threw ConcurrentModificationException in staging, so it became holds.removeIf(Hold::expired). A week later the job dies in production with UnsupportedOperationException, on a night when no hold had expired. The predicate was right both times.

removeIf Is the Safe Way to Remove While Iterating, and an Immutable List Refuses It Even When Nothing Matches

Four holds, of which B1 and B2 have expired. Pause before the output: in the first list the expired holds are second and fourth, in the second they are last. What does each loop leave?

The for-each runs on the list's Iterator. remove changes the list behind it, and the iterator's next call to next() sees the change count move and throws. In the second list, removing B1 shrinks the list to three, and hasNext() only compares its position, 3, with the size, 3. The loop ends without calling next(), so nothing throws and B2 is never tested. That seat stays held for another night.

removeIf hands the loop to the collection:

Java 21's ArrayList tests every element first and then moves the survivors down once, so no element is skipped. The result says whether anything was removed.

Whether the call is allowed at all is up to the list. The List.of javadoc says every mutator throws, and the removeIf of List.of, List.copyOf and Stream.toList() throws before testing a single element. A fixed-size Arrays.asList uses the default removeIf, which removes through the iterator, so it throws only when an element matches:

The release job in the opening had been handed an unmodifiable copy of the holds. Had it been given an Arrays.asList, it would fail only on nights with an expired hold, and tests without one stay green. When the caller's list may be immutable, filter into a new list and return that.

filter Keeps Every Match; takeWhile Stops at the First false

Log lines carry the minute they were written, and two servers write them. A report wants the lines before minute 10, once from the lines sorted by minute and once from the second server's lines appended to the first's:

On the sorted list both give the same lines, and takeWhile tested 6 elements where filter tested 7. takeWhile returns the longest prefix that passes: at the first false a sequential stream stops and never tests the rest. dropWhile returns the rest, starting at that first failing element. So on the appended lines the report lost minutes 2 and 6, with no error.

takeWhile is right when the order is part of the meaning: a sorted input you want to stop reading early, or a leading run such as a file's header. Anywhere else, use filter.

Unordered streams differ. On a stream with no encounter order, the javadoc lets takeWhile return any subset of the matching elements.

asPredicate Finds the Pattern Anywhere; asMatchPredicate Needs the Whole String

A voucher code is lower-case letters followed by digits. The validator was built from the pattern:

asPredicate() tests matcher(s).find(): true if the pattern occurs anywhere in the input. asMatchPredicate(), since Java 11, tests matcher(s).matches(): the whole input must match.

Anchoring the pattern with ^ and $ and keeping asPredicate comes close, but isn't the same:

^ and $ tie the match to the ends of the input, but $ also matches just before one final line terminator, so a code with a trailing newline passes and reaches the database with it. For validation, use asMatchPredicate.

Predicate.isEqual Is Null-Safe on Both Sides; equals Called Through a Lambda Is Not

A report counts the orders in one currency from their currency codes, where null means "no currency recorded". Three ways to write it, run against Arrays.asList("EUR", null, "USD", "EUR"):

Predicate.isEqual(target) tests Objects.equals(target, t), so a null on either side is just a value, and isEqual(null) matches only null. The lambda fails at the first null element. The method reference fails earlier: wanted::equals evaluates wanted when the predicate is created, and a null receiver throws on that line, before any element is tested.

isEqual still compares with equals, so the types must match: Predicate.isEqual(1).test(1L) is false, because an Integer never equals a Long.

Optional Criteria Reduce from the Operator's Identity: x -> true for and, x -> false for or

A search form has optional fields. The service turns each filled-in field into a Predicate<Order> and combines the list:

Pause: the user fills in nothing. Which identity lists every order?

The starting value is what an empty list means, and it is combined with every element, so it must not change the answer. x && true is x, so and starts from x -> true. x || false is x, so or starts from x -> false. With the other value, and rejects every order whatever the user typed, and or accepts every order.

The version of this bug that ships is reduce(Predicate::and).orElse(x -> false): right for every form with a field filled in, and empty for the form with none.

The no statuses line follows the algebra, and the form needs something else. "Any of these statuses" with no box ticked means "don't filter on status". The or-reduction of nothing is x -> false, and ANDed with the other criteria it empties the result. Add a criterion only when its field holds something.

The concurrent set keeps one order per customer, but the thread that reached a key first wins, and in these runs that was never the first order. filter keeps the passing elements in encounter order; it promises nothing about the order in which it tests them.

A stateful predicate is safe only when it is created for one sequential pipeline and dropped with it.

BiPredicate and IntPredicate Compose Like Predicate, Without not or isEqual

BiPredicate<T, U> tests two values. Files.find takes one, so the test can read a file's attributes without a second call:

IntPredicate (like LongPredicate and DoublePredicate) tests a primitive, and is what IntStream.filter takes. Both have and, or and negate, and neither has the static not or isEqual: Predicate.not(digit) on an IntPredicate doesn't compile. Use negate():

Summary

  • `removeIf` removes safely while iterating. A for-each removal throws or silently skips the last element, and List.of refuses removeIf even when nothing matches.
  • `takeWhile` stops at the first `false`. On unsorted input it drops matches that filter keeps.
  • `asPredicate` finds; `asMatchPredicate` matches the whole string. ^...$ still lets a trailing newline through.
  • `Predicate.isEqual` is null-safe on both sides; c.equals(w) and w::equals throw.
  • Reduce optional criteria from `x -> true` for `and` and `x -> false` for `or`, and leave out a criterion whose field is empty.
  • A predicate with state answers differently on reuse and arbitrarily in parallel.
  • `BiPredicate` and `IntPredicate` have and, or and negate, but no not or isEqual.

Challenges

  1. A cleanup must remove expired entries from a list that some callers create with List.of. Do you return a new list, copy defensively, or document the requirement? What does each cost the callers?
  2. A search form has ten optional fields, and product asks for "match any field" as a second mode. Design one builder for both modes, and say what an empty form returns in each.
  3. Write distinctBy so it is safe to share, or explain why it can't be, and measure what the toMap alternative costs on 10 million elements.

Design Note: Handing the Loop to the Collection

With removeIf the collection runs the loop instead of the caller. That lets ArrayList test everything first and compact once, so no element can be skipped. It also means the caller no longer controls the loop: the collection decides when the predicate runs, how often, and whether it runs at all, as List.of does when it throws before calling it. Every method in the first reference table works this way, so a predicate passed to one should answer from its argument alone.

Problem statement


The retry scheduler keeps failed jobs in a list that it shares with the dispatcher. Before every dispatch round it should take out the jobs that have used up their attempts, so that the dispatcher stops resending them. Since the last release, some payout jobs are resent long after they gave up, and one round in a few hundred fails before sending anything.


Write dropGivenUp(...) in src/main/java/practice/RetryQueue.java. It takes every job for which gaveUp(job) is true out of the list it is given, the same list the dispatcher reads, and returns how many it took out. About three lines in total.


The tests call it with ArrayLists of jobs in various orders.

Problem statement


The shipment desk pastes tracking references from carrier e-mails into a form. A reference is two capital letters, nine digits and two capital letters, and the pattern is already in TRACKING_REF. Anything else goes back to the sender for correction, because the carrier's tracking API rejects it a day later. The desk also lists shipments by carrier; a shipment with a null carrier hasn't been handed to one yet, and the desk asks for those by passing null.


Write validRef() and byCarrier(...) in src/main/java/practice/Shipments.java. A pasted text is valid only if it is a reference and nothing else. The carrier filter must work for every carrier, null included, on a list where some shipments have no carrier. About two lines in total.

Problem statement


The issue tracker's search form has an assignee field, a minimum priority and a row of label boxes. An issue is found when it meets every field the user filled in; for the labels, carrying any one of the ticked labels is enough. The service builds one Predicate<Issue> per filled-in field and combines them in matching(...).


Finish src/main/java/practice/IssueSearch.java:


  • allOf(...): one predicate that holds when every criterion in the list holds;
  • anyLabel(...): one predicate that holds when an issue carries at least one of the labels;
  • the label criterion in matching(...).


Users search with every combination of blank and filled-in fields, the completely blank form included, which they use to see the whole board. About six lines in total.

Problem statement


The marketing dashboard shows, for each user, the page they landed on: their first visit in the time range. One VisitReport object serves the dashboard while the application runs, and the dashboard asks it for a new report every few minutes, with that period's visits in the order they happened.


Write firstPer(...) and landingVisits(...) in src/main/java/practice/VisitReport.java. firstPer(key) is a reusable building block: a predicate that passes the first element it sees for each key and rejects the ones after it. landingVisits uses it to list each user's first visit, in the order the visits happened. About four lines in total.
