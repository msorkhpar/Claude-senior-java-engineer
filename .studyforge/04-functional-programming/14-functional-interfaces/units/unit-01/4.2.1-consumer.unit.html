The nightly customer import counts its rows and writes one audit line per row. On a test file of four rows the count is right and the audit is empty. The line that does both jobs:

peek takes a Consumer, and the stream never called it. Consumer<T> is the java.util.function interface for "do something with this value": one abstract method, void accept(T t), and a default andThen. You write the side effect; the code you pass it to decides when, how often, in what order and on which thread it runs. The page has four rules, one per heading.

A Consumer Is Called for Its Side Effect, and Whatever the Lambda Returns Is Dropped

accept returns void, so a Consumer exists only for what it changes, such as a collection or a log. It declares no checked exceptions either (unit Throwing exceptions using the throw keyword covers that case). An event handler remembers the ids it has seen. Pause before the output: after the third call, has anything told us that evt-17 was a repeat?

Nothing did: Set.add returned false and the Consumer dropped it. seen::add, like s -> seen.add(s), compiles as a Consumer because a void target may discard the result of a method call (unit Syntax and structure of lambda expressions). If the caller needs the result, the step is not a Consumer; make the call where its result is read:

Chain a notifier after seen::add and subscribers hear about evt-17 twice, because the only thing that knew it was a repeat was the discarded false.

The JDK takes a Consumer where it iterates for you or hands you a value that may be absent. Iterable.forEach calls it once per element. Map.forEach takes a BiConsumer<K, V> and calls it with each key and value, in the map's iteration order (sorted here, because it is a TreeMap). Optional.ifPresentOrElse takes a Consumer for the value and a Runnable for its absence:

IntStream.forEach takes an IntConsumer, whose accept(int) needs no boxing, and ObjIntConsumer<T>, with accept(T, int), is the accumulator of IntStream.collect:

andThen Runs the Steps in Order, and Stops at the First One That Throws

first.andThen(second) returns a Consumer that calls first.accept(t), then second.accept(t) with the same t. If either throws, the exception reaches the caller, and if first throws, second never runs. The parameter is a Consumer<? super T>, so a Consumer<Object> logger can follow a Consumer<Order>.

An order service reserves stock and emails a confirmation. Order A-100 asks for 9 items and 5 are in stock. Before reading the output, decide which of the two chains sends an email:

The caller gets the same exception from both chains, but the second has already told a customer that an order nobody can ship is on its way. andThen is a sequence, not a transaction: a step that has run stays done when a later step throws. Put the step that can refuse first, and the step that can't be taken back (an email, a payment, a message to another system) after everything that can fail.

A Null Step Fails When the Chain Is Built, Not When It Runs

An extra hook is configured per deployment, and staging has none:

The third frame is the andThen line. pipeline built never prints: andThen only composes, calls neither step, and checks its argument with Objects.requireNonNull before it returns. For a step that must exist, that is what you want: a service with a missing hook fails at startup, not on the first order an hour later. For an optional step, decide explicitly, with extraHook == null ? confirm : confirm.andThen(extraHook), or a do-nothing t -> {} (the JDK has no ready-made no-op Consumer).

    Stop confirming orders the shop can't fill

    • a.andThen(b) runs a, then b, on the same value, and if a throws, b does not run and the exception reaches the caller; so the step that can refuse goes first and the irreversible one last.
    • andThen(null) throws NullPointerException when the chain is built, not when it runs, so an optional step needs an explicit choice.

A Stream Calls Your Consumer Only for the Elements It Needs, and peek May Not Run at All


Back to the import. peek(action) is an intermediate operation: it calls the Consumer as each element passes through, if it passes through. Four sequential pipelines over the same four rows, each with its own LongAdder:




count() on a list's stream knows the answer from the list's size. Its javadoc lets the implementation skip the pipeline in that case: "no source elements will be traversed and no intermediate operations will be evaluated". A filter hides the size, so the second pipeline ran every row. map and sorted keep the size, and map(...).peek(...).count() skips peek the same way. findFirst pulls one element and stops, so peek ran once. A stream with no terminal operation runs nothing.


A refactor that removes a filter can therefore turn the audit off without a test noticing. The javadoc says peek "exists mainly to support debugging", but nothing switches it on or off: these runs used no flags, and the skip comes from count() alone. A side effect that must happen once per element goes in the stream's terminal forEach, or, as here, in Iterable.forEach beside the stream:




Java 8 differs. Java 8's count() traversed the stream, so a peek before it ran. The skip, and the javadoc note that allows it, came with Java 9, which is how code like the import's stops auditing after an upgrade.

On a Parallel Stream, forEach Calls the Consumer from Several Threads, in No Order


Stream.forEach promises no order, and on a parallel stream it calls the Consumer from whichever worker thread holds the element, several at once. forEachOrdered calls it one element after another, in the source's order:




forEachOrdered may still call the Consumer on different threads, but each call happens-before the next, so b needs no lock; a does. What happens without one? Here 10,000 numbers go into an ArrayList from a parallel forEach, five times:




Up to a third of the elements are lost, with no exception. ArrayList.add reads the size, writes the slot and stores the new size. Two threads that read the same size write the same slot, and one element is lost. When the array grows during a race, the same code can throw ArrayIndexOutOfBoundsException instead. With ten elements it failed in about one run in six, so the unit test is flaky rather than red.


The fix is to let the stream build the result, so that no thread touches a shared list:




collect(Collectors.toList()) does the same. When the Consumer writes to something that is not thread-safe, such as a file writer, compute in parallel and collect, then hand the result to the Consumer from one thread, or use forEachOrdered. A thread-safe target, such as a ConcurrentLinkedQueue, or a lock around the Consumer, as for a above, keeps every element and still gets them in no order: 5,000 ids added to a ConcurrentLinkedQueue this way came out 5,000 strong, in a different order on each of five runs.

Summary


  • A Consumer is for its side effect. A lambda or method reference such as seen::add that returns a value still compiles as a Consumer and the value is dropped, so a step whose result matters is not a Consumer.
  • andThen runs the steps in order and stops at the first throw. Steps that already ran stay done, so the irreversible step goes last; a null step fails when the chain is built.
  • A stream calls a Consumer only for the elements it needs. peek may run for every element, one, or none (count() on a sized stream), so a required side effect goes in the terminal operation.
  • A parallel forEach calls the Consumer from several threads in no order. A target that is not thread-safe loses elements silently; collect instead, or use forEachOrdered.

Challenges


  1. A team wants "log every element" in a pipeline that ends in count(). Compare peek, a filter that always returns true, and logging in a separate loop: which still logs after a refactor, and which would you accept in review?
  2. You compose six handlers with andThen, and one of them, a metrics push, fails once a day. Design the chain so that failure never blocks the others, without hiding the failures of the steps that matter.
  3. Measure how many elements a parallel forEach into an ArrayList loses for 1,000, 10,000 and 1,000,000 elements on your machine. Which size do unit tests usually use, and what do they see?


Design Note: Why the Stream Library May Skip Your Consumer


A stream describes a result, not a sequence of calls. That lets the library fuse operations, stop early for findFirst, split the work across threads, and skip the traversal when the source already knows the answer, as count() does. Each of those freedoms assumes the operations have no effects the caller depends on. peek and forEach are where a Consumer enters that model, and the library treats them on its own terms: peek as a debugging hook it may never call, forEach as an action whose order and thread it chooses.


The cost falls on code that treats a stream as a loop. A loop promises one call per element, in order, on your thread; a stream promises the result of its terminal operation.
