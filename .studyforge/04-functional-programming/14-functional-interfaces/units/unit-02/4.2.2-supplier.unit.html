The pricing service builds one Supplier<RateTable> at startup and hands it to every request handler, "so the rate table loads lazily, once". The database dashboard shows the rates query running 1,200 times a minute, about once per request. No handler calls the query directly.

Six rules, one per heading, say what Supplier<T> and its one method, T get(), promise and what they don't.

A Supplier Runs Its Body on Every get() and Remembers Nothing

Wrapping a computation in a Supplier defers it to get(), and runs it on every get(). The code below calls get() three times. How many queries reach the database?

Creating the lambda ran nothing; each get() ran the body again and returned a new table. The interface has no field to keep a result in, and its javadoc says there is "no requirement that a new or distinct result be returned each time the supplier is invoked". So every handler's get() paid for the query, and two get() calls in one method worked on two different tables. Code that wants the result once calls get() once and keeps the value, or wraps the supplier in a memo.

A Memo Written as Check-Then-Compute Loads Twice When Two Threads Arrive Together

The obvious memo keeps the result in a field. Spot the problem:

On one thread it loads once. At startup many handler threads ask for the table together, and two can pass (1) before either reaches (3); both then run (2). The test below forces that without sleeps. race(name, memo) wraps a load in memo, here NaiveMemo::new, and calls it from two threads. The load counts itself in loads, then waits (up to a second) on a latch until the other caller is inside the load too, as a slow query would.

The pair of tables varies from run to run (rates#1 and rates#1 also came up), because which write to value each thread reads last is a race too. On a cold start every thread that arrives during the first load runs its own, which a rate-limited upstream rejects, and two requests in the same second can price from two versions of the table.

A memo whose get() runs cached.compareAndSet(null, source.get()) on an AtomicReference and returns cached.get() fixes only the inconsistency: in the same test both callers always saw the same table, and the load still ran twice.

A Safe Memo Chooses What It Pays: a Lock, Class Initialisation, or Startup Time

Three forms load exactly once.

Double-checked locking. The first check skips the lock once the value exists. The second, under the lock, stops a thread that waited for the lock from loading again:

The same test, with LockedMemo::new:

The second caller blocked on the lock until the first load finished (after its one-second latch timeout), then found done set. Without volatile, the first check would read done with no lock and no ordering, and a reader could see done == true before it sees the write to value (reordering is unit Reordering and optimization by the compiler and runtime). The separate done flag also lets the memo keep a null result; a memo that tests value == null loads again on every call when the source returns null.

The holder class. For a value that belongs to a class rather than an object, the JVM already has a lock that runs code once: class initialisation. A nested class is initialised the first time it is used, and every other thread that uses it meanwhile waits for that to finish:

No lock, no volatile, and later reads are plain field reads. The price comes on failure. With the database down we call Rates.table() and a LockedMemo of Rates::loadRates, then bring the database back and call both again:

A class whose initialiser threw is marked as failed, and the JVM never runs it again. Every later table() throws NoClassDefFoundError until the process restarts, so a database that was down for one second at startup takes the service down until someone redeploys.

Computing eagerly. A final field set in the constructor, or a static final field, needs no memo: the value exists before any thread can ask for it. It pays when the object or class is created, usually at startup, even in deployments that never read the table, and a failed load fails there too. That is often what you want, since a service that can't price shouldn't accept requests.

Choose by what a failure should do. A value the service can't work without is loaded eagerly and fails the startup. A value that is optional, or whose source may recover, goes behind double-checked locking. The holder class fits a static value whose load can't fail, or whose failure should end the process anyway.

The JDK Takes a Supplier Where the Work May Not Be Needed

Several JDK methods take a Supplier for a value they need on one path only. The common one is a null check's message. An order validator builds a detailed message with describe(order), which formats the whole order and counts itself in built:

Java evaluates arguments before the call, so the String overload formats a message for every valid order. The Supplier overload builds one only when the check fails: two messages instead of a million for a validator that runs a million times an hour and fails twice. The javadoc warns that the supplier has a cost too: this lambda captures o, so creating it is an allocation, and for a constant message the String overload costs less.

Optional.orElseThrow(Supplier) does the same for an exception: on a hit the supplier never runs, and no exception, with its stack trace, is created. Optional.orElse against orElseGet, and loggers that take a Supplier<String>, follow the same idea; unit Best practices and readability considerations runs both. CompletableFuture.supplyAsync(Supplier) is a different use: it calls get() later, on a pool thread (concurrency is part 6).

A Factory Supplier Must Return a New Object on Every Call

The other use is a factory: the method calls get() each time it needs a fresh object. Collectors.toCollection takes one, and TreeSet::new makes a new sorted set per group. A sales report groups SKUs by region; the second version passes a lambda that returns a list it already made:

groupingBy called the supplier once per region and added each sale to the list it got back. Both regions got the same list, so each shows every sale. Nothing failed: it compiles, and with one region in the test data the output is right.

ThreadLocal.withInitial(Supplier) is a factory on another schedule: it calls the supplier on a thread's first get() and keeps the result for that thread.

SimpleDateFormat's javadoc says it isn't synchronized and recommends an instance per thread, which is what the supplier gives, as long as it returns a new one.

Stream.generate(Supplier) calls get() once per element, and its javadoc calls the stream it returns "infinite". Only a short-circuiting step such as limit ends it:

Summary

  • A `Supplier` runs its body on every `get()` and keeps nothing. Wrapping a load in one defers it; it doesn't make it happen once.
  • A check-then-compute memo loads twice under contention, and the compareAndSet memo keeps one result but still loads twice.
  • A safe memo chooses its cost. Double-checked locking needs volatile and retries after a failure; the holder class needs no code but turns one failed load into NoClassDefFoundError until restart; loading eagerly pays, and fails, at startup.
  • The JDK takes a `Supplier` for work it may skip: requireNonNull's message, orElseThrow's exception.
  • A factory supplier returns a new object per call. () -> shared makes every group or thread share one object; Stream.generate never ends without limit or another short-circuit.
  • Primitive suppliers are separate interfaces, adapted with a method reference.

Challenges

  1. A memo holds a token that expires after an hour. Extend LockedMemo to reload it, and decide what callers get while one thread reloads: the old token, or a wait.
  2. The upstream allows one rate-table request per second. Measure how many loads each memo form makes when 200 threads start together, and how long the slowest caller waits.
  3. Your library takes a Supplier<Connection> from its caller. Write down, in its javadoc, how often you call get() and whether the caller may return the same object each time.

Design Note: Why Supplier Has No memoize()

Function has andThen and Predicate has and, but Supplier has no default methods at all, and Java 21's JDK has no memoizing supplier. A memo has to settle what this page shows has no single answer: whether a failure is remembered or retried, whether null is a value, whether a waiting caller blocks, and whether the value ever expires. The JDK left those choices to the caller; the cost is that each codebase writes its own memo.

Problem statement


The FX service prices every request from a rate card it fetches from an upstream that answers slowly and allows a handful of requests a minute. The card is wrapped in one shared Supplier<RateCard> that all request threads call. After a deploy the upstream rejected the service for a minute: the first burst of requests had each fetched the card. Some desks have no card at all, and their source answers null. When the upstream is briefly down at startup, the service must keep trying on later requests rather than stay broken, and it must start without calling the upstream.


Write get() in src/main/java/practice/Once.java, adding the fields it needs. When you're done, the source runs once for all threads, on the first request, whatever it returns, and a load that throws is tried again by the next caller. About twelve lines in total.


The tests call get() from a thread pool, and hold a load in progress with a latch while a second caller arrives.

The outdoor-gear chain's nightly report says which products sold in which region. Several report threads share one RegionReport, and to save allocations each thread renders into a buffer it keeps between reports. The test data had a single region and the report looked right; the first real night, regional managers complained that their section listed products they don't stock, and one report came out with half of another report's lines in it.


Finish skusByRegion and newScratch in src/main/java/practice/RegionReport.java. Each region lists only its own SKUs, sorted and without repeats, and each rendering thread has a buffer that no other thread touches and that it reuses from one report to the next. About three lines in total.
