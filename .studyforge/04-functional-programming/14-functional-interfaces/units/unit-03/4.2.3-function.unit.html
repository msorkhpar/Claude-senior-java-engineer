A checkout service prices a basket in one statement:

In its first week in production two customers got an error page. One basket was [AB-1, CD-2, AB-1], the same SKU twice; the other was [AB-1, ZZ-9], with a SKU the catalogue had just dropped, for which priceOf returns null.

The failures come from what the JDK does with a function's result, or with a function of the wrong interface type; one rule per section. How andThen and compose order their steps, and the primitive specialisations, are in unit Using lambda expressions with functional interfaces.

UnaryOperator<T> Is a Function<T, T>, but a Function<T, T> Is Not a UnaryOperator<T>

UnaryOperator<T> extends Function<T, T> and adds no abstract method. BinaryOperator<T> extends BiFunction<T, T, T> the same way. Some JDK methods ask for the narrower type: List.replaceAll takes a UnaryOperator<E>, Stream.reduce a BinaryOperator<T>. Pass replaceAll a function that is already in a variable:

The same lambda written inside the call compiles. A lambda has no type of its own: it takes the type the call expects (unit Introduction to lambda expressions), so skus.replaceAll(s -> s.strip().toUpperCase()) creates a UnaryOperator<String>. The variable clean already has a type, and Function<String, String> is the supertype. Java's functional interfaces are named types, so two interfaces with the same method shape are still two types, and a value converts only to a supertype. A BiFunction<Integer, Integer, Integer> handed to reduce(0, add) fails the same way, and so does skus.replaceAll(Function.identity()), because identity() returns a Function.

A cast silences the compiler:

It compiles because a Function variable could hold a UnaryOperator. It fails at run time because the object behind clean was created as a Function and implements nothing else. Either declare the variable as UnaryOperator<String>, which still goes anywhere a Function<String, String> is accepted, or adapt it with a method reference, clean::apply, which creates a new UnaryOperator that calls clean. For a no-op, use UnaryOperator.identity().

Collectors.toMap Throws on a Duplicate Key or a null Value Until You Say What to Do

toMap(keyMapper, valueMapper) won't choose between two values for one key, and it won't store a null value at all. Those are the two failures from the start of the unit.

Where HashMap.put would silently keep the second value, the collector throws IllegalStateException, as its javadoc says. A repeated key usually means the key isn't what you thought it was: here the basket needs a quantity, and dropping one of the two lines would undercharge.

The third argument, a BinaryOperator<U>, gets the value already collected and the new one, and returns the one to keep. It doesn't help with null:

The three-argument form collects through Map.merge, which rejects a null value too. Deal with the null before the collector: filter the SKU out, or, here, reject the basket with a message that names the SKU the catalogue no longer prices.

A Merge Function Picks a Winner, and the Last One Seen Isn't Always the Newest

A price feed sends a SKU again whenever its price changes, with a version number. The service keeps one price per SKU. Two merge functions look equivalent:

The feed held AB-1 at version 7, then 9, then 8:

(older, newer) -> newer keeps whatever arrived last. That is the newest only while the feed arrives in order, and one retried message breaks that. BinaryOperator.minBy and maxBy turn a Comparator into a merge function that decides by the data.

Ties. The javadoc of minBy and maxBy doesn't say which operand wins when the comparator returns 0. On Java 21 both return the first one, the value already in the map. If a tie can happen, add a tie-breaker with thenComparing rather than rely on that.

Function.identity() or x -> x

Function.identity() and sku -> sku give the same map as key mappers: the checkout prints {CD-2=899, AB-1=1250} with either. On Java 21, identity() returns the same object every time, which its javadoc doesn't promise, and UnaryOperator.identity() is a different one:

Pass the one whose type the call asks for. Whether two lambdas are the same object is unit Introduction to lambda expressions's subject, and no code should depend on it.

A Remapping Function That Returns null Removes the Entry

Map.compute, computeIfPresent and merge take a BiFunction and store what it returns, except null, which removes the key. A stock service reserves one unit of a SKU, and returns null to mean "nothing left, do nothing":

The second reservation found zero units and deleted the SKU. A stock report no longer lists it, a bulk update such as replaceAll no longer reaches it, and every caller that unboxes stock.get(sku) throws. To leave an entry as it is, return the value you were given: left > 0 ? left - 1 : left.

This makes "update, or remove when done" one call. In a ConcurrentHashMap that call is atomic, so a counter can drop its key at zero without a race between the decrement and the remove. Return null only to remove.

When the key is absent, merge stores the value you pass without calling the function. merge("ZZ-9", -1, Integer::sum) on an empty map leaves {ZZ-9=-1}, a count below zero for something that was never counted.

A null Halfway Through an andThen Chain Fails in the Next Step; Optional.map Stops There

A shipping label takes an order's customer, the customer's address, and the address's city. An order collected in the store has a customer with no address:

andThen passes each result to the next step without looking at it. Customer::address returned null, Address::city was called on it, and the exception has no message. Because the steps are method references, no frame of theirs appears either: the trace stops at the JDK's andThen. Written as lambdas, the steps would add a frame and a helpful message, but still at the step after the one that returned null. Checking the order for null before apply doesn't help, because the null appeared in the middle. Optional.map does check after every step:

A step that returns null turns the Optional empty, and the steps after it don't run. Use this when a missing value is a normal case, like a pickup order. When it is a bug, the empty Optional hides which step was missing: fail at that step instead, with Objects.requireNonNull(value, message) naming what was absent.

A Memoized Function Must Be Pure, and Its Computation Must Not Go Back Into the Map

key -> cache.computeIfAbsent(key, slow) caches the function slow in one line; in the run, three lookups of two keys ran slow twice. That only works for a pure function: a cached price lookup keeps its first answer after the price changes. Recursion breaks it:

With a new ConcurrentHashMap for each call:

computeIfAbsent holds the key's slot in the table while the function runs, and the function here inserts other keys into the same map. The javadoc forbids it: "The mapping function must not modify this map during computation", but the map throws only when it notices. Here the twelfth entry, for 13, made the table grow while the computation for 14 still held its slot, and the resize found it. A unit test of fib(10) passes. A HashMap notices at once and throws ConcurrentModificationException. Unit Best practices and readability considerations covers functions that change their own map in general.

The fix is to recurse with no computation in progress: look the key up, compute the value outside the map, and store it with putIfAbsent.

Two threads may now compute the same key; for a pure function that costs only time.

A null result isn't cached. If the function returns null, computeIfAbsent records nothing, so the function runs again on the next call:

For a lookup that is slow because it goes to another service, the unknown keys are the expensive ones. Cache the absence too, for example as an Optional.

Summary

  • A `Function<T, T>` variable is not a `UnaryOperator<T>`. A lambda takes the type the call asks for; a variable doesn't convert, and a cast compiles and then throws ClassCastException.
  • `Collectors.toMap` throws on a duplicate key and on a `null` value. A merge function decides duplicates (maxBy by the data, not by arrival order); null values have to be dealt with before the collector.
  • A remapping function that returns `null` removes the entry. Return the old value to leave it, and remember that merge stores its value for an absent key without calling the function.
  • A `null` in the middle of an `andThen` chain fails in the next step, not in the step that returned it. Optional.map stops at the first null.
  • A memo built on `computeIfAbsent` needs a pure function that doesn't recurse into the map, and it doesn't cache null.

Challenges

  1. A toMap over orders keyed by customer id throws on a duplicate in production. Is the fix a merge function, groupingBy, or a different key? What does each choice do to the totals a finance report reads?
  2. Your memo wraps a remote lookup that sometimes returns null for "not found yet". How long should the absence stay cached, and what in your cache expresses that?
  3. Measure how long computeIfAbsent on a ConcurrentHashMap holds other writers back when its function takes 50 ms, for writers to the same key and to other keys.

Design Note: Why Java Has Both Function<T, T> and UnaryOperator<T>

Java 8 added function types as ordinary named interfaces, not as a new kind of type. That let Runnable, Comparator and every single-method interface already written accept lambdas without change, and it gave each interface a place for its own helpers: BinaryOperator.minBy, UnaryOperator.identity(). The cost is that two interfaces with the same shape are unrelated unless one extends the other, so a Function<T, T> can't go where a UnaryOperator<T> is asked for, and java.util.function needs 43 interfaces where a language with structural function types needs one arrow. Accept the widest type in your own parameters (Function<? super T, ? extends R>, unit Using lambda expressions with functional interfaces) and declare your variables as the type the API you call asks for.

Problem statement


The depot's sorter sends each parcel to a bin by the first two characters of its postcode. Since the depot started accepting parcels before the recipient's details are complete, the sorter stops dead now and then with a NullPointerException, and every parcel behind the one it choked on waits. Those parcels should go to the HOLD shelf instead, and the rest should keep moving.


Sorting already has the three steps from a parcel to its postcode, and binFor(...) turns a postcode into a bin. Finish the TODO in src/main/java/practice/Sorting.java: postcodeOf(...) returns the parcel's postcode, or nothing when the depot can't route the parcel yet, whichever of its parts is missing. About four lines.

Problem statement


The shipyard's planning tool asks the same slow questions over and over: what a hull section costs (its own work plus the section it is welded onto), who owns a berth (a call to another service that answers null for a berth nobody has leased). Memo wraps such a function so each key is computed once, and the tool already uses it everywhere.


Finish the TODO in src/main/java/practice/Memo.java: apply(key) answers from the cache, or computes the answer once and remembers it. The function you wrap may call the same Memo for other keys while it computes, and a null answer is remembered like any other. You may change the declaration of the cache. About seven lines.
