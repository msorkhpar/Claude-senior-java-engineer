A Lambda Is an Object of Whatever Interface Its Context Expects

A lambda has no type of its own. The same text becomes an instance of whichever functional interface the place it appears in asks for, its target type. Here Greeting is a one-method interface of our own, String text():

The Callable is not a Supplier, although its body is the same. A cast, (Supplier<String>) c, compiles, since one interface type may be cast to another, and throws ClassCastException when it runs. Where nothing names an interface, there is no lambda:

The interface's single abstract method also gives the lambda its parameter types and return type. Which contexts supply a target, and what to do when two overloads both could, is unit Syntax and structure of lambda expressions; the interfaces themselves are unit Using lambda expressions with functional interfaces.

The Compiler Turns a Lambda Into a Private Method and an invokedynamic Call

A lambda is often described as a shorter anonymous class. Jobs holds one of each:

The anonymous class is Jobs$1.class, created with new; the lambda has no file. Its body became lambda$main$0, a private method of Jobs, and the place where it stood became an invokedynamic. The first time that instruction runs, the JVM calls its bootstrap method, LambdaMetafactory.metafactory (listed in javap -v under BootstrapMethods), which spins a hidden class implementing Runnable whose run() calls lambda$main$0. That class's name, Jobs$$Lambda/0x…, is what toString(), a heap dump or a profiler shows, and it is not stable between runs. Stack traces hide it and show lambda$main$0.

  1. Concept check

    Check yourself: what a lambda is

    • An int[] or AtomicInteger holder gets around the effectively-final rule; the array loses updates under a parallel stream, AtomicInteger contends, and a stream reduction needs no shared state.
    • Whether evaluating a lambda gives a new object is unspecified; on HotSpot a non-capturing lambda from one site is reused and a capturing one is new, so code must not rely on either.
    • javac compiles a lambda body into a private lambda$ method of the enclosing class and the lambda site into invokedynamic; it writes no class file, unlike an anonymous class.
    • A lambda is an instance of the functional interface its context expects; the same text gives objects of unrelated interfaces, and a cast between them fails at run time.

A Lambda Copies the Locals It Uses, So They Must Be Effectively Final

A retry job counts what it resent, and a report names its region:

The second error is on a line that only reads region: a second assignment anywhere, even after the lambda, makes the local not effectively final. This factory returns a lambda that outlives the call that made it:

When eu.get() runs, label's stack frame is gone. The lambda object carries a copy of region in a final field and passes it to the private method (javap -p shows lambda$label$0(java.lang.String)). A copy can't follow later assignments, and the lambda may run on another thread. So Java refuses to capture a variable that is assigned again, rather than let the copy and the variable disagree. What is copied is the value: for a reference, the reference. The object it points to can still change, and the lambda sees the change.

That is how the usual workaround works: a one-element array or an AtomicInteger is effectively final, and the lambda changes the object inside. It compiles, but under a parallel stream:

The array lost most of its updates, a different number each run, with no error. hits[0]++ reads the element, adds one and writes it back, so two threads that read the same value write the same result. forEach returned only after every element was processed, as the AtomicInteger total shows. AtomicInteger is correct, but every thread fights over one memory location. Letting the stream compute the result (count(), sum(), a collector) needs no shared state at all. Unit Best practices and readability considerations has more on side effects in lambdas.

A Lambda Adds No Scope: this and Every Name Mean What They Mean Outside It


An anonymous class is a class: its body is a new scope, with its own this and its own inherited members. A lambda's body is in the scope of the method around it. A Widget whose toString() returns Widget[cpu-load] hands out both:




In the anonymous class, even the unqualified toString() found the anonymous object's own method, inherited from Object. In the lambda, both mean the widget, because the body is now lambda$lambda$0, an instance method of Widget. A lambda that uses this (or any field or instance method) captures the enclosing object, and reads its fields when it runs, not when it was made. In a Gauge:




No new scope also means a lambda can't reuse a name the method already has. An anonymous class's apply(String id) may shadow a local id; the lambda can't, as a parameter or a local:

A Lambda's Identity Is Not Promised: Keep the Instance You Need to Find Again


Each time a lambda expression is evaluated, the runtime decides whether to make a new object. On HotSpot, a lambda that captures nothing comes back from the same site as the same object every time, and one that captures anything is allocated fresh:




The Java Language Specification (§15.27.4) allows a new object or an existing one, so code must not depend on either. Lambdas don't override equals, so equals is ==, and two lambdas with the same text, or the same lambda evaluated twice with the same captured value, are not equal.


Now the opening problem. close() evaluates a different lambda expression from open(): another class, so another object, which the feed's list has never seen, and unsubscribe removes nothing. Even one shared site wouldn't help, because q -> onPrice(q) captures this and is new each time. Keep the instance:




Every leaked listener also holds its widget, through the captured this, so the heap keeps 10,000 widgets too. For the same reason a lambda is no use as a map key (found only with the instance that was put in) and as a lock: a non-capturing lambda may be one object shared by every caller, and a capturing one is a different lock for each.

Summary


  • A lambda is an object of the interface its context expects. With no target type there is no lambda, and the same text gives unrelated types in different places.
  • The compiler makes a private method and an invokedynamic, not a class file. The class is spun at run time by LambdaMetafactory, hidden, with an unstable name.
  • Captured locals are copied, so they must be effectively final. A mutable holder gets around the rule and loses updates under concurrency.
  • A lambda adds no scope. this is the enclosing object, its fields are read when the lambda runs, and a lambda can't shadow a local.
  • Lambda identity is unspecified. Keep the instance you subscribed; never compare lambdas, key a map or lock on one.

Design Note: Why Java Captures Values, Not Variables


JavaScript lets a closure assign to the variables around it, so those variables must live on the heap whenever a closure might capture them. Java keeps locals on the stack and copies what a lambda captures, which makes a lambda an object with final fields and nothing else. The price is paid by code that wants a shared counter: the int[] holder moves the variable to the heap by hand, and takes on the thread-safety problem the rule kept out.
