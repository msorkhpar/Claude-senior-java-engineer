A Long Lambda Is a Method Without a Name, and Its Stack Frame Shows It

Two versions of the invoice total, run on a line whose discount is null (the program prints the first three frames):

javac compiles a lambda body into a private method named after the enclosing method and a counter (unit Introduction to lambda expressions). The trace gets that name and a line number, and neither says which rule failed. netAmount does, without opening the source at the right revision, and a test can call it on one Line without building a stream.

Once a lambda has a block body with its own local variables, treat it as a method: name it and pass it by method reference (units 4.3.x). A lambda whose whole meaning fits on the call site (line -> line.qty() > 0) stays inline.

Spot the Problem: a Price Memo That Fails Only When a Bundle's Parts Are Unpriced

prices is a HashMap memo, parts maps a bundle to its SKUs, and base holds unit prices:

price("cable") returns 9. Then price("kit"), a cable plus a charger:

Pricing the charger inserted it into the same map while computeIfAbsent was running. Map's javadoc says the mapping function should not modify the map, and since Java 9 HashMap throws when it detects it, on a best-effort basis. The memo passes any test whose parts were priced first, because then nothing is inserted. Compute the value outside the map, then put it.

State a Lambda Changes Through an Array or a Field Is Shared by Every Invocation

A lambda can't assign a captured local (unit Introduction to lambda expressions), so count++ doesn't compile and a one-element array does. A quarter of a million rows out of a million are rejected:

The array reference is final; its contents are not. Every invocation of the lambda writes the same slot, and a parallel stream invokes it from several threads with no synchronisation, so increments are lost (20 cores; the loss varies by run). A field is shared by every call of the method too: counts add up across runs, or one caller resets another's. Let the library count (count(), a collector, units 4.4.x), or keep the state local to one call on one thread.

A Lambda Keeps Its Object Alive Only When It Uses this or an Instance Member

A 50 MB report screen registers a listener in a static list, then closes. One listener reads the screen's topic field, one calls its label() method, and one, in a third method, uses a local copy of topic:

We drop the screen, call System.gc(), and print whether a WeakReference to it was cleared and the types of the listener object's fields:

A lambda captures what its body uses (unit Introduction to lambda expressions). An instance field or method used without a qualifier is used through this, so the lambda holds the whole screen, and the static list keeps 50 MB reachable for every screen that closed. A lambda that uses only locals and parameters holds no this. System.gc() is only a request, so a test of this asks more than once.

Summary

  • A long lambda is a method without a name. Its frame reads lambda$method$0; a named method tells the trace and the test which rule ran.
  • The receiver decides when, how often and whether a lambda runs. orElse evaluates its argument every time; a mapping function that inserts into its own HashMap throws.
  • State changed through an array or a field is shared by every invocation. On several threads, increments are lost; a field also carries over between calls.
  • A lambda holds `this` only when it uses `this` or an instance member. Registered somewhere long-lived, it keeps its whole object alive.

Challenges

  1. Your team's rule is "lambdas at most three lines". Write a two-line lambda that should still be a named method, and a five-line one that shouldn't.
  2. A ConcurrentHashMap memo prices a bundle from its parts. Read its computeIfAbsent javadoc: what may the mapping function do, and how would you structure the memo?
  3. A listener has to call an instance method of its owner. How do you register it without keeping the owner alive, and who unregisters it?

Design Note: Why a Lambda's Frame Has No Useful Name

Java gives a lambda no name of its own, which suits code short enough that the call site explains it. The method javac generates exists only to hold the body, so its name records where the body was, not what it means. The cost falls on whoever reads traces and heap dumps later, and catching a long lambda in review costs less than reading its trace in production.
