A Lambda's Parameters Are All Inferred or All Declared

One list can't mix the forms:

An annotation or final needs a declared type or var: (@Trimmed s) -> s and (final s) -> s are syntax errors. var exists to allow them, and still counts as inferred.

Java 22 differs. (s, _) -> s marks an unused parameter. Java 21 rejects it ("unnamed variables are a preview feature and are disabled by default"); it is standard from Java 22.

A Body's Shape Decides Whether It Returns a Value, Nothing, or Either

An expression body returns its value. A void target accepts only a statement expression (a method call, an assignment, ++, new Foo()) and discards its value. So a call like seen.add(...) fits both kinds of target:

A block body is void-compatible when no return in it carries a value, and value-compatible when every return carries one and control can't reach the closing brace. javac names each mismatch:

somePaths falls off its end for a two-letter string. A block that can't reach its end and has no return, because it throws or loops forever, is both void- and value-compatible.

When a body fits both and its parameter types are known (declared, or there are none, as here), the compiler prefers the interface whose method returns a value. submit does the same:

An Implicitly Typed Lambda Can't Choose Between Overloads of the Same Arity


Back to the library. With both onMessage overloads:



m's type depends on the overload being chosen, so for an implicitly typed lambda javac checks only the body's shape. An expression body might return a value, so it fits both, even System.out.println(m). A block rules one out. Without declared types the value-returning preference doesn't apply, so the call is ambiguous. (var m) -> ack(m) is ambiguous too.



Declared types let the compiler check the body: a boolean isn't an Ack, so only Consumer fits the first; ack(m) fits both, and the value-returning one wins. A cast names the target directly. These fix one call site; only a new name fixes every caller. The JDK's comparingInt and mapToInt are separate names: a replica that overloads by(ToIntFunction) and by(Function) makes by(s -> s.length()) ambiguous.

Summary


  • Parameters are all inferred or all declared. var allows annotations and final, but to overload resolution it is still inferred.
  • A body's shape decides what it can return. A statement expression that has a value fits both void and value targets; a block that can reach its end returns nothing.
  • When a body fits both, the value-returning overload wins, so braces can turn submit(...).get() from a value into null.
  • An implicitly typed lambda can't choose between same-arity overloads. Declared types or a cast fix one call; only a distinct method name fixes every caller.
  • A lambda can't implement a generic method. Use a method reference, a class, or a generic interface.

Design Note: Overloads Are Chosen Before Inferred Bodies Are Checked


For an implicitly typed lambda, javac picks the overload from the arity and the shape of the body, and only then types the body, once, against one target. Typing it against every overload, with each candidate's parameter types, would multiply the work for nested lambdas, and an edit deep in a body could move the call to another method, which already happens for declared types. The price is this unit's ambiguity, and it falls on API designers.
