The plant dashboard's "first three alarms" panel, most severe on top, ran for a year against the nightly export of sensor readings. Pointed at the live feed, the request never returns, and the service's heap climbs until the container is killed:

Each call between the source and toList() is an intermediate operation. Most pass an element on at once; a few can't, and that difference decides what this code does. Every output below is from Java 21.

map Gives One Result per Element; flatMap Splices a Stream per Element into One

An order holds a list of SKUs, and the picking screen needs the SKUs. How many elements does each stream hold?

map calls its function once per element and passes on what it returns, so three orders give three lists, and the screen reports three items to pick where there are five. flatMap expects a stream from its function and passes on that stream's elements, one after another: two, none, three. The order without SKUs contributes nothing instead of an empty list.

Because a stream can hold zero elements, flatMap is also how a pipeline drops missing values. emailOf(customer) returns an Optional<String>, and c-2 has no address:

Optional.stream() has one element or none. Unwrapping with orElse(null) instead would put a null in the list, and the mailer would fail on it later, far from the lookup.

A function given to flatMap may return null: the javadoc says an empty stream is used instead. The same null returned to map stays in the stream as an element:

Return Stream.empty() anyway: a reader of the code shouldn't need that javadoc sentence.

map Stays on the Kind of Stream It Was Called On

IntStream.map takes an IntUnaryOperator, so its function must return an int:

mapToObj leaves a primitive stream and mapToInt enters one, mid-pipeline too. Here order-line quantities are filtered as ints and turned back into labels:

Unit Creating and using streams covers what the primitive streams add (sum, average) and how IntStream.sum() overflows.

mapMulti Emits Zero or More Results Without a Stream per Element, but javac Can't Infer What It Emits


Each order line becomes a pick task, plus a wrap task if it is gift-wrapped, and nothing if its quantity is 0. With flatMap that is a new Stream.of(...) for every line, usually of one element. mapMulti (Java 16) hands the function a Consumer instead, and each accept emits one result:




The javadoc recommends mapMulti over flatMap when each element yields a few results, possibly none, since it creates no Stream per group, or when an if or a loop is easier than building a stream. Without the <String>, the same code doesn't compile:



Among the arguments, the result type R appears only in the type of sink, a parameter of the lambda. javac doesn't infer it from the values the body passes to accept, and the List<String> on the left doesn't reach back through .toList(), so R becomes Object. Give the type argument, .<String>mapMulti(...), or declare the lambda's parameters: (Line line, Consumer<String> sink). Only when mapMulti's result goes straight to a Stream<String> (an assignment, a return, an argument) does the target type decide R; add .filter(s -> s.isEmpty()) after it and s is an Object again.


filter and map Pass Each Element On; sorted Holds Every Element Before It Emits One


Unit Introduction to the Streams API traced elements one at a time through a pipeline. With sorted in the middle, they wait:





filter and map are stateless: each looks at one element and passes it on at once. sorted is stateful: it can't know which element comes first until it has seen the last, so it buffers everything and emits only when the source is exhausted. A findFirst() or limit(3) after it stops nothing upstream. On the dashboard's feed the source is never exhausted:




That buffer is where the dashboard's heap went. The two orders also mean different things on a finite list: sorted().limit(3) is the first three in sort order of everything, limit(3).sorted() is the first three to arrive, sorted. The panel wants the first three alarms, most severe on top, so filter, then limit, then sorted.


sorted() without a comparator needs Comparable elements, and nothing checks that until the terminal operation compares two of them:




One ticket sorts without complaint, because there is nothing to compare it with, so a one-row test passes. Pass a Comparator, such as Comparator.comparingInt(Ticket::priority), for anything without a natural order.


A Cheap filter Goes Before an Expensive map, Because map Runs for Every Element That Reaches It


A catalogue has 2,000 products, 40 of them in stock. quote(product) calls the pricing service, and a counter records the calls. Both pipelines return the same 40 quotes:




The stream fuses the stages into one pass, but it runs them in the order you wrote them, on the elements that reach each one. If a quote takes 15 ms, the first pipeline spends 30 seconds where 0.6 would do, and a pricing service that limits calls per second throttles it long before the end. When the condition needs the mapped value, split it: filter on what the source already knows, map, then filter again on the result.


Moving limit changes the result, not only the cost. Before an expensive map, it caps how many elements reach the map; before a filter, it counts elements that the filter then throws away.

distinct Uses equals and hashCode, So a Class Without Both Keeps Every Copy


A scanner reads the same SKU twice. Each scan builds its own object, as a parser would, and the pick list runs distinct() over three versions of the SKU class:




distinct remembers what it has passed in a hash set. A class without equals inherits identity from Object, so two scans of one SKU count as different. With equals but no hashCode, the two copies are equal but have different identity hash codes, and the set never gets as far as asking equals. A record generates both, from all of its components.


On an ordered stream, distinct keeps the first of each group of equal elements, so the fields in equals decide what counts as a copy, and with it what survives. This Scan compares the SKU only, and keeps the 09:00 scan:




Drop the two overrides and the record compares all its components: the scan time joins the comparison, and two scans of one SKU differ again. For "distinct by one field" without changing equals, unit Predicate builds a predicate that remembers keys.

limit and skip Count in Encounter Order, and HashSet and Set.of Have None


skip(page * size).limit(size) cuts a page out of a stream. A HashSet has no encounter order, and Set.of changes its order from one JVM run to the next (unit Creating and using streams). Pages of six regions, from one program run three times:




limit and skip take the first elements in whatever order the stream has. Behind a load balancer, page one can come from one instance and page two from another: a user who got [south, west] and then [coast, central] never sees north or east. Sort first, then skip and limit. Sorting after paging only orders a page whose members were picked arbitrarily.


Parallel pipelines differ. On an ordered parallel stream, limit and skip must still find the first n elements, which the javadoc calls "quite expensive"; unordered() lifts that constraint when any n will do. Unit Parallel streams and performance considerations covers parallel streams.

Summary


  • map gives one result per element; flatMap splices a stream per element. map to a list gives a stream of lists; flatMap(Optional::stream) drops empties; a null stream counts as empty. mapToInt and mapToObj switch between object and primitive streams.
  • mapMulti emits zero or more results through a Consumer. Followed by another call, it needs .<R>mapMulti or typed lambda parameters, or R becomes Object.
  • sorted holds every element before it emits one. limit or findFirst after it doesn't stop the source, so on an endless stream it never returns. Non-Comparable elements fail at the terminal operation, and only once two are compared.
  • A cheap filter goes before an expensive map. The stream doesn't reorder stages, so map runs for every element that reaches it.
  • distinct uses equals and hashCode. Without both, every copy stays; the fields in equals decide what counts as a copy, and the first in encounter order survives.
  • limit and skip count in encounter order. Sort an unordered source before paging it.

Order and nulls: on an ordered stream sorted is stable and distinct keeps the first of equal elements; on an unordered one neither is promised (javadoc). sorted() throws NullPointerException once a null is compared (a lone null comes back as [null]); sorted(Comparator.nullsFirst(Comparator.naturalOrder())) puts nulls first (ran).


Challenges


  1. A report needs a customer's ten most recent orders from a stream of all orders. Where do filter, sorted and limit go, and how many orders does the stream hold at its peak? What would a database query do differently?
  2. Measure flatMap against mapMulti on ten million elements that each expand to zero or one result, then to fifty. At what size does the javadoc's advice stop mattering?
  3. A Customer class is a HashMap key in one place and goes through distinct() in another. Its equals compares the email ignoring case. What must hashCode do, and what breaks if it hashes the email as stored?


Design Note: Why sorted Is the Barrier in a Lazy Pipeline


A stream pushes each element through every stage before it pulls the next, which is what lets limit and findFirst stop an endless source. A stateless operation needs no buffer. sorted can't do without one: the first element it emits may be the last one the source produces. The library gives it a buffer and a whole-input pass, and the package documentation says so: stateful operations "may need to process the entire input before producing a result".


The cost is a pipeline whose behaviour depends on the order of its lines. Moving limit one line down, past sorted, turns a bounded job into one that holds every element. The compiler accepts both, and a test on a small input sees at most a different result, never the memory.
