The field reads like a filtered view of the items. A Stream is something else: a one-shot pipeline that reads its source only when a terminal operation asks.

Building a Pipeline Runs Nothing; the Terminal Operation Runs It

A pipeline is a source, any number of intermediate operations (filter, map, sorted, each returning a Stream), and one terminal operation (toList, count, forEach, findFirst), which returns something else or nothing. Three SKUs, and a filter and a map that print when they are called. Pause before the output: what has been printed by the time the last line runs?

Neither lambda ran. filter and map only added a stage to a chain. The Stream they return holds that chain and the source, not elements. Waiting is what lets the library run all the stages in one pass, stop early, and read from a source that never ends (unit Creating and using streams).

A pipeline written for its side effects with no terminal operation therefore compiles and does nothing (unit Consumer shows it with peek). And each lambda runs when the terminal operation runs, which can be long after the line that wrote it.

Each Element Goes Through the Whole Pipeline Before the Next, and Short-Circuiting Stops the Pulling

Now the same pipeline gets its terminal operation. Does filter see all three SKUs before map sees any?

The terminal operation pulls one element from the source and pushes it through every stage before it pulls the next. B-7 stops at the filter and never reaches map. No list is built between the stages.

Because elements arrive one at a time, an operation that has its answer can stop pulling. A fraud check runs over 1,000 order ids and flags every 300th; a counter records how often the check is called. Each row below is a fresh orderIds.stream(), with the counter reset:

The first three stop as soon as they have their answer. The last two ask the same questions as the first two and check every order, because toList() and count() need every element. If the check is a 20 ms call to a fraud service, that is 6 seconds against 20 for the same answer, and over an infinite source the last two never produce a result.

A stateful operation such as sorted breaks the one-at-a-time flow: it has to pull every element before it can pass the first one on. Unit Intermediate operations (filter, map, flatMap) shows how that changes the trace.

A Stream Can Be Consumed Once, So Keep a Supplier, Not the Stream

Back to the dashboard. The first count() pulled every item through the filter, and the stream was spent. The second count() found a stream that had already run. The check is stricter than "one terminal operation": a second operation that builds on the same Stream object throws, intermediate ones included. Branching one stream into two filters fails before anything has run:

A Stream reads its source through a Spliterator, a cursor that moves forward and can't be rewound, and each stage marks the one before it as used when it links to it. That mark is what the second filter tripped over.

The dashboard's test called count() once, so it passed; production made a second request. A method that returns a stream it keeps in a field fails the same way for its second caller. The fix is to keep the recipe and build a new stream each time. A method that returns items.stream().filter(...) on every call does that, and so does a Supplier:

Each get() streams the list as it is at that moment. Collecting the low items into a list in the constructor would also survive the second request, but would keep answering with the items as they were when the report was built.

The Source Is Read When the Terminal Operation Runs, and Must Not Change Under It

A stream is built over a queue of orders, an order is added, and only then does the terminal operation run. The same steps follow over a CopyOnWriteArrayList:

ArrayList's javadoc calls its spliterator late-binding: it binds to the list's elements at the first traversal, not when it is created, so o-3 is in. CopyOnWriteArrayList's javadoc promises a snapshot of the list as it was when the spliterator was created, and stream() creates it at once. The java.util.stream package javadoc uses the ArrayList case as its example and says streams from JDK collections behave that way; CopyOnWriteArrayList doesn't, despite that wording.

Changing the source while the terminal operation runs is different. The package javadoc calls it interference and says it must never happen with a non-concurrent source. Here a shipping job re-queues order o-2 from inside the pipeline:

The add succeeded, the retry was never shipped, and the exception came after all four orders had shipped. For forEach and toList, ArrayList's spliterator compares the list's modification count once, after the last element. A short-circuiting operation compares after each element, so filter(o -> o.equals("o-3")).findFirst() in place of forEach throws as soon as o-2 is done. Either way the exception doesn't say how much work was already done, and a caller that retries the batch on failure ships all four orders again.

Removing is worse. A cart cleanup removes an empty cart from inside filter:

Cart c-3 moved into the removed cart's slot and was never checked, and the spliterator, still counting four elements, handed the lambda the null left at the end. The NullPointerException came first; with a null-safe check the same run ends in ConcurrentModificationException after the null. Collect what has to change into a new list and apply it after the terminal operation, or use removeIf (unit Predicate).

A Loop Is Clearer When the Work Stops Early, Throws a Checked Exception, or Updates Several Variables

Stock adjustments arrive as lines like A-1 +5. The import must stop at the first bad line, and someone wrote it with forEach:

valid checks a line against SKU ±n, and applied is a list. With List.of("A-1 +5", "B-7 -x", "C-3 +2"), then the same import written as the loop below:

return in a lambda ends that one call of the lambda, so it skipped one line and the stream carried on. A loop can return, break or throw out of the method in the middle of the work:

Checked exceptions and running totals are things a lambda can't handle. It can't throw a checked exception that Consumer.accept doesn't declare (unit Using lambda expressions with functional interfaces), so a stream version has to wrap it, and the caller's catch (BadLineException e) no longer sees it. It can't assign the method's local variables (unit Introduction to lambda expressions), so counting accepted lines, rejected lines and a total in one pass needs holders or a custom collector, where a loop needs three +=. A stream also has no index: after a filter, an element's position in the source is gone, while a loop has it in i. A stream reads best as one transformation from a source to a result; when the body is about control flow, write the loop.

Summary

  • Building a pipeline runs nothing. Intermediate operations record stages; the terminal operation runs them, so a pipeline without one does nothing.
  • Each element passes through every stage before the next one is pulled. Short-circuiting operations (findFirst, anyMatch, limit) stop pulling; collecting first and picking later checks every element.
  • A stream can be operated on once. A second operation on the same Stream, intermediate or terminal, throws IllegalStateException; keep a Supplier<Stream<T>> or a method that builds a new stream.
  • The source is read when the terminal operation runs, and must not change under it. An ArrayList change made before the terminal operation is seen; one made during it ends in a ConcurrentModificationException, possibly after all the work is done; a removal also skips elements and passes on a null.
  • A loop is clearer for early exits, checked exceptions and several running totals. return in a forEach lambda skips one element and does not stop the stream.

Challenges

  1. A service method returns Stream<Order> so that callers can filter further. What does it promise about when the list or table behind it is read, and how many times a caller may use it? Compare it with returning List<Order>.
  2. A pipeline calls a remote price service in map and ends with findFirst. Someone adds sorted() before findFirst. Predict the number of remote calls, then measure it.
  3. Take a long loop from your codebase that keeps several counters and exits early. Write it as a stream, and decide which version you would rather debug during an incident.

Design Note: Why a Stream Runs Once

A Stream is closer to an Iterator than to a Collection: it wraps a cursor over the source and a chain of stages that is fused into one pass when the terminal operation starts. Making it reusable would mean either buffering every element, which an infinite or very large source can't afford, or reading the source again, which a stream over a file, a socket or a generator can't do. The designers chose one pass and an exception for a second use. The cost is that one pipeline can't feed two results: counting and listing take two streams, or one collector that does both (Collectors.teeing; collectors are unit Terminal operations (forEach, reduce, collect)).

Problem statement


Every night a supplier sends a price file, one SKU;cents line per product, with # comments and blank lines in between. Last week a file arrived with a broken line in the middle. The import should have stopped there so that someone could fix the file and run it again, but half a file of prices went live, and nobody was told which line was wrong.


PriceImport already parses a line (parse throws the checked BadLineException), recognises comments and stores a price. Finish the TODO in src/main/java/practice/PriceImport.java: importAll(lines), which returns how many prices it stored.


When you're done, a good file is stored in full, and the first bad line ends the import: the prices before it stay, nothing after it is stored, and the caller's catch (PriceImport.BadLineException e) gets the line's number as an editor would show it. About eight lines.
