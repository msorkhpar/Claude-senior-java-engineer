A retailer's back office builds a nightly report that asks a price service for the current price of 200 SKUs, one blocking call each. Someone adds .parallel(), and the report finishes many times sooner. From that night on, while the report runs, the service's other requests slow down, and the audit log, written with CompletableFuture.supplyAsync, stops until the report is done. Nobody touched that code.

A parallel stream borrows threads the whole JVM shares, and whether it is faster depends on the source, the work per element and the operations, more than on the number of cores. The timings come from one machine with 20 hardware threads and this helper, not from JMH: they show direction and rough size, not figures to cite.

A Parallel Stream Runs on the Common ForkJoinPool, With Its Caller as One More Worker

Which threads run a parallel forEach? Every program prints availableProcessors() first.

The stream split the range into pieces and ran them on ForkJoinPool.commonPool(), whose size defaults to availableProcessors() - 1. The twentieth thread is the caller: main didn't wait for the result, it took pieces like a worker (unit ForkJoinPool and RecursiveTask/RecursiveAction explains forking and work stealing).

The common pool is one static pool per JVM. Every parallel stream in the process runs on it, from every request thread, unless it starts inside another ForkJoinPool (below), and so does every CompletableFuture ...Async method called without an executor. Its size comes from the system property java.util.concurrent.ForkJoinPool.common.parallelism when it is given; nothing on a stream chooses the pool or the number of threads.

One Pipeline Runs in One Mode: the Last parallel() or sequential() Call Wins

The pricing step is slow and thread-safe; the writer after it is neither. Does this price in parallel and write on one thread?

parallel() and sequential() don't mark a point in the pipeline. Each sets one flag for the whole pipeline, which the terminal operation reads; the package documentation says the most recent setting applies to all of it. The first pipeline ran everything on main, so the speed-up .parallel() was added for disappeared without an error. The second ran the step meant to be sequential on 20 threads.

To price in parallel and write in order, end the parallel pipeline with forEachOrdered: it calls the action one element at a time, in encounter order, each call happening-before the next, though not always on the same thread. If the writer must stay on one thread, use two pipelines: collect the parallel part with toList(), which keeps encounter order (unit Consumer), then write the list in a plain loop.

A Blocking Call Inside a Parallel Stream Starves Every Other User of the Common Pool

The report from the start, with the price service played by a latch the program opens later:

Once the report's threads are all waiting, another request runs a CPU-bound parallel sum, and the audit code calls CompletableFuture.supplyAsync(() -> "audit written") and waits up to a second for it. Then the price service answers:

All 19 workers and the report's thread sat in fetchPrice, and the pool added no thread in their place: its javadoc promises no adjustment "in the face of blocked I/O or other unmanaged synchronization". The other sum finished on its caller alone, seven times slower. The audit task has no caller to run it, so it waited in the pool's queue until the price service answered. In production it waits until a worker is free, which can be most of the report, and so does every parallel stream and default ...Async call in the service.

Java 21 on a small machine. CompletableFuture's async methods without an executor use the common pool only when its parallelism is at least two. On Java 21 with one or two CPUs they start a thread per task instead; run with -XX:ActiveProcessorCount=1, Java 25 used the common pool.

Running the Stream Inside Your Own ForkJoinPool Works, but No Document Promises It

ForkJoinTask.fork() is documented to run "in the pool the current task is running in", and the JDK builds parallel streams from fork/join tasks, but the Stream API never says which threads run a pipeline. The technique rests on an implementation detail, so keep it in one helper with a test. Only a ForkJoinPool counts: started from a newFixedThreadPool thread, the same stream ran on the common pool, with the submitting thread as one more worker.

The report in a ForkJoinPool(8) of its own, sized for eight calls at once:

The pool is now yours: shut it down in finally, and expect a failure in the lambda as an ExecutionException from get(). Its cause has the lambda's exception type, though in our runs it was a copy wrapping the original. For work that mostly waits, an executor with one task per call, such as Executors.newVirtualThreadPerTaskExecutor(), is the documented route.

The Source Decides How Well the Work Splits

A parallel stream cuts its source with Spliterator.trySplit(), which hands off a prefix and keeps the rest. The sizes of the first three prefixes, for a million elements:

An ArrayList, an array or a range knows its size and can index its middle, so a split costs nothing and halves the work. A LinkedList reaches its middle only by walking, and Stream.iterate computes each element from the previous one. Their spliterators copy the next 1024 elements, then 2048, then 3072, into an array, one after another on the splitting thread. The same work per element over five sources (IntStream.iterate in its three-argument form, which needs no limit):

With cheap work, the sequential walk that cuts batches takes about as long as the work itself: the linked list and iterate gained 10 to 40 %, while the sources that split in halves ran four to six times faster. With twenty times the work per element, the walk is a small share, and all five sources got 7 to 12 times faster. In a second run the poor splitters gained nothing at all with cheap work.

Parallel Pays Only When the Work Outweighs Splitting and Merging

A parallel run pays a fixed price before any element is processed: tasks are created, handed to workers, woken and joined. Two kinds of work over arrays of growing size:

Squaring 10,000 ints took 20 µs against a fixed price of 100 to 300 µs, so parallel lost tenfold and won only from 100,000. With 80 ns of work per element, the crossover fell to between 1,000 and 10,000. What decides is the number of elements times the cost of each, against that price, which varies with the machine and the pool's load: repeated runs moved it two- to fourfold. There is no element count to memorise; measure on the target hardware, with JMH where the answer matters.

Boxed Elements Cost More Than Threads Win Back

The same ten million amounts, as a List<Integer> and as an int[]:

Twenty threads made the boxed sum three times faster, and it stayed five times slower than one thread summing the int[]. Most elements of the list are references to separate Integer objects, so the sum follows ten million pointers, where the int[] is read straight through (primitive streams are unit Creating and using streams). Fix the representation before you add threads.

Encounter Order Costs Coordination; Give It Up Only Where Nothing Depends On It

Four million ids in a List<Integer>, and a predicate that matches only in the second half, but often there:

findFirst must return the match nearest the start. A thread that finds one in the right half still waits until every piece to its left has been searched without a match. findAny takes the first match any thread reports and cancels the rest: 16 µs. It returned the same id three times here; "any" means the result isn't promised, not that it changes.

On an ordered stream, limit(10_000) must return the first 10,000 matches, so each piece keeps its matches until everything to its left is known, and the parallel run was more than twice as slow as the sequential one. After unordered() any 10,000 matches will do. That halved the parallel time, which was still slower than sequential with work this cheap, and the result came from the middle of the list.

groupingByConcurrent Trades the Order Inside Each Group for One Shared Map

Two million entries, grouped by four accounts and by 100,000:

In parallel, groupingBy gives every piece its own HashMap and merges them left to right, so each group keeps encounter order. groupingByConcurrent has every thread add to one ConcurrentHashMap, and its javadoc calls it an unordered collector: a group lists its entries in the order threads happened to add them. A merge function that keeps the first value keeps the first to arrive, not the first in the list.

With four accounts, twenty threads queued on four group lists, each filled under a lock, and the concurrent collector lost. With 100,000 accounts, merging dozens of per-piece maps of up to 100,000 keys cost more than the locking, and it won fivefold. Choose groupingByConcurrent for a result that doesn't depend on order, such as a count, a sum or a set, over many keys; lines someone will read in order need groupingBy.

Summary

  • A parallel stream runs on the JVM-wide common pool, availableProcessors() - 1 workers plus its caller, shared by every parallel stream and every default ...Async task.
  • The last `parallel()` or `sequential()` call sets the mode of the whole pipeline. A parallel step and an ordered one-at-a-time step need forEachOrdered or two pipelines.
  • A blocking call inside a parallel stream holds common-pool workers that the rest of the JVM needed. Blocking work belongs on an executor you own; a stream submitted to your own ForkJoinPool runs there, by undocumented JDK behaviour.
  • The source decides how well the work splits. Arrays, ArrayList and ranges halve; LinkedList and iterate are cut in batches on one thread.
  • Parallel pays only when elements times cost per element outweigh a fixed price of tens to hundreds of microseconds, and threads don't make boxed elements cheap.
  • Encounter order costs coordination. findAny, unordered() and groupingByConcurrent are faster only where nothing reads the order they give up.

Challenges

  1. Your service runs in a container limited to two CPUs. How many threads does a parallel stream get there, and what happens to the crossover you measured on your laptop? Try it with -XX:ActiveProcessorCount=2.
  2. A job groups 50 million events by customer and sums their amounts. groupingBy or groupingByConcurrent? What do you measure first, and does the answer change if the downstream becomes toList()?
  3. The custom-pool technique isn't documented. Write the helper that wraps it so that a JDK which changes the behaviour fails a test rather than raising production latency.

Design Note: Why Every Parallel Stream Shares One Pool

If each parallel stream created its own pool, ten requests running one each on a 20-thread machine would start two hundred CPU-bound threads, and the operating system would spend its time switching between them. One pool sized to the cores keeps CPU-bound work at about one thread per core, however many streams run, and it lets library code go parallel without asking its caller for an executor.

The cost is that the pool has no owner. A stream that blocks or runs long takes capacity from code that never mentioned it, and the Stream API has no parameter to pick another pool.

Problem statement


The bank's monthly statements are built from the ledger, which hands its lines over as a stream in posting order. For the large business accounts the month has millions of lines, so the stream is parallel. A customer reads a statement from top to bottom and checks it against their own books, and the statement starts with the account's opening line: its first posting of the month.


Finish the two methods in src/main/java/practice/Ledger.java:

  • openingLines(...): each account's first posted line.


Both must give the same answer for a sequential and for a parallel stream. About two lines in total.
