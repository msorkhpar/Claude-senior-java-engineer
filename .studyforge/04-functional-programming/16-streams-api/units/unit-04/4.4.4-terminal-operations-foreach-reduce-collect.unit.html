A billing job adds up a customer's per-request charges and a base fee of 250 cents: usage.stream().reduce(baseFee, Integer::sum). Its tests pass. To speed up the nightly run, a colleague changes stream() to parallelStream(), and the next morning every large bill is 31,750 cents too high. Nothing threw, and the small bills in the tests are still right.

Six rules, one per heading. Laziness and single use are in unit Introduction to the Streams API, forEach and forEachOrdered in unit Consumer, toMap in unit Function.

reduce Needs an Identity That Changes Nothing and an Operation That Can Be Regrouped

reduce(identity, op) is guaranteed to give the same answer on a sequential and a parallel stream if identity leaves every element unchanged (op(identity, t) equals t) and op is associative. The billing job, on a 20-core machine:

A parallel stream splits the list into chunks, reduces each from the identity into a partial result of its own, and combines the partial results with the same operation. Here there were 128 chunks, so the fee was added 128 times. The identity is not "the starting value": it is a value every chunk may start from, any number of times. For + that is 0, for * it is 1, for Integer::max it is Integer.MIN_VALUE. The fee is added once, outside.

The second condition rules out subtraction. A running balance is the obvious way to write one:

(a - b) - c is not a - (b - c). In parallel each chunk started from the opening balance, and the chunks' balances were then subtracted from each other. Sum the debits, then subtract once.

Neither bug shows on a sequential stream. Both appear when someone adds .parallel(), or a library hands you a parallel stream, months after the code was reviewed.

The Three-Argument Form's Combiner Runs Only on a Parallel Stream

reduce(identity, accumulator, combiner) lets the result type differ from the element type: here the elements are words and the result is the longest length. The accumulator folds one word into a partial result; the combiner merges two partial results. This combiner was copied from a sum:

The JDK's sequential path never called the combiner, so no sequential test can find a wrong one. The javadoc requires it to be compatible with the accumulator: combiner.apply(u, accumulator.apply(identity, t)) must equal accumulator.apply(u, t). Merging a partial result must do what folding in its elements would have done; here that is Math::max. The identity must also be an identity for the combiner.

Without an Identity, reduce Returns an Optional, and So Do min, max and findFirst

A dashboard shows the day's largest order. Integer.MIN_VALUE is a true identity for Integer::max, and in parallel it gives the right answer. The trouble is the day with no orders:

An empty stream returns the identity, so the dashboard reports an order of -2,147,483,648 cents, and nothing downstream can tell it from a real value. reduce(op) has no identity to fall back on: it returns an Optional that is empty for an empty stream, and the caller must decide what "no orders" means. min, max, findFirst and findAny return Optional for the same reason.

findAny Is Free to Return Any Match

On an ordered stream, findFirst returns the first match in encounter order, even in parallel. findAny's javadoc calls it "explicitly nondeterministic". Five runs each, looking for multiples of 1,000 in 1 to 10,000 on a parallel stream:

Sequentially, findAny returned 1000, so code that relies on it passes its tests. Use findAny when any match will do, such as "any idle worker"; use findFirst when you need the earliest, at the cost of waiting for the chunks before the one that found it.

reduce Combines Values; a Mutable Container Goes Through collect

reduce assumes the accumulator returns a new value and leaves its inputs alone. An ArrayList as the identity breaks that assumption:

The three parallel lines run the same reduce on ids.parallelStream(), and the last line is the collect shown further down:

The identity is one list, shared by every chunk. All the worker threads added to it unsynchronized, and the combiner then added it to itself. Eight ids came out as 80 to 352 entries; 1,000 ids threw ArrayIndexOutOfBoundsException on every run. A StringBuilder as identity fails the same way.

collect is the mutable form of a reduction. It takes a supplier instead of an identity and calls it once per chunk, so each thread fills a container of its own, and the combiner merges two different containers:

Collectors.toList() is the same supplier, accumulator and combiner packaged as a Collector. Use reduce for immutable values such as numbers and records, joining for strings, and collect for anything you add to.

groupingBy Gives a Map of Lists in No Promised Order; a Downstream and a Map Factory Change Both

groupingBy(classifier) puts each element in a list under its key. A downstream collector changes what each group becomes; a map factory changes the map. Six orders in four regions:

West has three orders from two customers: counting() counts orders, while mapping(Order::customer, toSet()) keeps the distinct customers. The default map was a HashMap, with the regions in hash order, and the javadoc gives "no guarantees on the type, mutability, serializability, or thread-safety" of that map. The three-argument form takes a supplier of the map: TreeMap::new for sorted keys, LinkedHashMap::new for the order in which keys were first seen.

teeing Feeds Two Collectors in One Pass, and joining Writes Its Prefix Even for Nothing

Collectors.teeing (Java 12) sends every element to two collectors and merges their results. joining(delimiter, prefix, suffix) concatenates strings:

partitioningBy Always Has Both Keys; groupingBy Has Only the Keys It Saw

A nightly report splits the orders of 1,000 cents or more from the rest. On a day when every order is small, the two collectors disagree:

groupingBy creates a key the first time an element maps to it, so a group with no members does not exist, and g.get(true).size() throws NullPointerException on a day with no large orders. partitioningBy's javadoc promises that the map "always contains mappings for both false and true keys", with empty lists where nothing matched. For a yes/no split, use partitioningBy; read a groupingBy map with getOrDefault.

toList(), Collectors.toList() and toUnmodifiableList() Return Three Different Lists

Each line collects "a", null, "c", then calls add("d") on the result:

Collectors.toList() returned an ArrayList, but its javadoc gives "no guarantees on the type, mutability, serializability, or thread-safety", so a caller that adds to it relies on an implementation detail. Collectors.toUnmodifiableList() (Java 10) rejects nulls with NullPointerException.

The costly swap is the refactor from collect(Collectors.toList()) to toList(): it compiles, and the first caller that sorts or appends to the result throws UnsupportedOperationException at run time. Choose by what the caller does: toList() (Java 16) for a result nobody changes, Collectors.toCollection(ArrayList::new) for one the caller will change, and toUnmodifiableList() when a null would be a bug you want reported at once.

toArray() returns an Object[], and casting it to String[] throws ClassCastException; toArray(String[]::new) passes the array's constructor and returns a real String[].

Summary

  • `reduce` needs a true identity and an associative operation. A fee used as identity, or a running subtraction, is wrong only in parallel, where the three-argument form's combiner also first runs.
  • Without an identity, `reduce` returns an `Optional`, as do min, max, findFirst and findAny, so "no data" can't pass for a value; findAny may return any match.
  • `reduce` is for values, `collect` for containers. A mutable identity is one object shared by every chunk; collect's supplier gives each chunk its own.
  • `groupingBy` returns a map of lists with no promised type or order. A downstream collector changes the values, a map factory the map.
  • `partitioningBy` always has both keys; groupingBy only has the keys it saw.
  • The three list collectors differ in mutability and nulls. toList() is unmodifiable and keeps nulls, Collectors.toList() promises neither, toUnmodifiableList() rejects nulls.

Challenges

  1. A dashboard computes the average order value with one reduce. Write it with the three-argument form and a small record as the partial result, then check your combiner against the compatibility rule. When is teeing or summaryStatistics() (unit Creating and using streams) the better tool?
  2. Your team adds .parallel() to every stream in a batch job. Which of its reduce and collect calls could change their results, and what test would find each one before production does?
  3. A method returns collect(Collectors.toList()) and fifty callers use the result, some of them adding to it. How would you move it to toList() safely, and what does each choice promise the callers?

Design Note: Why Java Has Both reduce and collect

reduce comes from functional programming, where values never change: combining two partial sums makes a third, and the identity can be shared because nobody modifies it. That is what lets the library split the work across threads without locks. Building a list that way would copy the list at every step, which is quadratic, and collect exists for that case: it trades shared values for a container per chunk and a combiner that merges two of them. The compiler can't tell the two apart: reduce(new ArrayList<>(), ...) compiles, and only a parallel run shows the shared identity.
