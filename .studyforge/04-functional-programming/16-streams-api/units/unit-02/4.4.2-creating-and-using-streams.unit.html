A log indexer counts the ERROR lines in every file of a directory, one Files.lines(log).filter(...).count() per file. It passes every test. In production, after a few hours, it dies with FileSystemException: ... Too many open files.

The method that creates a stream decides more than where its elements come from: whether it holds a file, in what order the elements arrive, what type they have, where the sequence ends and which arithmetic you get. Seven rules, one per heading. The pipeline itself, lazy and single-use, is unit Introduction to the Streams API.

A Stream Over a File Holds It Open Until close(), Not Until the Terminal Operation

We count the errors in 1,000 small log files, with and without try-with-resources, and count the process's open descriptors in /proc/self/fd (Linux):

count() read every line, and the file stayed open. A terminal operation finishes the pipeline; only close() releases what the source holds, and javac compiled errorsLeaky without a warning. Files.lines, Files.list and Files.walk all keep descriptors open until closed. The leaked ones do close eventually: 981 rather than 1,008 because a collection ran during the loop, and in a second run a System.gc() after the loop took the count from 1,008 back to 8. So the garbage collector decides when your files close. With ulimit -n 512, the same loop failed partway:

onClose handlers also run only on close():

flatMap closes each stream it maps to once that stream's elements have passed, so a flatMap that opens one file per element doesn't leak the inner streams; the outer stream is still yours to close. BufferedReader.lines() is the opposite case: closing the stream leaves the reader open, so you close the reader. A read error inside such a stream arrives as UncheckedIOException from the terminal operation (unit Checked vs. unchecked exceptions).

A Collection's Stream Has the Collection's Order, and a HashSet Has None

Five codes, added in the same order to four collections:

A HashSet has no encounter order: its spliterator doesn't report ORDERED, and what you see is its bucket layout. The set held the same five codes both times, but resizing for 20 temporary entries moved them, and findFirst() changed from bravo to delta. A Set.of set changes order between JVM runs: two runs of one program printed [echo, charlie, delta, bravo, alpha] and [alpha, bravo, delta, charlie, echo]. A report that takes "the first" element of a set, or a test that compares one to a list, works until the set resizes, the JDK changes or, for Set.of, the JVM restarts.

A Map isn't a Collection: stream one of its views, entrySet(), keySet() or values(). They have the map's order: none for a HashMap, key order for a TreeMap, insertion order for a LinkedHashMap.

Stream.of Streams Its Arguments: an int[] Is One Element, and So Is null

Stream has of(T t) beside of(T... values). An int[] isn't a T[], so Stream.of(ports) picks of(T t) with T = int[]: a stream of one array.

The lookup compiles because p is the whole int[], and an array never equals an Integer. Arrays.stream(int[]) and IntStream.of(int...) give an IntStream of the values, and Arrays.stream(array, from, to) a slice with to excluded. A String[] hosts has no such trap: Stream.of(hosts) streams its elements.

A null variable is one argument too, so Stream.of(nickname) holds one null, which fails later in whatever calls a method on it. Stream.ofNullable (Java 9) is empty for null. With a bare Stream.of(null), javac warns, the null binds to the array parameter, and Stream.of itself throws NullPointerException.

A Generated Sequence Ends Only Where Its Factory Says

Stream.iterate(seed, next) never ends; the Java 9 form iterate(seed, hasNext, next) stops like a for loop. A filter doesn't end a stream, it only drops elements:

Without limit(14) the second line never prints. The doubling overflows to -2147483648, then to 0, and 0 < 1000 passes forever. Ending at the first element that fails a test is takeWhile (unit Predicate); Stream.generate is endless in the same way (unit Supplier).

IntStream.range(1, 5) is 1, 2, 3, 4, and rangeClosed(1, 5) adds the 5. range(5, 5) and range(5, 1) are empty, not errors; rangeClosed is empty only when the end is below the start.

Only Primitive Streams Have sum() and average(), and IntStream.sum() Overflows

Stream<Integer> has no sum():

sum(), average() and summaryStatistics() exist on IntStream, LongStream and DoubleStream, where the elements are known to be numbers. mapToInt gets there; boxed() and mapToObj come back:

The sum of nothing is 0, but the mean of nothing doesn't exist, so average() returns an OptionalDouble. getAsDouble() on the empty one throws NoSuchElementException, and orElse(0) shows an idle service as answering in 0 ms. IntStream.sum() returns an int and wraps silently: two 1.5 GB uploads total -1.3 GB. summaryStatistics().getSum() and asLongStream().sum() are long.

String.chars() Streams UTF-16 Units, Not Characters

A post may be at most 280 characters long. How long is "Ship it 🚀"?

chars() streams a String's 16-bit UTF-16 units. The rocket, U+1F680, doesn't fit in one, so it is stored as the pair U+D83D U+DE80: chars() counts it twice, and a cut after nine units keeps half of it, which prints as ?. codePoints() streams one element per Unicode code point. A flag or an emoji with a skin tone is several code points; counting the symbols a reader sees takes java.text.BreakIterator.

Pattern.splitAsStream streams the pieces between matches. Its argument is a regular expression, so Pattern.compile(".") matches every character and leaves no pieces, while Pattern.compile(Pattern.quote(".")) matches a dot. A delimiter at the start gives an empty first piece, and trailing empty pieces are dropped:

Builder and concat Assemble a Stream; Repeated concat Overflows the Stack

Stream.builder() collects elements until build(); after that, add throws IllegalStateException. Stream.concat(a, b) joins two streams lazily, and each concat in a loop wraps the previous result:

With the default stack, 50,000 overflowed inside concat itself, before any element was read: the stack trace is one ConcatSpliterator.characteristics calling the next. The concat javadoc warns that deep concatenation can end in StackOverflowError. For more than a few streams, put them in a list and flatMap it, as the last line did.

Summary

  • A stream over a file holds it open until `close()`. Wrap Files.lines, Files.list and Files.walk in try-with-resources; the terminal operation doesn't close, and onClose handlers run only on close().
  • A collection's stream has the collection's order. A HashSet or Set.of has none, and the order you see changes when the set resizes, or for Set.of when the JVM restarts.
  • `Stream.of` streams its arguments. An int[] is one element and a null variable is one null; use Arrays.stream and Stream.ofNullable.
  • A generated sequence ends only where its factory says. The two-argument iterate is endless, a filter doesn't stop it, and range excludes its end.
  • Only primitive streams have `sum()` and `average()`. average() is empty for no elements, and IntStream.sum() overflows silently.
  • `String.chars()` streams UTF-16 units. Count and cut with codePoints().
  • Repeated `concat` overflows the stack. Use flatMap over a list of streams.

Challenges

  1. A service streams a directory tree with Files.walk and returns the stream to its caller. Who closes it, and how do you make that hard to forget?
  2. A test asserts that set.stream().findFirst() equals a value, and it passes on your machine. What change would make it fail, and what would you assert instead?
  3. Measure a sum over a List<Integer> of ten million elements with mapToInt(...).sum() and with reduce(0, Integer::sum). Where does the difference come from?

Design Note: Every Stream Is AutoCloseable, Few Need Closing

BaseStream extends AutoCloseable, so every stream has close(). The Stream javadoc says most streams don't need it, since collections, arrays and generating functions hold nothing to release. Putting close() on every stream lets a stream over a file travel as an ordinary Stream<T>, and lets code that consumes a stream ignore where it came from. The cost is that the type no longer tells you whether closing matters, so a convention has to: whoever opens a stream over a resource closes it with try-with-resources, and a method that returns one says so in its javadoc.

Problem statement


The support team's service runs LogScanner.countErrors(dir) every few minutes to show how many ERROR lines today's logs hold. The numbers are right, and the service runs fine for a day or two. Then every scan, and everything else in the process that opens a file, fails with Too many open files, until someone restarts it.


Finish the two TODO methods in src/main/java/practice/LogScanner.java:


  • listLogs(dir): the .log files of the directory, sorted by name;
  • errorsIn(log): how many lines of one log contain ERROR.


Open the directory with openDir and each log with openLog, never with Files directly: the tests replace those two methods to watch what the scanner opens. A log can fail while it is being read (a disk unmounted, a file truncated under you); that failure should reach the caller of countErrors. About seven lines in total.


When you're done, the scanner can run every few minutes for weeks and hold no file open between scans, whether a scan succeeds or fails.
