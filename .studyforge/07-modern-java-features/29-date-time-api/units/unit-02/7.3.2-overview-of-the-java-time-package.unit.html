Each Type Answers One Question, and Only Instant Is a Moment

java.time replaces java.util.Date and Calendar, where one class stood for a moment, a date and a wall-clock reading (unit Limitations of the Legacy Date and Calendar Classes). Its main types each answer one question:

Between a Moment and a Date There Is Always a Zone

An Instant has no date. The date is a question about a place, so every conversion between the two takes a ZoneId. Here is the payment's date in three places:

A method without a zone argument still uses one, the JVM's default: LocalDate.now() reads the system clock "in the default time-zone" (its javadoc). The same conversion with ZoneId.systemDefault() on two servers, run with -Duser.timezone=America/New_York and then -Duser.timezone=Australia/Sydney:

The default zone is a deployment setting, not a fact about the customer. The mail job runs daily at 22:30 on a UTC server. Take a Sydney customer whose trial ends on 1 April, even with ends computed in Sydney's calendar: at 22:30 UTC on 31 March it is already 09:30 on 1 April in Sydney, but the job's LocalDate.now() says 31 March. The mail goes out a day late.

Values Never Change: Keep What plusDays Returns

Spot the Problem: The Grace Period That Does Nothing

An invoice is due 30 days after issue, plus 7 for customers with a grace period:

For an invoice issued on 2026-03-02 (run with -Duser.timezone=UTC):

Line (1) computes 2026-04-08 and throws it away. Every java.time value is immutable: plusDays, minusMonths, with(...) and withZoneSameInstant return a new object and leave the one they were called on unchanged. Code ported from Calendar.add, which changes the calendar in place, looks correct and does nothing. The fix is due = due.plusDays(7), and it prints 2026-04-08 while issued stays 2026-03-02.

The javadocs of LocalDate, Instant, ZonedDateTime, Duration and Period each say "This class is immutable and thread-safe". Because of that, a static final LocalDate can be shared by every thread without a lock, and a getter can return its field without the defensive copy a Date needs (unit Limitations of the Legacy Date and Calendar Classes).

Code That Needs the Current Time Takes a Clock

LocalDate.now() hides two inputs, the current instant and the default zone, so a test can set neither; LocalDate.now(zone) fixes only the zone. Its javadoc: "Using this method will prevent the ability to use an alternate clock for testing because the clock is hard-coded." The fix is to take a Clock as a constructor argument and ask it:

LocalDate.now(clock) takes both inputs from the clock: its instant, dated in its zone. Production passes Clock.systemUTC(). A test fixes the moment, and moves it with Clock.offset:

The output is the same under -Duser.timezone=UTC and -Duser.timezone=Asia/Kolkata. A test of the old lastTrialDay had to build its account relative to the current date, so it could only test today on this machine, never the moment the Sydney bug needs.

Code that needs only the moment, never a date, can take an InstantSource (Java 17), which Clock implements.

A test that needs time to move during a call writes a settable clock: Clock is an abstract class with three abstract methods, instant(), getZone() and withZone(ZoneId).

Summary

  • Each type answers one question, and only `Instant` is a moment. A LocalDateTime stored for "when it happened" turns back into a moment only with a zone someone has to guess.
  • Between a moment and a date there is always a zone. A call without one uses the JVM's default, so the server's setting decides the customer's date.
  • Values never change. plusDays and with return the answer; a dropped result is a silent no-op, and immutability is what makes the types safe to share.
  • Code that needs the current time takes a `Clock`. Tests then choose the moment and the zone instead of depending on when and where they run.

Design Note: Why the Zone Is an Argument

java.time could have kept Date's approach and filled in the default zone wherever one was missing. It does that only in the now() methods, Clock.systemDefaultZone() and ZoneId.systemDefault(). Everywhere else the zone is a parameter, so the code says whose date it is asking for, and a change to a server's default zone can't silently change those results. The cost is longer calls and one more argument to pass through every layer that needs a date.
