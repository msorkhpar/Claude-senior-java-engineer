A booking service written before Java 8 gets three tickets in one week. Monday's standup moved from 08:00 to 07:45 UTC, and nobody asked for it. A guest booked a room for 30 February and was charged for 2 March. The nightly report puts a booking made at 23:30 UTC on Sunday on one server and on Monday on another. Each comes from how java.util.Date, Calendar or SimpleDateFormat behave by default.

Every output below comes from Java 21. Each run sets the default zone and locale explicitly: -Duser.timezone=Europe/Amsterdam unless stated, and -Duser.language=en -Duser.country=US.

A Date Is a Mutable Moment, So Anyone Holding It Can Move It

A Date holds one long, milliseconds since 1970-01-01T00:00Z, and setTime changes it. The meeting keeps its start in a private final Date field and returns it from a getter. The reminder service wants a time 15 minutes earlier:

final fixes which object the field points to, not what is inside it. The getter handed out the meeting's own object, so the reminder service moved the meeting itself. The constructor stores the caller's object too, so a caller that reuses its Date for the next booking moves this meeting.

Where you must keep Date, copy it in the constructor and in the getter: new Date(d.getTime()). The java.time value types are immutable, and their plus... methods return a new object (unit Overview of the java.time package).

Months Count From 0, Years From 1900, and Out-of-Range Values Roll Over

Calendar numbers months 0 to 11, and the deprecated Date constructors also take the year minus

  1. By default neither rejects an out-of-range value: the excess carries into the next field.

The year 2026 passed to the constructor became 3926, month 3 is April, month 12 is January of the next year, and 30 February is 2 March. The conventions are those of C's struct tm (tm_year since 1900, tm_mon from 0). Only the non-lenient calendar refused, and only when it next computed its fields. The bug appears wherever values cross into or out of the legacy API: a column written from getMonth() and read as a calendar month is a month early on every row. LocalDate.of counts months from 1 and throws on 30 February.

Parsing Is Lenient by Default, and Strict Mode Still Ignores What Follows the Date

SimpleDateFormat.parse uses the same lenient calendar:

The lenient formatter is how the guest got 2 March. Strict mode rejects impossible fields, but parse(String) stops reading once it has a date and returns it; the ParsePosition shows it stopped at index 10 of 13. MM does not require two digits, so 2026-3-5 passes. LocalDate.parse(text) reads the whole text and validates the date (a pattern formatter needs ResolverStyle.STRICT for the same check, unit DateTimeFormatter):

One SimpleDateFormat Shared by Threads Returns Wrong Dates

Legacy code often keeps one formatter in a static final field. Four threads each parse 10,000 dates (1,000 distinct ones, ten times over) through one shared instance and compare every result with the text they passed in (run with -Duser.timezone=UTC):

A SimpleDateFormat keeps a Calendar and a DecimalFormat in instance fields and uses them as scratch space on every parse, so concurrent parses overwrite each other's partial results. The counts vary between runs, but in each one most failures return a date, another thread's or a mix that nobody passed in, and nothing logs them; the exceptions are the few you would notice. The class is not synchronized, and its javadoc advises a formatter per thread; pre-Java 8 code used a ThreadLocal, a new instance per call, or a lock. DateTimeFormatter is immutable and safe to share (unit DateTimeFormatter).

A Date Has No Zone; toString() Uses the JVM's Default

The same Date printed in two JVMs, one started with -Duser.timezone=Europe/Amsterdam and one with -Duser.timezone=America/New_York:

Both JVMs hold the same getTime(). toString(), the deprecated getDate() and getHours(), and a SimpleDateFormat without setTimeZone all use the JVM's default zone. That is the nightly report: the code that cut bookings into days never named a zone, so each server used its own, and java.util has no date-only type to hold the result. To get a day, name the zone: d.toInstant().atZone(zone).toLocalDate() (zones in unit Zoned and Offset Date and Time).

java.sql.Date Is a java.util.Date That Breaks Its Parent's Contract

JDBC's date-only type, java.sql.Date, extends java.util.Date and still holds milliseconds. Its toString() prints only the day:

The constructor keeps the time of day and equals compares getTime(), so two values that print the same day aren't equal, and a Set of them keeps both. The subclass also throws from methods its parent declares: a method that takes a java.util.Date, calls toInstant() and is tested only with java.util.Date values fails on the first value from ResultSet.getDate (java.sql.Timestamp doesn't throw). For a moment, Instant.ofEpochMilli(d.getTime()) works on both types. A java.sql.Date names a day, though: valueOf stored midnight in the default zone, 23:00Z the day before, so reading it as a moment in another zone gives the wrong day, and toLocalDate() gives the right one. Conversions are unit Interoperability with Legacy Date and Calendar Classes.

Summary

  • A `Date` is mutable: a getter or constructor that shares one lets any caller move your moment, and final doesn't stop it.
  • Months count from 0, years from 1900, and `Calendar` rolls overflow into the next field instead of rejecting it.
  • `SimpleDateFormat` parses leniently by default, and strict mode still ignores text after the date.
  • A shared `SimpleDateFormat` returns wrong dates under concurrency, most of them silently.
  • A `Date` has no zone or day: toString() and Date's deprecated field getters use the JVM default.
  • `java.sql.Date` breaks `java.util.Date`'s contract: toInstant() throws, values that print the same day can differ, and its day comes from toLocalDate().

Challenges

  1. A library you can't change returns Date from its getters and keeps a reference. Where in your code do you convert, and what do you lose if a caller still needs the library's object?
  2. Rerun the shared-formatter test with one thread and with 32. What do the counts tell you about catching this bug in a test suite?
  3. A table stores Date.getMonth() values in a column named month. How do you migrate its readers without a day on which both conventions are live?

Design Note: One Type for Every Question

java.util.Date answers one question, "which millisecond", but the 1.0 API also made it answer "which day" and "which hour" through methods that used the default zone. JDK 1.1 deprecated those methods and moved calendar work to Calendar and text to DateFormat, but kept every type mutable and lenient by default. java.time (JSR 310, Java 8) gives each question its own immutable type, so a moment and a day have different types. The cost is at the boundary: legacy APIs still take and return Date, and converting to a day or a local time there needs an explicit zone.

Problem statement


A card processor settles with an exchange in Tokyo and totals its payments per business day of that exchange. The ledger API it reads still returns java.util.Date. Since part of the fleet moved to a data centre in São Paulo, the totals from those servers disagree with the exchange's for payments made in the evening there. One older caller passes, instead of a payment moment, the settlement day it read from a DATE column with ResultSet.getDate; its report has been crashing, and once fixed it must show the same day the column holds, on servers in any zone.


Finish businessDay(...) in src/main/java/practice/SettlementReport.java. About four lines.
