A document service answers the first edit of every new document with 409 Conflict, and the second edit of the same document always goes through. Creating a document stamps it with updatedAt = Instant.now() and returns the stamp to the client. An edit sends the stamp back, and the save rejects it unless it equals the updatedAt column. Nobody else touched the document.

An Instant Is Seconds and Nanoseconds Counted From 1970-01-01T00:00Z

An Instant holds two numbers: a long of seconds since the epoch, and an int of nanoseconds within that second, from 0 to 999,999,999. It has no zone and no calendar.

Half a second before the epoch is second -1 plus half a second, because the nanosecond part never goes negative. Writing it as getEpochSecond() + "." + getNano() gives -1.500000000, which reads as -1.5 s. toEpochMilli() drops the digits below the millisecond, rounding towards the past.

An epoch number on the wire carries no unit. A carrier's webhook sends "ts": 1773480600, in seconds, to a handler written for milliseconds:

Nothing throws. Read as milliseconds, today's events land in January 1970, and a 90-day cleanup deletes them that night. Read the other way (third line), they never expire. Put the unit in the field's name or the contract (tsMillis), and call the factory that matches it.

Instant.parse Accepts Only Text That Names Its Offset

Instant.parse reads the ISO form with a Z or a numeric offset, and converts an offset to UTC. Without one it refuses:

Text without an offset is a wall-clock reading (unit LocalDate, LocalTime, and LocalDateTime), and it names a different moment in every zone, so Instant won't guess. A depot in Amsterdam sends its scanner's local time, and the quick fix appends Z:

Appending Z declares the text UTC, and every scan lands an hour late, two in summer. A parcel scanned before the 18:00 cut-off shows as scanned after it. The receiver has to be told the sender's zone. Local times that fall in a DST gap or overlap are unit Zoned and Offset Date and Time.

A Timestamp Survives a Store Only at the Store's Precision

On Java 21 on Linux, Instant.now() fills the nanoseconds:

The counts change from run to run and machine to machine. Instant.now() reads Clock.systemUTC(), whose javadoc promises only "the best available system clock", possibly System.currentTimeMillis(). Many stores are coarser, such as a column of epoch milliseconds or a java.util.Date (unit Interoperability with Legacy Date and Calendar Classes). The client holds the value from memory, the column a truncated copy, and equals compares nanoseconds. After the 409 the client reloads, so its second edit carries the column's stamp. Truncate where the stamp is made, so the value in memory is the one the store keeps:

Clock.tickMillis(zone) gives a clock that does the same for every reading. Truncating further, to SECONDS, is not safer: two edits in the same second get the same stamp, and a check by stamp lets the stale one overwrite the other.

An Instant Has No Calendar, So Months Need a Zone

A subscription renews one month after payment. The payment is an Instant:

The length of a month depends on which month it is, and the date depends on the zone. Added in UTC, this renewal lands on 1 March, 08:30 in Tokyo; added in Tokyo, on 28 February. DAYS works only because the javadoc defines it as 86,400 seconds, which is not a calendar day across a DST change (unit Duration and Period).

The usual workaround, plus(30, DAYS), renews this payment on 1 March. Add the month in the customer's zone and convert back.

Summary

  • An `Instant` is epoch seconds plus nanoseconds. An epoch number read in the wrong unit gives a wrong instant, and nothing throws.
  • `Instant.parse` needs a `Z` or an offset. Text without one names no moment; appending Z misreads the sender's local time as UTC.
  • A stored timestamp keeps only the store's precision. Truncate when you stamp, to the store's unit and no coarser, or equality fails after the round trip.
  • An `Instant` has no months. Add them in the customer's zone, then convert back.

Challenges

  1. A service's database keeps microseconds and its event stream milliseconds. Which precision do you stamp with, and where do you enforce it?
  2. A feed sends epoch numbers with no unit, and you can't change it. Can you tell seconds from milliseconds by size, and for which dates would that guess fail?
  3. NTP can move the clock behind Instant.now(). What do you use to time a request, and why?

Design Note: A Day Is Always 86,400 Seconds

The Instant javadoc defines the Java time-scale: every day has exactly 86,400 seconds, and on a day with a leap second that second is spread over the day's last 1,000 seconds (UTC-SLS). So Instant can't name 23:59:60, and an interval across a leap second is a second shorter than atomic time says. In exchange, an Instant converts to any date by integer arithmetic, with no table of leap seconds. The javadoc doesn't require the system clock to perform the spreading, so around a leap second Instant.now() does whatever the operating system does.

Problem statement


A parcel's tracking page merges three feeds. The line-haul carrier posts JSON such as {"event": "picked up", "sentAt": 1795300000}, the courier sends ISO-8601 text with a Z or an offset, and the sorting depot's scanners report what their wall clock showed when the parcel went past, such as 2026-11-19T08:20:00. Customers of the Chicago depot see their parcel arrive at the depot hours before the truck that brought it left, and support keeps finding line-haul events dated 1970.


ParcelTimeline already merges and sorts the feeds, and reads the courier's text. Finish the two TODO methods in src/main/java/practice/ParcelTimeline.java:


  • fromSentAt(long): the moment a line-haul sentAt value names. The carrier's API documentation says it counts whole seconds since 1970-01-01T00:00Z.
  • fromScanner(String): the moment at which a scanner of this depot showed the given reading. The depot's zone is passed to the constructor.


When you're done, every event sits at the moment it happened, wherever its feed came from. About two lines in total.
