A payments service uses java.time everywhere in its own code. It still writes every payment to an audit library that stores java.util.Date, and to an old JDBC layer of java.sql.Timestamp columns. The batch host moved from a data centre in Amsterdam to a container in New York. Since then the nightly reconciliation flags every payment as changed, and payments made late in the UTC evening land on another day in the settlement report. Nobody changed the code.

Outputs are from Java 21.0.12.1 with tzdata 2026b, run with -Duser.language=en -Duser.country=US, once under -Duser.timezone=Europe/Amsterdam and once under America/New_York. Where the two differ, the page shows both.

Date and Instant Name the Same Moment, but a Date Keeps Only Milliseconds

Date.from(instant) and date.toInstant() need no zone, because both types count from 1970-01-01T00:00Z. They don't count in the same unit:

A Date holds milliseconds, so Date.from drops the rest; Timestamp keeps a separate nanosecond field. Instant.now() on Linux fills digits below the millisecond (unit Instant and Timestamps), so almost every payment comes back from the audit library as a different Instant, and equals reports a change.

Compare at the precision of the narrower side: date.getTime() == instant.toEpochMilli(), or instant.truncatedTo(ChronoUnit.MILLIS) before equals. Both truncate, like Date.from; rounding would turn .123987 into .124 and report a change again.

Timestamp and java.sql.Date Turn Local Values into Moments in the JVM's Default Zone

Timestamp and java.sql.Date are moments too, but they also convert to and from local values, with no zone argument. The same code under Europe/Amsterdam, then America/New_York:

The javadoc of valueOf(LocalDateTime) and toLocalDateTime() says the local value is read "in the local time zone", the JVM's default. The settlement report used Timestamp.from(paid).toLocalDateTime().toLocalDate(), so this payment belonged to 5 May in Amsterdam and to 4 May in New York. A java.sql.Date is midnight in the default zone, so its milliseconds sent to a JVM in another zone (through a cache or a message) can read back there as the day before.

Use the bridges in pairs: from/toInstant for a moment, valueOf/toLocalDateTime (and toLocalDate) for a wall-clock value. Mixing them shifts the value by the default zone's offset. For a wall-clock column in a known zone, do the zone step in java.time (LocalDateTime.ofInstant(paid, zone)) and hand valueOf only the result.

A pair that matches still changes a wall-clock time the default zone skips. Under Europe/Amsterdam, around the 2026 clock changes:

A booking stored at 02:30 comes back at 03:30. In the overlap, Timestamp takes the later offset and java.time the earlier one (unit Zoned and Offset Date and Time), so two parts of one service store the same local time as moments an hour apart.

JDBC 4.2 drivers. The JDBC 4.2 specification lets setObject take LocalDate, LocalDateTime and OffsetDateTime, and getObject(column, LocalDateTime.class) return them, with no Timestamp in your code. Whether a driver goes through the default zone inside is up to the driver; this unit runs none, so test yours.

Build a TimeZone from a ZoneId, So a Wrong ID Fails

TimeZone.getTimeZone(ZoneId) and timeZone.toZoneId() convert between the two zone types. How you build a TimeZone from a configured ID decides what a typo does:

TimeZone.getTimeZone(String) answers an unknown ID with GMT, so a service configured with a typo runs on UTC all year and nothing fails. ZoneId.of rejects it at startup. The old three-letter IDs convert, not always as the name suggests: EST becomes a fixed -05:00 with no summer time, and ZoneId.of("PST") throws.

A Calendar Converts With Its Own Zone, Not the JVM's

A Calendar carries a TimeZone. GregorianCalendar.from(ZonedDateTime) sets it from the zone, and toZonedDateTime() reads it back. calendar.toInstant() keeps only the moment, so the zone you attach next decides the hour. Two runs again, Amsterdam then New York:

A 09:00 pickup in Kolkata shows as 05:30, or as 23:30 the day before. Only GregorianCalendar has toZonedDateTime(); for any other Calendar, use cal.toInstant().atZone(cal.getTimeZone().toZoneId()). The old way in, new GregorianCalendar() and then setTime(date), has the same flaw: it takes the default zone.

from() also brings ISO week rules: weeks start on Monday, and week 1 is the first with four days in the new year. A report keyed on WEEK_OF_YEAR changes when its calendars start coming from from():

1 January 2027 is a Friday, so under ISO rules it belongs to the last week of 2026.

Summary

  • A `Date` keeps milliseconds. An Instant that goes through one loses the rest, so compare at millisecond precision, truncating; Timestamp keeps nanoseconds.
  • `valueOf`, `toLocalDateTime` and `toLocalDate` use the JVM's default zone. Use from/toInstant for moments, do any other zone step in java.time, and expect a DST gap to move a wall-clock time.
  • `TimeZone.getTimeZone(String)` turns an unknown ID into GMT. Build the TimeZone from ZoneId.of.
  • A `Calendar` converts with its own zone: GregorianCalendar.from/toZonedDateTime, or toInstant() plus getTimeZone().toZoneId(). from() brings ISO week rules.

Challenges

  1. The audit library returns Dates that someone else's code already rounded. How do you reconcile against them, and what false matches can you get?
  2. A TIMESTAMP column was written for years by servers in two zones. How do you find which rows were written where, and what do you migrate the column to?
  3. Which calls that use the JVM's default zone can a static check find, and which only a test run under two -Duser.timezone values?

Design Note: Why the Bridges Live on the Legacy Classes

Java 8 put every conversion on the old classes (Date.from, Timestamp.valueOf, GregorianCalendar.from, TimeZone.toZoneId), and no public java.time type mentions Date, Calendar, TimeZone or java.sql. The new API stays free of the old one, and the legacy types can go without touching java.time. The cost is that each bridge keeps its old class's rules, so convert once, where the legacy API is called, with the zone as an argument.

Problem statement


The payment service records each payment's time as an Instant taken from the system clock, and hands an audit library a copy made with Date.from(...). Every night a job reads the copies back and lists the payments whose audit copy is missing or was edited. Since the service moved to a newer host, the job lists almost every payment, and nobody has touched the audit data.


AuditReconciler.changed(...) already walks the payments. Finish the two TODO methods in src/main/java/practice/AuditReconciler.java:


  • asStored(recorded): the time the audit library holds once it has been given recorded;
  • matches(recorded, copy): whether the copy is still exactly what the library was given.


When you're done, an untouched copy never shows up in the list, and a copy that someone moved, even by a single millisecond, always does. About two lines in total.
