A service keeps its settings in enum Setting { PORT, HOST, TIMEOUT } and reads them through Object get(Setting), so every caller casts. A refactor changes TIMEOUT from a number of seconds to a Duration. Everything compiles, and the first request after the deploy fails in code nobody touched:

The fix everyone reaches for is enum Setting<T>, so that get(TIMEOUT) returns a Duration and the compiler finds the stale cast. Despite this unit's title, Java has no generic enums.

An Enum Can't Declare a Type Parameter; JEP 301 Proposed It and Was Withdrawn

That is javac 21; javac 25 prints the same. JEP 301, "Enhanced Enums", proposed type parameters on enums, so that each constant could carry its own type argument (PORT a Setting<Integer>, HOST a Setting<String>). It was withdrawn and never shipped.

Erasure is not the obstacle: a generic class can hold static final constants with different type arguments, which is the first replacement below. The enum declaration has no place for a type parameter, so every constant has the one type Setting, and nothing ties a constant to the type of its value. Unit Limitations of Traditional Enums shows the usual result, an Object field and a cast at every call site. An enum may declare generic methods (unit Generic Methods in Enums), but those don't give a constant its own type either.

A Final Class With Typed Constants Lets the Compiler Check Every Key

A class with a private constructor and public static final instances behaves like an enum's constant list. Make the class generic and each constant gets its own type argument:

The store's methods take the key's T, so the value's type follows the key:

int port = config.get(Key.PORT) and Duration timeout = config.get(Key.TIMEOUT) need no cast. Pause before reading on: do these two lines fail at run time, or earlier?

Both fail to compile; the second is the opening's mistake, now caught by javac. Only Config casts, through the Class<T> object, because its one map stores every value as Object. The private constructor keeps the set closed: no code outside Key can construct a fourth key.

The Class Must Rebuild values(), valueOf() and Serialization Itself

For an enum, the compiler writes values() and valueOf(), switch accepts its constants, and serialization writes the constant's name and reads back the existing constant. A class gets none of that.

Spot the Problem: The Restored Config Runs on Defaults

A node caches its Config by serializing it, and reads it back after a restart. Port 9090 was set; the restored config disagrees:

Deserialization creates a new object. The restored map's keys are copies of PORT, and Key inherits identity equals from Object, so get(Key.PORT) misses and returns the default. Nothing throws; the node listens on the wrong port.

Resolve by name, as enum serialization does. readResolve replaces the object the stream produced with the one it returns:

Overriding equals and hashCode by name would fix the map lookup but not ==, which every caller used while Key was an enum. Resolving fixes both.

The Registry Is Yours, and So Is Its Order

values() reads the list each constructor appends to. Move ALL below the constants and the class still compiles but can't load, because the constants' initializers run first, while ALL is still null:

values() returns an unmodifiable copy, so no caller can change which keys exist (an enum's values() returns a new array on every call for the same reason). Write valueOf(String) too, and follow the enum: throw IllegalArgumentException for an unknown name rather than return null.

You can't rebuild switch. A case label is a constant expression, an enum constant or a pattern, and Key.PORT is none of them, so javac refuses case Key.PORT ->. The nearest is a guard, case Key<?> k when k == Key.PORT ->, and a switch of guards always needs a catch-all (default, or an unguarded case Key<?> k), so the compiler never tells you a key was left out. EnumSet and EnumMap require E extends Enum<E>; a HashMap takes their place.

A Sealed Interface of Records Brings Back an Exhaustive switch, but Not Typed Cases

A sealed interface lists its implementations, and each record implements it with its own type argument:

Integer port = new Setting.Port().parse("9090") is typed as before. A switch over the records with no default is checked for coverage:

Add a fourth record, Retries, and this method stops compiling until someone decides what it means:

A default -> branch added "for safety" turns that error off without a warning (even under -Xlint:all), and Retries silently gets whatever the default says. Leave it out on sealed types.

A case doesn't narrow T. Inside case Setting.Port p the setting must be a Setting<Integer>, so a generic parse through a switch looks as if it should work:

javac does not narrow T to Integer inside the case (two more errors follow for the other cases). A (T) on each branch compiles with unchecked warnings, and then a body pasted into the wrong case, case Setting.Port p -> (T) raw.strip(), fails where the opening's cast failed, at the caller:

Put typed behaviour in a method each record implements, as parse is above, and keep the switch for decisions whose result type every case shares.

Records are values, not singletons: new Setting.Port() == new Setting.Port() is false and equals is true. Compare them with equals and key maps with HashMap. A serializable record comes back as an equals copy, so it needs no readResolve. values() is still hand-written, and nothing checks that list; Setting.class.getPermittedSubclasses() at least lists the record classes without going stale.

Summary

  • Java enums can't be generic. javac says enums cannot be generic; JEP 301 proposed them and was withdrawn. Every constant has the enum's one type.
  • A final class with typed constants (Key<Integer> PORT) makes a wrong value or a wrong target type a compile error, and its private constructor keeps the set closed.
  • That class rebuilds what the enum got for free. Without readResolve a deserialized key is a copy that misses every lookup; the registry is declared before the constants; there is no switch on its constants and no EnumMap.
  • A sealed interface of records gets the exhaustive switch back, but a case does not narrow T, so typed behaviour lives in each record's methods. Records compare by equals.

Challenges

  1. An enum may implement a generic interface: enum IntOption implements Option<Integer> next to enum TextOption implements Option<String>, both permitted by a sealed Option<T>. What does that give back (EnumMap, serialization by name), and what does it cost when a setting changes type?
  2. A typed key is sent to another service as JSON. Which of the designs makes the receiving side's lookup simplest, and what replaces readResolve there?
  3. Your team has 40 settings in an Object-valued enum. Plan a migration to typed keys that ships in steps, with the old and the new API side by side.

Design Note: Why a Constant With Its Own Type Fights the Enum

An enum is one type with a fixed list of instances, and the platform relies on that: EnumSet is a bit vector and EnumMap an array, both indexed by ordinal, a switch expression checks coverage against the list, and serialization needs only a name. A constant with its own type argument splits that one type into several, Setting<Integer> and Setting<String>, and each of those services would have to say what it means for them. Java kept enums as they were and left typed keys to classes and sealed hierarchies.

Problem statement


The shop's web sessions live in a session store: after each request the store serializes the Session, and the next request, possibly on another node after a rolling restart, reads it back. The session's attributes used to be an enum. They are now Session.Attribute<T>, so that session.get(USER_ID) returns a Long and session.get(LOCALE) a Locale without a cast.


Since that change shipped, every deploy logs users out and empties their carts, and two older modules that compare attributes with == and look them up with valueOf misbehave.


Finish the three TODOs in src/main/java/practice/Session.java:


  • values(): every attribute, in declaration order;
  • valueOf(String): the attribute with a given name;
  • readResolve(): what a deserialized attribute becomes.


When you're done, a session read back after a restart holds everything it held before, an attribute read back from a stream is the declared attribute itself, valueOf treats an unknown name the way the old enum's did, and no caller can change which attributes exist through the list values() hands out. About eight lines in total.
