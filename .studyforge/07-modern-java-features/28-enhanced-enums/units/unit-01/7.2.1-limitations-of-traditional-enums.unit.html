An enum is a class with a fixed list of instances, and most of its limits follow from that.

An Enum's Type Is Closed: It Can't Extend a Class, Take a Type Parameter, or Be Extended

Three designs come up in review: a Plan enum that inherits pricing rules from a base class, a Key<T> enum whose constants carry their value type, and a plug-in that adds a CRITICAL level to the core Severity enum. None of them compiles (javac 21; the first error of each):

Every enum E already extends java.lang.Enum<E>, and a class has one superclass, so the enum grammar has no extends clause at all: the first error is a parse error. Writing that superclass yourself is refused too:

The constants are all the instances there are, created when the enum class initialises. A subclass could add instances that values(), switch and EnumSet don't know, so subclassing is forbidden. An enum with no constant bodies is implicitly final.

The missing type parameter is a language choice, not an effect of erasure: a generic class can hold static final constants with different type arguments. JEP 301 proposed generic enums and was withdrawn. In Java 21 a constant can't say "my value is an Integer". A shared Object field and a cast at every call site is what teams write instead, and a wrong cast fails at the caller, at run time.

What does work: an enum may implement interfaces, so several enums can share a contract (unit Parameterized Enum Constants), and typed keys are a final class or a sealed interface with records (unit Declaring Generic Enums).

A Constant With a Body Is an Anonymous Subclass, So getClass() Isn't the Enum

A constant may override a method in a body of its own:

Each body compiles to a class of its own, Fee$1 and Fee$2, which extends Fee. These are the only subclasses the language allows: each is final, and Fee becomes implicitly sealed, permitting exactly them (Fee.class.isSealed() printed true). getDeclaringClass() returns the enum for every constant; getClass() returns it only for constants without a body.

Code that identifies a value by getClass() now treats two constants of one enum differently. A formatter registry keyed by class:

The same run printed false for FLAT.getClass().isEnum() and an empty string for FLAT.getClass().getSimpleName(), so a log line built from it shows no type at all. EnumSet.allOf(FLAT.getClass()) doesn't compile, but framework code that holds the class as a raw Class and passes it on gets ClassCastException: class Bodies$Fee$1 not an enum. All of this starts the day someone adds a body to one constant.

What doesn't break: instanceof Fee, switch, EnumSet.of(FLAT), EnumMap keys and Enum.valueOf(Fee.class, ...) all go through the declared enum type. Use getDeclaringClass() wherever code asks "which enum is this?"

  1. Coding practice

    Keep the audit log's type names when a constant gets a body

    • A constant with a body is an instance of an anonymous subclass, so getClass() is not the enum for it; getDeclaringClass() is, and switch, EnumSet and EnumMap are unaffected.

An Ordinal Is a Position, and Inserting a Constant Moves It


ordinal() is the constant's index in declaration order. The opening incident, in two releases and three rows:



Release 1 writes ordinal() into one column and name() into another; release 2 reads both back, with Status2.values()[storedOrdinal] and Status2.valueOf(storedName):



Every row after the insertion point now means the constant before it, and every one is a valid status, so no check fails. Support releases "held" orders that already shipped, and the warehouse ships them again. Rows written by release 2 use the new meaning; after a rollback to release 1 they shift again, and old and new rows can't be told apart. Deleting a constant or sorting the list alphabetically does the same.


Never let an ordinal leave the running process: not into a database column, a message, a cache or a file. Store name(), or a code of your own that you never change (unit Parameterized Enum Constants maps a code back to its constant). Not toString(): a constant may override it with display text that valueOf doesn't know. JPA's @Enumerated defaults to EnumType.ORDINAL, so the safe mapping has to be written: @Enumerated(EnumType.STRING). EnumSet and EnumMap use ordinals inside, which is safe because they never outlive the class.

valueOf Accepts Only the Exact Name and Throws on Anything Else


Storing names moves the risk to the read. valueOf is the generated lookup, and it is strict:




It never returns null. A name it doesn't know is an IllegalArgumentException, but a null name is a NullPointerException, so a catch (IllegalArgumentException e) around it misses the nullable column.


The unknown name is the production case. During a rolling deploy, release 3 writes RETURNED while release 2 still serves reads; a page that lists an order's history calls valueOf on every row, and one new row fails the whole page until the rollout ends, or for good after a rollback. Decide what an unknown name means (skip it, map it to UNKNOWN, or return an empty Optional) at the one boundary where names enter, not by letting the exception decide.


Renaming a constant is now the breaking change that inserting one used to be: old rows hold the old name. Normalising case before the lookup has a trap of its own:



Use toUpperCase(Locale.ROOT).

A Constructor Runs Before the Enum's Static Fields Are Assigned


A currency enum that indexes itself by ISO code as each constant is built looks natural:




BY_CODE is declared after the constants, as it must be, since the constants come first in an enum's body. Static fields are assigned in the order they are declared, and the constants are static fields too, so EUR is constructed while BY_CODE is still null. The compiler refuses a constructor that refers to an enum's own static field, unless the field is a constant variable: MAX_CODES, a static final int initialised with 3, compiled without complaint.


The compiler only checks direct references. Moving the put into a private static void register(Currency c) and calling that from the constructor compiles, and fails when the class first initialises:



A class whose initialisation failed stays failed for the life of its class loader. The first request gets the real cause; every later one gets NoClassDefFoundError, which reads like a packaging problem, until a restart or a redeploy loads the class again. Build the index in a static block after the constants, from values() (unit Parameterized Enum Constants).

Summary


  • An enum's type is closed. It can't extend a class, declare a type parameter (JEP 301 was withdrawn) or be subclassed; enums share behaviour through interfaces.
  • A constant with a body is an anonymous subclass. getClass() is then not the enum; use getDeclaringClass(). switch, EnumSet and EnumMap are unaffected.
  • An ordinal is a position. A stored ordinal silently points at another constant after an insertion, deletion or reorder; store the name or a code of your own.
  • valueOf accepts only the exact name. It throws IllegalArgumentException on an unknown name and NullPointerException on null; decide what an unknown name means where it enters.
  • A constructor runs before the enum's static fields are assigned. A direct read is a compile error, an indirect one an ExceptionInInitializerError that leaves the class unusable.

Challenges


  1. Your table has ten million rows of ordinal() values, and release 2 needs a constant in the middle. Plan the migration so that release 1 and release 2 can run side by side during the rollout. What do you store while both are live?
  2. A partner sends a status you don't know yet. Where do you choose between rejecting the message, mapping it to UNKNOWN, and keeping the raw text, and what does each choice cost a report written a year later?
  3. Search a codebase you know for getClass() in equals, in serializers and in maps keyed by Class. Which of them could receive an enum constant, and what happens on the day someone adds a body to it?


Design Note: Why the Instances Are Closed


Each limit protects one guarantee: the constants listed in the source are all the instances there will ever be. That lets == replace equals, makes switch exhaustive, lets EnumSet be one bit per constant, and makes an enum the simplest safe singleton (unit Use Cases and Examples). A subclass, a type argument per constant, or a constant added at run time would each break one of those. The price is that an enum fits a set you control and change only by redeploying. When the set comes from configuration or from other teams, or each member needs a type or fields of its own, a sealed interface or a registry is the better shape, and you give up the guarantees above.
