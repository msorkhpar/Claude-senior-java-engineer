An Enum Can't Take a Type Parameter, but Its Methods Can, and Each Call Picks T

An enum declaration can't be generic:

JEP 301 proposed generic enums and was withdrawn; unit Declaring Generic Enums covers the replacements. A method of an enum can still declare its own type parameter. This is the Setting that RetryPolicy uses:

With props holding http.retries=3, which of these lines compile?

Both do. T belongs to each call, not to the constant: the compiler infers it from what the caller assigns the result to, so T is Integer in the first line and String in the second. Nothing ties RETRIES to Integer, because a constant has no type argument to carry it; only a typed key (unit Declaring Generic Enums) can make that promise.

An Unchecked Cast Checks Nothing Where It Is Written

javac compiles Setting with a note to recompile with -Xlint:unchecked, which gives:

After erasure, T inside read is Object, so (T) compiles to no check at all. The compiler adds a check (a checkcast instruction) in the caller, at the point where the value meets a concrete type, and only when the target needs it: even an explicit <Integer> adds no check when the result goes into an Object. Where the check lands decides where, or whether, the program fails (r is the result of RETRIES.find(props)):

An Optional<Integer> holding a String is stored without complaint, which is how RetryPolicy started cleanly. It fails in the caller's code at orElse and inside the JDK at map. At equals, which takes an Object, no check runs at all: it answers false and sends a comparison down the wrong branch. None of these places is the enum, so the developer reading the trace starts in the wrong class.

The warning is the one message that points at the cause. Putting @SuppressWarnings("unchecked") on such a method removes it and leaves the bug.

A Class<T> Token Makes the Cast Real, Inside the Method

The method can't see T, but the caller can hand it over as a Class<T> object, a type token. Class.cast checks at run time, so the check moves into the enum:

It compiles with no warning under -Xlint:unchecked. Each constant now parses its own value, and the token decides whether the caller may have it:

A wrong request now fails on its own line, with both types in the message. cast accepts any instance of the token's class, so a supertype such as Number works.

int.class has the type Class<Integer> and so compiles, but no object is an instance of a primitive type, and int.class.isInstance(3) is false; a method that should accept int.class must map it to Integer.class first. And a token names a class, not a parameterized type: List<Integer>.class doesn't compile, so Class.cast can check that a value is a List but not what the list holds. A key missing from props is no longer an empty Optional, either: HOST.read returns null, since cast(null) passes, and RETRIES.read throws NumberFormatException: Cannot parse null string from its parser.

Summary


  • An enum can't take a type parameter, but its methods can, and each call picks T. The constant can't promise a type; any caller can ask RETRIES for a String.
  • An unchecked cast checks nothing where it is written. The value is checked where it meets a concrete type in the caller, or never, so the trace points away from the enum.
  • A Class<T> token makes the cast real, inside the method. It fails at the wrong request, but can't express int (map it to Integer) or List<Integer>.
  • E extends Enum<E> accepts any enum and hands back that enum's own type. Use getDeclaringClass(), which returns Class<E>; getClass() of a constant with a body isn't an enum class.
  • A generic parse reads any enum through getEnumConstants(). It returns the caller's own type and pairs with EnumSet.noneOf(type).

Design Note: Why Enum Is Declared Enum<E extends Enum<E>>


The self-referencing bound lets methods written once in Enum talk about the subclass: Priority.LOW.compareTo(Shipment.CREATED) doesn't compile (Shipment cannot be converted to Priority), and EnumSet and EnumMap get the constants of exactly the caller's enum with no cast in the caller's code.


The price is the signatures. <E extends Enum<E>> is hard to read, and a reader meeting it in EnumSet for the first time has to learn that it only means "an enum". It says nothing about any other type: a setting's value type still needs a token, and a token still can't name List<Integer>.
