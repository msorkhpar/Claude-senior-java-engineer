A contract test compares the order service's JSON with a fixture written as a text block, and it fails. The failure message prints both values, and they match line for line. The serializer returned 34 characters and the fixture holds 35. The extra one is a newline, and it comes from where the fixture's closing """ sits.

A text block is a string literal written over several lines, with stricter delimiter rules than a quote, and each rule decides something about the value. What plain literals cost for multi-line text is unit Limitations of Traditional String Literals; literals, equals and interning in general are units 1.4.x.

The Opening Delimiter Ends Its Line, So Even One Line of Text Takes Two

Two attempts at a short text block, and javac 21's errors:

After the opening """ only white space and a line terminator may follow, and a comment is not allowed there either. The second error in each file points at the closing quotes: javac has read them as another opening delimiter, so editing that end fixes nothing. For the same reason """a""" + """b""" gives four errors, one per delimiter.

So a single word takes two lines. A closing delimiter at the end of the content line gives the word alone, and one on the line right after the opener gives the empty string:

For one line, use a plain literal.

The Closing Delimiter's Line Decides Whether the Value Ends With a Newline

The fixture from the start of the unit, beside the same text closed on its last content line, and the length and last three bytes of each:

Each line break inside the text block becomes \n, including the one before a closing delimiter on its own line, which leaves a \n (0a) after the }. A closing delimiter on the last content line ends that line before any line break, and the value has none. Counting with lines() hides the difference: both hold four lines, because a final terminator ends a line without starting another.

The extra byte matters wherever text is compared or hashed rather than read: an equals, an HMAC over a request body, a checksum of a generated file. A format that wants a final newline, as POSIX text files do, needs the closing delimiter on its own line.

The closing delimiter's column matters as well: placed to the left of the content it keeps that much indentation in every line. Unit Formatting and Indentation covers how the margin is computed.

A Text Block Is a Compile-Time Constant, the Same Object as the Equal Literal


A text block has type String, and javac turns it into the same constant a quoted literal would be. The comparisons below go through a helper, so that javac cannot fold the ==:






javap -v shows why. PAID, HEADER and HEADER_V2 are stored in the class file as ConstantValue strings, and the JVM interns string constants, so each is the one pooled instance of its characters. A text block joined with + to another constant is still a constant. GREETING is computed in the static initializer by a call to String.formatted, which returns a new object.


A string from a request, a file or a StringBuilder is a separate object with the same characters, and == against the constant is false. Tests that pass literals to an == check never see this.


Being a constant also lets a text block go where Java requires one: a case label, an annotation element, a static final field that other classes inline when they compile. The formatted constant can't be a label:




Written as """ … PING""" + " " + VERSION it compiles, and answer("PING v2") returns PONG.


Indentation stripping and escape translation happen in javac, so text read at run time gets neither. A template read from a file keeps its source indentation, and its \t stays two characters. String.stripIndent() and String.translateEscapes() apply the compiler's two steps at run time (units Formatting and Indentation and Escape Sequences and Special Characters):

formatted() Is String.format With the Default Locale, and Every % Is a Specifier


Text blocks have no interpolation. String templates (STR."...") were a preview in Java 21 and were later dropped (javac 25 rejects their syntax), so a text block is filled with format specifiers and formatted(...). Its javadoc defines it as String.format(this, args), and that includes the locale. On a server whose default locale is German:





formatted has no overload that takes a Locale. When the text goes to a machine (a file another system parses, a protocol message, a log someone greps), use String.format(Locale.ROOT, template, …). Keep formatted for text meant for people, where the reader's locale is what you want.


The template is a format string, so every % in it starts a specifier. Text blocks hold CSS, SQL and prose, which use % freely (attempt prints the exception a call throws):




Write a literal percent sign as %%, and never put data into the template. The second example appended a note to the template and failed on % u. Passed to %s, the note is copied unchanged:



SQL built this way is also open to injection; unit Use Cases and Benefits uses bind parameters instead.

Summary


  • The opening """ must end its line. A comment after it doesn't compile, a one-line text block takes two source lines, and a closing delimiter on the next line gives "".
  • The closing delimiter's line decides the final newline. On its own line the value ends with \n; on the last content line it doesn't. lines() can't tell them apart; equals and a hash can.
  • A text block is a compile-time constant String. It is == to the equal literal and can be a case label, but a string built at run time is a different object, and formatted(...) makes a run-time value.
  • formatted is String.format with the default locale. Use String.format(Locale.ROOT, …) for machine-read text, write %% for a percent sign, and pass data only as arguments.

Challenges


  1. Your team's fixtures mix both closing styles. Would you normalise the fixtures, the comparison, or the code under test, and what does each choice hide?
  2. A library exposes public static final String SCHEMA as a text block. You change it and ship only the library jar. Which callers see the change? Try it with two classes compiled separately.
  3. Find the formatted calls in a codebase you know. Which produce text that a machine parses, and which would change if the server's locale changed?


Design Note: Why the Opening Delimiter Must End Its Line


A language could allow text right after the opening """, and some do. Requiring a line break means every content line starts at a column javac can measure. The incidental indentation is the smallest of those columns. Text on the opener's line would start at a column set by the code before it, such as String json = , which has nothing to do with the content.


The cost is that a text block is never a compact inline literal: it spans at least two lines, even when it holds one word.
