The Compiler Removes the Smallest Indentation Among the Non-Blank Lines and the Closing Line

This block sits indented in a method. Its blank line has no spaces at all, because the editor removed them on save:

The compiler counts the leading whitespace of each non-blank line and of the line that holds the closing """, and removes the smallest count from every line. Here that is 8: the incidental whitespace, which comes from where the block sits in the code. The two extra spaces of the nested lines are essential and stay. Re-indenting the whole block doesn't change its value.

Pause on the blank line: it has 0 leading spaces, so why isn't the minimum 0?

Blank lines, empty or whitespace only, take no part in the count, and they come out empty. If they counted, an editor that strips whitespace from blank lines and one that keeps it would compile the same block to two different strings. Moving the Closing Delimiter Left Indents Every Line; Moving It Right Changes Nothing

A deploy bot posts this note to a chat that renders Markdown. Someone moved the closing delimiter back to the method's indentation, 4 spaces left of the content:

The same note with the delimiter 8 spaces to the right of the content:

On the left, the delimiter has the smallest count, so every line keeps the 4 spaces between the delimiter and the content. On the right, its count is larger than the content's and the minimum stays where the content puts it. Moving the delimiter left is how a literal keeps indentation common to every line; otherwise that indentation is removed.

After the incidental whitespace, the compiler removes all whitespace at the end of every line. The reason is the one behind blank lines: trailing whitespace can't be seen, and many editors delete it on save.

To keep it, end the line with \s (unit Escape Sequences and Special Characters). Escapes are translated after the stripping, so the \s becomes a space and protects the spaces before it:

A Tab and a Space Each Count as One Character

The second line of this query was indented with four tabs and four spaces, in an editor that shows a tab as four columns. There it sits four columns right of SELECT, as intended. SourceView shows what the file holds:

The compiler can't know how wide your editor draws a tab, so it counts each whitespace character as one; the stripIndent() javadoc says the same of all whitespace. The tabbed line has 8 leading characters and the others 16, so 8 go: the space-indented lines keep 8 spaces and the tabbed line keeps none. In SQL that only looks wrong; in YAML or Python the line would move to another level. The same lint flags it:

  1. Coding practice

    Show reviewers the value of a text block

    • Blank lines, empty or whitespace only, take no part in the count and come out empty, so the value does not depend on how an editor treats them.
    • A closing delimiter on its own line left of the content leaves the difference in front of every line.
    • A closing delimiter on its own line right of the content removes no more than the content allows.
    • javac removes from every line of a text block the smallest leading-whitespace count among its non-blank lines and the closing delimiter's line; indentation beyond it is kept.
    • A tab counts as one character of indentation, like a space, so a tab-indented line among space-indented ones comes out misaligned.
    • Whitespace at the end of every line of a text block is removed, so padding typed in the source is lost.

At Run Time, Indentation Is Your Job: indent() and stripIndent()


All of the above happens in javac, to the literal. A value inserted by formatted (unit Syntax and Usage of Text Blocks), Java's only interpolation since String templates were withdrawn after previews in Java 21 and 22, arrives later, and nothing re-indents it. A code generator inserts a method body:




Only the first inserted line got the 4 spaces in front of %s. indent(n) adds n spaces to every line, turns every line terminator into \n and ends the result with one. So indent(4) supplies both the indentation and the final line break: the placeholder moves to the block's margin and the closing brace follows it:




indent(n) puts its spaces on blank lines too, and a negative n removes up to -n leading whitespace characters from each line (both in the Reference).


stripIndent() applies the compiler's rule to any string, closing line included: its javadoc counts the last line "even if blank". Text read from a file usually ends with a newline, so its last line is empty, counts 0, and nothing is removed, as with a closing delimiter at column 0:




Strip the final line break first with stripTrailing(), and add it back if the caller needs it. Neither method translates escapes; that is translateEscapes(), unit Escape Sequences and Special Characters.

Summary


  • The compiler removes the smallest indentation among the non-blank lines and the closing line. Blank lines don't count and come out empty, so the value doesn't depend on the editor.
  • Moving the closing delimiter left indents every line; moving it right changes nothing. A delimiter moved left for tidiness adds its distance to every line.
  • Trailing whitespace is removed from every line. Padding needs \s, and -Xlint:text-blocks warns when it is missing.
  • A tab and a space each count as one character. A line indented with tabs among lines indented with spaces ends up misaligned.
  • At run time, indentation is your job. formatted doesn't re-indent inserted lines; use indent(n). stripIndent() removes no indentation from text that ends with a newline.

Design Note: The Closing Delimiter Is a Ruler


Java could have kept every character between the delimiters, or made you mark the margin on every line. It infers the margin instead: the least-indented line, or the closing delimiter, sets it. A block then moves with its code, and the source carries no markers.


The price is that the value depends on whitespace nobody sees: a delimiter moved for tidiness, a tab from another editor, padding the compiler drops, and javac says nothing by default. Where whitespace is part of the format (fixed-width files, YAML, Markdown), turn on the lint and test the value, not the source.
