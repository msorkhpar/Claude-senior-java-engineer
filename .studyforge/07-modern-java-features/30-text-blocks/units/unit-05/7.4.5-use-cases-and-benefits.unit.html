A security scan of the support tool sends x' OR '1'='1 as the e-mail address in the customer search, and the response lists every customer. The query is a tidy text block, filled in with formatted, and three reviewers approved it because it read like the SQL in the DBA's notes.

Text blocks are worth using wherever a program holds text in another language: SQL, JSON, HTML, XML, a long regex. The block changes how that text looks in the Java source. It changes nothing about how the database, the test comparison, the XML parser or the regex engine reads it. Units Syntax and Usage of Text Blocks to Escape Sequences and Special Characters cover the syntax.

A Value Formatted Into SQL Becomes SQL; a Bind Parameter Stays a Value

The search, filled in with formatted and bound with a placeholder:

There is no database here. conn is a java.lang.reflect.Proxy that prints what bound sends to the driver, and each method is called with a normal address and with the scanner's:

formatted copies characters. The input's first quote closes the literal that the template opened, and the rest is a condition that is true for every row. The quotes around %s protect nothing. Escaping quotes yourself means reproducing each database's literal syntax. With a placeholder the statement text is the same constant for every input, and the address travels separately through setString, so it can't change the statement's structure.

The SQL still belongs in a block: one source line per SQL line, no + between lines where a space can go missing (unit Limitations of Traditional String Literals), and a static final constant. Java has no interpolation to use instead; the string templates previewed in Java 21 and 22 were withdrawn.

A placeholder stands only for a value; PreparedStatement's javadoc calls them "IN parameter values". A table name, a column in ORDER BY or a sort direction can't be bound, so code that lets a user choose one picks it from a fixed set of names and rejects anything else. The module's createSelectQuery(table, columns, whereClause) formats all three into the text, so each of them is open to injection.

A Text Block Fixture Has \n Line Endings, So Compare Lines When the Format Doesn't Care

A JSON fixture as a text block is readable and diffs well. It is also exact: every line break in it is \n, whatever the line endings of the .java file (unit Escape Sequences and Special Characters), and whether the last line has one depends on the closing delimiter (unit Syntax and Usage of Text Blocks). Here it is next to the same fixture as a file checked out on Windows with core.autocrlf=true, and next to the serializer's output:

The file has four \r characters more, and the serializer one \n less. JSON doesn't care about either. lines() splits at \n, \r\n or \r and treats a final terminator as the end of the last line, not the start of an empty one, while a trailing space still counts.

A test that compares the fixture file with equals passes on the developer's Linux laptop and fails on the Windows build agent. The usual fix, a more lenient assertion, can go too far: AssertJ's isEqualToIgnoringNewLines deletes the line breaks, so output with two lines run together passes (see the Reference). Decide what the format ignores. JSON ignores the line ending, so compare lines. A signed payload or a file with a checksum ignores nothing, so compare bytes and put the closing delimiter where the producer puts its final newline. Comparing JSON as text at all assumes a fixed key order and spacing; comparing parsed trees with a JSON library doesn't.

A Regex in a Text Block Keeps Its Line Breaks, So It Needs Comments Mode

A long regex laid out one part per line, with a comment for each, is easier to review than one line of 80 characters. In a text block, though, the line breaks and the spaces are part of the string:

Compiled as it is, the pattern demands those spaces, the # comments and the newlines, and it fails to match without any error. Pattern.COMMENTS, or (?x) at the start of the pattern, makes the engine ignore white space and treat # to the end of the line as a comment. That mode has its own cost, shown by spaced in the last line: a space you meant to match is ignored too. Write it as \\x20, or \\s if any white space will do; in Java's comments mode even [ ] is empty and fails to compile. A single \s is the text block's own escape for a space (unit Escape Sequences and Special Characters), so the engine never sees it. The other backslashes are doubled, as in any literal (unit Limitations of Traditional String Literals).

Summary

  • A value formatted into SQL becomes SQL. Keep the statement a constant text block with ? placeholders and bind the values; choose identifiers from a fixed set.
  • A text block fixture has `\n` line endings and an exact final newline. Compare lines when the format ignores line endings, bytes when it doesn't, and avoid assertions that drop the breaks.
  • Markup keeps its quotes, but values still need escaping. Escape & first, then <, > and the quotes, or a company name breaks the XML and a visitor's name becomes markup.
  • A multi-line regex needs comments mode. Without it the layout is part of the pattern; with it a space you mean must be escaped.

Challenges

  1. Find the formatted and + calls that build SQL in a codebase you know. Which take a value a user can influence, even indirectly through a stored record?
  2. Your contract tests compare JSON as text. What would a parsed comparison catch that comparing lines doesn't, and what would it stop catching?
  3. A team keeps 200-line SQL reports in text blocks. When would you move them to .sql resource files, and what do you lose in the move?

Design Note: Why a Text Block Escapes Nothing for You

A text block produces a plain String, and the compiler can't know whether that string will reach a database, a browser or a regex engine, each with its own escaping rules. So the escaping belongs with the code that knows the destination: the driver binds values, an encoder or a template engine escapes markup. String templates would have let a processor escape each value for its target, and they were withdrawn after two previews. So the code that calls formatted escapes every value it passes, or nothing does.
