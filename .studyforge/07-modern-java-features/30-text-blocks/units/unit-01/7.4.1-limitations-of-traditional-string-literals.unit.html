At 02:00 the nightly cleanup job logged out every user of the shop. It was meant to delete only expired sessions, and its DELETE had been copied from the DBA's script, comment included, one "..." + per line. Nothing failed: the statement ran and reported a row count.

A traditional string literal holds one line of text, and quotes, backslashes and line breaks inside it are written as escapes. Multi-line SQL, JSON and HTML pay for that, in four ways, one per heading below.

Every Quote and Backslash Is Written Twice, and a Wrong Backslash Can Still Compile

Inside a literal, " is written \" and \ is written \\. JSON that itself contains an escaped quote gets both layers:

That is hard to review, but a dropped \" usually fails to compile. A dropped backslash fails only when the letter after it is not a known escape:

Pause before the next run: a Windows path and a regex for the whole word cat, each written with single backslashes. Do they compile?

Both compile. \t and \n are valid escapes, so the path holds a tab (9) and a newline (10), and any code that opens it looks for a folder that doesn't exist. \b is a valid escape too: backspace, U+0008. The regex engine never sees a word boundary, so the pattern matches nothing, and an alert built on it never fires.

javac processes the escapes first, and only what is left reaches the regex engine, the JSON parser or the file system. Each backslash the inner language needs is \\ in the source, and a single one is either an error or a different character, depending on the letter after it. The Reference lists the letters that compile.

    Make the error alert fire and the log archive land on the share

    • Inside a traditional literal every quote and backslash meant for the text is written with a backslash in front, so text for another language that has escapes of its own (JSON, regex, a Windows path) carries two layers.
    • Only escapes javac doesn't know are errors; a single backslash before t, n, b, r, f or s compiles and silently puts a control character or a space into a path or a regex.

A Value Split Across Lines Has a Seam at Every +, and a Missing \n or Space There Changes It


A literal can't contain a line break (javac says unclosed string literal), so a statement copied from a script becomes one literal per line, joined with +. These two came from the cleanup job and from a report:



Printed, then run against an in-memory H2 database holding three sessions, two of them expired:



The value holds exactly what is between the quotes. The line breaks you see in the editor are outside them, so they are not in the string. In the script, the comment ended at the end of its line; in the string there is no end of line, and -- comments out the WHERE. A DELETE without a condition is valid SQL, so the database deleted every row and reported success. The second seam lost a space, and fails only when it runs, with an error that names a column.


The + itself costs nothing at run time: both expressions are constant, and javac folds each into one string (javap shows a single ldc per statement; unit String concatenation). The cost is that every seam needs its \n or its space by hand, and a reviewer reading the Java sees the layout of the source, not of the value. If you build multi-line text from literals, end every piece with \n, so comments stay terminated and the value prints the way the source looks.


\n Is Always a Line Feed; %n, println and lineSeparator() Follow the Platform


Which newline goes at the end of each piece? The same program, run as it is and with line.separator set to \r\n, the value Windows uses (hex prints the UTF-8 bytes; buf holds what a PrintStream's println("ok") wrote):




\n is decided by javac: it is U+000A in the class file, whatever machine runs it. %n, println and System.lineSeparator() use the line.separator property as the JVM started with it, which the javadoc gives as "\n" on Unix and "\r\n" on Windows.


A test that compares a report built with %n against an expected "...\n" passes on the Linux CI and fails on a colleague's Windows laptop. In the other direction, a format that requires CR LF, such as HTTP/1.1 headers, SMTP or CSV per RFC 4180, gets bare LF from %n on a Linux server. Choose by where the text goes: a format with fixed line endings gets the escape it requires (\r\n or \n), and only text for the local console or a local file gets %n.

A Text Block Removes the Escaped Quotes and the Seams, Not the Backslashes or the Values


A text block (Java 15, unit Java 15) is one literal between """ delimiters that may span lines. Here is the JSON, once concatenated and twice as a block, one of them with a placeholder in the style of other languages:




The quotes need no escape and the line breaks are real ones, so there are no seams to get wrong: the cleanup DELETE written as a block, one source line per SQL line, deleted 2 of the 3 sessions. filled is an ordinary String, equal to the concatenated one.


A text block has no interpolation: ${sku} is six characters of text, and values still go in through formatted, +, or, for SQL, bind parameters (unit Use Cases and Benefits). String templates (JEPs 430 and 459) were previews in Java 21 and 22 and were then withdrawn: javac 21 rejects STR."..." without --enable-preview, and javac 25 rejects its \{ as an illegal escape. And a block still processes escapes, so the regex problem of the first section is unchanged:



A block's line breaks are \n on every platform, so the previous section still applies when one is compared with output written with %n. How the delimiters and the trailing newline work is unit Syntax and Usage of Text Blocks, indentation is Formatting and Indentation, and the block-only escapes are Escape Sequences and Special Characters.

Summary


  • Every quote and backslash is written twice. Unknown escapes fail to compile, but \t, \n, \b, \r, \f, \s and octal ones such as \1 compile and silently change a path or a regex.
  • Text split across lines has a seam at every +. A missing \n lets a SQL -- comment swallow the rest of the statement, which then reports success; a missing space joins two words, and the statement fails only when it runs. The + of literals is folded at compile time and costs nothing.
  • \n is fixed; %n, println and lineSeparator() follow the platform. Write the escape a format requires, and keep %n for local output.
  • A text block removes escaped quotes and seams. It still processes backslash escapes and has no interpolation; string templates were withdrawn.

Design Note: Why a Text Block Still Processes Escapes


A text block could have been raw, with every backslash kept as written. Java chose to process the same escapes as a traditional literal, so moving a literal into a block never changes what an escape means, and a block can still say \t or \r\n where an invisible character is needed. The cost is the one the first section measured: a regex or a Windows path in a block doubles its backslashes exactly as before, and a single \b is still a backspace.
