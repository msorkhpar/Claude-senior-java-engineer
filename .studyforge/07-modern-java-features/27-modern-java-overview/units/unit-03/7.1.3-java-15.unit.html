An order service moves from Java 11 to Java 21 in one step. The first pod on 21 never comes up:

Someone deletes the option from the start script. The pod starts, and the first order that needs a discount rule fails (the trace is from the reproduction in the Nashorn section):

Both failures go back to Java 15 (September 2020), a release between two LTS releases that many teams skipped, meeting its changes all at once. Most of what 15 made standard has its own unit: text blocks (JEP 378, units Limitations of Traditional String Literals to Use Cases and Benefits), helpful NullPointerException messages switched on by default (unit Throwing exceptions using the throw keyword), hidden classes, which lambdas have used since then (JEP 371, unit Introduction to lambda expressions), and ZGC and Shenandoah as production collectors (JEPs 377 and 379, modules 40 and 43). Records and sealed classes were still previews in 15 (units Defining and using records and Defining sealed classes and interfaces).

Outputs are from Temurin 21.0.12 unless a line says Java 25 (Temurin 25.0.4). Java 15 itself was not run; where a claim is about 15, the JEP is named.

Preview Features Must Be Switched On Twice, at Compile Time and at Run Time

A preview feature is a complete language or VM feature that ships switched off, so that a later release can still change it (JEP 12). On 21, string templates (JEP 430) were one:

javac needs the flag and a release; java needs the flag:

The compiler marks the class file: major version 65 is Java 21 (the release number plus 44), and minor version 65535 means "uses preview features". The JVM checks that mark when it loads the class, so the java command needs the flag too.

The compiler plugin and the test runner get --enable-preview, and the start script doesn't. The build is green, and the service fails on its first class load.

A Preview Class File Runs Only on the Release That Compiled It

The same Greeting.class, on Java 25 with the flag:

An ordinary class compiled for 21 loads on every later JVM. A preview class doesn't, because the next release may have changed the feature. String templates were withdrawn after Java 22, and Java 25's javac reads \{ as a bad escape:

The compiler applies the same rule. Java 21's javac compiles for older releases, but previews only for its own. Point is a record and Shape a sealed interface:

So code that used records on 15 (JEP 384, their second preview) had to be rebuilt on 16, where records became standard, and its sealed types (JEP 360) were rebuilt as a preview again on 16 (JEP 397) and once more on 17. The cost lands on whoever shares the code: one internal library built with --enable-preview pins every service that uses it to that release, until the library is rebuilt without previews. Keep previews out of anything another team deploys.

Nashorn Is Gone, and the Engine Lookup Returns null Instead of Failing

The discount rules from the opening are JavaScript, evaluated through the scripting API:

Java 15 removed the Nashorn JavaScript engine (JEP 372), which 11 had deprecated for removal. On 21 the JDK ships no script engine. Looking up "nashorn" and "js", and counting getEngineFactories(), prints:

getEngineByName returns null for a name it doesn't know; it throws only when the name itself is null. In a service that looks the engine up at startup, the failure moves to the first use: the first order with a rule. The NPE message names engine because the class was compiled with -g; without it the message says "<local1>" is null (unit Throwing exceptions using the throw keyword).

Code that used Nashorn's own API fails differently, and the build can hide it. Compiled with --release 14, it only warns:

--release 14 checks the code against 14's API, not against the JVM that will run it. With --release 15 the same source doesn't compile (package jdk.nashorn.api.scripting does not exist). Build with the --release you run on.

The fix has two parts. Put an engine on the class path as a dependency: the standalone OpenJDK Nashorn and GraalJS both register through javax.script (not run here). Code that imported jdk.nashorn.api.scripting also has to change its imports, since the standalone engine has its own package. Then check the lookup's result when the service starts, so that a missing engine stops the deploy instead of the first order.

A Removed JVM Option Is Ignored for a While, Then Stops the JVM From Starting

Java 15 switched biased locking off by default and deprecated its options (JEP 374). Biased locking made a lock that only one thread ever takes nearly free; JEP 374 argues that modern code rarely gains from it and that it complicated the JVM. The cost falls on old code that locks without contention, such as Vector, Hashtable and StringBuffer: each uncontended synchronized pays an atomic instruction again. JDK 18 removed the code.

A HotSpot option leaves in three stages, and Java 21 shows all three:

A deprecated option still works and warns. An obsolete one is accepted and ignored, with a warning, and the JVM starts. An expired one is unknown, and the JVM refuses to start. The option that 21 ignores, 25 refuses:

Upgrading one LTS at a time leaves a release of warnings to clean up; jumping from 11 to 21 can skip them, and the first sign is a crash loop. Before an upgrade, start the new JVM with the production options and -version: it fails the way the pod would, in a second.

Summary

  • A preview feature must be enabled twice. javac --enable-preview --release N marks the class file (minor version 65535), and java --enable-preview must accept it.
  • A preview class file runs only on the release that compiled it. One shared library built with previews pins every service that uses it to that release.
  • Nashorn is gone since 15, and `getEngineByName` returns `null`. Check the engine at startup, and build with the --release you run on.
  • A removed JVM option is deprecated, then ignored, then refused. Jumping several releases can skip the warning and go straight to a JVM that won't start.

Design Note: Why a Preview Is Tied to One Release

Java promises that a class file compiled today loads on every later JVM. Previews are the one exception, and the exception is what lets Java ship features early: if preview class files ran on later releases, the code built against a preview would freeze its first design. String templates were withdrawn, and no code built without previews broke.

The cost falls on teams that let a preview leak into shared code. The JVM's refusal is immediate and clear, but it comes at upgrade time, from a jar nobody remembers building with the flag.
