  20. Check yourself: Java 21

A team moves its service from Java 17 to 21 in two steps. First the jar built for 17 runs on a 21 JVM for a month without a problem. Then the build's --release goes to 21, and a class nobody has changed in three years stops compiling: getFirst() in Batch cannot implement getFirst() in List. Java 21 only added to the library. How did that break a build?

Virtual threads (units Lightweight threads for high concurrency and Differences between virtual threads and platform threads) and record patterns and pattern matching for switch, final in 21 (units Record patterns (Java 19+) and Switch patterns (Java 19+)), have their own units, and so does generational ZGC (unit Garbage Collection Algorithms), opt-in on 21 with -XX:+ZGenerational. This page covers sequenced collections and a few small methods with sharp edges. Every output is from Java 21.

Ordered Collections Now Share getFirst, getLast and reversed(); Unordered Ones Don't Get Them

Before 21, the last element of a List was list.get(list.size() - 1), of a Deque getLast(), of a SortedSet last(), and of a LinkedHashSet a loop over the whole set. JEP 431 adds SequencedCollection, SequencedSet and SequencedMap, one set of first, last and reverse methods for every collection with a defined order (listed in the Reference). List, Deque, SortedSet, SortedMap, LinkedHashSet and LinkedHashMap now extend or implement them. HashSet and HashMap don't: they have no order, so the type doesn't offer a first element.

attempt prints what a call returned, or what it threw:

getFirst() on an empty collection throws, while firstEntry() on an empty map returns null, as NavigableMap.firstEntry() always has. Replacing get(0) with getFirst() changes the exception, and NoSuchElementException is not an IndexOutOfBoundsException, so a catch (IndexOutOfBoundsException e) around it stops catching. A sorted set decides positions by its comparator, so it refuses addFirst and addLast, and an unmodifiable list refuses them as it refuses add.

On LinkedHashSet and LinkedHashMap, addFirst and putLast Move an Existing Entry

add and put keep insertion order, so an element already present stays where it was. The new methods name a position, so they move it there. A "recently opened" list built with add never moves a file the user opens again; built with addFirst, it moves the file to the top.

reversed() Is a View: Writes Go Through, and Later Changes Show Through

reversed() copies nothing. It returns a view over the same elements, in the other order:

The caller's add went to the end of the view, which is the front of events. A view costs the same at any size, which is why the JDK returns one. But a method that returns events.reversed() to show a feed newest first gives every caller write access to the feed, and a caller that keeps the view sees events that arrived later. Return Collections.unmodifiableList(events.reversed()) for a read-only live view, and List.copyOf(events.reversed()) for a snapshot. Iterating the view while the list changes underneath throws ConcurrentModificationException, as iterating the list itself would.

A Class That Already Had These Names Runs on 21 but No Longer Compiles for It

List.getFirst() is a new default method, so a getFirst() that a class already had now overrides it, and must follow the rules for overriding. The class from the opening:

javac --release 17 Batch.java compiles it. javac --release 21 Batch.java doesn't:

The same happens to a package-private String getLast() helper in a subclass of ArrayList<String> (attempting to assign weaker access privileges; was public), and to a class that implements both List<E> and Deque<E>, which now inherits two reversed() methods with unrelated return types (both define reversed(), but with unrelated return types). Unit Java 8 (LTS) covers that conflict between two defaults: the class must declare a reversed() whose return type is both, as LinkedList does with LinkedList<E> reversed().

The class file compiled for 17 still runs on 21:

The JVM links a call by name and full descriptor, return type included, so getFirst() returning Optional and List.getFirst() returning Object are two different methods to it. The clash is a rule of the language, which only javac applies, and nothing recompiled Batch until the build moved to --release 21. Build with --release 21 before you deploy on 21, and rename the colliding method (firstRow()). Giving it the interface's signature instead would change what every caller that sees it as a List gets. A method that already matched, public with the same return type or a subtype of it, compiles and now silently overrides the default.

Math.clamp Narrows a long Without Wrapping and Refuses a Reversed Range

Math.clamp(long value, int min, int max), new in 21, returns an int, so it narrows safely. A paging endpoint reads ?size=4294967396 as a long:

The cast keeps the low 32 bits, and 4,294,967,396 is 2³² + 100, so the oversized request becomes a page of 100 that passes every later check. Clamping the long gives the maximum. A reversed range throws, where the Math.max(min, Math.min(value, max)) that clamp replaces quietly returned min. A NaN value comes back as NaN: clamp doesn't decide what an undefined ratio means, so the caller has to.

The Range Form of indexOf Throws Where the Old Form Returned -1

String.indexOf(ch, beginIndex, endIndex) (and the same with a String to find) searches only [beginIndex, endIndex). Unlike indexOf(ch, fromIndex), it checks its range:

The result, 10, counts from the start of the string, not from beginIndex. The old form returns -1 for a fromIndex past the end; the range form throws for an endIndex past the length, a negative beginIndex, or beginIndex > endIndex. The last one is easy to hit: the last field of a line has no ; after it, so end is -1, and a parser that works for every other field throws on that one.

isEmoji and StringBuilder.repeat Have Code-Point Overloads, and isEmoji Says Yes to Digits

Character.isEmoji(int) and its siblings (isEmojiPresentation, isExtendedPictographic and others) take a code point. An emoji outside the Basic Multilingual Plane is two chars in a String:

chars() hands isEmoji the two surrogate halves, and neither is an emoji. codePoints() finds it, but isEmoji also says yes to user42: the methods follow the Unicode emoji data, where the digits, # and * have the Emoji property because they can start a keycap sequence such as 1️⃣. A filter meant for pictographs tests isExtendedPictographic, which is false for digits.

StringBuilder.repeat(int codePoint, int count), beside repeat(CharSequence, int count), has the same int parameter. A char widens to int, so repeat(5, '-') compiles and appends code point 5 forty-five times.

Summary

  • Ordered collections share `getFirst`, `getLast` and `reversed()`; `HashSet` and `HashMap` don't. getFirst() throws on an empty collection where firstEntry() returns null; sorted and unmodifiable collections refuse addFirst. On linked sets and maps, addFirst/putLast move an existing entry and add/put don't.
  • `reversed()` is a view. Writes go through to the original and later changes show; copy it for a snapshot, wrap it for a read-only view.
  • A class that already had these names runs on 21 but no longer compiles for it. A different return type, weaker access, or List plus Deque all fail at --release 21.
  • `Math.clamp` narrows a `long` without wrapping and throws on `min > max`. Clamp before you cast; NaN passes through.
  • The range form of `indexOf` throws where the old form returned -1; its result counts from the start of the string.
  • `isEmoji` and `StringBuilder.repeat(int, int)` take code points, and isEmoji is true for digits.

Challenges

  1. Your codebase has a UserList extends ArrayList<User> with public User getLast() that returns null on an empty list. It compiles on 21. What do callers that see it as a List get now, and what does users.reversed().getFirst() do? Run it before you guess.
  2. A REST endpoint returns items.reversed() from a field. Measure List.copyOf(items.reversed()) on 10, 10,000 and 1,000,000 elements, and decide when the view is worth the risk.
  3. Find three places in your code that reach an end of a collection with get(0), iterator().next() or last(), and decide for each whether getFirst() changes what happens when it is empty.

Design Note: Why the New Methods Are Defaults on Old Interfaces

JEP 431 could have added a new collection hierarchy beside the old one. Then no existing ArrayList would have gained getFirst(), and a method taking a SequencedCollection would accept none of the collections already in use. Adding default methods to List, Deque and SortedSet made every existing ordered collection sequenced on the day of the upgrade, without a change to its code. The price is the one the opening paid. A subclass whose getFirst, reversed or addFirst had another return type or narrower access stops compiling, and one that matched compiles and silently overrides the new default. An interface you publish has the same trade: a new default method is binary compatible with every implementer, and source compatible only with those that never chose the same name with a different signature.
