An order service moves from Java 11 to 17. On 11 its log started with one line nobody read, WARNING: An illegal reflective access operation has occurred, naming a serialization helper. On 17 the service doesn't start: the same helper calls setAccessible(true) on a private field of a JDK class and gets InaccessibleObjectException.

That is the change in 17 most likely to stop an upgrade. Sealed classes (2.5.x), records (2.4.x), pattern matching for instanceof (Pattern matching for instanceof (Java 14+)) and Stream.toList() (Terminal operations (forEach, reduce, collect)) have their own units; the Reference lists them. Outputs are from Java 21; behaviour specific to 17 is cited by its JEP and was not run here.

Java 17 Refuses Deep Reflection into the JDK, and --illegal-access Is Gone

This program reads the private size field of an ArrayList, the way serialization and mocking libraries used to read JDK internals:

Since Java 9 the JDK is split into modules, and java.base doesn't open its packages: code outside may use their public API but may not reflect on their private members. Up to 15 the JVM let such access through and printed the warning from the opening, once, on the first access. Java 16 denied it by default, and --illegal-access=permit still turned it back on (JEP 396). Java 17 removed the option (JEP 403), so the JVM ignores it with the warning above.

Public members of exported packages are as reachable as before, and sun.misc.Unsafe stays open on purpose: it lives in the jdk.unsupported module, which opens sun.misc (JEP 260).

InaccessibleObjectException is unchecked and is not a SecurityException. Reflective code written before 9 typically catches SecurityException and IllegalAccessException, so this one escapes both catches and, usually at startup, stops the application.

Open One Package by Name, or Stop Reaching Inside

When a library can't be upgraded yet, open each package it needs, by name, on the command line:

--add-opens module/package=target opens one package to one module; ALL-UNNAMED means the class path. An executable jar can carry the same in its manifest's Add-Opens attribute, which java -jar honours. Your own module-info.java can't do it: a module opens only its own packages.

An opened package works only while the JDK's private fields stay as the library expects, and the JDK promises nothing about them. String's private value was a char[] up to Java 8 and has been a byte[] since 9 (JEP 254). The lasting fix is to stop reaching inside: call list.size(), move to a library version that uses public API, or use a VarHandle on your own fields instead of Unsafe.

Code that must reflect on objects it doesn't own, such as a debug dump or a generic serializer, should expect the refusal. trySetAccessible() returns false instead of throwing, as the first line of the output shows, and the code can fall back to toString() or skip the field.

RandomGenerator Names the Algorithm, and Replay Needs the Algorithm and the Seed

Java 17 added java.util.random (JEP 356): a root interface, RandomGenerator, and a factory that finds algorithms by name. With --release 16 the package doesn't exist:

Two generators with the same algorithm and seed, one with another algorithm, and the old Random:

A sequence is fixed by the algorithm and the seed, so a test, a simulation or a chaos run that must replay records both. Two shortcuts lose one of them:

  • RandomGenerator.of("L64X128MixRandom") takes no seed; it is seeded differently every time.
  • RandomGenerator.getDefault() picks the algorithm for you. On 21 it is L32X64MixRandom, and its javadoc says there is no guarantee it stays the same over time.

Names are case-sensitive: L64x128MixRandom throws IllegalArgumentException.

Random, SecureRandom, SplittableRandom and ThreadLocalRandom all implement RandomGenerator, so a method that takes a RandomGenerator accepts any of them, and a test can pass a seeded one.

Spot the Problem: A Trimmed Runtime Has No Algorithms

A team builds a small runtime with jlink, letting jdeps choose the modules. Jl prints the class of RandomGenerator.of("Random"), then asks for "L64X128MixRandom":

The interface is in java.base, but on 21 the new algorithms live in the jdk.random module, found at run time through ServiceLoader. jdeps sees no reference to it, so the image ships without it, and only the legacy names resolve. Add --add-modules jdk.random to the jlink call.

A Generator Shared Across Threads Is Either Slow or Wrong

Random is thread-safe: it updates its seed with a compare-and-set. The new algorithms are not, as their javadoc says. Four threads draw 250,000 longs each from the generator they are given, and we count every value that came out a second time:

Among a million draws from 2^64 possible values, a correct generator practically never repeats. The shared one let several threads read the same state before any of them wrote it back, and they produced the same numbers: 17 % of the draws were repeats, with no exception. For request ids that means collisions; for sampling, a skewed sample.

The shared Random gives no repeats, but every draw is a compare-and-set on one field. Eight threads drew 10 million ints each on a 20-CPU machine:

ThreadLocalRandom.current() returns a generator whose state lives in the calling thread. Its javadoc asks for the form ThreadLocalRandom.current().nextInt(...) at each use. Storing the result in a field breaks this:

Two worker threads, started fresh in each run, draw four values from JITTER, then four from current(). The program ran twice:

The stored instance reads the calling thread's state, and a thread that never called current() has never had it seeded. Its numbers then depend only on the thread's id, so with the same JVM flags and CPU count they are the same after every restart. Used as retry jitter, every identical pod of a service backs off by the same delays after a deploy, and the retries arrive together.

For a seeded run on several threads, give each thread its own generator, derived from the run's seed so it replays too.

The Security Manager Still Compiles, Warns, and Since 18 Refuses to Install

JEP 411 deprecated the Security Manager for removal in 17. It was the in-process sandbox for applets and plugin hosts. This program asks whether one is installed, then installs one:

The [removal] warnings appear without any -Xlint option, one per use. Compiled with --release 11, the same source gives none, because javac checks it against the 11 API, where nothing here was deprecated. A build pinned to an old release hides the change until the code runs on the new one.

At run time the change came one release later. On 17, setSecurityManager still installed it, with a warning (JEP 411, not run here). Since 18 it throws, as above, unless the JVM starts with -Djava.security.manager=allow; on 24 no flag enables it (JEP 486). A plugin host upgraded to 21 with a catch-all around that call runs its plugins with no sandbox at all. JEP 411 gives the reasons: few applications used it, and its permission model was brittle and hard to program against. Most deployments now isolate with containers or operating-system processes instead.

Summary

  • Java 17 refuses deep reflection into the JDK. setAccessible(true) on a private JDK member throws the unchecked InaccessibleObjectException, and --illegal-access is ignored.
  • Open one package by name, or stop reaching inside. --add-opens or the Add-Opens manifest attribute opens a package; reflective code uses trySetAccessible() and falls back.
  • `RandomGenerator` names the algorithm, and replay needs the algorithm and the seed. RandomGeneratorFactory.of(name).create(seed) replays; RandomGenerator.of and getDefault() don't. A jlink image needs jdk.random.
  • A generator shared across threads is either slow or wrong. The new algorithms repeat values under a race, a shared Random makes the threads queue, and a stored ThreadLocalRandom repeats across restarts.
  • The Security Manager is deprecated for removal. Since 18 it doesn't install by default, and --release 11 hides the warnings.

Challenges

  1. Your build has 40 dependencies. How do you find every reflective access into the JDK before the upgrade rather than in production, and which of them do you fix with --add-opens?
  2. A load test must replay a failure seen last week, on 16 threads. Design the seeding so that adding a seventeenth thread doesn't change what the first sixteen draw.
  3. A library you depend on calls System.getSecurityManager() on every request. What does that cost on 21, and what changes on 24?

Design Note: Why the JDK Closed Its Internals

For twenty years any jar could read and write the JDK's private fields, and many did, so a change to the layout of String or ArrayList broke libraries that had nothing to do with it. Strong encapsulation gives the JDK back the right to change its internals. The price fell on the libraries that relied on them: they needed new versions and, in the meantime, --add-opens lines that every application had to copy into its start script. sun.misc.Unsafe was left open because taking it away before libraries could move to VarHandle (9) and a public memory API (final in 22) would have left them with nothing.

Problem statement


The support team's /debug/dump endpoint shows the instance fields of whatever object an engineer points it at. Since the service moved to Java 17, pointing it at a JDK object, such as the ArrayBlockingQueue behind the job scheduler, makes the endpoint answer 500, and the engineer gets nothing at all.


FieldDump.dump(...) already walks the fields. Finish the TODO in src/main/java/practice/FieldDump.java: read(field, target) returns the field's value as text, or FieldDump.HIDDEN when the JVM won't let the dump read it.


When you're done, the service's own objects show every field, private ones included; a JDK object shows whatever the JVM lets it read and <hidden> for the rest; and no object makes the dump fail. The tests run without any --add-opens option. About five lines.

Problem statement


The payment team runs chaos tests against its gateway: several workers send calls at the same time, each on its own thread, and ChaosRun decides which of each worker's calls fail. Each run is named by an algorithm and a seed, which the report prints, for example L128X256MixRandom / 4417. Last week a run found a double charge, and nobody could make it happen again from the name in the report.


ChaosRun.failingCalls(...) already makes one draw per call. Finish the TODO in src/main/java/practice/ChaosRun.java: generatorFor(worker) returns the generator that worker draws from in this run.


When you're done, every worker draws with the algorithm the run is named by, and a new ChaosRun with the same algorithm and seed fails exactly the same calls for every worker, in whatever order the workers start. Within one run the workers fail different calls from each other, and draw on their own threads without getting in each other's way. About three lines.

  • each worker gets a generator of its own, since workers draw at the same time on their own threads
    • 

  • the algorithm the run names is the one the workers draw from
