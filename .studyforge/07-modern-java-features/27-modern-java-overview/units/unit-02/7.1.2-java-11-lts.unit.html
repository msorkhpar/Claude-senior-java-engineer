An order service built for Java 8 moves to Java 21. The build stops at package javax.xml.bind does not exist. A reporting jar nobody rebuilt starts, passes its health check, and throws NoClassDefFoundError on the first export. A sign-up check rewritten with Set.of on the way throws NullPointerException for a missing username. All of this arrived in Java 9, 10 and 11, and 11 was the first long-term-support release to carry it.

Features of 9 to 11 taught in other units are listed in the Reference.

Java 11 Removed the Java EE Modules, and Code Built for 8 Fails at Its First Use

JEP 320 took JAXB (java.xml.bind), JAX-WS, JavaBeans Activation, CORBA and the java.transaction module out of the JDK. This helper compiles for Java 8:

Built with javac --release 8, then run on Java 21:

The JVM loads a class when code first needs it, so the error waits for the first call to hex: a smoke test that never exports passes. With --release 11 the import fails to compile. The fix is a dependency, and its version matters:

The 4.0.2 jar holds jakarta.xml.bind.DatatypeConverter: Jakarta EE 9 renamed the packages, so the newest jar needs new imports too. For hex or Base64 alone, the JDK has HexFormat (17) and java.util.Base64 (8).

Java 9 and 10 differ. The modules were still in the JDK but not resolved by default: javac --release 9 reports package javax.xml.bind is not visible, and --add-modules java.xml.bind fixes it. With --release 11 that flag fails: module not found: java.xml.bind.

var Takes the Initializer's Type, Which Is Not Always the Type You Meant

Java 10's var gives a local variable the type of its initializer, fixed at the declaration:

The prices add up to 26.04. 0 makes total an int, and total += p means total = (int) (total + p), so each sum loses its fraction. An invoice that drops its cents passes every test with whole-number prices. javac -Xlint:lossy-conversions (Java 20 and later) flags the line; var total = 0.0 or a declared type fixes it.

With nothing to infer from, the diamond makes names an ArrayList<Object> that takes the 42, and the error moves to the read: String first = names.get(0) doesn't compile.

var needs an initializer with a type, and only declares local variables (the reference lists what javac refuses). Java 11 allowed it on lambda parameters, so a parameter can carry an annotation and keep an inferred type: (@NonNull var s, var n) -> s.length() + n fails with --release 10. var is not a reserved keyword: a variable named var compiles.

List.of and Map.of Build Unmodifiable Collections That Reject null, Even in a Lookup

Java 9's factories (List.of, Set.of, Map.of, and copyOf from Java 10) return collections that throw UnsupportedOperationException on add, set or remove, and refuse null:

A HashSet answers false for null; Collection.contains lets a null-refusing collection throw, and Set.of does. Replacing a new HashSet<>(Arrays.asList(...)) constant with Set.of(...) turns every sign-up without a username into a 500. Check for null before the lookup.

Collections.unmodifiableList is a read-only view: a caller holding it sees every later change to the list behind it. List.copyOf takes a snapshot.

Map.of and Set.of don't keep insertion order, and their order can change between JVM starts. One program, run three times:

A test that compares a printed map passes on one run and fails on the next. Where order matters, sort, or use a TreeMap or LinkedHashMap.

  1. Coding practice

    Close the sign-up tickets left by the Java 21 move

    • List.copyOf takes a snapshot; Collections.unmodifiableList is a view that shows later changes to the list behind it.
    • Collections from Set.of, List.of and Map.of throw NullPointerException on contains(null) or get(null), where HashSet answers false.
    • Map.of and Set.of iteration order is unspecified and changes between JVM starts.

lines() Splits on Every Line Terminator; split("\n") Leaves the \r Behind


Java 11 added isBlank, strip, stripLeading, stripTrailing, lines and repeat to String. strip and isBlank use Character.isWhitespace, where trim removes everything up to U+0020 (unit String methods (e.g., length(), charAt(), substring())). lines() fixes a common bug:




split("\n") cuts at line feeds and leaves each carriage return at the end of its line, so no line equals "OK" and every upload from Windows fails validation. lines() ends a line at \n, \r\n or \r, keeps an empty line in the middle, and adds none after a final terminator. Skip the empty line with isBlank(), which also skips a line of spaces or tabs.

HttpClient's Connect Timeout Bounds Only the Connection, and an Error Status Is a Response


java.net.http.HttpClient (standard since 11) is the modern alternative to HttpURLConnection. The examples call a com.sun.net.httpserver.HttpServer on 127.0.0.1 at base: /quote doesn't answer until the program lets it, and /stock answers 503.




A request without its own timeout waits as long as the server takes ("block forever", says the javadoc). When a partner API stalls, every thread that calls it parks in send() until the pool is used up and the service stops answering its own callers.


The /stock call:




send throws IOException on I/O failures, never because of the status. A 4xx or 5xx returns like a 200, so code that reads the body without checking statusCode() treats an error page as data. Build one client and share it: it is immutable, and a new client per call can't reuse connections.


Java 21 differs. HttpClient is AutoCloseable from Java 21 (--release 17 rejects try-with-resources on it). close() waits for requests in flight, so a request without a timeout hangs the close too: against /quote it had not returned after 2 s.




    

  1. 

    Coding practice
    

    Keep a stalled quote service from taking the checkout down
    

      

    • HttpClient's connectTimeout bounds only the connection; without HttpRequest.timeout a stalled server makes send() wait forever.
      • 

    • send() throws only when no response came; a 4xx or 5xx is a normal response whose status the caller must check.

java Report.java Compiles One File in Memory and Runs Its First Class


Since Java 11 the launcher runs a source file (JEP 330): it compiles the file in memory, writes no .class file, and runs the first top-level class:




Two edits javac accepts break it on Java 21: declaring Helper above Report, or moving Helper to its own file beside it:



Other classes come from the same file or, compiled, from the class path. On Unix, a file not named *.java can start with #!/usr/bin/java --source 21 and run as a script; in a .java file that line doesn't compile.


Later releases differ. On Java 25 both commands above print 2 error lines. JEP 458 (Java 22) lets the launcher compile other source files from the program's directory.

  • var takes the initializer's type. var total = 0 is an int that += truncates.
  • The factories are unmodifiable and reject null. contains(null) throws, copyOf snapshots, and Map.of order can change between runs.
  • lines() splits on every terminator. split("\n") leaves the \r.
  • Each HttpClient request needs its own timeout, and a 5xx is a response, not an exception.
  • java File.java compiles that one file and runs its first class on Java 21.

Challenges


  1. How do you find every use of a removed module, third-party jars included?
  2. Your team wants every new HashSet<>(Arrays.asList(...)) constant replaced with Set.of(...). Which call sites change behaviour, and how would you find them?
  3. An upstream answers in 800 ms at p99, and your caller gives you 2 s. Pick a request timeout and a retry policy, and say what happens to your thread pool when the upstream stalls.


Design Note: Why the Factories Refuse null and Vary Map.of's Order


A null in a constant collection is almost always a bug, and failing at once finds it sooner. For the sets and maps there is a second reason: they are arrays searched by probing, and the JDK source marks an empty slot with null, so a null element couldn't be stored.


The order varies on purpose: ImmutableCollections draws a salt at JVM start so that, in its own comment, "iteration order will vary between JVM runs". Code that relies on hash order then breaks on the next restart, in a test, rather than on a JDK upgrade. The cost is that moving to the factories isn't mechanical: every lookup that might see null and every output that depends on order has to be read.
