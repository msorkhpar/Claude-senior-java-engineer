The payments service adds wallet payments. The ticket asks for a 1.5 % fee, so the developer adds a Wallet record and one branch to feeCents(), and the fee tests pass. Two weeks later finance reports wallet money booked a day before the provider pays it out, receipts that say only "payment", and a customer whose wallet refund failed with an exception. Three other methods had their own copy of the same type check, and nothing told anyone they existed.

A module is open for extension and closed for modification when a new case is added as new code and the code that already works isn't edited. All output below is from Java 21.

A Type Check Copied Into Several Methods Still Compiles When One Copy Is Missed

The service decides each payment's fee, settlement delay, receipt text and refund route in four methods, each with its own instanceof chain:

Before reading the output: which of the four methods are wrong for a wallet, and which of them says so?

Three are wrong, and all compile. Each chain ends in a fallback or a throw, and both hide the missed case. A fallback answer (return 1, return "payment") is wrong without a sound: the wallet provider pays out after two days, so for a day the books show money that isn't there. A throw waits until the path runs, which for refunds is weeks later, in front of a customer.

The knowledge "what a wallet is" is spread over every method that asks. The only list of those methods is a text search for instanceof, which also finds every unrelated type check, and settlementDays() never mentions Card at all.

An Interface Is Closed to a New Operation: Adding One Edits Every Implementation

Disputes now need each payment type's chargeback window. That is a new question, not a new type. Adding int chargebackDays(); to PaymentMethod and recompiling our sources (error lines only):

A partner team also ships a GiftCard implements PaymentMethod, compiled in its own build against the old interface. We update our three classes (a wallet has no chargebacks: 0) and run the disputes report with the partner's class file as shipped:

The usual way out is default int chargebackDays() { return 120; }. It compiles with nothing else edited, and answers for everyone:

A bank transfer has no chargebacks, so this is the silent fallback of settlementDays() in the first section, moved into the interface. Unit Interface Segregation Principle (ISP) covers what default methods cost an interface's design.

An interface is open only to new types. A new operation, or a new parameter on an existing one, edits every implementation, and the ones you don't own fail when the new method is called. In the chain layout of the first section, the chargeback window would have been one new method.

When the Types Are Fixed and the Operations Grow, Seal the Hierarchy and Let javac List the Switches

Card, transfer and wallet are a set the payments team owns and changes a few times a year, while finance, disputes and reporting keep adding questions about them. For that shape the first section's layout, one method per question, is right, written as switches over a sealed type (unit Use cases for sealed classes and interfaces):

The wallet ticket again: Wallet goes into permits, and a case goes into feeCents() only.

These are the three methods that went wrong in the first section, found by the compiler instead of by finance. The chargeback window is now one new method with a switch, and no record changes. With both done:

A default branch would have switched the check off for that switch; unit Switch patterns (Java 19+) shows that, and what a caller compiled against the old permits list gets at run time.

So the hierarchy is closed to new types and open to new operations, where the interface is the reverse. Choose by who adds what. Types added by other teams or plug-ins need the interface: they can't edit your switches. A set of types you own, with questions that keep coming, needs the sealed type.

A Closed Pipeline Still Runs Every Extension on Its Own Threads

The module's ConcurrentPipeline is closed code with an extension point: it takes any TaskProcessor<T, R>, whose one method is R process(T input), runs each item on a virtual thread, and guards its result list with a lock. A team plugs in a processor that counts the orders it sees:

Each runs through new ConcurrentPipeline<>(processor).processAll(orders) with 100,000 orders, three times:

The pipeline calls process() outside its lock, from many threads at once, so seen++ loses updates (unit Monitors and synchronized blocks). The pipeline itself is correct, but nothing in R process(T input) tells an implementation that it is called concurrently. Closed code still shares its threads with every extension, so the extension point's contract has to state them.

Summary

  • A type check copied into several methods compiles when one copy is missed. A fallback answer is silently wrong; a throw fails when the path first runs.
  • Behaviour on the type makes a new type one new class. javac refuses it until every operation is written, and the callers' class files don't change.
  • An interface is closed to a new operation. Every implementation is edited; one you don't own fails with AbstractMethodError, and a default method brings back the silent fallback.
  • A sealed type with exhaustive switches is the mirror image. A new type is a compile error at every switch, and a new operation is one method. Pick the axis by who adds what.
  • An extension runs on the framework's threads. The extension point's contract says whether calls are concurrent, and the implementation holds its state accordingly.

Design Note: Closed to What

Every design in this unit is closed to one axis of change and open to the other. The chain is cheap to add operations to and unsafe to add types to; the interface reverses that; the sealed type keeps the chain's layout and adds the compiler's check. Making code "open for extension" before a second case exists picks an axis without evidence. If the first change comes on the other axis, as the chargeback window did, it edits every implementation of the abstraction instead of adding one method.
