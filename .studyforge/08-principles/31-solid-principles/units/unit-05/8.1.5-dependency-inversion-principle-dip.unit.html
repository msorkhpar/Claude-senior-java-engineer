The refund rule is three lines: refund a purchase made within 30 days, and tell the customer. Its unit test fails on every CI run with IllegalStateException: SMTP_HOST is not set. On a laptop where the variable is set, the same test sends a real email. Nothing is wrong with the rule: the policy builds its own mailer.

The Dependency Inversion Principle says the policy declares the interface it needs, in its own terms, and the mail code implements it.

A Policy That Builds Its Own Mailer Can't Run Without a Mail Server

The test of the rule checks a refusal on day 31 and an approval on day 30. On CI, and then with SMTP_HOST=mail.example.com:

The day-31 check never sends anything and fails anyway: the field initializer runs in the constructor, before any rule. A class that calls new on its detail can't be built without that detail, so every test of the class needs a mail server and sends real mail.

The fix gives the policy an interface and takes the implementation as a constructor parameter:

The test passes told::add, the add method of a list named told, as a fake that remembers whom it told. It runs without SMTP_HOST:

The Interface Belongs to the Policy, So the Policy Compiles Without the Mail Code

A constructor parameter of an interface type is dependency injection. It is not yet inversion. Here the mail team published the interface, in their own package and their own terms:

The billing and mail code build as separate jars. Compiling billing on its own:

The interface lives in smtp, so billing still imports the mail code. Billing can't be built, tested or released without the smtp jar, and a push or SMS channel added later has to fill in a from address and a subject to fit an envelope.

Move the interface to billing, named for what the policy needs (the RefundNotifier above), and make smtp.SmtpNotifier implements billing.RefundNotifier. Now billing compiles alone, and the mail code is the side that needs the other on its class path:

That reversal is the inversion: the detail depends on the policy's abstraction, and the policy depends on nothing below it.

A Constructor Parameter Turns a Forgotten Dependency Into a Compile Error

A service locator also keeps new SmtpMailer() out of the policy: a global map from type to implementation, filled in at start-up.

The registration line in main was lost in a merge. The code compiles, the service starts, and the smoke test of a late refund passes:

The exception comes at the first approved refund. Nothing in RefundPolicy's constructor or method signatures says it needs a notifier; only its body does. With the constructor version from the first section, the same lost line is a build failure:

The wiring is plain code in main, new RefundPolicy(new SmtpNotifier()), and needs no framework. A container such as Spring does the same wiring by reflection at start-up; there a missing dependency fails when the container starts, before any request but not at compile time. The compiler can't see a null argument, which is what requireNonNull in the constructor is for. A constructor that replaces null with new SmtpNotifier() as a default brings back the problem of the first section.

A Fake Checks the Outcome; a Mock Checks the Calls

The policy now also refuses a second refund of the same order, through a RefundLog it owns: its constructor takes (notifier, log) and refund takes the order id first. It called log.contains(orderId), then log.add(orderId). Two requests for the same order could both pass contains before either added (the check-then-act race of unit Monitors and synchronized blocks), so the two calls became one, which is safe when add is atomic, as in a concurrent set. contains stays for the support screen:

Two tests guard the rule. One uses a Mockito mock and verifies the calls; the other uses a fake, a working in-memory RefundLog, and checks what happened:

Before and after the change:

The mock test pinned the old call sequence, so the race fix failed the build although every refund decision stayed the same. The fake test only knows that the second refund of B-77 is refused, which is the rule. A two-method fake is cheap because the policy owns a small interface; a fake of java.sql.Connection would be a project of its own. When the call is the outcome, as with the notifier, check the call: the told list records it.

ServiceLoader Picks the Implementation From the Class Path

The composition root, the main that builds the objects and wires them, can choose the implementation without naming it. java.util.ServiceLoader reads, from every jar or directory on the class path, a file META-INF/services/<interface name> that lists implementation classes, one per line. The mail jar holds its class and that file:

META-INF/services/billing.RefundNotifier contains the line smtp.SmtpNotifier. The application asks for any RefundNotifier:

Run with no mail jar, with a mail jar built without the services file, and with the full one:

In the second run smtp.SmtpNotifier is on the class path and still not found: on the class path, ServiceLoader doesn't scan classes, it reads the file. A build that leaves resources out of the jar ships an application that finds no notifier. Neither billing nor the application names smtp.

Iterating the Loader Builds Every Provider Before the One You Want

A second channel ships as push.jar. Its constructor needs a PUSH_KEY that this installation doesn't have, and the configuration asks for smtp.SmtpNotifier. Main has three modes: first calls findFirst(), loop compares each instance's class, and stream (the default branch) compares each ServiceLoader.Provider's type:

The iterator constructs each provider as it reaches it, so the push channel that nobody asked for failed the lookup. The last run is the loop again with the jars in the other order, and it works: the result depended on class path order. Provider.type() returns the class without building it, and only get() calls the constructor, so the stream builds just the chosen channel.

ServiceLoader.load(type) looks through the current thread's context class loader. Code that keeps plug-ins in a class loader of its own passes it: ServiceLoader.load(type, loader).

Summary

  • A policy that calls `new` on its detail can't run without it. Its tests need the mail server, and on a machine that has one they send real mail.
  • The policy owns the interface, in its own terms. Injecting an interface that the detail publishes still leaves billing unable to compile without the mail jar.
  • A constructor parameter makes a forgotten dependency a compile error. A service locator hides it until the first request that needs it.
  • A fake checks the outcome, a mock the calls. A test that verifies calls can fail a refactor that changes no decision.
  • `ServiceLoader` finds implementations through `META-INF/services`. Without the file the class is never found; iterating builds each provider it passes, and Provider.type() builds none.

Challenges

  1. The billing team wants to ship RefundNotifier in a jar of its own so that two policies can share it. Who owns that jar, and what happens to it when one policy needs a new method?
  2. A module's test suite uses Mockito for every collaborator. Pick one interface it mocks and write the fake. Which tests get shorter, and which can no longer be written?
  3. ServiceLoader finds two RefundNotifiers in production. Design how the composition root chooses, and what it does when the configured one is missing.

Design Note: ServiceLoader Is a Service Locator

ServiceLoader.load(RefundNotifier.class) is a global lookup by type, the thing the third section warned about. It is safe in one place: the composition root, the main that builds the objects and passes each one its dependencies through constructors. There, a missing provider fails at start-up, before any request, and the policies still declare everything they need in their constructors. Called from inside a policy, it would hide the dependency again, and a test would need a services file on its class path to run the rule. The JDK finds JDBC drivers and java.nio.file file-system providers through ServiceLoader, and DriverManager shows the cost of leaving the lookup open: it is a global registry that any code can call with a URL, and a missing driver shows up as SQLException: No suitable driver found for <url> at that call.

Problem statement


The notification service sends alerts to operators through one of several channels: SMS, email, push. Each channel ships as a jar of its own, so a customer installs only the channels they pay for, and the service never names a channel class in its code. A channel's jar holds a class that implements Channels.Notifier, carries @Channels.Channel("<name>"), and is listed in that jar's META-INF/services/practice.Channels$Notifier. The service's configuration names the channel to use.


The service keeps its plug-in jars in a class loader of their own and hands it to Channels.forChannel(channel, plugins), the method you write in src/main/java/practice/Channels.java. Last week's incidents decide what it must do:


  • the service started on a thread whose context class loader can't see the plug-in jars, and it found no channel at all;
  • a customer installed the push jar without its key; push's constructor throws, and the SMS alerts they had configured stopped too;
  • a typo in the configuration ("emial") sent the alerts somewhere other than where the customer asked, and nobody noticed for a week.


Return the configured channel's notifier, built once. A channel that no plug-in provides fails with IllegalArgumentException, and its message names the channel. About seven lines.
