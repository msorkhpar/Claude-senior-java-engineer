javac Checks an Override's Signature; Only a Caller Run on Every Subtype Checks Its Contract

javac enforces the part of a contract it can read. An override that wants to report a disk error through a method that declares none doesn't compile:

javac accepts the narrower return type, String for Object, and an UncheckedIOException in place of the checked one (unit Inheritance basics shows what such an override does to its callers). Which inputs a method accepts, what it returns for them and which unchecked exceptions it throws are written only in the javadoc. The one executable check is a caller written against the supertype and run on every implementation. The runs below use this helper:

Here it runs normalizeTags on "web", " Java", "java", "api", built the five ways the service's callers build a List<String>:

The test suite built its input with new ArrayList<>, the one row that works. Arrays.asList is a fixed-size view of the array: it sorts in place and fails at remove. The others fail at the first change.

List's Mutators Are Optional Operations, So the Caller That Changes Its Argument Is in Breach

List.add, remove and set are each marked "(optional operation)" in the javadoc, and Collection says what that means: an implementation that doesn't support one throws UnsupportedOperationException. Throwing is part of List's contract, so List.of keeps it. normalizeTags is the code in breach: it relies on a promise List never made, so its signature hides a precondition, "pass a modifiable list". The fix builds a new list and leaves the argument alone:

Read methods have optional clauses too. Collection.contains may throw NullPointerException "if the specified element is null and this collection does not permit null elements (optional)". A gateway forwards a header if its name is on an allow-list, and a request arrives without the header:

Moving the allow-list from Arrays.asList to List.of passes every test that sends the header and fails on the first request that doesn't. Set.of rejects a null query the same way.

The JDK made these subtypes legal by weakening the supertype: List promises so little that an unmodifiable list keeps the contract. The cost moved to every caller, which must copy before changing a list it was given and check for null before asking.

Timestamp Breaks the Symmetry Object.equals Promises, So a Set of Dates Depends on Arrival Order

Object.equals makes a promise with no optional clause: x.equals(y) should be true exactly when y.equals(x) is. java.sql.Timestamp extends java.util.Date and breaks it. An audit job counts distinct event times; some come from new Date() in the service, others from rs.getTimestamp(...), held as Date:

Date.equals compares milliseconds and accepts any Date. Timestamp.equals returns false for anything that isn't a Timestamp, even at the same millisecond: its javadoc gives the reason that a Date's nanoseconds are unknown. A HashSet calls equals on the element being added, and the same moment counts once or twice depending on which source answered first. Timestamp's javadoc admits it: the inheritance "really denotes implementation inheritance, and not type inheritance", and code should not treat a Timestamp as a Date. The fix follows that advice and converts at the boundary, keying by Instant:

The same reuse through extends gave java.sql.Date overrides that throw (unit Limitations of the Legacy Date and Calendar Classes) and Properties an inherited put its own methods can't read back (unit Inheritance).

A Subtype May Accept More and Promise More, Never Less

In your own hierarchy, the supertype's javadoc is the contract, and the caller test is written against the interface, next to that javadoc. Checkout takes any Discount:

Each coupon passed its own unit test, written with a cart big enough for it. The contract is checked once, against the interface:

FlatCoupon weakens the postcondition: a 3-euro cart checks out at minus 2 euros. MinimumSpendCoupon strengthens the precondition: it rejects carts the interface says every discount accepts, so the cart page throws for an empty cart with a coupon applied. The fixes cap both coupons with Math.min(cents, subtotalCents), and the minimum-spend one returns 0 below its minimum. The same check passes:

The opposite changes pass. PercentOff(10) promises more than the interface, never above a tenth of the subtotal, and keeps the contract. A discount that also accepted a negative subtotal would break no caller, since none written against the interface sends one. An implementation that can't serve every input the interface allows needs an interface of its own (unit Interface Segregation Principle (ISP)).

Summary

  • javac checks an override's signature, not its contract. Accepted inputs, results and unchecked exceptions are checked only by a caller test run on every implementation.
  • `List`'s mutators are optional operations. List.of keeps the contract by throwing; a method that changes the list it was given is the code in breach, and copies instead.
  • `Timestamp` breaks `equals` symmetry with `Date`. Mixed in one collection, the count of duplicates depends on arrival order; convert to Instant at the boundary.
  • A subtype may accept more and promise more, never less. Rejecting an input the supertype accepts, or returning outside its range, breaks every caller that trusted the supertype.

Challenges

  2. Write the contract test for Map.get as your service uses it. Which of HashMap, ConcurrentHashMap, Map.of and TreeMap pass it with a null key?
  3. Your team's Repository interface has a delete that one read-only implementation can't support. List the options and which callers each one breaks.

Design Note: Why the Collection Interfaces Have Optional Operations

The collections framework could have given each kind of collection several interfaces: modifiable, fixed-size, unmodifiable, null-tolerant, each for List, Set and Map. It kept one type per kind and marked the mutators optional, so one interface covers every list. The type then no longer says which calls will work, and a caller finds out at run time. Splitting an interface by what its clients need is unit Interface Segregation Principle (ISP).

  • a queue that serves the newest item first is reported as breaking the order clause
    • 

  • a bounded queue that answers false once it is full keeps the contract
    • 

  • a queue that throws once it holds a few dozen items is reported
    • 

  • a queue that refuses null with an exception other than NullPointerException is reported
