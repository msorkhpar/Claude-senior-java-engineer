The nightly expiry sweep for the EU region failed at 02:00 with UnsupportedOperationException: replica is read-only. A config change had pointed it at the read replica instead of the primary. The change passed review and compiled: the replica implements the same ListingStore interface as the primary, so the compiler had no reason to object.

The Interface Segregation Principle says a client should not depend on methods it doesn't use. Imports are left out of the examples, and every output is from Java 21.

A Fat Interface Compiles Calls Its Implementations Can Only Refuse

One interface serves SearchPage, which only reads, and ExpirySweeper, which reads and deletes. PrimaryStore implements all four methods on a HashMap. ReplicaStore can't write, so it refuses:

The job picks its store by region, from configuration; primary and replica are the two stores:

The compiler checks that ReplicaStore has a delete, not what it does, so the mistake surfaced at the first expired listing, at 02:00. Whether a refusing implementation is also a broken subtype is the question of unit Liskov Substitution Principle (LSP); here the interface made the stub necessary.

Role Interfaces Turn the Refusal into a Compile Error

Split the interface by what its clients do with it. Reading is one role, writing another, and a client that needs both names a type that extends both:

PrimaryStore implements ListingStore, SearchPage takes a ListingReader, and the sweeper still takes a ListingStore. The same wiring mistake:

ReplicaStore has no delete, so it can't be passed to a client that deletes. Without that line, the search page runs on the replica and the sweeper on the primary:

Configuration code gets the same check: a readerFor(region) method declared to return ListingReader can serve the replica regions, and javac rejects its result as the sweeper's argument.

Split by Client, Not by Method

A role is the set of methods one kind of client uses together. Split further, and the clients pay instead. With one interface per method, the sweeper needs an intersection type and three fields that all hold the same object:

No implementation can refuse anything here either, so this split buys nothing over two roles.

  1. Coding practice

    Keep the repricing job away from frozen price books

    • A client that only reads takes the reading role, so it runs on implementations that can't write.
    • Splitting the interface into roles lets the read-only implementation drop its writer methods, so handing it to a client that writes no longer compiles.
    • An implementation that throws UnsupportedOperationException from a method of a fat interface compiles, and the wiring mistake that calls it fails only at run time.

Neither the replica nor the search page exports anything, yet the replica gets a third stub and the search page's fake a fourth empty method.

A Default Method Keeps Implementations Compiling, and Runs Code That Never Saw Their Locks


Java 8 added removeIf to Collection as a default method that iterates with iterator() and removes through it, so ordinary implementations kept compiling. That is the partial fix for growing an interface: old implementations compile, and they inherit code written without them in mind. This bag was written years earlier, with a lock on every method:



A caller in 2015 runs bag.removeIf(...) on [a, b, c], removing b. While the predicate looks at a, a second thread calls bag.add("d") and is given 200 ms to finish. LockedBag2 is the same class with one more method:



The third row is the JDK's Collections.synchronizedCollection:



The inherited removeIf iterated without the bag's lock, so the add landed in the middle. The ConcurrentModificationException is the lucky outcome: the fail-fast check is best effort (unit Order of Operations in Concurrent Collections), and a missed one can leave the list silently wrong. The JDK's synchronized wrapper overrides removeIf and forEach to run them under its lock; its source marks them "Override default methods in Collection". A default that throws UnsupportedOperationException instead, as SequencedCollection.addFirst does, keeps everything compiling and moves the failure back to run time, as in the first section.

Collection Is Fat on Purpose, and Java 21's SequencedCollection Repeats It


The JDK's collection interfaces carry every mutator, and the Collection javadoc calls them "optional operations": an implementation may refuse them. There is no read-only List type to ask for, so a method that only reads a list still receives add, set and sort; unit Liskov Substitution Principle (LSP) shows such a method sorting its argument and failing on List.of.


Java 21 added SequencedCollection, a role for collections with an order. It puts getFirst and getLast beside addFirst, addLast, removeFirst and removeLast, and its defaults for addFirst and addLast throw. A read-only playlist that takes on the role, and four calls on it (attempt runs a call and prints the exception it throws):





javac accepted all four calls. The playlist can serve only the reads, and the role offers no type that holds just those, so a client that needs the first and last track still depends on four mutators, and the playlist refuses them at run time, as the replica did in the first section. In your own interfaces, give the reads a role of their own.

Summary


  • A fat interface compiles calls its implementations can only refuse. A stub that throws turns a wiring mistake into a production failure half-way through a job.
  • Role interfaces turn the refusal into a compile error. Split by the methods one client uses together; one interface per method makes clients carry intersection types.
  • A method added to a fat interface breaks classes that never call it, test fakes included. A new role breaks nobody.
  • A default method keeps implementations compiling and runs code that never saw their invariants, such as a lock. Override it where the class has rules the default can't know.
  • Collection is fat on purpose, and Java 21's SequencedCollection repeats it. A read-only implementation compiles calls to addFirst and refuses them at run time.

  2. You maintain a library interface with 200 implementations outside your company and need one more method. Compare a default method, a new sub-interface, and a new role. What does each cost the implementers you can't see?
  3. Sketch the split you would have given SequencedCollection. Which JDK classes would implement each part, and which client of yours would take each one?


Design Note: Three Ways to Grow an Interface


An interface gains a method in one of three ways, and each has a different cost. An abstract method breaks every implementation at compile time, which is honest and expensive when the implementations belong to other teams. A default method breaks none of them at compile time, and each one inherits behaviour its author never reviewed. A new role interface breaks nobody and changes nothing, but only the clients that ask for it get the method. Java 8 chose defaults for Collection; Java 21 chose a new role, SequencedCollection, then filled it with defaults that throw, so the cost moved back to run time. Why the collection interfaces have optional operations at all is the design note of unit Liskov Substitution Principle (LSP).
