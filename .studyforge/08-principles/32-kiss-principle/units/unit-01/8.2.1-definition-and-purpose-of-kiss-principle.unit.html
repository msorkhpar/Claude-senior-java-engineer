  15. Check yourself: keeping it simple

On a Friday afternoon the shop reprices its best-selling mug from 18.99 to 21.49. Half an hour later checkout still charges 18.99, although the price cache's time to live is five minutes. The cache class is sixty lines: per-SKU entries, LRU eviction, hit counters. The pricing team's requirement is one sentence: a price shown at checkout is never more than five minutes old.

KISS ("keep it simple") asks for the simplest code that meets a stated requirement. The caches on this page are measured against that requirement written as a check, so "simple" means "passes the check with the fewest moving parts", not "short".

Expiry Counted From the Last Read Keeps a Popular Price Forever

Read price() and decide which SKU goes stale: the one read once an hour, or the one read every minute?

The check drives any sku -> price function with a fake clock (an InstantSource, injected as in unit Overview of the java.time package): the mug is repriced at minute 1, read every minute to minute 30, and must show 21.49 from minute 7 on.

Each hit writes now back into the entry, so the five minutes count from the last read, not from the load. A SKU read at least every five minutes is never reloaded; the one read hourly always is. The bestseller keeps the old price until reads stop at night or the service restarts.

Nobody asked for "keep hot entries alive". It is a different policy, sliding expiry, written in because general-purpose caches offer it, and it runs on every hit whether the requirement wants it or not.

One Load Time for the Whole List Meets the Requirement

The catalogue has 3,000 SKUs, and the price-list query returns all of them in a few milliseconds. So there is no need for an entry per SKU: load the whole list, record when, and reload after five minutes.

loadedAt is written only when the list is loaded, so the age it measures is the age of the data. There is no eviction because 3,000 prices fit in memory, and no hit counter because nobody reads one.

The class is single-threaded as written. Shared between request threads it needs one more choice of construct, which unit Applying KISS in concurrent programming makes; unit Benefits of KISS for concurrency counts the interleavings that choice removes.

Code Simpler Than the Requirement Is a Bug, Not KISS

A one-line memo is simpler still:

computeIfAbsent calls the loader only when the key is absent, and nothing removes keys, so the first price loaded stays until the process restarts. Where PriceCache added a rule nobody asked for, the memo lacks the one rule that was asked for, and the check fails both.

Summary

  • Expiry counted from the last read keeps a popular price forever. A general-purpose cache brings rules of its own, and sliding expiry broke "never more than five minutes old" for the SKU read most.
  • One load time for the whole list meets the requirement. With 3,000 SKUs that load in milliseconds, a map and a timestamp written only on load pass the check.
  • Code simpler than the requirement is a bug. A computeIfAbsent memo never reloads and fails the same check.
  • An option nobody needed changes what other code may do. Access order, turned on for eviction that never runs, makes get a structural modification, and the report throws CME with two SKUs.
  • A rule engine for one form adds failures the plain method cannot have. Its order changes between runs, and a renamed accessor compiles and fails at the first signup.
  • The plain version fits today's numbers. At two million SKUs one checkout every five minutes waits a second; the replacement is written when that requirement exists.

Challenges

  1. The pricing team adds a rule: a price changed by hand in the back office shows at checkout within ten seconds. Which of the three designs on this page survives, and what is the simplest change that meets the new requirement?
  2. Your service already has a cache library on the classpath, with expiry after write as an option. Is configuring it simpler than PriceList? Count the rules each one brings.
  3. Find a class in your codebase with an option set "in case": a pool size, a retry policy, an eviction limit. What does it change about the code around it today?

Design Note: Why the Check Comes Before the Code

"Simple" has no measure on its own. The computeIfAbsent memo has fewer lines and branches than PriceList and fails the check; PriceCache handles more situations than either and fails it too. Written first, the requirement's check turns "simplest" into a question with an answer: the least code that passes it.

The cost is that the plain design is chosen for today's numbers and replaced, not extended, when they change. The alternative is a general design on day one, which carries rules nobody requested (sliding expiry, access order, string-keyed rules) from the start, each with behaviour no check was written for.

Problem statement


Checkout converts card payments in foreign currencies to euros at the treasury service's rates. Last month the US dollar moved sharply one afternoon, and finance found dollar payments converted at the morning's rate for more than an hour. The old rate class has been deleted, and its replacement is half written.


Two rules come from the treasury team:


  • a payment is never converted at a rate fetched more than ten minutes before it (MAX_AGE);
  • the treasury accepts at most one call per ten minutes from this service, and one call to allRates() returns every currency it quotes.


Finish rate(...) in src/main/java/practice/ExchangeRates.java so that both hold, with as little machinery as they allow. Take the time from the clock you are given, never from the system clock: the tests move it by hand. The class has one caller thread. About eight lines in total, fields included.
