Each code of the spring campaign may be redeemed three times. A week after launch, finance finds codes redeemed four and five times. The web checkout reads how often a code was used and, if that is under the limit, adds one, so two orders that read at the same moment both pass. The team makes the web checkout check and update in one atomic step, its load test goes from oversold to clean, and the fix ships. The next week's report still shows oversold codes.

A Fix Made in One Copy of a Check-Then-Update Leaves the Other Copy Racing

The counters live in PromoCodes, which hands each checkout a code's counter:

The mobile checkout, which nobody looked at during the incident, has the same lines the web checkout had:

After its fix, the web checkout uses getAndUpdate, which stores the function's result only if no other thread changed the count in between, and retries otherwise. The function adds one only while the count is under the limit:

The load test releases eight threads together; each tries each of 20,000 codes once, in the same order; the mixed rows split the eight threads four and four. A code is oversold when more than three of its eight attempts succeed. Each row is 20 runs on fresh counters:

The first two rows are the team's load test, which the fix passed. The mobile row is the same check-then-update, still racing. The last row is production: both checkouts share the codes, and the fixed web copy doesn't protect them. The mobile copy reads 2, a web order moves the counter to 3, and the mobile copy adds a fourth. This is the check-then-act of unit Monitors and synchronized blocks: each call is atomic, and the pair is not. On one thread nothing can come between the mobile copy's check and its update, so it refuses the fourth redemption too; only a test that runs several threads through the unfixed copy finds the race. With the incident closed, the next report's oversold codes look like a new bug.

A Fix Made in the Owning Class Reaches Every Caller Without Touching Them

Unit Applying DRY in concurrent programming shows how to move a compound action into the class that guards its state. Here PromoCodes.tryRedeem first held the mobile checkout's get and incrementAndGet, racing as before; after the fix it reads:

The checkouts never see a counter. Each is now one line, and MobileCheckout is the same class under another name:

The same load test, before and after the one edit to tryRedeem:

Every row went to zero, mixed traffic included. javac produced the same bytes for WebCheckout.class and MobileCheckout.class before and after the fix, so a load test of tryRedeem covers every caller that only delegates to it.

One machine. Java 21, 20 cores, each program run three times: every racing row was oversold in 19 or 20 of its 20 runs, every fixed row in none.

getAndUpdate may call its function more than once when threads collide (unit Atomicity violations and ensuring atomic operations), so the function only computes the new count; anything with a side effect, such as recording the order, goes after tryRedeem returns true.

The Fix Holds Only While No Caller Can Reach the Counter

A month later, a support tool needs to apply codes to phone orders, and its author pastes the redemption lines from an old branch of the mobile checkout:

Against the fixed PromoCodes:

The public counter() of the first design is what made the copies possible: any class holding the AtomicInteger could write its own check-then-update, and nothing but review would stop it. With counter() gone, and limit(), which only the copies needed, the third copy fails to compile, and the author has to call tryRedeem.

Not every accessor reopens the race. A method int redeemed(String code) that returns the count as a number is safe to add: a caller may check it, but the only way to change the count is tryRedeem, which checks again.

Summary

  • A fix made in one copy of a check-then-update leaves every other copy racing. The fixed copy's own load test passes, and with mixed traffic the codes are still oversold.
  • A fix made in the owning class reaches every caller without an edit to them. One method and one load test cover every path; the callers compiled to the same bytes.
  • The fix holds only while no caller can reach the state around the owner's method. Return values, not the counter, and a pasted copy stops compiling.

Challenges

  1. The redemption limit moves into a database that three services in different languages share. Where is the owner now, and what is the single step that validates and updates?
  2. Finance adds a per-customer limit next to the per-code one. Can tryRedeem still be one atomic step, and what does keeping two counters consistent cost?
  3. A code base has a dozen copies of a check-then-update against a shared cache. Which change tells you, with a compile, that you have found all of them?

Design Note: Why the Counter Is Hidden Rather Than Documented

The first design had a rule, "check and update a code's count in one step", that nothing in the code enforced. Hiding the counter moves the rule into the type: the only operation a caller has is the one that is correct.

The cost is that the owner must offer every compound action callers need. A checkout that wants "redeem these two codes together, or neither" can't build it from two tryRedeem calls; the owner needs a new method, and with it a lock or a single holder for both counts. Each such method makes the owner larger, and merging actions that only look alike has its own failure, which unit Balancing DRY with other principles (e.g., SRP) shows.
