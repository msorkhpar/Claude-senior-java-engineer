On Monday the catalog import rejects every product whose name holds an inch mark, such as Monitor 27". Friday's deploy changed only the bank-statement import: the bank had started putting payee names in quotes, and the bank team's tests passed. Nobody on that team opened the catalog code. Both imports call one method, Fields.split, extracted a year earlier because the two importers had the same loop.

Removing duplication (DRY) and keeping each actor's rules apart (SRP, unit Single Responsibility Principle (SRP)) pull against each other when two pieces of code look alike.

Merging Look-Alike Code Ties Two Formats Together, and a Change for One Breaks the Other

The bank's statement file has a date, a payee and an amount on each line; the supplier's product feed has a name and a price. Both importers split a line on commas and stripped the spaces, so a developer moved that loop into one class:

CatalogImport.parse builds an Item(name, price) the same way. Each team has a check; the bank's already uses the new quoted format:

Split on every comma, ACME, Inc. becomes two fields, and the bank check fails with a NumberFormatException. The bank developer fixes Fields.split:

Which check fails now?

The supplier's feed quotes nothing, so the " in 27" is an inch mark. The new loop read it as an opening quote, took the comma after it as part of the name, and returned one field.

The two loops were the same text for two file formats, one owned by the bank and one by the supplier. Unit Definition and purpose of DRY principle's test (must one copy change when the other does?) answered no before the extraction. In unit Single Responsibility Principle (SRP)'s terms, Fields answers to two actors.

A Flag for Each Caller Keeps the Method Shared, and Every Change Must Be Checked Against Both

The fix that keeps Fields is a parameter: split(line, quotes), true from the bank, false from the catalog. Both checks pass. Next the supplier moves its feed to ; with decimal commas, Monitor 27";199,00;SPRING, where the last field is a promo code and is often empty; split gets a sep parameter. Meanwhile the bank's importer has started rejecting any line without exactly three fields (if (f.size() != 3) throw ...). Then the bank's file starts ending every line with a ,, as in 2026-03-02,"ACME, Inc.",-120.00,, and every bank line is rejected. An empty last field looked like noise in any file, so that change went in without a flag:

The checks now read the new formats, and the catalog has a third: Desk lamp;49,90;, a product with no promo code.

For the catalog an empty last field is data: no promo. The repair that keeps the method is a fourth parameter, boolean dropTrailingEmpty, guarding that line. All three checks pass, and the call sites read:

quotes and dropTrailingEmpty are true only for the bank, and the value ; comes only from the catalog. A parameter value that only one caller passes is that caller's rule written inside shared code.

A flag separates the callers only where the body reads it: the drop line sat outside every flag, so it ran for both, and a line added inside a branch runs for every caller that takes that branch. Every later change must now choose between "for everyone" and "another flag" by reading both callers' formats. A wrong choice breaks the other import, and its tests catch it only if they hold the case: without the desk lamp, the catalog checks pass and every product without a promo code is rejected in production.

Inlining the Method Back Gives Each Format Its Own Code, and All Checks Pass

Inlining reverses the extraction. Copy the method's body into each caller, replace each parameter with the value that caller passes, and delete what can no longer run. For the bank, sep becomes ',' and both flags become true, so the body stays as it is:

For the catalog both flags are false, so the quote branch and the line that drops an empty last field never run. What remains is a split on ;, which String.split(";", -1) does, with each field then stripped:

Fields is deleted, and the same checks print:

The -1 matters: with no limit, split drops trailing empty strings, and the desk lamp line throws again.

The Rule of Three Is a Heuristic for When You Can't Yet Tell

The usual guard against early extraction is the rule of three, which Martin Fowler's Refactoring attributes to Don Roberts: write it once, tolerate a second copy, refactor at the third. Two copies that agree show little about which of their parts will vary; a third shows more before you choose parameters.

The count decides nothing when you already know the answer. A second copy of one rule, such as unit Definition and purpose of DRY principle's username check, gets one home at once, because the copies must change together and the next fix would reach only one of them. Three importers that each split a line are three formats, and the third copy is no reason to merge them.

Summary

  • Merging look-alike code ties two formats together. The bank's quote handling, made in the shared Fields.split, broke every catalog line with an inch mark.
  • A flag for each caller keeps the method shared and makes every change answer to both. A parameter only one caller sets is that caller's rule; a change that skips the flag breaks the other import, as the trailing-field change did.
  • Inlining back gives each format its own code. Copy the body into each caller, substitute the caller's arguments, delete the dead branches; the bank keeps its loop, the catalog becomes one split, and all checks pass.
  • The rule of three is a heuristic. One rule gets one home at the second copy; look-alike copies of different rules stay apart at any count.

Challenges

  1. The bank's next format writes a quote inside a payee as "". Change StatementImport.fields for it. Which check could that change break now, and which could it have broken while Fields was shared?
  2. A payroll import arrives: ,-separated, quoted names, no trailing separator. Copy the bank's fields, or extract a CSV reader both use? Name each parameter that reader would take, and who would ask for changes to it.
  3. Find a method with a boolean parameter in a codebase you know, and list its callers with the value each passes. Which flags does only one caller set, and what would inlining the method into that caller remove?

Design Note: Why a Wrong Abstraction Outlives Its Use

Sandi Metz described the pattern in "The Wrong Abstraction" (2016): each developer who meets the shared method takes its existence as proof that it is right, and adding one more parameter looks cheaper than undoing a colleague's work. Her advice is the one this page ran: inline the code back into every caller, delete what each caller doesn't need, then look again for what is common.

Inlining has a cost of its own. If the bank and the payroll file both follow one published CSV specification, their quoting is one rule, and two copies of it can drift as unit Definition and purpose of DRY principle's username checks did. Inlining swaps one risk for another, a shared rule fixed in only one copy, and the trade is right only when the copies answer to different owners.

Problem statement


The shop computes two deadlines from a date. Operations promises customers a ship date, and support promises a reply date for every ticket. Both have called WorkingDays.add since someone noticed the two loops were the same; it has since gained a saturdays parameter for the warehouse and a holidays parameter for support.


This week brings one request from each team:


  • Operations: the warehouse now works public holidays, as well as Monday to Saturday. An order ships at most two warehouse days after the day it was placed.
  • Support: nothing changes about which days support works (Monday to Friday, never a public holiday), but a ticket opened on a day support doesn't work now counts as opened on support's next working day. The reply is due one support day after that.


Write shipBy and replyBy in src/main/java/practice/Deadlines.java so that each team gets its request, and neither team's dates move because of the other's. About twelve lines in total.
