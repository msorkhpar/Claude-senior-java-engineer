The login service keeps its sessions in MapSessions, a small class with a private HashMap. Since the request handlers moved onto more threads, the "active sessions" gauge reads tens of thousands low, and now and then a user who has just logged in is told the session doesn't exist. The fix is one line inside MapSessions. What else has to change, and what has to be checked again? Every output below is from Java 21 on a 20-core machine.

Callers That Know Only the Wrapper Run Unchanged When Its HashMap Becomes a ConcurrentHashMap

The handlers see an interface, and the map is a private field of the class behind it:

A load program, LoginLoad, plays eight request threads. Each logs in 25,000 users, checks right away that its own session is there, and logs every second one out again, so 100,000 sessions should stay open:

We compile everything once and run the load five times. Then we change one line of MapSessions to new ConcurrentHashMap<>() (and its import), recompile that file alone, and run the same LoginLoad.class five more times. Each block's first line gives the first 16 hex digits of the SHA-256 of each caller's class file (GuestLogin comes in the next section):

Over HashMap the store loses sessions, misses ones just written, and leaves threads looping inside it (unit Thread Safety of Common Data Structures shows why). Over ConcurrentHashMap every run is exact, and the caller's bytes are the same. A compiled call names the method it calls, Sessions.open(String, String), and never the type of a private field, so nothing a caller was compiled against moved.

The same store written as a subclass has no private part to change. Here a nightly report copies it with clone(), which HashMap makes public:

After extends HashMap becomes extends ConcurrentHashMap and only SessionTable is recompiled, the old report class fails when it runs, and recompiling it fails too:

A subclass publishes every public method of its superclass, so the superclass is part of what each caller compiled against, and changing it means finding every caller. Units Definition and purpose of Composition over Inheritance and Applying Composition over Inheritance in concurrent programming show the coupling in the other direction: a subclass that depends on how its base calls its own methods, and one that locks a different object than its base.

The Swap Is Free Only for What the Wrapper Promises: HashMap Accepted null, ConcurrentHashMap Throws

Both builds also ran GuestLogin, compiled once with the load:

Over HashMap, then over ConcurrentHashMap:

Over HashMap the guest's session was stored and then looked missing, since user returns null for both. Over ConcurrentHashMap the same call throws from inside the map, in a class nobody edited. The Map interface allows both: its javadoc says some implementations prohibit null keys and values and throw when given one, and ConcurrentHashMap's says it allows neither.

A wrapper hides an implementation only where its own contract is narrower than every implementation it may hold. MapSessions decides about null itself, in every method; open and user:

The guest login over both backings now prints the same thing, pointing at the caller's line (unit Definition and purpose of Fail-Fast and Fail-Safe iterators):

Iteration is the other difference. A method that returned the live map, or a view of it, would give callers a fail-fast iterator over HashMap and a weakly consistent one over ConcurrentHashMap (unit Order of Operations in Concurrent Collections). A wrapper that lists its contents returns a copy, such as Map.copyOf(byId).

One Metrics Decorator Serves Every Implementation, and Its Own Counters Must Be Thread-Safe

Operations wants call counts and latency for the store. A decorator implements Sessions, holds another Sessions, and measures each call it passes on:

new MeteredSessions(new MapSessions()) measures the store over either map, and wraps a test fake as well. Measuring by subclassing would take one subclass per class measured.

Its first version kept private long calls; and counted with calls++. Eight threads made 800,000 calls through each version, over the ConcurrentHashMap store, five runs each:

The store kept all 400,000 sessions while the metrics lost a quarter of the calls. A decorator has its own fields, every thread that uses the store uses them, and the thread-safety of what it wraps doesn't extend to them. calls++ reads, adds and writes, and two threads that read the same value write the same result (unit Monitors and synchronized blocks). LongAdder or AtomicLong makes each update atomic. LongAdder keeps several cells under contention and adds them up when read, so eight counting threads don't all fight over one variable.

A Synchronizing Decorator Protects Only the Calls That Go Through It

A decorator can add a lock instead of a different map:

HashMapSessions is MapSessions with its original HashMap field and the null checks. Wrapped, it kept every session in all five runs of the first section's load:

Reads take the lock too: in the first section, a user call that ran beside another thread's put missed sessions its own thread had just written.

Collections.synchronizedMap(m) is the JDK's version of this class. It returns a Map that holds m and runs each Map method under one lock, the wrapper object itself, over any Map. A TreeMap inside still walks in key order, but the wrapper is only a Map: it is not a SortedMap, which is why synchronizedSortedMap exists. A walk is many calls, so it must hold the wrapper's lock (unit Thread Safety of Common Data Structures). The javadoc adds a condition: all access to the backing map goes through the returned map.

Here the expiry job was built before the wrap and kept the HashMap itself. Seven request threads put 25,000 sessions each through the wrapper while the job removes 50,000 expired ones through its own reference:

The wrapper's lock kept its own callers apart and nobody else: the job's removes ran beside the puts. size(), the number on the gauge, was wrong in every run, by up to 577, and one session vanished in one run. Any reference to the inner object that outlives the wrap is a path around the lock. new SynchronizedSessions(new HashMapSessions()) leaves no such reference.

Which Layer Holds the Lock Decides What the Metrics Measure

Stacking both decorators gives two orders, and both compile and pass a single-threaded test. In the second, threads call insideShared and the metrics are read from inside:

Eight threads made 200,000 calls each through each stack, three rounds:

The store did the same work. Outside the lock the timer also runs while a caller waits for the lock, which is the latency a request sees. Inside, it is how long the store holds the lock, the number to check before blaming the map. These are one machine's numbers; the ratio depends on cores and contention.

Summary

  • Callers that see only the wrapper's methods survive a change of what it wraps. Replacing a private HashMap with a ConcurrentHashMap changed no caller's class file and ended the lost sessions; the same change to a subclass of HashMap broke a caller at run time and at compile time.
  • The swap is free only within the wrapper's own contract. Maps differ on null and on iteration; a wrapper that rejects null itself and returns copies behaves the same over all of them.
  • A decorator's own state needs its own thread-safety. long counters in a metrics decorator lost a quarter of the calls over a correct store; LongAdder counted every one.
  • A synchronizing decorator protects only the calls that go through it. Collections.synchronizedMap miscounted once another reference to its map was used. Stacked with metrics, its position decides whether the timings include waiting for the lock.

Challenges

  1. MapSessions must also list the sessions of one user. Can you add that without making a swap back to HashMap (for a single-threaded batch tool) unsafe, and what does the copy cost on 100,000 sessions?
  2. Write a test that would have caught the long counters in MeteredSessions. How many threads and calls does it need to fail every time on your machine, and on a two-core CI runner?
  3. A cache needs eviction (LinkedHashMap in access order) and sharing between threads. Compare Collections.synchronizedMap over it with a ConcurrentHashMap plus your own eviction: what does each cost readers, given that get on an access-ordered LinkedHashMap moves the entry?

Design Note: Why the JDK Wraps Instead of Subclassing

Java 1.2 could have shipped SynchronizedHashMap, SynchronizedTreeMap and so on, one subclass per map. It shipped Collections.synchronizedMap, one private class that holds any Map, and the same for unmodifiable and checked collections. One class covers every implementation, including ones written later, and none of them has to be designed for extension. The design pattern behind it is the decorator of unit Decorator Pattern (adding behavior dynamically). It costs in two ways. A decorator exposes only the interface it implements, so a wrapped TreeMap stops being a SortedMap and the JDK needed synchronizedSortedMap and synchronizedNavigableMap as well. And a decorator can't control who else holds the object inside, so its guarantee depends on how callers use it, as the javadoc conditions say; a compound action still needs its lock or a single call such as merge. ConcurrentHashMap, added in Java 5, is the other answer: the thread-safety is built into the implementation, with no lock to hold from outside.

The callers never see which: they get a store from shared(), sorted() or plain() and call its methods.


Last month a bug reached production that every test had passed: code that worked over the HashMap failed in the box office. Make sure that can't happen again. Finish the three TODO methods in src/main/java/practice/SeatHolds.java:


  • hold(seat, guest): the guest now holds the seat;
  • holder(seat): who holds the seat, if anyone;
  • holds(): every hold at this moment.


When you're done, a caller that works with one of the three stores works the same way with the other two, including when it passes null and when it changes the store while walking the list it got from holds(). release is already written. About four lines in total.

The checkout threads are moving onto the warehouse's MapStock, which was written for one thread. Nobody wants to change MapStock or the checkout code. Finish, in src/main/java/practice/Stocks.java:


  • SynchronizedStock.level and SynchronizedStock.set, a wrapper that makes any Stock safe to share between threads;
  • shared(base), which wraps base for the checkout threads and returns the stock they call together with the MeteredStock the dashboard reads.


When you're done, the checkout threads can call the shared stock at the same time without corrupting it, a refused update (a negative count) doesn't stop other threads from using it, and the dashboard's busy gauge shows how many calls are working in the store right now, not how many are waiting their turn. About eight lines in total.
