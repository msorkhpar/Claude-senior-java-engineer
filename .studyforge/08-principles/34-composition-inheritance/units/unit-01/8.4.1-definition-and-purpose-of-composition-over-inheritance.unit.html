HashSet's addAll Calls add, So a Subclass That Counts in Both Counts Each Element Twice

HashSet has no addAll of its own. It inherits this one from AbstractCollection (JDK 21 and 25 source):

super.addAll(c) runs that loop on our object, so add(e) reaches InstrumentedHashSet.add (unit Inheritance basics shows the mechanism with TreeSet): three counted in addAll, three again in add. Every batch inflates the metric by its own size.

The subclass is correct only if it knows which of HashSet's methods call which, and HashSet doesn't say: the loop is documented only as AbstractCollection's implementation note, two levels up. This is the fragile base class problem: the subclass depends on its superclass's implementation, not its contract.

Counting Only in add Fixes HashSet and Breaks ArrayList: the Count Follows Code the Subclass Can't See

The quick fix is to delete the addAll override, since "addAll goes through add anyway". Here are the same overrides on two superclasses, with and without addAll, each given three elements through addAll:

ArrayList overrides addAll with a System.arraycopy of the argument's array and never calls add, so a counting list that trusts add misses every batch.

On HashSet the "add only" version is right as long as HashSet keeps inheriting AbstractCollection.addAll. If a later JDK gives HashSet an addAll of its own, as ArrayList has, batches stop being counted, and the subclass still compiles and passes its add tests. AbstractCollection's @implSpec describes that class's code, not a promise from HashSet.

An addAll override that loops over c calling this.add, without super.addAll, counts right on both, because it no longer uses the superclass's addAll at all. That is reimplementing the superclass method, which works here only because addAll needs nothing but add.

A Forwarding Wrapper Counts Each Element Once over Any Set, Because the Set's Own Calls Stay Inside It

Instead of being a HashSet, the counter can hold a Set in a field and pass every call on to it. The forwarding part is written once per interface:

The same four tags, through new InstrumentedSet<>(backing) where backing is a new set of each of three implementations:

InstrumentedSet.addAll counts three and calls ForwardingSet.addAll, which calls s.addAll(c). The HashSet's loop still calls add, but on the HashSet, a different object whose add is HashSet's own. Nothing the wrapped set does internally can reach the counter. The wrapper is a view: what goes in through it lands in backing.

Because the wrapper takes any Set, the implementation behind it can change without touching the counter or its callers (unit Benefits of Composition over Inheritance for concurrency swaps a HashMap for a ConcurrentHashMap this way). Adding behaviour around an object of the same interface is the decorator pattern (unit Decorator Pattern (adding behavior dynamically)).

The price is the forwarding class, one line per method of the interface, and the type: an InstrumentedSet is not a HashSet, so a method declared to take a HashSet won't accept it.

With them:

Set.equals promises that two sets with the same elements are equal. saved keeps that promise: it checks that the wrapper is a Set of the same size containing the same elements. The wrapper inherits Object's identity check, so the answer depends on which side is asked, which breaks the symmetry equals requires (unit instanceof operator). The log line is Object.toString. The lookup in seen misses because the wrapper's identity hash code differs from saved's, so the lookup never compares the two, and code that asks "have we seen this tag set before?" answers no every time.

Forwarding equals as s.equals(o) makes the wrapper equal to every set the wrapped set is equal to, and hashCode must be forwarded with it, or the hash lookup still misses. Map.equals makes the same promise about mappings, so a forwarding Map without the two methods fails the same way: wrapper.equals(Map.of("x", 1)) is false while Map.of("x", 1).equals(wrapper) is true.

Extend a Class Through the Hook It Documents: LinkedHashMap Calls removeEldestEntry from put and putAll

Inheritance still fits when the subclass is a genuine kind of the superclass, and the superclass was designed for extension: its javadoc says which overridable method it calls, and when.

A gateway keeps the last three request ids it has seen, to spot client retries. A map of recent ids is a Map, and LinkedHashMap was built to be extended into one. One version bounds it at three entries by overriding put:

the other through the hook LinkedHashMap offers:

Each gets r-101 to r-105 through five put calls and, in a new map, through one putAll (a batch replayed after a restart):

putAll doesn't call put: HashMap, which LinkedHashMap extends, inserts each entry through an internal method, so the override never runs and the map grows with every replay. That is the ArrayList problem again.

removeEldestEntry comes with the promise the put override lacked. Its javadoc says: "This method is invoked by put and putAll after inserting a new entry into the map." Three things make it a hook:

  • it is protected, so only subclasses (and java.util) can call it;
  • its javadoc names the methods that call it, so the subclass relies on documented behaviour;
  • its default, return false, does nothing, so a plain LinkedHashMap is unaffected.

A designed base also makes the methods that must not change final: the template method of unit Inheritance. The bound is behaviour every caller of RecentIds accepts: a put can make an older key's get return null.

Summary

  • `HashSet.addAll` calls `add`. A subclass that counts in both counts every batch twice, and a test that only calls add passes.
  • Counting in fewer methods moves the bug. The count depends on which methods the superclass calls internally: right on HashSet, zero for batches on ArrayList, and open to change in any JDK release.
  • A forwarding wrapper counts once over any `Set`. The wrapped set's internal calls stay on the wrapped set, so only Set's contract matters.
  • A forwarding class must forward `equals` and `hashCode`. javac doesn't ask for them, and without them equality depends on which side is asked and hash lookups miss.
  • Extend when the superclass documents its hook. removeEldestEntry is called from put and putAll by contract; an override of put is skipped by putAll.

  2. A framework requires your entity to extend its base class, and you need a count of writes to one of its collections. Where do you put the counter so a framework upgrade can't change it?
  3. Collection gained default methods in Java 8, among them removeIf. Which of ForwardingSet's methods does removeIf on the wrapper go through, and what does that mean for a wrapper that counts removals?

Design Note: Why HashSet Isn't Final

Making a published class final breaks every subclass that already exists, so HashSet, ArrayList and HashMap stay open to subclassing. They are not designed for it: they document no self-calls of their own and offer no hooks, which leaves the JDK free to change which of their methods call which, and a subclass that overrides a public method breaks without warning when it does. A documented hook binds the JDK instead: once LinkedHashMap documented that putAll calls removeEldestEntry, every later putAll has to keep calling it.

Problem statement


The config service keeps feature flags in a Map<String, Boolean>, and the audit needs to know how many flag writes each deploy made. Flags are written one at a time from the admin UI (put) and in batches by the config sync (putAll). The store isn't always the same map: production passes a HashMap, the nightly report a TreeMap so its output is sorted. The audit also compares each snapshot of the flags with the previous one, and keeps the snapshots it has already filed in a HashSet so the same one isn't filed twice.

  • ForwardingMap.equals and hashCode: a wrapper compares and hashes like the map it wraps, so the audit's comparisons and its HashSet treat it as the flags it holds.

Problem statement


The edge service caches geo-IP answers by address so it doesn't call the lookup provider for every request. Memory allows a fixed number of answers. When a new one arrives and the cache is full, the answer that has gone longest without being used must go: an address read a second ago stays, even if it was first cached long before the others. Answers arrive one at a time, and at start-up a warm-up job loads the previous run's answers in one putAll; the bound must hold either way.


RecentLookups.java extends LinkedHashMap, and its constructor already passes orderedByUse() as the third argument of LinkedHashMap(int, float, boolean) (see that constructor's javadoc). Finish the three TODO methods, about four lines in total:


  • orderedByUse(): the order that makes "the eldest entry" the least recently used one;
  • removeEldestEntry: keeps the cache at no more than capacity answers;
  • nextToDrop(): the address that would be dropped next, or null when the cache is empty.
