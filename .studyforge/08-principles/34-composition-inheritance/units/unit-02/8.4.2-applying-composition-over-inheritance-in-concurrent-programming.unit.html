A webhook service keeps each customer's endpoint URLs in a list that every event walks. The list class extends Vector<String> and adds one method, a synchronized subscribe(url) that adds the URL only if it isn't there yet. Since events far outnumber new subscriptions, someone changes extends Vector<String> to extends CopyOnWriteArrayList<String>, whose reads take no lock, and a new nightly import job adds URLs with the list's own addIfAbsent(url). It compiles, every test passes, and a week later a customer reports receiving each order event twice: their URL is in the list twice.

Every output below is from Java 21 on a 20-core machine.

A Subclass's synchronized Method Excludes Only Code That Locks this

contains and add are each atomic, and subscribe holds the subclass's monitor across both, so two subscribe calls on the same object can't overlap. Which lock does the import's addIfAbsent take?

In the run, validate waits on a latch when called from a thread named subscribe, so that thread stops after its contains found nothing. The main thread then calls addIfAbsent for the same URL:

addIfAbsent didn't wait. CopyOnWriteArrayList locks an internal field, final transient Object lock, and never this, so the subclass's synchronized excluded only other subscribe calls. Every reading and writing operation of Vector locks this, so over Vector the same subclass excluded every other caller. Vector's javadoc says only that it "is synchronized"; which object it locks is in its source.

Without the latch, eight threads add the same 2,000 URLs, half through subscribe and half through addIfAbsent; a second test sends all of them through subscribe:

The window is the stretch between contains and add, and a run with no duplicates proves nothing; the forced interleaving shows the race every time. A subclass also inherits every public method of the base, and each one reaches the same data under the base's own lock: add, set, addAllAbsent, removeIf. The subclass can't take them away. Unit Definition and purpose of Composition over Inheritance shows the same coupling without threads: a HashSet subclass whose count depends on how addAll is written inside.

A Helper Outside the Class Must Take the Lock the Class Takes

Each tenant's request handler gets its own service over one shared Collections.synchronizedList:

A second version's subscribe is not synchronized and wraps its body in synchronized (urls) { ... } instead. Eight threads, one service each:

The synchronized method locks the service, and there are eight services: the per-object lock of unit Monitors and synchronized blocks's order counter. Collections.synchronizedList's methods lock the returned wrapper for one call each, which is why its javadoc tells callers to synchronize on it for iteration (unit Thread Safety of Common Data Structures). Locking the collection a helper works on is called client-side locking, and it holds only while the class keeps locking that object. Over a CopyOnWriteArrayList or a ConcurrentHashMap, synchronized (urls) excludes none of the class's own methods.

A Class That Owns the State and the Lock Doesn't Depend on What It Wraps

SubscriberSet holds the list as a private field and does its own locking:

The same latch, with the second caller another subscribe on a thread named import; the run reads that thread's state and lock owner from ThreadMXBean.getThreadInfo:

The inner list can be a plain ArrayList: no reference to it leaves the class, so every access goes through lock, whatever the list's own locking is. Swapping the inner list for another type touches no caller (unit Benefits of Composition over Inheritance for concurrency).

Every operation callers need is a method you write: there is no inherited removeIf or iterator. One lock now serializes readers too, so every event's walk starts with a snapshot() copy taken under the lock, the cost the switch to CopyOnWriteArrayList was meant to remove. And the guarantee holds only while the list stays private: a constructor that stored a list the caller passed in, or a getter that returned it, would give callers a path around the lock.

When the Class Already Has the Compound Action, Call It

CopyOnWriteArrayList already had the action the subclass wrote:

addIfAbsent is atomic against every other method of the list: it adds under the list's lock, and checks again there if the array changed since its first look. A composed class that keeps a CopyOnWriteArrayList private and calls addIfAbsent from subscribe needs no lock of its own, and its readers keep walking without one.

An API gateway keeps one rate limiter per client in a ConcurrentHashMap:

Eight threads ask for the same 10,000 clients; the run counts the limiters constructed and the clients that were handed two different ones:

Two more runs gave 1,286 and 10 split clients for get-then-put, and 0 for computeIfAbsent. A split client is counted against two or more limiters (up to one per thread), so it gets a multiple of its quota. The javadoc of computeIfAbsent states the guarantee: the whole call is atomic, and the function runs exactly once per call if the key is absent, else not at all. Some updates to the map by other threads may wait while it runs, so the function should be short, and it must not modify the map.

Inheriting from ConcurrentHashMap to add a synchronized compound method fails as the list subclass did: the map's own methods never lock the map object (unit Thread Safety of Common Data Structures). Removing a limiter has the same shape. remove(client, limiter) removes the entry only if it still maps to that limiter, so a caller holding a limiter that an admin reset already replaced leaves the new one in place:

A plain remove(client) would have removed the new limiter. When no single call expresses the action, such as a limiter and its quota in two maps changing together, a composed class's own lock has to guard both maps, and the maps' own concurrency then buys nothing.

putIfAbsent Builds the Value Before It Knows It Is Needed

putIfAbsent is atomic too, and a third version uses it correctly, returning the winner:

No client was split, but every call built a limiter, and 70,000 were thrown away: the value is an argument, so it exists before the map sees the key. Where the constructor registers a metric, reads a quota from a database or opens a connection, that work runs on every lookup, not once per client. putIfAbsent fits a value that already exists or costs nothing to make.

Summary

  • A subclass's `synchronized` excludes only code that locks `this`. Over a base that locks a private object, like CopyOnWriteArrayList, the compound action races with every inherited write, and a stress test may miss it.
  • A helper must take the lock the class itself takes. Locking the helper excludes nothing; locking the collection works only where its contract names that lock, as Collections.synchronizedList does.
  • A class that owns its state and its lock is correct whatever it wraps, while no reference to the state escapes. It pays with methods you write and one lock for readers too.
  • When the class already has the compound action, call it. addIfAbsent, computeIfAbsent and remove(key, value) are atomic against the class's own methods; putIfAbsent builds its value on every call.

Challenges

  1. The subscriber list must also cap each customer at five URLs. Can CopyOnWriteArrayList's own methods express "add if absent and fewer than five", and if not, what does the composed class cost its readers?
  2. Run the subscribe() vs addIfAbsent() stress test with 64 threads and with validate removed. How many runs does it take to see one duplicate, and what does that say about load tests as proof of thread safety?
  3. A team wants TracingConcurrentHashMap extends ConcurrentHashMap that logs every put. Which inherited methods add entries without calling put, and how would a composed version avoid the question?

Design Note: Why the Newer Collections Keep Their Locks Out of Reach

Vector and Hashtable lock this, which makes client-side locking and subclassing work, and also lets any holder of a reference stall every caller (unit Monitors and synchronized blocks). The java.util.concurrent classes lock something no caller can reach: CopyOnWriteArrayList an internal object, ConcurrentHashMap its bins. Their locking stays an implementation detail they can change. The price is that every compound action a caller needs has to be a method on the class, since there is no lock to extend from outside: CopyOnWriteArrayList has addIfAbsent, but no "add if absent and below a limit".

Problem statement


The notification service keeps the push tokens of each user's devices in a DeviceTokens store. Request threads register a token when an app starts, revoke it on logout, and rotate it when the push provider renews a device's token. The sender takes a snapshot() for every notification. Since the store went live, some users get each notification twice, and support has a log where a renewed token shows up twice in a snapshot.


Finish the two TODOs in src/main/java/practice/DeviceTokens.java:


  • register(token): add the token unless it is already registered, and say whether it was added;
  • rotate(oldToken, newToken): replace the old token by the new one, only if the old one is registered and the new one isn't; when it can't, change nothing and return false.


When you're done, a token is stored once however many threads register or rotate onto it at the same moment, and a rotation that returns false has left the store as it was. About ten lines in total.


The list inside the store is a Collections.synchronizedList. The tests hand the store a list of their own through the package-private constructor, which holds a thread right after a lookup with contains or indexOf, so look tokens up with one of those.

Problem statement


A reporting service keeps one connection pool per tenant in TenantPools, and every request asks for its tenant's pool. Opening a pool connects to the tenant's database and takes a while. The database team reports that after each deploy some tenants get two or three pools' worth of connections, and that once, after an admin reset a tenant's pool by hand, a pool the health check had just opened was closed under running reports.


Finish the two TODOs in src/main/java/practice/TenantPools.java:


  • poolFor(tenant): the tenant's pool, opened with the opener the store was given when the tenant has none;
  • discard(tenant, pool): forget that pool, unless the tenant's pool is already a different one, and say whether it was discarded.


When you're done, every request for a tenant gets the same pool, a tenant's pool is opened once however many requests arrive while it opens, and discarding a pool that was already replaced leaves the replacement alone. About three lines in total.
