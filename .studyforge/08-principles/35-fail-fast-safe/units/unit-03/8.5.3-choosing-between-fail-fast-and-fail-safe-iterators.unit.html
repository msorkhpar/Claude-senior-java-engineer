A price-alert service threw ConcurrentModificationException in production: one thread was walking the ArrayList of alert listeners while a user's dashboard subscribed. The fix that shipped made every shared list a CopyOnWriteArrayList, the audit log included, which takes one append per request, 2,000 a second at peak, and passes 100,000 events within the first minute. Since then CPU and GC time climb the longer the service runs. The end-of-day stock report walks a ConcurrentHashMap; it has never thrown, and most nights its total is off by a few units.

Each of the three needs a different kind of iterator. How fail-fast, snapshot and weakly consistent iterators behave is unit Order of Operations in Concurrent Collections, and unit Applying Fail-Fast and Fail-Safe principles in concurrent collections goes further into weakly consistent walks. Every output is from Java 21 on one machine.

Once Another Thread Writes, a Fail-Fast Walk Fails at Random; a Small Listener List Needs a Snapshot

Twenty listeners, one thread dispatching ticks to them, and a dashboard on another thread that subscribes and unsubscribes in a loop. The same code runs with an ArrayList, then with a CopyOnWriteArrayList:

This dashboard changes the list without pause; in production it subscribed a few times an hour, and the exception came about once a week. Most failed dispatches had already reached some listeners: a retry sends them the tick twice, and giving up never sends it to the rest. Not every failure was a ConcurrentModificationException either: the iterator handed back a null, which the call turned into the NullPointerException, and once found no next element after hasNext() had promised one. The counter and the array are plain fields, and nothing makes the dispatching thread see another thread's writes in order, so the check unit Order of Operations in Concurrent Collections calls best-effort promises nothing here. Over 16 runs, between 39 % and 99.7 % of dispatches threw. Fail-fast fits a collection one thread owns (unit Best practices for safe concurrent programming), where its exception reports a bug in the loop.

The copy-on-write list passed every run. A subscribe copies 20 references, and a dispatch walks the array that was current when it began, without a lock. A synchronizedList walked under its own lock (unit Thread Safety of Common Data Structures) is also correct, but then every subscribe waits for the whole dispatch in progress, every remaining listener included.

Every Copy-on-Write Write Copies the Whole Array, So Its Cost Grows with the List

The audit log got the same list type. This program keeps a list at size n and replaces one element per write, on one thread, with nothing competing; for comparison it also times a locked ArrayList and a ConcurrentLinkedQueue held at the same size:

median runs three warm-up rounds, then five timed ones, and keeps the middle one; allocation comes from ThreadMXBean.getThreadAllocatedBytes. There is no JMH here, so read the times as orders of magnitude on one machine. One of three runs:

From 1,000 elements on, the copy-on-write time and allocation grow tenfold with each tenfold size, because every mutative operation makes "a fresh copy of the underlying array" (its javadoc): here 4 bytes per element, plus the array header and the boxed value. The other two stay flat. Between runs the times moved by up to a factor of three (2.2 to 7.3 µs at 10,000); the bytes didn't move.

For the audit log at 100,000 events, each append copies 400 KB. At 2,000 requests a second that is 800 MB of garbage a second and about 4 % of a core spent copying, and both grow with every event appended. By the same table, a subscribe to the 20-listener list costs about 20 ns and 100 bytes.

Measuring it yourself. set skips the copy when the new element is the same object as the old one, and Integer.valueOf returns cached objects for -128 to 127. Our first version wrote i, so each round stored the same cached objects for 0 to 127 into the same slots again, and the 100,000 row showed 374,430 bytes instead of 400,032. Hence the i + 1_000.

A Weakly Consistent Walk Fits Work on One Element at a Time, Not a Total Across Elements

The log needs an append that doesn't depend on its size, and an export that doesn't hold up requests. The log starts with 100,000 events; four threads append while an export walks it once:

The weakly consistent walk took no lock and threw nothing while the requests went on appending. Under the list's lock they waited for the whole walk; the 108 landed just before it took the lock or just after it let go. An export that writes each line to a file holds that lock as long as the file takes. Each event stands on its own, so it doesn't matter whether one appended mid-walk makes this export.

The stock report is different. Stock moves between warehouses as a debit and a credit, so the total never changes, and the report adds up every warehouse. Each merge on a ConcurrentHashMap is atomic, and the walk takes no lock:

One thread moves stock as fast as it can, and a report runs every 10 ms for a second:

Almost every report was wrong, and none threw. The walk reads each warehouse at a different moment, so a report that reads one side of a move before it and the other side after it counts the units twice or not at all (unit Order of Operations in Concurrent Collections showed the same with account balances). Atomic single-key updates don't help: the report needs every warehouse at one moment, and no walk over a structure that changes under it gives that.

A Total That Must Add Up Needs a Snapshot or a Lock, and Size Decides Which

A snapshot gives the report one moment: each move builds a new map and publishes it in one atomic step, and the report walks whichever map was current when it began.

So does a lock: moves take the write lock of a ReentrantReadWriteLock, and the report walks a plain HashMap under the read lock, so no move lands mid-walk. The same run with both:

Every report added up. The snapshot copies the whole map on every move: with 100 warehouses the mover managed about a million moves in the second, against 14 million on the live map, and with 100,000 warehouses it managed 366. The lock lets moves run between reports and stops them for the length of each walk: 2 ms per report at 100,000 warehouses, a fifth of the second at a hundred reports a second. Size and write rate decide between them.

A lock that only move takes leaves the report walking a map that changes under it. A mutable map kept in the AtomicReference and changed in place is the live map again: get() hands every reader that one map, and nothing is copied.

Summary

  • Once another thread writes, a fail-fast walk fails at random, and not only with ConcurrentModificationException; a dispatch that fails has often reached some listeners already. Fail-fast fits data one thread owns; a small, rarely written list that threads share fits a CopyOnWriteArrayList.
  • Every copy-on-write write copies the whole array. Time and garbage per write grow with the list: about 20 µs and 400 KB at 100,000 elements here, so a large or write-heavy list doesn't fit.
  • A weakly consistent walk fits work on one element at a time. It never blocks writers, and a total it adds up can be one the collection never held.
  • A total that must add up needs a snapshot or a lock. The snapshot charges each write a copy, so it fits small or rarely written data; the lock makes writers wait out each read.

Challenges

  1. Each websocket session registers a listener, so the list reaches 5,000, with 200 connects and disconnects a second. Estimate from the write-cost table what a CopyOnWriteArrayList costs there. What would you use instead, and what would a dispatch then see?
  2. The stock report runs once a night over 2 million items, while moves arrive 5,000 times a second. Neither a copy per move nor a lock held for the whole walk is acceptable. What else gives the report one moment?
  3. Run the write-cost measurement with four writer threads. Which column changes most, and why?

Design Note: Three Iteration Contracts and What Each Gives Up

The JDK could have given every collection one iterator. It gives three, and each gives up something different. Fail-fast costs one counter and one comparison per step, and gives up correctness once a second thread writes. A snapshot iterator gives readers one moment without a lock, and makes every write copy everything. A weakly consistent iterator makes neither readers nor writers wait, and gives up the moment: a read that spans elements can mix before and after.

None of the three gives a lock-free reader one moment of a structure that writers change in place without copying it, which is why the consistent report above cost either a copy or a lock. Unit Definition and purpose of Fail-Fast and Fail-Safe iterators uses "fail fast" in a wider sense, checking arguments in constructors and refusing bad configuration.

Problem statement


Every request to the back office appends an event to AuditLog: who did what, numbered in order. By the end of a day the log holds tens of thousands of events. Compliance can start an export at any moment; it walks the log and writes each event to the archive, which takes a few milliseconds per event, while requests keep arriving.


Ops wants three things from the log. Request latency must not creep up as the day's log grows. A request must never wait for an export that happens to be running. An export must finish, with every event that was in the log when it began, once each and in order; whether it also includes events appended while it runs doesn't matter.


Finish src/main/java/practice/AuditLog.java: choose the collection in newStore(), and write store and export. About six lines in total.

Problem statement


A chain of about thirty shops keeps one product in StockLedger: units per warehouse. Transfer threads move units between warehouses a few times a minute; nothing is ever added or sold here, so the chain's total never changes. The stock-take report prints one line per warehouse on a label printer, which takes about a second per line, and then the total.
