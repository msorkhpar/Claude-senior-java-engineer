One release of the order service changed the switch that sends customer emails, and three tickets came in the same week. Customers whose order was cancelled were told their parcel was on its way. Orders in the new ON_HOLD status got no email at all. And the nightly resend job died with a NullPointerException on a legacy row with no status, although the switch has a default.

All three come from how the classic switch statement (case X: with a colon) runs. The arrow form and switch expressions are unit switch expressions (Java 14+); patterns in a switch are units 1.5.x.

A Case Label Is Where Execution Enters, and It Runs On Until a break

The emails switch, after the change:

A case label is an entry point, not the start of a block that ends at the next label. The switch evaluates the selector once, jumps to the matching label, and runs everything below it, across later labels, until a break, return, throw or the end of the switch. CANCELLED has no break, so the cancelled customer gets both emails. Plain javac says nothing; javac -Xlint:fallthrough does:

The same rule makes grouping work. Labels stacked with nothing between them, or listed with commas (case 'y', 'w':, allowed in the colon form since Java 14), share the statements below them, and the lint doesn't flag them.

default is a label like the others: its position doesn't change which values reach it, but in the middle it falls through like any case. This router puts it before 503:

A 418 gets retried.

The switch body is also one block for declarations: a variable declared under one label is in scope under the later ones, so declaring msg under two labels doesn't compile (variable msg is already defined).

The Selector Is an int-Compatible Type, a String or an Enum, and Every Label Is a Distinct Constant

With constant labels, a switch takes char, byte, short, int, their wrappers, String or an enum. An order id in a long doesn't compile:

and neither does a boolean, float or double. The rule matches the bytecode: javac compiles a switch to a tableswitch (a jump table, for dense values) or a lookupswitch (sorted keys, for sparse ones), both keyed by an int, so a String or an enum is mapped to an int first. The order of the cases in the source doesn't affect speed.

Each label must be a constant expression the compiler can put in that table:

final alone is not enough: a constant is a final primitive or String variable initialised with a constant expression. The error for BOXED is not a type mismatch with the int selector: a field of type Integer is never a constant. A label must also fit the selector (case 200 on a byte is a possible lossy conversion), and no two labels may be equal: case RETRY:, where RETRY is 503, beside case 503: is a duplicate case label. An if chain that tests 503 twice compiles without a warning, and its second branch never runs.

A String Switch Matches With equals, So It Is Exact and Case-Sensitive

A decoder picks its codec from the Content-Encoding header:

A value parsed from a request (fromHeader, built with new String("gzip")) is a new String, not the literal (== is false), and it still matches: javac compiles the switch to a lookupswitch on encoding.hashCode(), then encoding.equals("gzip") (javap -c shows both calls). equals compares characters exactly, so a client that sends GZIP is refused. HTTP defines this header as case-insensitive, so the value is normalised before the switch:

toLowerCase() uses the default locale, and in Turkish an I lowers to a dotless ı. A server whose default locale is Turkish refuses every IDENTITY. Use toLowerCase(Locale.ROOT) for protocol values.

A null Selector Throws Before Any Label Is Compared, default Included

The resend job's switch has a default. Here a String, an enum and an Integer switch, each with a default, are called with null (compiled with -g, so the messages name variables):

Before any label is compared, the switch turns the selector into an int: hashCode() for a String, ordinal() for an enum, unboxing for a wrapper. On null that call throws, and default is never considered. The resend job stops at the first legacy row, and every customer after it gets nothing.

Before Java 21 the fix is a null check in front of the switch. Java 21 adds a case null label:

case null, default: sends both to one body. A case null also changes the rules for the whole statement: the compiler now requires it to cover every value. The same switch without its default fails with the switch statement does not cover all possible input values.

A Switch Statement Over an Enum Needn't Name Every Constant, So a New Constant Runs Nothing

The fraud team added ON_HOLD to the status enum. A version of the emails switch that names PLACED, PAID, SHIPPED and CANCELLED, with no default, compiles, with -Xlint:all too. For ON_HOLD it returns:

A classic switch statement over an enum, without case null, is not checked for coverage: a value no label names runs nothing. The same happens when only the enum is recompiled, with ON_HOLD inserted in the middle so the later ordinals move: the old switch class still sends each constant to its case, because it builds its ordinal-to-case table from the constants' names when it first runs, and ON_HOLD matches none.

A default that throws makes the first ON_HOLD order fail:

A local assigned under every label and read after the switch doesn't compile without a default, even when every constant is listed (variable subject might not have been initialized). A compile-time error for the missing ON_HOLD comes from a switch expression (unit switch expressions (Java 14+)), or from a statement with case null, which must then name every constant.

Summary

  • A case label is an entry point. Execution runs on through later labels until break, so a missing break runs the next case, and a default in the middle falls through too.
  • Selectors are `char`, `byte`, `short`, `int`, their wrappers, `String` or an enum; labels are distinct compile-time constants. long, a boxed field and a duplicate are compile errors.
  • A `String` switch uses `hashCode` and `equals`. It matches values built at run time, exactly and case-sensitively; normalise with Locale.ROOT.
  • A `null` selector throws `NullPointerException` before `default` is considered. Check first, or use Java 21's case null, which makes the compiler demand full coverage.
  • A switch statement over an enum, without `case null`, is not checked for coverage. A new constant runs nothing unless a default throws.

Challenges

  1. Find a switch in your codebase that falls through on purpose. Would a new team member notice? Rewrite it so the intent can't be missed, and compare with the arrow form of unit switch expressions (Java 14+).
  2. Your enum has 40 constants and 12 switch statements over it in five services. Which get a throwing default, and which a harmless one? What does each choice cost the day a constant is added?
  3. A switch over 2,000 String keys, or a HashMap lookup: measure both with JMH, then decide on something other than speed.

Design Note: Why the Switch Statement Falls Through

Java's switch follows C's, where a case label is a jump target inside one block of code and falling through is what happens after the jump. The cost is that the common case, one value and one action, needs a break that nothing forces you to write, and falling through on purpose looks like a forgotten break unless a comment says otherwise. Unit switch expressions (Java 14+)'s arrow form has no fall-through, so it needs no break.

Problem statement


The on-call desk turns every alert into an incident with a severity from 1 (worst) to 4. The response is cumulative: severity 4 only writes the incident log; severity 3 opens a ticket and does what severity 4 does; severity 2 posts to the incident channel and does what severity 3 does; severity 1 pages the on-call engineer and does what severity 2 does. Within one incident, the most urgent action comes first. Last week a monitor with a bad config sent severity 0, and nobody noticed because nothing happened.


Escalation already validates the monitor's name. Write escalate(int severity) in src/main/java/practice/Escalation.java, as one switch statement, so that each severity runs its actions in that order and a severity outside 1 to 4 throws IllegalArgumentException before any action runs. About a dozen lines in total.

Problem statement


Sensors upload their readings to the ingest API, some compressed. BodyDecoder looks at the request's Content-Encoding header and wraps the body in the matching decoder. The API accepts identity, gzip (and its old alias x-gzip) and deflate. The firmware of one vendor sends GZIP, an older gateway sends no Content-Encoding header at all for uncompressed bodies, and the service is about to be deployed to a data centre in Istanbul whose servers run with a Turkish default locale.


Write codecFor(String contentEncoding) in src/main/java/practice/BodyDecoder.java with a switch statement, so every one of those clients is understood, and an encoding the API doesn't accept is refused with IllegalArgumentException. About ten lines in total.
