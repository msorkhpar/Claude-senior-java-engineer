One release of the order service shipped three bugs, each in an if that passed review. Customers whose parcel never arrived got no refund. Customers who spent the most got the smallest discount. And the nightly export died with a NullPointerException on a line where nothing looks like it could be null. None of them is about syntax.

An else Belongs to the Nearest if, Whatever the Indentation Says

The refund rule: a delivered, damaged parcel is refunded, and a parcel that never arrived gets a tracking request. Without braces it was written like this:

An if owns exactly one statement, and without braces the inner if (damaged) ... else ... is that statement. The grammar attaches an else to the nearest if that has none, so this else belongs to if (damaged). Indentation is for people: javac compiles this without a warning, even with -Xlint:all. A parcel that never arrived falls through to "no action", and a delivered parcel in good condition triggers a tracking request. Braces on every branch make the binding the one you wrote.

An else-if Chain Runs the First Branch That Holds, So the Order Is the Specification

The discount tiers were 5% from 1,000 euros and 10% from 5,000:

else if is not a keyword of its own: it is an else whose one statement is another if. So the conditions are tested from the top, and the first one that holds ends the chain. Every amount of 5,000 or more already passes >= 1_000, so the 10% branch never runs. javac compiles it without a warning: it doesn't compare conditions, so a branch that no input reaches is still reachable code to the compiler.

When ranges overlap, put the narrow one first: >= 5_000, then >= 1_000. When one case is a special value inside a range, the special value comes first. The boundary operator belongs to the same specification: with > 1_000 instead of >= 1_000, a customer who spent exactly 1,000 euros gets nothing, and only a test at exactly 1,000 shows it.

The Compiler Judges an if by Its Constants and Its Exits, Never by What Its Conditions Mean


A parcel fee, declared without an initializer so that every path must set it, and final so that none sets it twice:




Every int passes one of the two conditions, but the definite-assignment rules evaluate only constant expressions, not what weightKg <= 5 means, so to javac both conditions can be false. Make the last branch a plain else and it compiles. Dropping final changes nothing: the error comes from reading a local that might be unassigned, and a local of any type, String included, has no default value.


The tempting fix is int fee = 0;. It compiles and switches the check off. Add a third weight class, forget one assignment, and the method returns 0: a free shipment, and no tool complains. A local declared without a value and assigned in every branch keeps a missing assignment a compile error.


Constants are what the compiler does evaluate. if (false) { ... } compiles, while while (false) { ... } is error: unreachable statement. The language exempts if on purpose, so that a constant flag can switch code off:



javap -c shows the body of handle as a single return: the trace code isn't in the class file.


The compiler also tracks whether a branch can complete. A pattern variable introduced by a negated instanceof is in scope after the if when the if's body can't finish normally:



Replace the return -1 with a log line and return text.length() becomes error: cannot find symbol: a non-String can now reach that line. That makes the guard clause, which rejects the bad case and returns, the natural shape for checks at the top of a method: the main path stays unindented and gets the typed variable.

Summary


  • An else binds to the nearest if without one. Indentation doesn't count; braces do.
  • An else if chain stops at the first condition that holds. Order overlapping conditions from narrow to wide and test each boundary value; javac never reports a branch no input reaches.
  • ?: has one type, taken from both operands. An int on one side unboxes an Integer on the other and throws on null; an int beside a double becomes a double.
  • The compiler evaluates constants and tracks exits, nothing else. A chain needs a final else to assign a local declared without a value, if (CONSTANT) removes code, and a guard that returns keeps its pattern variable in scope.

Challenges


  1. Find an else if chain of five or more branches in your code base. Which conditions overlap, and which test would show that their order is wrong?
  2. Your team's style allows a brace-less if for one-line returns. Write a rule that keeps that and still rules out the refund bug, or argue for braces everywhere.
  3. A method returns Integer from a ?: whose operands come from two other methods. One of them changes its return type from Integer to int. What breaks, where, and when do you find out?


Design Note: Why a Condition Must Be a boolean


In C an if takes any integer, and if (x = 0) compiles, assigns, and never runs its branch. Java requires a boolean, so that mistake is a type error, and writing 0 == x to guard against it buys nothing for numbers. The rule costs a comparison (if (count != 0), not if (count)), and it still lets one case through: when the variable is itself a boolean, if (dryRun = true) is legal. Test a boolean by using it, if (dryRun), and there is no = to mistype.
