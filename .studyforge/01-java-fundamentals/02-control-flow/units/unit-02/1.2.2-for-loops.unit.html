The Enhanced for Copies Each Element Into Its Own Variable, So Assigning to It Changes Nothing

The Java Language Specification (14.14.2) defines the enhanced for by what it compiles to. Over an array, it is an index loop that copies prices[i] into a new variable p at the start of each pass. Over an Iterable, it calls iterator() once, then hasNext() and next(), and copies each result into the variable. Either way p is a local. Calling a method on the copy, such as append on a StringBuilder element, does change that object, because the copy and the element refer to the same object. Declaring the variable final int p turns the assignment into a compile error.

The copy is also where unboxing happens, before the first line of the body:

One unknown count fails the whole total, and no check in the body can prevent it. Declare the variable as Integer and test it for null. To write back, use the index loop. To remove while walking, use Iterator.remove or removeIf (unit Order of Operations in Concurrent Collections).

  1. Coding practice

    Make the morning restock stick

    • The enhanced for copies each element into a new local variable, so assigning to that variable leaves the array or collection unchanged; writing back needs an index loop.
    • With a primitive loop variable over a collection of wrappers, a null element throws NullPointerException as it is copied, before any check in the body runs.

A Lambda Can Capture the Enhanced for's Variable, Not the Basic for's Counter


The warm-up builds one task per shard and hands the tasks to a pool. The first version doesn't compile:




A lambda copies the value of a local (for an array or other object, the reference), so Java accepts only a local that is never reassigned. A basic for has one shard for the whole loop, and shard++ changes it. A common way to silence the compiler is a holder whose reference never changes:




Each task reads the holder when it runs. Here they run after the loop, which left it at 3, a shard that doesn't exist; on a real pool each task gets whatever value the holder has at that moment. Copy the counter into a variable declared inside the body. The enhanced for already does that, since its variable is declared anew for each pass; it can be captured as long as the body doesn't assign to it:

A Loop Ends Only When Its Condition Turns False, and int Overflow Can Keep It True


The ID walk processes batches of 100 million up to the last possible ID:




No int is greater than Integer.MAX_VALUE, so from <= lastId is never false. The update wraps past the top into negative numbers (unit Primitive data types), walks through them, climbs back through IDs it has already processed, and never stops. The same happens with i <= Integer.MAX_VALUE stepping by one.


A long counter can go past the last ID, so the condition turns false:




Because from is a long, the batch's end is too; with an int from, from + 100_000_000 - 1 wraps on the last batch. The bound must also be <=: with from < lastId, a last batch of a single ID is never processed.




    

  1. 

    Coding practice
    

    Split an ID range into batches, up to the last int
    

      

    • With < instead of <= on an inclusive bound, a last batch of a single element is never processed.
      • 

    • A loop whose int counter must pass Integer.MAX_VALUE, or whose step overflows, never makes its condition false; a long counter ends it.

A Floating-Point Counter Changes the Number of Passes, So Count With an int


How many passes does this make?




0.1 is a binary fraction slightly off its decimal value, and each addition rounds (unit Primitive data types). After ten additions x is just below 1.0, so the condition holds once more. With x <= 0.3 the error goes the other way: the third addition gives 0.30000000000000004, and the loop makes 3 passes instead of 4.


A float counter can stop moving. Between 2^24 (16,777,216) and 2^25, adjacent floats are 2 apart. At 16,777,216, f + 1 falls exactly between two floats, and rounding to even gives back 16,777,216:




Count passes with an int and compute the value from the count. Prefer i / 10.0 to i * 0.1: 10.0 is exact, so the result is the double nearest i/10, while 0.1 is already rounded and the multiplication rounds again:

Summary


  • The enhanced for copies each element into a new variable. Assigning to it changes nothing, and unboxing a null element throws in the header.
  • A lambda captures values, so it needs a variable that never changes. Copy the basic for's counter inside the body; a shared holder gives every task the final value.
  • A loop ends only when its condition is false. An int bound at MAX_VALUE, or a step that overflows, keeps it true: count in long.
  • A floating-point counter makes the wrong number of passes, and a float can stop moving. Count with an int and compute the value.

Design Note: Why the Enhanced for Hides the Index


The enhanced for, added in Java 5, gives the body neither the index nor the iterator, so the same loop reads alike over an array and over any collection. The cost: the body can't write back, skip ahead or remove, so a loop that needs one of these is rewritten as an index or iterator loop. And code that assigns to the variable still compiles, unless the variable is declared final.
