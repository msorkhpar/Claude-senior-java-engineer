In one week the file service stored a 4 GiB upload as a 100-byte file, paid a 4.35 refund as 4.34, answered "no such account" for an account that exists, and couldn't read back a price file that its Frankfurt servers had written. Each bug is a conversion that compiled, and none of them threw where the value went wrong.

A Narrowing Integer Cast Keeps the Low Bits and Never Fails

The upload's length arrives as a long, and the legacy storage API takes an int:

A long-to-int cast keeps the low 32 bits. Nothing is checked, so nothing throws. A negative result is more likely to fail somewhere later; 100 is a plausible length, and the service stored the first 100 bytes as the whole file.

A compound assignment hides the same cast. total += x means total = (int) (total + x), so this compiles and wraps:

total = total + 3_000_000_000L would not compile. Where a value must fit, convert it with Math.toIntExact(uploaded), which throws instead:

Casting a double to int or long Truncates Toward Zero, Clamps at the Range, and Turns NaN Into 0


The refund service converts euros to cents:




4.35 is not exact in binary (unit Primitive data types), and the product lands just below 435. The cast drops the fraction, so the customer gets 4.34. Math.round returns the nearest whole number, as a long for a double.


This cast doesn't wrap the way integer casts do. It truncates toward zero, clamps values outside the range to MIN_VALUE or MAX_VALUE, and turns NaN into 0:



A feed that sends NaN for an amount produces a refund of 0 cents, with no error, and Math.round(Double.NaN) is 0 as well.


Rounding by adding 0.5 and casting works only for positive values: a reversal of -4.35 becomes -434 cents. Math.round breaks ties toward positive infinity, so -2.5 rounds to -2.




    

  1. 

    Coding practice
    

    Pay partner refunds to the cent
    

      

    • Casting a double to an integer type truncates toward zero, so a computed amount just below a whole number loses one; Math.round rounds to nearest, and adding 0.5 before the cast is wrong for negative values.
      • 

    • A cast from NaN gives 0 and Math.round(NaN) is 0, so a value that is not a number becomes a plausible zero unless the code rejects it.

Widening to float or double Is Implicit and Rounds Large Values


Java converts int and long to float and double without a cast, because the range fits. The precision may not: a float has 24 significant bits, so an int above 2^24 can round, and a double has 53, so a long above 2^53 can.




An order id above 2^53 that passes through a double, in a metrics library or a JavaScript client, can come back as a different order. The last line widens implicitly: when one branch of ?: is an int and the other a double, the result is a double, on either branch.


A Wrapper Converts Only to Its Own Primitive: an Integer Is Never a Long


int widens to long, but Integer and Long are unrelated classes. Accounts are kept by a Long id, and the id arrives as an int:




get takes an Object, as do containsKey, remove and a set's contains, so get(42) compiles. It boxes 42 to an Integer, which never equals a Long. A reference cast converts nothing: it checks the object's class and throws ClassCastException on a mismatch. JSON decoders that read into a Map<String, Object> often return an Integer for a small number and a Long for a large one, so (Long) id passes tests that use large ids and fails in production on small ones. ((Number) id).longValue() accepts both.

Text Conversions: parseInt Rejects Spaces, parseDouble Accepts NaN, and String.format Uses the Default Locale


The price export writes String.format("%.2f", price), and the import reads the file back with Double.parseDouble. On the Frankfurt servers:




String.format without a Locale uses the JVM's default format locale, taken from the operating system at startup unless -Duser.language and -Duser.country override it. parseDouble and String.valueOf never do. String.format(Locale.ROOT, "%.2f", 1.5) prints 1.50 on every machine.


Integer.parseInt(" 42") throws, while Double.parseDouble trims spaces and accepts "NaN", "Infinity" and "1e3". An import that validates prices with parseDouble lets NaN in, and every later <, > or == with it is false (unit Primitive data types). Check Double.isFinite after parsing.

Summary


  • A narrowing integer cast keeps the low bits: an out-of-range value turns into another valid-looking number, and += casts for you. Use Math.toIntExact where it must fit.
  • A cast from double truncates toward zero, clamps, and maps NaN to 0: round with Math.round, and reject NaN yourself.
  • Widening to float or double needs no cast and can round above 2^24 (float) or 2^53 (double).
  • Wrappers don't widen: an Integer key never finds a Long one, and (Long) on an Integer throws. Go through Number.
  • Text conversions differ: String.format follows the default locale, parseDouble accepts NaN, and parseInt rejects spaces.

Design Note: Why a Cast Never Throws


The JLS defines the result of every narrowing primitive conversion, down to NaN and values out of range, and states that it never causes a run-time exception. A check would cost a branch on every cast, so checking is opt-in: Math.toIntExact and the other *Exact methods. The cost falls on review: once the cast is written, the compiler no longer reports the lossy conversion, and a compound assignment never reports it at all.
