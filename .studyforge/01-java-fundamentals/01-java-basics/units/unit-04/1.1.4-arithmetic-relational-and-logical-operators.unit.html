Integer Division Truncates Toward Zero, and % Takes the Sign of the Dividend

The progress bar computed its percentage like this:

/ on two integers discards the fraction, so 450 / 1200 is 0 and the multiplication comes too late. Multiply first, and check that the product fits (unit Primitive data types).

Discarding the fraction rounds toward zero, not down, and that matters once values can be negative. The dashboard grouped samples into one-minute windows by their offset in seconds from the deploy, so a sample three seconds before it has offset -3:

Pause on the -3 row. / puts it in window 0 with the samples taken three seconds after the deploy, so the last slow requests of the old version count against the new one. Window 0 spans 119 seconds, every other window 60. Math.floorDiv rounds toward negative infinity and puts the sample in window -1.

% follows /: Java defines it so that (a / b) * b + a % b == a, which gives the remainder the dividend's sign. -3 % 60 is -3, and as an index into a 60-slot array it throws ArrayIndexOutOfBoundsException. Math.floorMod takes the divisor's sign and stays in 0 to 59. Use the plain operators where both operands are known to be non-negative, and the floor methods where either can be negative.

  1. Coding practice

    Keep pre-rollout samples out of the canary's first window

    • Integer / discards the fraction, so a percentage computed as part / whole * 100 is 0 until part reaches whole; multiplying first keeps it.
    • % takes the sign of the dividend, so a negative left operand gives a negative remainder and a negative index; Math.floorMod takes the divisor's sign.
    • Integer / rounds toward zero, so a small negative offset falls in the same bucket as a small positive one; Math.floorDiv rounds toward negative infinity.

Precedence and Associativity Group an Expression; Its Operands Still Run Left to Right


Predict the four lines before reading the output:




retries++ has a value, the old one, and increments the variable as a side effect when it is evaluated. The assignment then stores the old value back: the increment is lost, and a retry loop bounded by this counter never reaches its limit. ++retries has the new value; as a statement of its own, either form works.


Operators of equal precedence group left to right, and + with a String on either side concatenates. "Total: " + 10 is already a string, so + 20 appends "20". In 10 + 20 + " items" the first + adds two ints. Parenthesise arithmetic inside a concatenation.


Precedence decides how the expression is grouped: b * c is computed before it is added to a. It does not decide what runs first. Java evaluates the left operand of every binary operator fully before the right one, so log runs for a, b and c in that order. Assignment works the same way: in a[i] = ..., the index is read before the right side runs. Give each side effect its own statement, so nobody has to work this out.

&& and || Skip Their Right Operand; & and | Always Evaluate Both


On booleans, &, | and ^ are logical operators too, and & gives the same result as && whenever both sides can be evaluated. The difference is whether the right side runs:




&& stops when its left side is false, and || when it is true, so the left side of && can guard the right. & evaluates both and calls startsWith on null.


The re-pricing job hit the other side of the same rule. It ran every SKU and recorded whether any price changed:




After A-1, changed is true, so || never calls reprice again. B-2 and C-3 keep their old prices, and the job reports a change. Write changed |= reprice(sku) or changed = reprice(sku) || changed, so the call runs every time. A call whose side effect must happen goes on the left of && and ||, or outside them.

    Coding practice
    

    Make the price sync apply the whole feed
    

      

    • && and || skip their right operand when the left decides the result, so && can guard a null check; & and | evaluate both and throw on the null.
      • 

    • A call on the right of || or && is skipped once the left decides, so changed = changed || apply(x) stops applying after the first change.

Bit Operators Bind Looser Than ==, and an int Shift Counts Only to 31


On integers, &, | and ^ combine bits and ~ flips them, which is how a set of flags fits in one number. Their precedence is below == and !=, so this check doesn't compile:




ADMIN != 0 is grouped first. Write (roles & ADMIN) != 0. With boolean operands the same grouping compiles and means something else: a & b == c is a & (b == c).


That test reads one bit. For a set of several bits, (roles & set) != 0 is true when any of them is on, and (roles & set) == set only when all are. roles & ~set clears the set's bits, while roles ^ set flips them: it clears the ones that were on and sets the ones that were off.


The dashboard kept 48 feature flags in a long, and set flag 35 like this:




1 << 35 is an int shift, and an int shift uses only the low five bits of its distance: 35 becomes 3, and the result, 8, is widened to long afterwards. A long shift uses the low six bits, so 1L << 64 is 1. Only the left operand sets a shift's type, so make it a long.


>> copies the sign bit into the top bits, and >>> fills them with zeros. The difference matters when an int holds a sum that overflowed, as in a binary search's midpoint over a large array:




The sum wraps negative, and / 2 and >> 1 keep it negative: an index that throws. The true sum still fits in 32 bits read as unsigned, and >>> 1 halves it that way. low + (high - low) / 2 gives the same result without the trick.

    Coding practice
    

    Give every feature switch its own bit
    

      

    • (mask & set) != 0 asks whether any bit of the set is on and (mask & set) == set whether all are; mask & ~set clears the bits while ^ flips them.
      • 

    • An int shift uses only the low five bits of its distance and a long shift the low six, so 1 << 35 is 8 even when assigned to a long; the left operand must be a long.

Summary


  • Integer / truncates toward zero and % takes the dividend's sign: multiply before dividing, and use Math.floorDiv and Math.floorMod where a value can be negative.
  • Precedence groups an expression, and operands still run left to right: x = x++ loses the increment, and "s" + 1 + 2 concatenates.
  • && and || skip their right operand: that makes a null guard safe, and silently skips a call whose side effect was needed.
  • Bit operators bind looser than ==, and an int shift uses the low five bits of its distance: parenthesise masks, and shift a long when the bit can be 32 or higher.

Challenges


  1. Find every / and % in a code base you know whose left operand can be negative: a time offset, a delta, a hash. Which of them should be floorDiv or floorMod?
  2. A percentage must be rounded to the nearest whole number, not truncated, using only long arithmetic. Write it, and decide what it returns when total is 0.
  3. Feature flags outgrow 64 bits. Compare long[], java.util.BitSet and EnumSet for storage, the cost of checking several flags at once, and how a wrong flag index fails.


Design Note: Why Integer Division Truncates


Java defined / to truncate, as C compilers on common hardware already did (C itself required it only from C99), so / maps closely onto the processor's divide instruction, and % follows from it. Floor division would make every negative window and ring index correct, at the price of a sign test on every division and a correction when the signs differ and the remainder isn't zero. Java kept / close to the hardware and, in Java 8, added Math.floorDiv and Math.floorMod for the code that needs them, leaving the default that is wrong for negative offsets.
