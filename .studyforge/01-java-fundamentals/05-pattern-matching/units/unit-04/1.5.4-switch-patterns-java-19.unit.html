The refunds service routes payment events with a switch. A rule added in March sends every refund above 10,000.00 to manual review. In June an auditor finds a B2B refund of 25,000.00 that was paid without one, and the code compiled without a warning. The same week, a replay from a legacy queue that stores empty slots as null stopped the consumer with a NullPointerException, although its switch has a default. Switch patterns were a preview in Java 17 to 20 and are standard since Java 21; every output below is from Java 21.

A case With a Type Pattern Tests, Casts and Binds, and the First Case That Matches Wins

A switch over a reference type can use the type patterns of unit Pattern matching for instanceof (Java 14+) as labels. case Refund r matches when the selector is a Refund, and binds it, already cast, to r. A when clause, the guard, adds a condition the case must also meet. The events and the router:

Pause here: where does Refund("B2B-7", 2_500_000) go?

The switch tries the cases from the top and runs the first whose pattern matches and whose guard is true. The B2B case matched first, so the review case never saw the refund. Nothing ranks cases by how specific they are, the way overload resolution ranks methods: order is the only priority. The fix is to put the case that must win, here the review, first.

A binding is in scope only in its own guard and arm. A colon-style case can't fall into a case that declares a binding (illegal fall-through to a pattern), since the binding would be unset there.

The Compiler Rejects a Case That an Earlier Case Always Wins, but It Does Not Read Guards

The compiler does reject a case that can never run because an earlier, unguarded case matches everything it would:

Every String is a CharSequence, so case String s could never run. An unguarded case dominates every later case of its own type or a subtype, guarded or not: case Integer i followed by case Integer i when i > 100 gets the same error. So does a default before a pattern case, or case 0 after an unguarded case Integer i.

A guarded case dominates nothing, because the compiler doesn't evaluate guards, apart from a constant true or false. These two compile without a warning, and the second never returns "big":

The router's two guards test different fields, so no compiler could tell that they overlap. Within one type, write the guarded cases in priority order and the unguarded case last.

A Guard Runs Only After Its Pattern Matches, and Again for Every Case That Tries It

A guard runs only after its pattern matches, so it can use the binding, and again each time the switch reaches its case, so a call in two guards runs twice for one event. Here isFlagged(account) stands for a call to the risk service: it flags accounts ending in -X, and counts its calls:

A large refund that isn't flagged costs two calls: a second bill or quota unit on a paid service, and on a call that consumes something (iterator.next(), queue.poll()) a second guard that reads a different element. An exception thrown in a guard propagates as it is: Integer.parseInt in a guard ends the switch with NumberFormatException, and no later case is tried. A local variable that a guard reads must be effectively final.

Keep guards to cheap checks on the binding. When a decision needs a call, make it once in the arm:

Over a Sealed Type, Naming Every Permitted Subtype Is Exhaustive, and Only Unguarded Cases Count

A switch with patterns must cover every value of its selector. The router has no default and compiles, because Event is sealed: Charge and Refund are its only subtypes, and each has a case. Over a selector of type Object, cases for String and Integer alone are refused; the switch needs a default or a case Object o.

A guarded case covers nothing, unless its guard is the constant true. Over a sealed Shape of Circle and Square:

The compiler doesn't try to prove that the guards together accept every square.

As with enums in unit switch expressions (Java 14+), when the events library adds Chargeback to the permits list, every switch over Event without a default stops building at the switch, and someone decides what a chargeback means for the ledger, the refunds and the reports. A switch with default -> "refunds" builds, and books every chargeback as a refund.

null Matches Only case null; Neither default Nor case Object Does

The replay's consumer, reduced:

Called with null, it throws, and so does the same switch with case Object x in place of default:

A pattern switch keeps the rule of unit switch statements: a null selector throws before any case is tried, unless the switch has case null. case Object x matches every object, and null isn't one. So the binding of a case's type pattern is never null, and a switch written before Java 21 still throws on null as it did.

case null sends null to its own arm, and case null, default sends it with everything else:

null can't share a label with a pattern: case null, String s is refused with invalid case label combination. Merge null into default only when "missing" and "a type I don't handle" mean the same thing to the caller. Otherwise the merged arm turns a type the code was never written for into an ordinary missing value. case null plays no part in exhaustiveness: the sealed router is exhaustive with or without it.

Summary

  • The first case that matches wins. A type pattern tests, casts and binds; cases are tried in order, and a broader guard placed first takes values a later case was written for.
  • The compiler rejects a case that an earlier unguarded case always wins, but it doesn't evaluate guards other than constants, so overlapping guards compile silently.
  • A guard runs after its pattern matches, once for every case that tries it. A call in two guards runs twice; make it once in the arm.
  • Over a sealed type, an unguarded case for every permitted subtype is exhaustive. Without a default, a new subtype stops the build, and throws MatchException in code that wasn't rebuilt. A statement with patterns must be exhaustive too.
  • `null` matches only `case null`. Neither default nor case Object does, so without case null a null selector throws NullPointerException.

Challenges

  1. A switch over a sealed type has twelve cases and a default that logs and returns a safe value. What would you check before removing the default, and what must the services that use the library do on its next release?
  2. Two guards on the same type call a service whose answer can change between the two calls. What can the switch return that neither answer alone would give, and how do you rule it out?
  3. The Event hierarchy is used by twenty services you don't own. Would you seal it? What does each choice cost when you add Chargeback?

Design Note: A Switch Over a Sealed Type, or a Method on Each Type

Before patterns, the object-oriented answer to "do X for each kind of event" was an abstract method on Event, overridden in each subtype. Adding a subtype was safe: the compiler demanded the method. Adding an operation meant editing every subtype, which you can't do when the types live in a library you don't own.

A switch over a sealed type reverses that trade. Operations live with the code that needs them, so the ledger, the refunds service and the reports each write their own switch, and adding a subtype touches every one of them. The exhaustiveness check is what makes that safe: each switch without a default shows up as a compile error. Sealed types and switches suit a set of types that is stable while the operations on it keep growing.
