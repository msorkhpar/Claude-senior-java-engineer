The export API accepts an optional timeout per request. Clients report that it does nothing: a request sent with 800 ms still waits the 30-second default. The commit that rewrote the option parsing with a pattern compiled cleanly, and the default-timeout test still passes.

o instanceof String s tests o, casts it and binds the result to a new variable s in one step; it is standard since Java 16, after previews in 14 and 15. Unit instanceof operator covered the test itself: the run-time class, null, generic types. This unit is about the variable.

A Pattern Variable Exists Only Where the Match Is Certain

Before reading the errors, guess which uses of s compile (the line numbers count the file's class Scopes { line):

Within the enclosing block, the scope follows the boolean logic: s exists wherever the test is known to have been true, on the right of &&, in the true branch of ?:, in the else of a negated test. On the right of || the test has failed, and & evaluates its right side even when the left is false, so s doesn't exist there. After a statement, s exists only if the statement can't finish while the test is false. The if (!(o instanceof String s) || s.isBlank()) falls through, so the final return s.length() fails. A guard clause that returns (unit if/else statements) or a while loop without a break keeps s in scope for the rest of the block.

Inside its scope s is an ordinary local variable. It isn't implicitly final: s = s.strip() compiles, unless the pattern says instanceof final String s. Once reassigned, it is no longer effectively final, and a lambda can't capture it. A local with the same name is an error, as the last error shows. A field with the same name is not.

A Condition Joined with && Sends a Matching Object That Fails It to the Next Branch


A payment router receives record Payment(String account, long cents) and record Refund(String paymentId, long cents) events, and was flattened from nested ifs into one chain:



Where does a refund with no payment id go? Below, flat is this chain and nested tests each type first, with its condition inside and an else that returns "dead-letter"; the last event is a String:



event instanceof Refund r && r.paymentId() != null is one boolean. When it is false, the else can't tell which half failed, so it receives refunds without an id as well as every other type. The comment says "the ordinary payment"; the code puts a refund that matches no payment, and a chargeback, on the payments queue. Give each type one branch that ends the chain for that type and put its conditions inside, or end with a test for the last type and an else that rejects.


A related failure is order: the first pattern that matches wins, so a supertype tested before its subtype takes every subtype object, and javac doesn't warn in an if chain. A switch over the same patterns refuses to compile (this case label is dominated by a preceding case label, unit Switch patterns (Java 19+)).

Since Java 21 a Pattern of the Declared Type Compiles, and It Is Still False for null


get on a Map<String, String> returns a String or null, so instanceof String can only fail on null:




The pattern is a null check and a local variable in one, and get runs once. Java 16 to 20 rejected a pattern that the declared type already guarantees; Java 21 accepts it. javac 21 with --release 17:



"Unconditional" describes the type only. instanceof is false for null whatever the pattern, so the variable is never null. A reader who takes the line for a declaration and rewrites it as String id = headers.get(...) turns the absent header into a NullPointerException at id.isBlank().

Summary


  • A pattern variable exists only where the match is certain. &&, ?:, the else of a negated test and a guard that exits extend it; ||, & and a guard that falls through don't. Inside, it is an ordinary local, reassignable unless final.
  • Out of its scope, the name means a field of the same name. The code compiles with no warning and reads the field.
  • A condition joined with && sends a matching object that fails it to the next branch. An else after it receives that type too, and an if chain never checks order.
  • A pattern of the declared type compiles since Java 21 and is false for null. It is a null check.

  2. A chain tests five record types, two of them with conditions. Rewrite it so a new condition can't send objects to the wrong branch, and compare the result with a switch (unit Switch patterns (Java 19+)).
  3. Your build moves from --release 17 to 21. Which null checks followed by a local variable would you turn into an unconditional pattern, and which would you leave as they are?


Design Note: Why the Scope Follows the Logic


A pattern variable could have been scoped like any declaration, to the block around it. Then o instanceof String s && s.length() > 3 and the guard clause wouldn't work, and every use would need a nested if. Java scopes it by where the test is known to have been true, which lets patterns combine with &&, ! and early returns, and later with switch and record patterns.


The cost is that one name can mean two variables in the same method, depending on the branch. When the other meaning is a field, a change to control flow, such as removing a return, changes which variable a line reads without any error.
