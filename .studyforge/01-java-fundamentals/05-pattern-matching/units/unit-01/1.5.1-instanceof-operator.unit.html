instanceof Asks About the Object's Class at Run Time, and null Has None

A YAML reader filled this configuration map:

The test ignores the declared type, Object here, and asks whether the class of the object the variable refers to is T or a subtype of T. A Long is a Number and a Comparable, never an Integer. null refers to no object, so the test is false for every T. Class.isInstance is the same test with the type as a value.

The cast disagrees on null. It checks the class and throws ClassCastException on a mismatch (unit Type casting and conversion), but it lets null through, so the missing key surfaces later, as a NullPointerException where the Integer is unboxed. Test a value that may be absent before casting it.

A Class Is Its Name and the Loader That Defined It

The plugin from the start of the unit, reduced: a URLClassLoader with no parent defines its own Greeter from the same class file the application loaded.

At run time the JVM identifies a class by its name and the loader that defined it. The caller's Greeter is the application loader's, so the plugin's object is of an unrelated class. A cache that keeps objects across a reload hands out instances of the old classes. Load the shared type from a parent loader both sides use, or drop the old objects with the old loader.

The Compiler Rejects a Test That Can Never Be True, Judging Only the Declared Types

javac accepts x instanceof T only if a cast from x's declared type to T could succeed for some object. No object is both an Integer and a String. A Thread can be a List, since a subclass of Thread may implement it, so the worker test compiles and is decided at run time. String is final, as are Integer and Long, and it doesn't implement Runnable, so no subclass can add it. The cast follows the same rule.

Against an Object parameter every test compiles, even one no caller can satisfy.

Primitive types. Java 21 rejects x instanceof Integer for an int x: the left side must be a reference. Java 25's javac reports it as a preview feature ("primitive patterns").

Arrays Keep Their Element Type at Run Time; Generic Types Lose Their Type Arguments

An array's class is fixed when it is created, whatever it holds later: untyped holds only strings and is still no String[]. A String[] is also an Object[], and the array checks every store, hence the ArrayStoreException. An int[] holds no references, so it is an Object but not an Object[].

A generic type keeps no type argument at run time: ArrayList<String> and ArrayList<Integer> are one class. The cast to List<String> could check only List, and javac flags it only as unchecked. The ClassCastException comes from a cast the compiler inserted at tags.get(0), in whatever code reads the list, as with the varargs array in unit Method parameters and return types. For the same reason javac refuses payload instanceof List<String> for an Object payload:

Since Java 16 a type argument is allowed where the declared type already guarantees it: tags instanceof ArrayList<String> compiles for a List<String> tags. Before that, only a raw type or <?> was. To get a List<String> out of an Object, test List<?>, then test every element.

In equals, instanceof Breaks Symmetry With a Subclass, and getClass() Refuses Every Subclass

Unit Method overloading fixed an equals(Sku) overload with an equals(Object) that starts with a type test. Here both classes test with instanceof, and the subclass adds a field:

Output for depot = new Point(3, 4) and gate = new LabeledPoint(3, 4, "gate B"), then with if (o == null || getClass() != o.getClass()) return false; in place of each instanceof line, then against an anonymous new Point(3, 4) { }:

Object.equals requires symmetry: x.equals(y) is true exactly when y.equals(x) is. depot accepts any Point; gate only a LabeledPoint. contains calls equals on its argument, so contains answers differently depending on which of the two the list holds, and a HashSet keeps one or both depending on which was added first.

getClass() restores symmetry by refusing every other class, even a subclass that adds no field. A final value class avoids the choice, since instanceof is then exact; every record is final. When a type needs more state, hold a Point in a field instead of extending it.

Summary

  • `instanceof` tests the run-time class of the object, subtypes included, and is `false` for `null`. A cast lets null through, and a class is its name plus its loader, so a reloaded class is a different type.
  • The compiler rejects a test that can never be true, from the declared types only. An interface test compiles unless the class is final and doesn't implement it; an Object parameter turns the check off.
  • Arrays know their element type; generics don't. An int[] is not an Object[], and an unchecked cast to List<String> fails later, where an element is read.
  • In `equals`, `instanceof` with a subclass that adds state breaks symmetry; `getClass()` refuses all subclasses. Make value classes final, or compose instead of extending.

Challenges

  1. Your service decodes JSON into Map<String, Object>. Find every cast that follows a get and decide which should test, which should fall back to a default, and which should fail loudly.
  2. A library's class hierarchy uses instanceof in equals. You must subclass it and add a field. What are your options, and what does each cost?
  3. How does your framework's development-mode restart load your classes, and which cached objects could outlive a restart?

Design Note: Why Java Lets Code Ask an Object's Class

Polymorphism is the usual way to vary behavior by type: each class overrides area(), and the caller calls it. A chain of instanceof tests does the same from outside the classes and must be edited for every new subtype; one it misses falls to the else without a warning. Java still needs the test where code receives an object whose type nobody could declare: equals(Object), deserialized data, a plugin. Sealed types with a switch (unit Switch patterns (Java 19+)) bring the compiler back into such a chain, which then fails to compile when a subtype is added and not handled.
