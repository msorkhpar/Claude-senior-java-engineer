A variable of a reference type holds a reference, and assignment copies it (unit Reference data types). Passing an argument is one more such copy.

Java Copies Every Argument, So Assigning to a Parameter Never Reaches the Caller's Variable

Predict the three lines:

When a method is called, each parameter is a new local variable initialised with the argument's value (JLS §8.4.1). For a primitive that value is the value itself; for a reference type it is the reference, or null. swap exchanged its own two copies and returned. emptyByAssigning pointed its copy at a new list, which nothing referred to once it returned. clear() followed the copy to the one list both variables refer to.

Pass by reference (C++ &, C# ref) makes the parameter another name for the caller's variable, so swap works there. Java has no such parameter, for objects either, which is why "empty cart" changed nothing without an error.

Declaring the parameter final turns the assignment into a compile error (final parameter cart may not be assigned). It does nothing about cart.clear(), which still compiles.

Spot the Problem: a Default That Never Arrives

The import job gives every post an imported tag, and an untagged post general as well:

Line (1) points tags at a new list, so line (2) adds to that list, and the caller's post keeps no tags at all. A method that changes the caller's object never assigns to the parameter that refers to it: tags.add("general") instead. Reassigning a parameter is harmless when the method never meant to change the caller's object (s = s.strip()).

  1. Coding practice

    Make "Archive all" move the messages

    • A parameter is a new variable holding a copy of the argument's value, so assigning to it, primitive or reference, never changes the caller's variable, while a call through the copied reference changes the caller's object.
    • After a method assigns a new object to its parameter, every later change through that parameter goes to the new object, not to the caller's.

An Immutable Argument Can't Be Changed, So a Method That Computes a New Value Returns It


Two versions of the coupon code, and two other helpers written the same way:



Called on 80.00 with 15.00 off, a count of 1000 and "TEA-1":



BigDecimal, String and the wrappers have no method that changes the object. subtract returns a new BigDecimal; visits++ unboxes, adds and assigns the boxed result to the parameter; += builds a new String into the parameter. The only "change" these methods can make is an assignment to the parameter, which the caller never sees. javac -Xlint:all compiles them without a warning. The shop charged full price until someone compared receipts.


Return the new value, and let the caller assign it: total = withCoupon(total, off) printed 65.00. A method with two results returns an object that holds both, such as a record, not an int[] or AtomicInteger out-argument the caller has to know to read.

A Method That Keeps Its Argument Keeps the Caller's Object


The nightly batch reuses one buffer list for each customer's lines, and the invoice stores what it is given:





The constructor stored the caller's reference, so the three invoices and the buffer share one list. Each clear() rewrote every invoice built before it. final stops the field from being reassigned, not the list from changing. The second line is the same batch with record InvoiceRecord(String customer, List<String> lines): a record's implicit constructor stores its components as given. The third wraps the argument in Collections.unmodifiableList(lines) before storing it, which is a read-only view of the caller's list, not a copy.


An object that keeps an argument copies it on the way in:




List.copyOf copies only the list, not the elements (unit Reference data types), and throws NullPointerException if the list holds a null. Unit Getter and setter methods covers the other direction, a getter that hands out its field.

Summary


  • Java copies every argument: assigning to a parameter, primitive or reference, never changes the caller's variable, and code after that assignment works on the new object.
  • An immutable argument can't be changed: subtract, ++ and += produce a new value instead of changing the object, so a method that computes a new value returns it.
  • Changing an argument is part of a method's contract: callers lose state they relied on, and callers that pass an unmodifiable list get an exception. A method that only reads leaves its input alone.
  • Keeping an argument keeps the caller's object: later changes by the caller show through a final field, a record component or an unmodifiable view; copy on the way in.

Challenges


  1. Find a method in your codebase that takes a collection and returns void. Does it change its argument, and does anything but its body say so?
  2. An API takes a 50 MB byte[] and must keep it. Copy it, or document that the caller must not change it after the call? What does each choice cost, and who pays?
  3. A parser has to return the parsed value and the position where it stopped. Compare a record, an int[] position argument and a mutable parser object that remembers its position.


Design Note: Why Java Has No Pass by Reference


Because every parameter is a copy, a reader of a call site knows that process(order) leaves the variable order pointing where it pointed, whatever process does, without opening process. In C++, where a & parameter looks the same at the call site, the reader has to open it.


A method with several results needs an object to return them, which records made cheap to write. A signature never says whether the method changes the object it is given or keeps it, so that part of the contract lives in names, documentation and immutable types.

These tests demonstrate:


  1. Primitives are passed by value, and modifications inside methods don't affect the original value.
  2. Objects (like StringBuilder) are passed by value of the reference, allowing modifications to the object's state.
  3. Reassigning object references inside methods doesn't affect the original reference.
  4. Arrays, being objects, behave similarly to other objects.
  5. Strings and wrapper classes (like Integer) are passed exactly like any other reference; because they are immutable, the method cannot change the object, and s += " World" or i = 20 only reassigns the local parameter.
