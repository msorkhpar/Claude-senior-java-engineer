A shared utility library ships a release, and three teams file bugs in the same week. The audit helper audit(String event, Object... fields) throws NullPointerException on a call that passed null as its one field. A nightly report removed a nurse from the on-call shift it was only supposed to print. And a generic pair(a, b) throws ClassCastException on a line with no cast in it.

Each one is a parameter or return type that allowed more than its author meant: an array the caller still owned, a list the caller could edit, a generic type that was gone at run time. Declaring and calling a method is unit Method declaration and invocation, and what passing a reference copies is unit Pass by value and pass by reference. Every output is from Java 21.

A Varargs Parameter Is an Array: the Caller Can Pass Its Own, or null

Object... fields is an Object[] parameter. The compiler builds the array only when the call lists loose arguments; an array that is already an Object[], or a null, is passed as is. Before reading the output: how many fields does each call pass?

A String[] or a null already fits Object[], so it is passed as the array itself: fields is null, and fields.length throws. A cast to Object makes either one a single element. javac warns about both calls:

The method holds the caller's array, not a copy, so a helper that sorts its varargs to find the largest value reorders the caller's data:

A method that stores its varargs in a field keeps the caller's array too, which the caller can change later. Copy it on the way in, and decide what a null array means.

A primitive array is never an Object[], so an int[] passed to Object... becomes one element. Arrays.asList(T... a) can't spread an int[] either, because T can't be int:

For an int[] ids that holds 8, Arrays.asList(ids).contains(8) is false.

  1. Coding practice

    Keep an alert's recipients as they were when it was sent

    • A null argument to a varargs parameter arrives as a null array, not as an array holding one null, so the method must decide what a null array means.
    • An array passed to a varargs parameter becomes the parameter itself, so the method shares the caller's array: sorting it or keeping it reaches the caller.

A Generic Varargs Array Has the Erased Type, So Handing It Out Fails Somewhere Else


Spot the Problem: a Generic Method That Returns Its Varargs Array




The compiler creates the varargs array at the call site, with the type it knows there. In main, T is String, so toArray gets a String[]. Inside pair, T is a type variable, erased to Object at run time, so the array built there is an Object[]. pair returns it as a T[], and the cast the compiler inserted into String[] viaPair = ... fails, on a line with no cast, two calls away from the cause. Copying the array doesn't help: Arrays.copyOf returns an array of exactly the class of the one it copies, so the copy is an Object[] too, and the cast at the caller fails the same way.


A plain build prints only a note about "unchecked or unsafe operations". With -Xlint:unchecked, javac names both methods:



Heap pollution means a variable of a parameterized type refers to an object that isn't of that type. A List<String>... parameter shows the other way it happens:




@SafeVarargs on toArray silences the warnings at its call sites, and pair("a", "b") still throws: the annotation is the author's promise, and the compiler doesn't check it (-Xlint:varargs even flags the return items). It is allowed only on constructors and on methods that can't be overridden (static, final or private); on an instance method that is neither final nor private it is a compile error. The promise holds when the method only reads the elements and never hands the array out as a T[] or writes into it. List.of and Arrays.asList carry the annotation and return a List<T>, never the array.


A Returned Collection Is Whatever the Caller Can Do With It


A Shift keeps its staff in an ArrayList, and staff() returns that field. The night report should list who is on call, without trainees (names starting with b):




A List<String> has removeIf, so returning the field gave the report write access to the shift. A method that returns internal state returns a copy (the caller's own, editable), a List.copyOf snapshot (immutable) or an unmodifiable view (read-only, but it shows later changes); unit Reference data types has the table of what each one shares.


The opposite surprise is a result that is only sometimes unmodifiable. This module's example class, MethodParametersAndReturnTypes, has a generateEvenNumbers that returns Collections.emptyList() for a negative count and an ArrayList otherwise:



A caller that adds to the result passes every test written with ordinary counts and fails in production on the first negative one. The type can't say which kind of list comes back, so the documentation must, and every path of the method must return the same kind.

Put Absence in the Return Type: an Empty Optional or an Empty Collection, Never null


A directory lookup returns null for a user it doesn't know. The caller checks the domain:




Nothing in String emailOrNull(String) says the result can be missing, so the caller didn't check. Optional<String> email(String) says it in the type, and the caller has to unwrap the result before it can call endsWith. askDirectory below is a remote call:




Optional.of is for a value that can't be null, and throws if it is; a value that may be null is wrapped with ofNullable. orElse(x) is an ordinary method call, so x is evaluated before orElse runs, whether or not a value is present: here, a remote call on every lookup. orElseGet takes a Supplier and calls it only when the Optional is empty.


For a collection, absence is the empty collection: a caller loops over it with no check, and the loop runs zero times. Optional<List<T>> gives the caller two kinds of nothing to handle. The javadoc intends Optional for return types; as a parameter or a field it adds a third state, since the Optional itself can be null.




    

  1. 

    Coding practice
    

    Ask the supplier only for prices the shop doesn't have
    

      

    • A value that may be missing is returned as an Optional built with ofNullable, since Optional.of throws on null and a bare null fails at the caller.
      • 

    • Optional.orElse evaluates its argument whether or not a value is present; orElseGet calls its supplier only when the Optional is empty.

An Override May Narrow the Return Type and the Checked Exceptions, Never Widen Them


A caller holding a Shape relies on copy() returning a Shape. An override that returns a Circle keeps that promise and makes a stronger one, so Java allows it (a covariant return type):



new Circle().copy() is a Circle with no cast. The JVM identifies a method by its name, parameter types and return type, so javac adds a bridge method to Circle for callers that hold a Shape:



A wider return type breaks the promise: had Circle.copy() returned Object, javac would refuse it with return type Object is not compatible with Shape. The check is against the method an override replaces directly, so once Circle.copy() returns Circle, a subclass of Circle can't go back to Shape.


The throws clause works the same way. An override may declare fewer or narrower checked exceptions than the method it overrides, never broader ones:



What a caller must catch comes from the type it calls through, not from the object. CachedPrice implements Callable<Integer> with a call() that declares nothing. Called on a CachedPrice variable, it needs no try. Called through a Callable<Integer> variable, the same object needs one, because Callable.call() declares throws Exception:



So every caller that holds the interface type must catch or declare Exception, whatever the implementation does.


final on a parameter is not part of the signature at all: it stops the method's own body from reassigning the parameter (final parameter n may not be assigned), an override may drop it, and the caller can't tell.

    Check yourself: method parameters and return types

Summary


  • A varargs parameter is an array. An argument that is already an array of the parameter's type is passed as is, so the method shares the caller's array, and a null argument arrives as a null array; Arrays.asList(int[]) has one element.
  • A generic varargs array has the erased type. Returning or storing it causes a ClassCastException in a caller with no cast; @SafeVarargs is an unchecked promise.
  • A returned collection is whatever the caller can do with it. Return a copy, a snapshot or a view, never the field, and the same kind on every path.
  • Absence belongs in the return type. Optional for one value, an empty collection for many; Optional.of(null) throws, and orElse evaluates its argument every time.
  • An override may narrow the return type and the checked exceptions, never widen them. Callers catch what the type they call through declares; final on a parameter is invisible to them.

Design Note: Why Varargs Is an Array


Varargs arrived in Java 5 as a compile-time rewrite: the method is compiled with an array parameter marked as varargs, and each call site builds the array. The JVM needed no change, and an existing method that took an Object[], such as reflection's Method.invoke, could become a varargs method without breaking its callers.


The price is that the array is visible. A caller can pass its own or null, and the method can keep it or return it. Generics arrived in the same release, with erasure, and an array of a type variable can't be created with its real type, so T... builds an array of the erasure and the language needed @SafeVarargs to mark the safe uses. A List parameter would have avoided the generic array problem, at the cost of an object per call and of compatibility with every method that already took an array.
