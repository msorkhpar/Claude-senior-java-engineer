One release of the inventory service brought three bugs. A SKU that is in the stock set is reported missing. The cleanup that retires the 1-second retry delay removes the 5-second one. An exported JSON array has no opening bracket. Overloads are methods with one name and different parameter lists, and the compiler picks one per call. Every line responsible compiled without a warning, and each call went to an overload its author didn't mean. Every output below is from Java 21.

The Compiler Chooses an Overload From the Arguments' Declared Types

Spot the Problem: an equals That Works Until a Collection Calls It

equals(Sku) doesn't override Object.equals(Object): its parameter list differs, so it is an overload. At each call the compiler searches the methods of the receiver's declared type, compares the declared types of the arguments, and records which overload to call. With b declared Sku it chose equals(Sku). a.equals(asObject) passes an Object, and so does the JDK's code in HashSet and List, so those calls go to Object.equals, which compares references. The object's class at run time takes part in only one choice: which override of the chosen method runs on the receiver (unit Method declaration and invocation).

The unit tests called a.equals(b) and passed, while every collection missed the SKU. Add @Override and javac rejects the method: method does not override or implement a method from a supertype. The fix takes an Object: @Override public boolean equals(Object o) { return o instanceof Sku other && code.equals(other.code); }. When behaviour must depend on an argument's class at run time, put the method on that class, or test the class with a type pattern, as this equals does.

Widening First, Then Boxing, Then Varargs: the First Phase That Fits Wins

The compiler looks for an applicable overload in three phases. The first allows only subtyping and widening (int to long, long to double, char to int), the second adds boxing and unboxing, and the third varargs. It stops at the first phase that finds a candidate and takes the most specific one there. Predict each line:

char is an integral type, so 'x' widens to long in the first phase. An Integer is already an Object, so the first phase finds track(Object), and unboxing to long is never tried. A single int reaches tag(Object) by boxing, before varargs is considered. The first phase matches how Java chose overloads before version 5 added boxing and varargs, so calls written before then still choose the same method.

The JSON exporter's missing bracket is the char rule in the JDK:

StringBuilder has no char constructor. '[' widens to the int 91, so javac picks StringBuilder(int capacity).

On a List of Integers, remove(int) Takes an Index, Not a Value

List has remove(int index) and remove(Object o). An int argument fits remove(int) in the first phase, so it is never boxed:

The 5-second delay went, and the 1 stayed. A value that isn't a valid index throws, so the bug is loud only for large values; whenever the value happens to be a valid index, the wrong element goes without an error. The same call through a variable declared Collection<Integer> removes the value, because Collection has only remove(Object). Integer.valueOf(retired) states the intent. The last line is the trap from unit Type casting and conversion: on a Set<Long>, remove boxes an int to an Integer, which never equals a Long, and removes nothing.

null Goes to the Most Specific Overload, and Two Unrelated Ones Don't Compile

With audit(Object) and audit(String), audit(null) calls audit(String): both fit, and String is more specific because every String is an Object. Add audit(Integer), and the same call stops compiling:

Neither String nor Integer is more specific than the other. A cast picks one: audit((String) null). So a library release that only adds an overload can break its callers' builds. Overloads Must Differ in Erased Parameter Types: the Return Type and Type Arguments Don't Count

A class can't declare two methods with the same signature, and a signature is the name and the parameter types: the return type isn't part of it, and type arguments are erased from it. Both of these fail:

Give them different names, such as totalQuantity and totalPrice.

Summary

  • The compiler chooses an overload from the arguments' declared types. A narrower equals is an overload that collections never call; @Override catches it.
  • Widening first, then boxing, then varargs. A char goes to an int or long overload, and an Integer to Object before it would unbox.
  • On a `List<Integer>`, an `int` argument is an index. Box it to remove the value.
  • `null` goes to the most specific overload, and adding an unrelated one makes the call ambiguous.
  • Overloads differ in erased parameter types. The return type and type arguments don't count.

parameter typesdiffer after erasurethe same

Choosing an overload (JLS 15.12.2):

PhaseConversions allowed
1identity, widening primitive, subtyping
2phase 1, plus boxing and unboxing
3phase 2, plus varargs

Within the first phase that finds candidates, the most specific wins; if no candidate is more specific than all the others, the call is ambiguous and doesn't compile.

Challenges

  1. Search your code for remove( on lists of Integer or Long. Which calls pass a value that is meant as a value?
  2. Your logging API has log(String, Object...). A colleague proposes adding log(String, Object) for speed. Which existing calls change overload, and could any break?
  3. Would you overload send(Email) and send(Sms), or give each its own name? Consider a caller that holds a Message.

Design Note: Why Overloads Are Bound at Compile Time

Choosing at compile time is cheap and reports ambiguity before anything runs. The choice is written into the caller's class file, so a new overload reaches callers only when they are recompiled. A library adds record(long) beside record(Object), and a caller of Metrics.record(5) runs against it before and after recompiling:

Two services built from the same source, one rebuilt and one not, call different methods. Treat an overload that existing calls could fit better as a behaviour change, not an addition.
