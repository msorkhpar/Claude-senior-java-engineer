The payments service keeps its audit trail in one StringBuffer field, chosen because StringBuffer is thread-safe. Request threads append user=… action=… lines to it, and a flusher writes it to disk every second. After a load test the trail holds lines like user=u4 action=loginuser=user=. In review, one engineer wants a StringBuilder, because StringBuffer is slow. Another wants one StringBuilder per thread in a ThreadLocal, cleared with setLength(0), to save allocations. The first change loses lines and throws; the second, in a service whose threads also build multi-megabyte reports, keeps hundreds of megabytes that nobody uses.

StringBuffer Locks Each Call, So a Line Built from Several Calls Still Interleaves

Four threads record 50,000 lines each, three ways, in three rounds in one JVM (\0 prints as .):

Each StringBuffer call such as append or length() locks the buffer and sees what every earlier call wrote, but between two calls the thread holds no lock, so another thread's text lands mid-line. What must be atomic is the whole line, and no buffer method writes one: a compound action, as in unit Monitors and synchronized blocks.

A shared StringBuilder also corrupts the text. Its appends read and update the length with no lock, so two threads write to the same positions, or one writes into the old array just after another copied it to a larger one; the dots are where a write was lost. And when one thread checks the capacity, then another advances the length, the first writes past the end of an array that is too small: ArrayIndexOutOfBoundsException, and here three of four threads died.

The local builder never leaves its thread, so it needs no lock; the only shared operation is one append of a finished line, which StringBuffer does make atomic. Where several calls on a shared object must stay together, hold its lock across all of them, and build the text before you take it.

Warm-up hides it. By round 2 the JIT had merged the adjacent locks on the same buffer into one (lock coarsening). With -XX:-EliminateLocks, which turns that off, every round broke 63 to 69 % of the lines. A concurrency test that passes after warm-up shows what this JIT did with this code, not what the language promises.

A Builder Is an Array: Growing It and Inserting at the Front Copy What Is Already There

A builder keeps its text in an array with room to spare. The capacities a default builder passes through while we append one character at a time:

When an append doesn't fit, JDK 21's AbstractStringBuilder.newCapacity picks the larger of what is needed and twice the old capacity plus 2, allocates that array and copies everything over. The copies add up to about the final size again, so appending stays linear, but the old arrays are garbage. We built a 1,400,000-character export from 100,000 rows, with the default builder and with one sized to the result:

Sizing halved the allocation. Half of what remains is toString(), which always copies the text into a new String. Times varied from 0.3 to 1.4 ms across runs for both, so expect less garbage, not a reliable speed-up. Size a builder when you know the result's length, and don't guess high: an oversized builder holds its whole array until it is dropped.

Appending at the end copies only on growth. insert(0, row) shifts every character already in the builder, on every call. A newest-first log view built that way:

Doubling the rows quadrupled the time, as with += in unit String concatenation. deleteCharAt(0) and delete(0, n) shift the rest the same way. Collect the rows, then append them in the order you want.

setLength(0) Empties a Builder and Keeps Its Array

setLength(0) only sets the length; the array the builder grew stays. We gave each of 32 pool threads one 3,000,000-character report to build with its ThreadLocal builder, then only short lines:

Every thread that ever built something large keeps that much for as long as it lives, and pool threads live as long as the service. trimToSize() gives it back, but leaves capacity 0, so the next line regrows from nothing. For short lines, reuse saved nothing:

79 bytes is the result String. The JIT removed the fresh builder entirely (with -XX:-OptimizeStringConcat, 375 bytes per line), but not for every chain: unit String concatenation's chain with a long kept its builder. Create a builder where you build the text. If you do keep one, replace it when it has grown past what normal work needs.

Two Builders Are Equal Only When They Are the Same Object

StringBuilder and StringBuffer inherit equals and hashCode from Object. A content hash on a mutable object would change with every append, and a set would lose the entry it filed under the old hash. So a HashSet<StringBuilder> used to drop duplicate messages keeps every one. Compare contents with compareTo (since Java 11), CharSequence.compare, or String.contentEquals (unit String comparison (equals() vs. ==)), and key collections by toString().

Summary

  • `StringBuffer` locks each call, not the line. Text written with several calls interleaves; build it in a local StringBuilder and publish it in one call. A shared StringBuilder loses text and throws.
  • A builder is an array. It grows to twice its capacity plus 2 by copying; sizing it halves the allocation, and insert(0, …) in a loop is quadratic.
  • `setLength(0)` keeps the array. A reused builder holds its largest size for the life of its thread, and saved nothing per line in our run.
  • Builders compare by identity. Use compareTo, contentEquals or toString() for content.

Challenges

  1. Find a StringBuffer in a codebase you know. Is it shared between threads, and if so, is every line written to it in one call?
  2. A report's output varies from 2 KB to 40 MB. How would you size its builder, and what does a wrong estimate cost in each direction?
  3. Measure what your service's per-thread builders hold: take a heap histogram after a day of traffic and look for large byte[] arrays reachable from ThreadLocals.

Design Note: Why StringBuilder Came Eight Years After StringBuffer

Java 1.0 shipped StringBuffer with its methods synchronized, and javac compiled + to it. Java 5 added StringBuilder, the same class without the locks, and moved the compiler to it: nearly every buffer is local to one method, and each concatenation paid for locks no other thread could contend. StringBuffer stays for compatibility, and today it is worth choosing only where an old API asks for one.
