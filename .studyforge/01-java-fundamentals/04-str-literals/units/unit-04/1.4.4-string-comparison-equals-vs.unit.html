The sign-up service keeps usernames unique in a HashSet<String>, and since the duplicate-order bug of unit Reference data types it compares strings with equals, never ==. Four tickets are still open. Two accounts are named José, and nobody can see a difference. Jane and JANE both registered after someone made the check ignore case. The admin list puts Émile after zoe, and a fix to the sort made three accounts disappear from it. And the profile editor's audit log records a change on every save, including saves that changed nothing.

String.equals answers one narrow question: is the argument a String holding the same UTF-16 units (unit String methods (e.g., length(), charAt(), substring()))? Each ticket asked it a different question.

equals Is True Only for Another String, and Its Receiver Must Not Be null

The editor keeps the name being edited in a StringBuilder, and the audit compares it with the saved value:

equals takes an Object, so the compiler accepts any argument, and javac says nothing even with -Xlint:all. A StringBuilder, a Character or an Optional<String> with the same text is never equal. Objects.equals adds null-safety and calls the same equals. contentEquals(CharSequence) compares the characters of any CharSequence. With equals, every save is a change, the customer gets a "profile updated" mail each time.

The other half is the receiver. The nickname is optional and was never set (compiled with -g, so the message names the variable):

x.equals(y) throws when x is null; equals(null) is false. Put the literal first where null is a valid value. Use Objects.equals where both sides may be null and two nulls count as equal. Where null means a bug upstream, the literal-first form hides it: reject it where it enters, with Objects.requireNonNull (unit Reference data types).

Text That Looks the Same Can Be Different Code Points: Normalize Before Comparing

Unicode can write é two ways: as one code point, U+00E9, or as e followed by a combining acute accent, U+0301. Both render the same, and which one arrives depends on the keyboard, the operating system and whatever the text was copied from.

Different units give different hash codes, and the set keeps both: two accounts named José, and a login that finds one or the other depending on how the user typed it. Case was never the difference, so equalsIgnoreCase doesn't help. Unicode calls the two forms canonically equivalent, and java.text.Normalizer turns either into one form: NFC composes, NFD decomposes. Normalize once where the text enters and store the result; then equals, hashCode and length() agree.

Removing the accents (NFD, then deleting the combining marks) is a different operation: it makes René and Rene one user. NFKC goes further than NFC and also folds compatibility forms, such as the ligature ﬁ into fi; use it only where such look-alikes should collide.

equalsIgnoreCase Has No Matching hashCode: Compare and Hash One Key

The username check moved into a value class whose equals ignores case:

With Jane in a HashSet:

A HashSet picks the bucket by hashCode and calls equals only on entries with the same hash. "Jane" and "JANE" hash differently, equals is never asked, and JANE registers. Object.hashCode requires equal objects to have equal hash codes, and a hash of the raw text gives Jane and JANE different ones. Derive one key and use it for both:

Never pair equalsIgnoreCase in equals with a lower-cased key in hashCode: the folds disagree. equalsIgnoreCase compares code point by code point, upper-casing then lower-casing each, with no locale:

It ignores the default locale, which toLowerCase() uses: under Turkish, TITLE lowers to tıtle (unit switch statements). It can't match ß with SS, since one character never equals two. And it treats the dotless ı as i, which a toLowerCase(Locale.ROOT) key doesn't, so an equals that calls equalsIgnoreCase beside a hash of that key breaks the contract on exactly those names. Where no hash is needed, a TreeMap with String.CASE_INSENSITIVE_ORDER folds the way equalsIgnoreCase does, and keeps the first spelling as the key:

compareTo Orders UTF-16 Units; People Need a Collator, and Its 0 Merges Set Entries

The admin list, sorted three ways:

compareTo compares the first differing char by its number. Uppercase ASCII letters (65–90) come before lowercase ones (97–122), and É (201) after both. CASE_INSENSITIVE_ORDER fixes case, not accents. A java.text.Collator orders by a language's rules: letters first, then accents, then case. Ask for an explicit locale, because Collator.getInstance() uses the server's default, and the order differs by language:

Swedish sorts Ö as a letter after Z; German sorts it with O.

The fix that lost accounts wanted adam and Adam side by side. It set the collator's strength to PRIMARY, which compares letters only, and kept the list in a TreeSet:

A TreeSet never calls equals. When its comparator returns 0, the new name counts as already there and is not added, so the admin list shows four of seven accounts. Sort with a collator into a List. Use a sorted set or map only with a comparator whose 0 means what you want a duplicate to mean. compareTo's 0 matches equals; a collator's 0 merges different strings, even at its default strength.

Summary

  • `equals` is true only for another `String`, and its receiver must not be `null`. Compare a StringBuilder with contentEquals; use Objects.equals where both sides may be null.
  • Text that looks the same can be different code points. Normalize to NFC where text enters, or equal-looking names get different hash codes and both register.
  • `equalsIgnoreCase` has no matching `hashCode`. Derive one canonical key and use it for both equals and hashCode; a different fold in each breaks hash sets on the letters where they disagree.
  • `compareTo` orders UTF-16 units. Sort for people with a Collator for an explicit locale, and keep collated names in a List: a sorted set treats its comparator's 0 as a duplicate.

Challenges

  1. Your usernames are stored un-normalized in a database with a unique index. Plan the migration to NFC: what do you do with the pairs that collide, and how does the database's own collation change the answer?
  2. Sorting 100,000 names with a Collator compares each pair from scratch. Measure it against sorting precomputed CollationKeys, and decide where the keys belong.
  3. Find a class in a code base you know whose equals ignores case or trims. Does its hashCode apply the same fold, and does any TreeMap use a comparator that disagrees with it?

Design Note: Why String.equals Is Exact

String.equals compares units and nothing else. It needs no locale and gives the same answer on every server, which a hash key or a protocol value needs. Everything a person means by "the same text" (case, accents, the order of a list) depends on the language and on the application, so Java leaves it to explicit, separate tools: Normalizer, equalsIgnoreCase with its documented limits, and Collator.

The price is that the plain call is the wrong one for user-facing text, and the compiler says nothing.
