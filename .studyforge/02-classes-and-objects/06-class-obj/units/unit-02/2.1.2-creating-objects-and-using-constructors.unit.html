The feed called onPrice before the fields were assigned, so it read null and 0.0, even though both are final. The second constructor threw and new returned nothing, but the feed already held the object. It answers every price for as long as the feed lives. The feed holds a reference, not a copy: on the same thread, every field the constructor assigned before throwing shows through it.

Threads. The Java Language Specification (§17.5) promises that another thread sees a final field's assigned value if it got the reference after the constructor finished. A thread started in the constructor, or a listener registered there and called from another thread, can see fields assigned after that point at their defaults.

A Static Factory Can Name, Reuse or Choose the Class of What It Returns

Constructors are told apart only by their parameter types, so Temperature(double celsius) and Temperature(double fahrenheit) can't both exist: constructor Temperature(double) is already defined. Factories have names:

new always returns a new object of exactly the named class (an anonymous new C() { } aside). A factory may return an existing one, or a subclass:

Currency promises one instance per currency; List.of promises only an unmodifiable List. == compares references (unit Reference data types), so it is true only when a factory returns the same object. Code that locks on a factory's result may share the lock with every other caller. Code that checks getClass() breaks when the JDK picks another class. Rely on identity or class only where the javadoc promises it: Integer.valueOf promises its cache only for -128 to 127 (unit Primitive data types).

Summary

  • Declaring any constructor takes away the default one. Reflective frameworks then fail at run time, and subclasses stop compiling.
  • Overloaded constructors chain with `this(...)` to one that checks and assigns. A copied overload skips the checks; arguments are computed by static methods, since the call comes first.
  • A constructor that hands out `this` lets others use a half-built object. They see default values, and a constructor that throws leaves its escaped object behind. Publish from a factory.
  • A static factory can name, reuse or choose the class of what it returns. Callers rely on identity or class only where it is documented.

Challenges

  1. Your entity needs a no-argument constructor for JPA, but every object built in your own code must be valid. How do you keep application code off that constructor?
  2. A base class registers this with a scheduler in its constructor. What can a subclass do about it, and what would you change in the base class?
  3. Find a factory in a library you use that returns cached objects. Does its javadoc promise it?

Design Note: Why a Constructor Can't Choose What It Returns

new allocates the object before any constructor code runs, so a constructor can only fill in the object it was given. It can't return a cached one, pick a subclass, or have a name. That keeps new predictable. The cost is that every class needing more adds a static factory, and the reader no longer sees from the call whether the object is new.

Problem statement


The payment client reads its retry settings for each endpoint from YAML. The settings loader creates a RetrySettings through its no-argument constructor and then sets the fields the document names. Application code also builds settings by hand, mostly with the one-argument constructor that takes just the endpoint.


Two problems came back from staging. Documents that name only the endpoint gave a client that never retried. And a client built with new RetrySettings(...) from a value typed by an operator was never recognised by the circuit breaker, which compares endpoints as text, while the same value passed to the three-argument constructor was.


Finish the two TODO constructors in src/main/java/practice/RetrySettings.java. When you're done, every RetrySettings, however it was made, has the defaults the class declares for what nobody gave it, and holds to everything the three-argument constructor promises about its values. Problem statement


The ops team watches disk usage through a monitoring feed. A DiskAlarm raises an alarm for each reading of its volume at or above its limit. The feed sends a new listener the latest reading of every volume as soon as it subscribes, so an alarm started while a disk is already at 97 % should raise at once.


Two complaints came in about the old version: an alarm started on a full disk stayed silent until the next reading, and an alarm whose limit was typed as 0 was refused with an error, yet the feed's listener count kept growing with every such attempt.


Finish the private constructor and watch(...) in src/main/java/practice/DiskAlarm.java. When you're done, watch either returns an alarm that hears every reading from the latest ones on, or throws IllegalArgumentException for a limit outside 1 to 99 and leaves the feed as it was. About six lines in total.
