Initializers Run Top to Bottom, After super() and Before the Constructor Body

Predict the five lines new Account() prints:

javac copies the field initializers and instance blocks, in source order, into every constructor that calls super(...), explicitly or implicitly, right after that call. A constructor that starts with this(...) gets no copy, so they run once per object. Until its initializer runs, a field holds its default: null, 0 or false (unit Reference data types).

An Inner Class's Instance Holds Its Outer Object; a Static Nested Class's Doesn't

Rows of a report are cached in the user's session, which serializes them:

We cache one row of each kind, set the report variable to null, call System.gc() and serialize the row (the same result in 10 runs out of 10):

An inner row is created as report.new Row(...), and price() reads the report's currency. To make that work, javac gives Row a hidden field, this$0, that refers to the report. The cached row keeps the report's 50 MB reachable for the session's lifetime, and serialization follows this$0 to the non-serializable Report. Making Report serializable would silence the exception and write the PDF into every session.

javac 21 adds the field only to an inner or anonymous class that uses its outer instance (reads its fields or calls its instance methods) or is Serializable; lambdas are in the Reference. A listener registered on a static registry pins its outer object the same way. Declare a nested class static unless each instance needs its outer object, and pass it the values it needs.

Local Classes and Lambdas Capture Copies of Effectively Final Locals

A local variable lives in the method's stack frame, which may be gone by the time the lambda runs. Java copies the value into the object: a local class that reads a local variable region gets a field val$region. If the variable could change, copy and variable would disagree, so the compiler forbids it. A one-element array satisfies the compiler:

All three lambdas copied a reference to the same array, and read it after the loop. Declare a new variable in each iteration instead (int n = attempt;), which prints retry 1 retry 2 retry 3. An enhanced for variable is already new in each iteration.

A File Has at Most One Public Top-Level Class, and the File Is Named After It

Invoice.java declares public class Invoice and public class TaxTable:

With TaxTable package-private, Invoice.java compiles. Checkout.java, in the same package, uses TaxTable. javac Checkout.java on a clean checkout:

javac finds a type it hasn't compiled by its name: it looks for TaxTable.class or TaxTable.java on the class path (here the current directory). Visibility isn't the problem: compiled together, both files build. It also compiles once an older TaxTable.class exists, which may be stale. Give each top-level class its own file; a helper only one class uses becomes a private static nested class.

Summary

  • Initializers run top to bottom, after `super()` and before the constructor body. A field read earlier, from a method or from a superclass constructor, holds its default; a constant variable is inlined and hides the bug.
  • An inner class's instance holds its outer object. It keeps the outer reachable and drags it into serialization; a static nested class doesn't.
  • Local classes and lambdas capture copies of effectively final locals. A shared mutable holder brings back one variable for every lambda.
  • A file has at most one public top-level class. javac finds classes by file name.

Challenges

  1. Your framework's base class calls init() from its constructor. What do you tell the teams who override it, and what would you change in the framework?
  2. Which inner or anonymous classes in your service outlive their outer object (listeners, cached callbacks), and which of those pin a large object?
  3. A job captures a mutable List that the loop keeps filling. Is that a bug?

Design Note: Why Java Copies Captured Values

The JVM has no lexical nesting: inner, local and anonymous classes are separate classes, and javac gives them extra fields (this$0, val$region) for what they use from outside. Copying a value instead of sharing the variable keeps the stack frame free to go. The cost shows when lambdas must count or accumulate: they need a shared holder array, which races once they run on different threads, or an AtomicInteger.

Problem statement


The invoicing service runs one router for many tenants. Each tenant gets its own handler, new InvoiceHandler("northwind"), whose paths() builds /northwind/invoices and /northwind/invoices/{id} from the tenant it was given. The first version of the new Handler base class built each handler's routes as the handler was created, and every tenant's handler registered /null/invoices: every invoice request got a 404. The router asks each handler for its routes() when it registers it, and again on every configuration reload, a few times a minute.


Finish routes() in src/main/java/practice/Handler.java. When you're done, every handler serves the paths its own paths() builds from its own fields, and a reload hands back the same routes without making the handler build its paths again. Subclasses of Handler stay as they are. About four lines in total.
