super.m() Calls the Superclass's Version, and Nothing Reaches Past It

An audit logger extends a JSON logger and wants Logger's plain text. Calling format("card blocked") on it:

A cast changes the declared type, not the object, so the call dispatches to AuditLogger.format again, which calls itself. super.format(msg) would print AUDIT {"msg":"card blocked"}: a super call is not dispatched on the object. It runs the version the direct superclass has, declared there or inherited, here JsonLogger's. super.super.format(msg) doesn't compile (<identifier> expected).

Once JsonLogger overrides format, no subclass of JsonLogger can reach Logger's version. If the plain version is needed, JsonLogger must offer it under another name.

Code Called Through super Still Calls Your Overrides, So a Subclass Depends on Its Superclass's Self-Calls

The dashboard's set counts in both methods:

super.addAll(c) runs TreeSet's code, but on this object, and the calls that code makes to add are ordinary virtual calls that reach CountingSet.add. For a List, TreeSet.addAll adds the elements one by one through add. For a sorted set with the same ordering, added to an empty set, it builds the tree directly and calls no add at all. None of this is in TreeSet's javadoc, so a later JDK may change which method calls which, and the counts change without a compile error. This is the fragile base class problem: a subclass that overrides a method its superclass calls on itself depends on the superclass's implementation, not its contract.

Wrap the set and forward to it instead, so its internal calls never reach your code (unit Definition and purpose of Composition over Inheritance develops this). Or, for a class you write to be extended, document which methods call which and make the rest final.

An Override Can Widen Access but Not Narrow It, So a Subclass Can't Take a Method Away

An escrow account must not be closed by hand, so its author tries to hide close():

A caller holding an Account compiled against a public close() and gets the escrow override at run time. Access is checked against the declared type, so a narrower override couldn't keep anyone out. Leaving out @Override changes nothing: the method still overrides, and the same error follows. Widening is allowed: Object.clone() is protected, ArrayList.clone() is public.

That leaves an override that throws. It compiles, and the failure moves to run time: a loop that closes three accounts closes the first, throws at the escrow one, and never reaches the third. Code written against Account breaks: the Liskov principle, unit Liskov Substitution Principle (LSP).

protected Reaches a Subclass in Another Package Only Through Its Own Type

Outside bank, PremiumAccount may use balance only through references of type PremiumAccount or its subclasses. Otherwise any class could read any account's balance by declaring a subclass. Inside bank, every class reads balance freely: protected includes package access, so it exposes more than package-private does.

Summary

  • Fields are hidden, not overridden. Code in the superclass reads its own field; vary a value through an overridable method.
  • `super.m()` runs the direct superclass's version. A cast to a superclass still dispatches to the override, and super.super doesn't exist.
  • Code run through `super` calls your overrides. A subclass that overrides a self-called method depends on the superclass's implementation, and can break when it changes.
  • Overrides can't narrow access. A subclass can only refuse an inherited method at run time, which breaks callers of the superclass.
  • `protected` works across packages only through the subclass's own type, and opens the member to the whole package.

Challenges

  1. AbstractCollection documents that its addAll goes through add; TreeSet says nothing. Which other JDK classes document their self-calls, and would you subclass one that doesn't?
  2. You maintain a library class that users already subclass, and you want addAll to stop calling add for speed. How do you find out whom you would break, and what do you ship instead?
  3. A framework makes your entity extend its base class, and you need a count like the dashboard's. Where does the counter go so a framework upgrade can't change it?

Design Note: Why Fields Don't Dispatch

Java dispatches overridable instance methods and binds the rest without looking at the object: fields, static and private methods, super calls. A field read stays one instruction with no lookup, and a superclass's fields keep their meaning when a subclass adds one with the same name. The price is this page's opening bug. Keep fields private and expose behaviour through methods, which a subclass overrides on purpose.
