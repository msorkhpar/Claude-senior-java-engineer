A guest asks the front desk to move a stay from 10–12 March to 20–22 March. The app calls setCheckIn, then setCheckOut, and the move is refused: check-in 2026-03-20 is not before check-out 2026-03-12. In the same order, moving a stay earlier works. Both setters validate.

A Setter Can Check Its Own Value, Not a Rule That Spans Two Fields

Stay keeps check-in before check-out. Each setter checks its new value against the other field; reschedule takes both:

Before reading on: for a move later, which order of the two setters works? For a move earlier?

A setter compares its value with the fields as they are now, and in the middle of a two-step change one of them still holds the old date. The order that works depends on the direction of the move, so a caller that learns "out first" breaks the other way. A rule over two fields belongs in one method that receives both values.

That method checks every argument before it assigns any field. A version that assigns checkIn first and then throws leaves the stay as 2026-03-20..2026-03-12, a state no setter would have accepted.

  1. Coding practice

    Let marketing move a campaign to any week

    • A method that checks every argument before it assigns any field leaves the object unchanged when it refuses; one that assigns first leaves half a change behind.
    • A setter can compare its value only with the fields as they are now, so a rule over two fields set one at a time refuses some valid changes, and it needs one method that takes both values.

Tools Find Properties by Method Name, and isX Works Only for a Primitive boolean


JavaBeans tools, including the JDK's java.beans.Introspector, look for methods named getX, isX and setX, not for fields. A class Flags has these accessors:



Introspector.getBeanInfo(type, Object.class), which leaves out getClass(), on Flags and on record Endpoint(String host, int port):



is names a getter only when it returns a primitive boolean, so enabled can be written and never read. A setter must return void: the fluent setPort is invisible, and a binder built on the introspector leaves every port at its default. getArea() has no field behind it and is still a read-only property. getURL gives the property URL, not url: a name whose first two letters are capitals keeps its case. A record's accessors have no prefix, so the introspector finds no property in Endpoint.


Libraries differ. Jackson, Spring and others apply their own versions of these rules. Check the one you bind with.

A record's accessor may be declared explicitly, as long as it is public with the component's type. This one normalises a tag:

The generated equals, hashCode and toString read the fields, not the accessors, so two tags that report the same name are two entries in a set. Summary


  • A setter checks one value against the current state. A rule spanning two fields needs one method that validates both arguments, then assigns.
  • A getter that returns a Date or an array hands out the field. Return a copy, or store an immutable type.
  • Tools find properties by method name. isX only for boolean, setters return void, and a record's accessors have no prefix.
  • A record's equals and toString read fields, not accessors. Normalise in the compact constructor.

Design Note: Why Records Didn't Adopt getX


A record's state is its components: the canonical constructor takes them, the accessors return them under the same names, and new R(r.a(), r.b()) rebuilds it. The JavaBeans prefix was a convention for tools to discover properties to read and write, and a record has nothing to write. The cost falls on tools built on that convention: a record bound by one needs a getHost() added by hand.
