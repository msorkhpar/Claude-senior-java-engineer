In one week the order service sent shipping emails whose tracking link ended in /track/null, and answered a declined card with HTTP 500 because a new endpoint never caught DeclinedException, and both bugs compiled. A sealed type can make the compiler, or a constructor, refuse each of them, at a price. How a switch over a sealed type is checked is unit Switch patterns (Java 19+)'s subject; here we choose where to use one.

A Sealed Result Makes an Expected Failure a Value the Caller Has to Match

A declined card is not a bug: the gateway declines cards every day. charge can throw, or it can return one of two records:

The exception ended the batch at the second card. Card 4111 had been charged, and its receipt was lost with the list. The Result version kept going and reported every card. A checked exception would not help in a stream, since it can't leave the lambda (unit Throwing exceptions using the throw keyword).

The switch is the only check. A caller that drops the value, charge("4120");, compiles without a warning, even under -Xlint:all, and so does an instanceof with no else. Each layer passes a failure on by hand, and there is no stack trace (here charge takes only the card):

Use a Result for outcomes the caller acts on, a decline or a validation error. A bug, a null argument or a broken invariant, still throws: nobody can act on it but the developer, who needs the trace (unit Checked vs. unchecked exceptions).

Nothing ties trackingNo to SHIPPED. With a sealed interface, each state is a record that holds exactly the data true in that state, and each transition takes the state it starts from:

Shipping a pending order no longer compiles, and shipping without a number fails where it happens, not in a customer's inbox:

The record alone doesn't refuse the null: without the compact constructor, new Shipped("pay-7781", null) builds and prints trackingNo=null. The hour between leaving the warehouse and getting a number becomes a fourth permitted state, Dispatched(paymentId), with no tracking number for the email to print. The cost: every transition builds a new object, and whatever stores or serializes an order must record which record it holds.

An Enum Is Still the Right Choice When a Variant Carries No Data

When every variant is one fixed value, an enum gives more: values(), valueOf for a database column, EnumSet and EnumMap, and one instance per value. A sealed interface has none of these. Its variants are classes, and getPermittedSubclasses() lists classes, not values (unit Defining sealed classes and interfaces).

The trouble starts when one variant needs data per order. A constant is one shared instance, so a field on it belongs to every order at once:

The second order overwrote the first one's number. A sealed interface can mix both designs, since an enum may be one of its permitted subtypes (unit Permitted and non-permitted subclasses).

Public Sealed Interfaces Over Package-Private Records Let Callers Match but Not Implement

A shipping library returns tracking states. Callers must switch over them, and must not build a Delivered the carrier never reported. Public records fail the second rule: anyone can call their constructor. Package-private records fail the first: a caller can't name them in a case:

Summary

  • A sealed `Result` makes an expected failure a value. A batch keeps going and a switch must name Failure, but a dropped result compiles and each layer passes failures on by hand.
  • A record per state holds only that state's data. A transition that takes Paid refuses a Pending at compile time; the compact constructor, not the record, refuses a null.
  • An enum stays right for fixed variants without data; a field on a constant is shared by everyone.
  • A sealed exception base lets one catch switch over every failure, and a new subtype breaks that switch. javac doesn't count one clause per subtype as covering the base, so the method declares the base and a new subtype escapes.
  • Public sealed interfaces over package-private records let callers match but not implement or construct; their tests need a factory.
  • An expression tree is records plus a recursive switch. Keep the walk free of default, so a new node breaks the build.

Challenges

  1. Your service has 40 methods that throw OrderNotFoundException. Which would you move to a Result, and what does each caller have to change?
  2. The order states gain Cancelled, reachable from Pending and Paid but not from Shipped. Write the transition methods so a wrong one doesn't compile, and count what else changes.
  3. The shipping library must add Lost, and some callers can't recompile this quarter. How would you ship it, and what do those callers' switches do meanwhile?

Design Note: A Public Sealed Type Makes Every New Variant a Breaking Change

Inside one codebase, the compile error a new variant causes is the point: it lists every switch to update. Across a library boundary the same error lands in code the library team doesn't own, and callers who don't recompile get a MatchException when the new variant reaches their switch (unit Switch patterns (Java 19+)). A library that seals a public type promises its variants as part of its API, so it adds one only in a release that may break callers. When the set must grow freely, a non-sealed branch (unit Permitted and non-permitted subclasses) or a plain interface lets it grow without breaking callers.

Problem statement


The monitoring service stores each alert as a tree of rules: Above(metric, threshold), And, Or, Not, and Const(true) or Const(false). The rule editor produces constants whenever someone switches a condition off, so stored rules are full of And(Const(true), …) and Not(Not(…)), and the on-call engineers can no longer read them. fires already evaluates a rule.


Finish simplify(Rule) in src/main/java/practice/AlertRules.java. The result must fire for exactly the readings the input fires for, with no Const left beside an And or an Or, no Not of a Const and no Not directly inside a Not, at any depth of the tree. A rule that ends up always or never firing becomes a single Const. About fifteen lines in total.


The tests build their own rules over their own metrics.
