The billing library seals PaymentMethod to cards, bank transfers and wallets, so its fee switch needs no default (unit Switch patterns (Java 19+)). A partner team asks for its own gift wallet, which by contract carries no fee. Someone removes final from Wallet and the build fails. A colleague adds one word and it compiles. What does the fee switch charge the gift wallet now?

Every Permitted Subclass Says Whether the Hierarchy Goes On: final, sealed or non-sealed

Wallet is in the permits list and implements the interface, and still fails:

javac has no default here. Open by default, one forgotten word would let any class extend Wallet, and a switch over PaymentMethod could meet types nobody listed. Final by default, a class meant as an extension point would be shut without anyone deciding it. So the author picks one:

  • final: the branch ends here;
  • sealed, with its own permitted list: the branch goes on, closed;
  • non-sealed: anyone may extend this class.

non-sealed is allowed only on a class or interface that has a sealed direct supertype. On any other class javac refuses it with non-sealed modifier not allowed here.

Records and Enums Are Already final, or sealed

A record is implicitly final, so record Voucher(String code) implements PaymentMethod {} needs no modifier. Writing final record is allowed and redundant; non-sealed record doesn't even parse. An enum is implicitly final. If a constant has a body, the enum is implicitly sealed and permits the anonymous class of each such constant:

Those are the only anonymous classes a sealed type can have: unit Defining sealed classes and interfaces showed every other anonymous class refused, and a class declared inside a method fails the same way (local classes must not extend sealed classes). An enum takes neither final nor non-sealed (modifier ... not allowed here). A permitted interface can be sealed or non-sealed, never final.

A sealed Subclass Keeps the Set Closed, but a Switch Needs a Case for It Unless It Is Abstract

Cards split into debit and credit, so Card becomes sealed in turn. Pause before the error: which values can reach this switch without a case?

new Card() is a value of neither Debit nor Credit. The permitted subtypes cover a sealed class only when it is abstract or an interface, so it has no instances of its own. Any of three changes compiles: abstract sealed class Card, sealed interface Card (with Debit and Credit changed to implements), or a case Card c after the two subtypes. If Card exists only to group the two, make it abstract. A default also compiles, but then a new subtype no longer breaks the build (unit Switch patterns (Java 19+)).

non-sealed Reopens One Branch, and Subtypes Nobody Listed Arrive Through Its Case

The word the colleague added was non-sealed, on Wallet:

The partner compiles public class GiftWallet extends Wallet in its own package, against the library jar, and charges three payments:

The gift wallet is a Wallet, so case Wallet w takes it and charges 190 bp, a fee its contract excludes. Unit Switch patterns (Java 19+) showed that adding a type to a permits list stops every switch without a default, and throws MatchException in code that wasn't rebuilt. Neither happens here: the switch is still exhaustive, because every possible subtype of Wallet, known or not, is a Wallet.

The root stays sealed: a class still can't implement PaymentMethod directly. Below Wallet, the hierarchy is as open as any class: a switch over Wallet that names its subtypes also needs a case Wallet w or a default.

The wallet arm must charge through something a subtype can override, a feeBasisPoints() method on Wallet, or the library must keep Wallet final and add the gift wallet itself.

Permitted Subclasses Live in the Sealed Type's Module, or in Its Package When There Is No Module

The library team moves Wallet to billing.wallets and compiles on the classpath:

javac's wording names the sealed type, but the rule is about where Wallet lives. The same three files, with a module-info.java that makes them one named module, compile without an error. In a named module the permitted subclasses may sit in any of its packages; on the classpath they share the sealed type's package.

A sealed type and its permitted subclasses can't be split across modules; a class below a non-sealed one, like the partner's gift wallet, can live anywhere. PaymentMethod names Wallet, so its module must read the wallets module, and Wallet implements PaymentMethod, so the wallets module must read the core: javac reports cyclic dependence involving billing.wallets. Without the requires, it reports package billing.wallets is not visible.

The JVM checks the module too, as it checks the list in unit Defining sealed classes and interfaces. We compiled the hierarchy as one module, then ran it with Wallet in a module of its own, billing.wallets:

The JVM's rule is looser than javac's. At load time it checks the permits list and the module, and the package only for a subclass that isn't public. The same class files, run on the classpath with Wallet public and in its own package, loaded without an error.

Summary

  • Every permitted subclass is `final`, `sealed` or `non-sealed`. javac has no default; records are final already, and an enum is final, or sealed when a constant has a body.
  • A `sealed` subclass keeps the set closed, but a switch covers it through its subtypes only when it is abstract or an interface; otherwise it needs its own case.
  • `non-sealed` reopens one branch. The root switch stays exhaustive, and every unknown subtype arrives through that branch's case, with no compile error and no MatchException.
  • Permitted subclasses share the sealed type's module, or its package on the classpath; the JVM checks the list and the module again at load time.

Challenges

  1. Wallet is non-sealed and three partners extend it. You want the fee switch to break the build when a fourth arrives. What would you change, and what does each partner have to do?
  2. A sealed Card class has instances of its own today. List what changes, in the library and in every switch over PaymentMethod, if you make it abstract.
  3. The billing team wants to ship PaymentMethod in one jar and the wallets in another, both on the module path. What has to change, and what does the split cost the next release?

Design Note: Why the Subclass, Not the Root, Decides What Is Open

permits controls one level. Without a modifier on each subclass, a sealed root would close only its direct children, and any of them could be extended freely below. Java makes each level state its choice, so reading one declaration tells you whether the hierarchy goes on below it, and the compiler can trust a final or sealed branch when it checks a switch.

non-sealed is the way to say "extension point" in the same vocabulary, and the exhaustiveness check over the sealed root stops at that class.

Problem statement


The event bus writes a type id into every message it sends and reads it back to pick the class to decode into. A message whose class has no id fails, and it fails in production, at the first message of that class. So at startup TypeRegistry.of(Event.class) registers every class a message can have at run time, by walking the sealed hierarchy under Event.


Last month a team added a class to the hierarchy that the registry never saw, and the first message of that class was lost. The registry should never start in a state where that can happen.


Finish collect(Class<?> type) in src/main/java/practice/TypeRegistry.java. When you're done, of(root) registers exactly the classes a value of root can have, and it throws IllegalArgumentException, naming the class, when the hierarchy lets in classes that no list names. About eight lines in total.


The tests build their own hierarchies, with records, classes and interfaces at more than one level.
