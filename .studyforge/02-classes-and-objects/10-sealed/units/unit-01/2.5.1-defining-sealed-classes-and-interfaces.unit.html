The payments library exports an interface Payment and two records, Card and Transfer. The ledger books a payment through an instanceof chain whose last branch throws unknown payment. A partner team implemented Payment for its gift cards, and at month end 312 gift-card payments sat in the dead-letter queue. Sealed types (Java 17) let a type's owner name its direct subtypes. Outputs are from Java 21.

A Sealed Type Names Its Direct Subtypes, and javac Refuses Any Other

The partner's record, in its own file, no longer compiles:

sealed works on a class or an interface, and permits lists every direct subtype. A record is implicitly final, so it qualifies as it is; a class needs final, sealed or non-sealed, and every subtype must sit in the sealed type's module or package (unit Permitted and non-permitted subclasses).

An anonymous class is refused too, and so is a lambda: a sealed interface isn't a functional interface.

The JVM Checks the List When It Loads a Subtype

javac stores the list in the class file. We compiled GiftCard against the unsealed Payment, then ran it with the sealed library:

Sealing a published type is a breaking change: the partner's build fails, and an upgrade without a rebuild fails when the class loads.

Without permits, the Subtypes in the Same File Are the List

Payment.class.getPermittedSubclasses() returns:

javac takes every direct subtype declared in the same source file; a Voucher in another file of the same package gets the not listed in its 'permits' clause error.

Without permits, whatever someone adds to the file joins the closed set, and no review sees a list change. The demo's TestPayment is now a payment that every exhaustive switch (unit Switch patterns (Java 19+)) must handle. Write permits on a type other code depends on; leave it out for a small hierarchy nested in one file.

At Run Time, getPermittedSubclasses() Lists the Direct Subtypes Only

Printing isSealed() and the simple names of what getPermittedSubclasses() returns:

Sepa and Wire don't appear under Payment. Code that needs every concrete type, a decoder or a test that each type has a handler, walks down through each sealed subtype. For a type that isn't sealed the method returns null, not an empty array, and the javadoc leaves the order of the array unspecified.

Summary

  • `sealed ... permits` names the direct subtypes, and javac refuses any other, anonymous classes and lambdas included. Records qualify as they are.
  • The JVM checks the list again when it loads a subtype, so an implementation compiled before the sealing fails with IncompatibleClassChangeError.
  • Without `permits`, the list is every direct subtype in the same file, never the package.
  • `getPermittedSubclasses()` returns the direct subtypes only, and null for a type that isn't sealed.

Challenges

  1. Four services you don't own implement your library's Event. What would you release, and in what order, to seal it?
  2. Forty tests stub Payment with anonymous classes. After sealing, what replaces them?
  3. Write a test that fails when a permitted subtype of Payment has no handler in the ledger. Which part could the compiler check instead?

Design Note: Why the List Lives in the Type

Before Java 17 a library closed a hierarchy by hiding it: a package-private constructor stops other packages from extending an abstract class, but an interface has no constructor, and nobody could read off which subtypes existed. Sealing makes the list part of the type, read by javac for exhaustive switches, by the JVM to refuse a stranger, and by tools through reflection. The cost is that the list becomes public API: adding a subtype breaks the build of every exhaustive switch without a default, and removing one breaks the clients that name it.

Problem statement


The parcel service receives tracking webhooks from its carriers. Each payload carries a "type" field, and the decoder looks that name up in a map to find the record class to decode into. The map was written by hand, and when the carriers' Damaged events were split into Crushed and Soaked, nobody updated it: for two days every damage report was rejected as an unknown type.


The payload types already form sealed hierarchies of records, so the decoder should build the map from the hierarchy at startup. of(...) and register(...) are written. Finish the TODO in src/main/java/practice/PayloadTypes.java:


  • collect(...): add every record class a value of the given type can be.


When you're done, of(...) returns every payload record of a hierarchy however it is nested, and nothing else. A map it can't make complete is worse than none, so for such a type of(...) throws IllegalArgumentException instead of returning. About eight lines in total.
