The billing team turns Invoice into a record to drop its boilerplate. The class extends an Audited base, caches its total in a field, and is loaded by an ORM. The first build fails on the header, the second on the cache, and once it compiles, the ORM can't load it.

A Record Extends Only java.lang.Record, and Nothing Extends It

javac 21 on three attempts to fit Invoice into a hierarchy:

A record has no extends clause: its superclass is always java.lang.Record. It is implicitly final, so it can't be abstract either. Its state is exactly its components, which lets the generated equals compare them and new Invoice(i.number(), i.totalCents()) rebuild an equal copy. A superclass or a subclass would add state those methods can't see.

Turn Audited into an interface; the accessors implement its methods:

The cost is repetition: every Audited record declares createdAtMillis itself.

  1. Concept check

    Check yourself: limitations and use cases for records

    • A framework that calls a no-arg constructor and then sets fields can't build a record: a no-arg constructor must delegate, and reflection can't write a record's fields even after setAccessible(true).
    • A record's superclass is always java.lang.Record and the record is final and can't be abstract; shared shape goes into an interface the accessors implement.
    • A record can't declare an instance field or initializer, and a field made static to satisfy javac holds one value for every instance.

A Record's Only Instance State Is Its Header

javac refuses the old class's cache field, and any instance initializer:

The error says to make it static. What do two bills print?

A static field belongs to the class, so the first bill's total became every bill's. Compute a derived value in a method on each call; if that is too slow, make it a component the constructor checks, or use a class. State that changes, such as a retry count, lives outside the record, for example in a map keyed by it.

A Framework That Builds an Object Empty, Then Fills It, Can't Build a Record

Many ORMs create an object with its no-arg constructor, then set its fields by reflection. Jakarta Persistence requires an entity to have a public or protected no-arg constructor, a class that isn't final, and persistent fields that aren't final. A record and its fields are final. A no-arg constructor can be added, but it can only delegate with placeholder values:

What a framework then does, with record Point(int x, int y) for comparison:

setAccessible(true) lets reflection write a final instance field of an ordinary class, but not of a record. The way in is the canonical constructor, with every value at once. getRecordComponents() gives the components' names and types in header order:

Mappers that support records work this way, and the constructor's checks run on every row. The entity stays a class; a record carries what is read out of it.

Keep a Class for Identity, Changing State, or Many Optional Parts


A record's equals compares components. Two different visitors with the same name and birth date check in at two gates:





The two objects are distinct but equal, so the second add returns false and the set of who is inside counts one person. A visitor or an account stays the same thing while its data changes. That is identity, and it needs a class whose equals uses an id, or none. Changing a record makes a new copy, and every other holder of the old one keeps the old state.


A record's canonical constructor is positional, and with four int components a swap compiles:





With many components, or many optional ones, put a builder class or named factory methods in front of the record.

Summary


  • A record extends only java.lang.Record and is final. Shared shape goes into an interface.
  • A record's only instance state is its header. A static "cache" is shared by every instance.
  • A framework that constructs empty, then sets fields, can't build a record. Build it through the canonical constructor.
  • Identity, changing state and many optional parts call for a class, or a builder.

Design Note: Why a Record Is Closed


A record promises that its state is its components and nothing else, so equals, hashCode, toString, deconstruction and serialization are derived from the header and agree. The cost is that a record can't join a class hierarchy, be filled lazily, or be an entity.
