A shop caches prices under a hand-written key class. In March the team added region to it, because Germany and Austria charge different prices in the same currency. Since then, whenever the German price is cached first, Austrian customers are shown it. No test failed, and the cache code wasn't touched.

The advantages of a record that matter are about what can't drift apart when the class changes, and they come with a limit and a migration cost. Every output here is from Java 21; declaring records and what they generate is unit Defining and using records.

A Record's equals and hashCode Follow Its Component List, So a New Field Can't Be Left Out

Pause here: the cache holds the German price, 1990 cents, and a request for Austria comes in. Which price does it get?

The class's equals and hashCode were generated by an IDE when the class had two fields, and nothing ties them to the third. The two keys are equal, so the cache answers with the German price, and nothing throws or logs.

A record's equals, hashCode and toString are derived from the component list in the header, so adding region there changes all three, and the Austrian request misses and gets priced for Austria.

Adding a Component Breaks Every Constructor Call and Record Pattern at Compile Time

Quote gains a currency component. Code written against the old shape:

A record has one canonical constructor and one deconstruction shape (record patterns, unit Record patterns (Java 19+)), both equal to the header, so every call and pattern written for two components stops compiling. You can keep old calls compiling with an extra Quote(String sku, long cents) constructor that passes a default currency, but the pattern still breaks: it has no such escape. Code that only calls q.sku() still compiles. A class with a no-arg constructor and setters gets none of this: every old call site compiles and leaves currency null.

A Record Is Only Shallowly Immutable: a List Component Can Change Under a Map Key

A record's fields are final, but a final field that holds a List holds a list anyone with a reference can change. A booking service keeps seat holds in a map keyed by a flight leg, and the caller reuses its seat list:

The record's hashCode reads the list, so the key's hash changed after it was stored. The entry was filed under the old hash, so get with the new one doesn't find it, although the map still holds the entry and that entry equals leg. The hold can't be found or released, so the seats stay blocked.

Copy the component in the compact constructor. Both candidates were checked after the same seats.add("12C"):

Collections.unmodifiableList is a read-only view of the caller's list, not a copy, so the caller's change still reaches the key. List.copyOf makes an unmodifiable copy (and refuses null elements). Maps and sets have Map.copyOf and Set.copyOf. An array can't be made unmodifiable: clone it in the constructor and in the accessor, and note that it is compared by identity (see the Reference).

Moving a JavaBean DTO to a Record Turns Identity into Value Equality

A monitoring service collects alerts in a HashSet and pages someone when one host sends two 503s within a minute. The DTO was a JavaBean with no equals, and the team migrates it to a record that checks its code:

The same two alerts go into a Set<AlertBean> (the old bean, with setters) and a Set<Alert>:

The bean inherited Object.equals, which compares identity, so two alerts with the same values were two set elements. The record compares values: equal hash codes only bring the two alerts together, and the record's equals makes the second one a duplicate, so the rule never fires. The code around the set compiles unchanged, and every test that sends one alert passes.

Before migrating, find every Set, map key, contains, remove and indexOf that sees the DTO. Where two equal values are two events, give the record a component that tells them apart, such as an id or a timestamp.

A Binder Can Build a Record Only Through Its Canonical Constructor

A binder written for JavaBeans creates the object with its no-arg constructor, then sets each property through a setter or by writing the field. A record has no no-arg constructor and no setters (unit Getter and setter methods covers the missing getX names). What the binder tries, each call wrapped in its own try, and whether Alert can be subclassed:

Field.set refuses to write a record's field even after setAccessible(true), as its javadoc states. A record is also implicitly final, so a library that subclasses at run time, a lazy-loading proxy for example, can't do so.

A binder that supports records reads the components in declaration order and calls the canonical constructor:

Binding through the constructor runs the compact constructor's checks on every object; a setter-based binder skips them. Reflection delivers the check's exception wrapped in an InvocationTargetException.

Libraries differ. Recent versions of the common JSON and mapping libraries bind records through the canonical constructor; older versions, and tools that require a no-arg constructor (JPA entities among them), don't. Check the version you run before migrating.

Summary

  • A record's `equals` and `hashCode` follow its components. A component added later is part of equality at once; a hand-written class drifts and serves the wrong value without an error.
  • Adding a component is a compile error at every record pattern and canonical-constructor call. The compiler finds the sites that build or take apart the old shape.
  • A record is only shallowly immutable. A mutable component changed after the record is a map key loses the entry; copy it with List.copyOf, not a view.
  • Migrating a JavaBean DTO changes its equality from identity to values, so sets and maps that held equal beans apart now merge them.
  • Binders need the canonical constructor. No-arg construction, field writes and subclassing fail on a record; constructor binding works and runs its validation.

Challenges

  1. Your record holds a List<Item> and Item is a mutable class. Is List.copyOf enough to make the record a safe map key? What would be?
  2. List the places in a service you know where a DTO is put in a set or used as a map key. Which of them would change behaviour if the DTO became a record?
  3. A record holds a password. Do you override toString, wrap the password in a type of its own, or keep it out of the record? What does each choice do to equals?

Design Note: A Record's API Is Its State

Record's javadoc requires that new R(r.c1(), ..., r.cn()) equals r: the header is the constructor, the accessors, the equality and the pattern. As long as you don't override them, the generated members can't drift from each other, and a binder can build a record from its components alone. The cost is that a record can't hide its representation. Changing a component changes the canonical constructor, every record pattern and the serialized form; a class could keep its old constructor and convert behind it.
