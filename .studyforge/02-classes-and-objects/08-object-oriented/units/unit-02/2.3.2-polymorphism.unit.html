The release that added fragile parcels and pallets to the shipping service brought three tickets. Fragile parcels are billed as ordinary parcels, and pallets go out free. Since a cleanup that removed "duplicate code", the customs printer prints skipped for every shipment. And a helper that totals weights won't accept a List<Parcel>, so its callers copy their lists first. All of it compiled.

How a call reaches an override is unit Method declaration and invocation, and why an overload is chosen at compile time is unit Method overloading.

Java Chooses the Method by the Receiver Alone, So Dispatching on a Second Object Takes Two Calls

Customs needs a form per kind of shipment, and other handlers (labels, insurance) need their own method per kind. Each handler implements one overload per type:

The obvious call, customs.visit(s) with s declared as Shipment, runs visit(Shipment) for every shipment. The overload is chosen from the argument's declared type (unit Method overloading), and the run-time choice looks only at the object left of the dot, customs. To dispatch on the shipment as well, the call goes through the shipment first, and each class declares the same one-line method:

s.accept(customs) is dispatched on the shipment, which picks the class. Inside that class this has the class's own type, so the compiler picks the matching overload, and that call is dispatched on the handler. This is double dispatch, and the Visitor pattern is built on it.

A List of Parcels Is Not a List of Shipments; a Wildcard Says Whether the Method Reads or Writes

A helper that totals weights takes a List<Shipment>. Passing it a List<Parcel>:

If it compiled, the helper could call items.add(new Letter()), and the caller's list of parcels would hold a letter. The ClassCastException would come later, in whatever code read a Parcel from it. Arrays allow the conversion and check every store at run time instead, with unit instanceof operator's ArrayStoreException. Generics refuse at compile time: neither of List<Parcel> and List<Shipment> is a subtype of the other.

A wildcard tells the compiler whether a method reads from the list or writes to it:

Both methods now take a List<Parcel> (1,200 g and 800 g) and a List<Shipment> (a truck holding one letter), and the program adds a return to each. A Comparator<Shipment> sorts a List<Parcel> for the same reason, since List.sort takes a Comparator<? super E>:

Each wildcard allows only one of the two. A List<? extends Shipment> could be a list of pallets, so the compiler won't add a letter to it. A List<? super Parcel> could be a List<Object>, so what comes out is only an Object. CAP#1 is javac's name for the unknown element type:

A parameter the method reads from is ? extends T, one it writes to is ? super T, and one it does both with is plain T. The JDK's own signatures follow this, as in Collections.copy(List<? super T> dest, List<? extends T> src). An API without wildcards passes the cost to its callers: they copy lists, or cast to a raw type and give up the check.

A Call Site That Has Seen Three Classes Isn't Inlined, Which Matters Only in a Hot Loop

Is every virtual call a lookup in a method table? This loop calls feeCents() from one call site over 1,000 shipments, drawn in equal shares from one to four small final classes of the benchmark's own, with one JVM run per number of classes:

The interpreter and the first compiler tier record which classes reach each call site, and C2 reads that profile. It keeps two classes (TypeProfileWidth=2 on Java 21), so a third class leaves C2 with a virtual call, unless one class has at least 90 % of the calls (TypeProfileMajorReceiverPercent): with three classes and 95 % letters, the same call site printed CallSiteSkew$Letter::feeCents (3 bytes) inline (hot). Measure your own workload. These numbers come from a hand-timed loop whose methods return a constant, on Java 21; once a call is inlined, the time is per element more than per call, and the gap between three and four classes is not explained by dispatch alone. Java 25 on the same machine gave 1.70 ns for both three and four classes, and prints the inlining lines in another format. A few nanoseconds matter only when the method does as little as the call costs, in a loop that runs millions of times. Use JMH and a profiler before replacing an override with an if.

Summary

  • An `instanceof` chain fails silently: an early test hides a subclass's branch, and a new type falls into the default. An abstract method puts the decision in each type, and the compiler names every class that lacks it.
  • Java dispatches on the receiver only. An overload is fixed by the argument's declared type, so dispatching on a second object takes a second call: accept in every class, calling visit(this). One accept in the base class sends everything to the default.
  • A `List<Parcel>` is not a `List<Shipment>`. Read through ? extends T, write through ? super T; arrays allow the conversion and fail at run time instead.
  • HotSpot doesn't inline a call site that has seen three or more classes, unless one of them dominates. That costs nanoseconds per call, which matters only in hot loops with tiny methods; measure before designing around it.

Challenges

  1. A rules engine applies twelve kinds of rule to every order through one interface, and a profile shows the dispatching call near the top. What would you measure before changing the design, and what would you change it to?
  2. Your shipment types live in a library you can't edit, and you need a new operation on them. Compare a Visitor the library would have to add, a switch over a sealed type, and an instanceof chain in your own code.
  3. merge(List<Shipment> a, List<Shipment> b) returns a new list. Write its signature with wildcards, and decide what element type the result should have.

Design Note: Why Java Dispatches on the Receiver Only

Java chooses the implementation at run time from one object, the receiver, and the overload at compile time from the declared types of everything else. That keeps every call checkable before it runs: the compiler knows the one method signature each call will use, and only the class that supplies it is left to run time. Languages with multiple dispatch choose from the run-time classes of all the arguments, so a two-type decision needs no Visitor, but an ambiguity between two methods can then appear only at run time.

The cost in Java is boilerplate: an accept in every class, and a handler interface that changes when a type is added. Switches over sealed types (units Record patterns (Java 19+) and Switch patterns (Java 19+)) now cover many of the cases the Visitor was written for, and the compiler checks that they handle every type.
