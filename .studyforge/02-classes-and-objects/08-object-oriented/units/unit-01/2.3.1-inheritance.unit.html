The platform team ships a new payments-api jar with one addition: a default method maxAttempts() in the Idempotent interface, announced as backward compatible. Refund implements Idempotent and the team's own Retryable, which already has a maxAttempts() default. The refund service picks up the jar without being rebuilt. key() keeps working; the first call to maxAttempts() fails with IncompatibleClassChangeError: Conflicting default methods, and the service's next build doesn't compile.

A subtype is bound to what its supertypes promise and to how they change later. Unit Inheritance basics covered the mechanics of extends (hidden fields, super, self-calls, access); this unit covers when to use it, for classes and for interfaces with default methods.

A Subclass Can Be Used Wherever Its Superclass Is, So It Inherits Every Promise the Superclass Makes

java.util.Properties extends Hashtable<Object, Object> to reuse its storage. A caller sets a timeout with the inherited put:

getProperty returns null, so a caller that passes a default gets its default timeout without a word, and store fails at save time, far from the put that caused it. A rule a subclass puts in one override covers that method only. A caller holding a List runs the object's own methods (unit Method declaration and invocation), so on a subclass of ArrayList that checks in add, the inherited set runs unchecked: it replaces the element without calling add.

extends makes the subclass a subtype: code that accepts a Map<Object, Object> accepts a Properties and may put any object in it, because the superclass promised that works. A table that holds only strings can't keep that promise and its own at once, and the javadoc can only ask: "Their use is strongly discouraged". A subclass can't hide an inherited public method (unit Inheritance basics), and overriding it to throw breaks the callers that use it, a violation of the Liskov substitution principle (unit Liskov Substitution Principle (LSP)).

Extend only when every caller of the superclass may use the subclass without knowing it. To reuse code without that promise, hold the other object in a field and expose only what you mean (unit Definition and purpose of Composition over Inheritance). equals is where a broken promise shows first; unit instanceof operator has that case.

A Class Open to Subclassing Needs a Final Skeleton and Protected Hooks; Otherwise Make It final

Every test of the bulk exporter checks its rows and passes, and its exports are missing from the audit. Nothing told its author that export carried a duty, and nothing stopped them replacing it.

Declaring the skeleton public final void export(...) turns that override into a compile error:

This is the template method pattern. The base class owns the order of the steps and every rule around them, and subclasses fill in protected hooks: abstract ones they must write, or empty ones they may. protected keeps callers in other packages from running a step on its own, outside the skeleton; code in the same package still can (unit Inheritance basics). The rules the skeleton owns include the failure path: when a step throws, its cleanup must still run, so it goes in a finally.

A class designed this way documents which of its methods call which, as AbstractCollection.addAll does ("This implementation iterates over the specified collection, and adds each object returned by the iterator"), because subclasses depend on it (unit Inheritance basics). It calls no overridable method from its constructor (units Class structure and components and Creating objects and using constructors). A class not designed for subclassing should be final, as String and Integer are; a sealed class names the subclasses it allows (unit Defining sealed classes and interfaces).

A Class Method Beats a Default, a More Specific Interface Beats Its Parent, and Any Other Conflict Is Yours to Resolve

A class has one superclass but may implement many interfaces, and since Java 8 interfaces carry code, so two supertypes can offer the same method. Refunds are safe to retry, and the platform team gives Idempotent a default. Predict what a refund returns:

A class's method, declared or inherited from a superclass, beats any default, even when the call goes through the interface, and the order in which the class lists its supertypes plays no part. There is no warning, and refunds are tried once. The default runs only if Refund declares the method and returns Idempotent.super.maxAttempts(), which calls the default of a direct superinterface. Had Payment.maxAttempts() been package-private in Refund's package, Refund wouldn't compile: the inherited method would implement a public interface method with weaker access. From another package it compiles, and the call through Idempotent throws IllegalAccessError.

A default that Payment itself inherits from an interface doesn't count as a class method. If Payment gets maxAttempts() from a default in a Retryable interface it implements, Refund inherits two defaults:

When one interface extends the other, its override is more specific and wins without an error: a class that implements both Retryable and Idempotent extends Retryable gets Idempotent's 5. Retryable.super.maxAttempts() then doesn't compile ("redundant interface Retryable is extended by Idempotent"), so a class can't reach past the more specific default, just as it can't call super.super.m(). Interfaces have no instance fields, so no state can be inherited twice, which is the diamond problem in languages with several superclasses. Only behaviour can collide.

Adding a Default Method Can Break Implementers: Their Source Stops Compiling and Their Old Class Files Fail at the Call

The opening's failure is this conflict, arriving through an upgrade. Refund implements Retryable, Idempotent was compiled when only Retryable had a maxAttempts() default. Version 2 of Idempotent adds one:

The same Refund.class, run against version 1 and then version 2, then compiled against version 2:

The class loads and every other method works; only the call to the conflicting method throws, so the service starts and fails later, in the middle of a refund. The reverse case is harmless: if an implementing class already has a public method with the same signature and return type, the class's method wins and the new default never runs for it.

A default is safe for implementers that know nothing of the new method, and unsafe for those that already inherit a method of that name from another interface. Before adding a default to a published interface, search its implementers for the name. If you can't, put the method on a new interface.

Summary

  • A subclass inherits every promise of its superclass. Callers of the superclass may use any inherited method on it, so extend only when all of them make sense; Properties shows the cost.
  • A class open to subclassing needs a final skeleton with protected hooks. Otherwise a subclass can replace the method that carries the rules; a class not designed for it is final.
  • A class method beats a default, then the more specific interface wins. Anything else is a compile error that the class resolves with X.super.m(), naming a direct superinterface.
  • A new default can break existing implementers. Their source stops compiling, and class files built earlier throw IncompatibleClassChangeError at the first call.

Challenges

  1. java.util.Stack extends Vector. List the Vector methods that let a caller break the stack's order, and decide whether replacing it with ArrayDeque in a codebase is a refactor or a behaviour change.
  2. Your library has an abstract Job class that users subclass, and its run() is public and not final. You want to add a timing metric around every run. What do you ship in the next minor version, and in the next major one?
  3. You own a published interface with hundreds of unknown implementers and need a new method. Compare a default method, a new sub-interface, and a static helper by what each can break.

Design Note: Why Java Allows One Superclass but Many Interfaces

A superclass contributes fields and constructors, and two superclasses raise the questions C++ has to answer: is a shared ancestor's state stored once or twice, and which constructor builds it. Java gave classes one superclass and interfaces no instance state, so the diamond can't arise for state. Default methods, added in Java 8 so that Collection could gain stream() and removeIf without breaking every collection already written, brought it back for behaviour only. The price is the opening's failure: a conflict the compiler would have reported surfaces at run time in a class compiled before the conflict existed.

Problem statement


Every service applies its schema migrations on start. Migrations.Migration is the class each team extends, and each subclass writes the statements of one change. Three incidents this quarter came from the same place:


  • a team overrode apply to log timings, dropped the history check, and its change ran twice on the next deploy;
  • a deploy script called migrate on a migration it had loaded and ran the change with nobody holding the lock;
  • a change that failed halfway left the history locked, and every later deploy refused to start.


Finish src/main/java/practice/Migrations.java so that a migration runs its change at most once per database and only while holding the history's lock, a change that throws is not recorded and releases the lock, and none of the three incidents can be repeated by a team's subclass or by code that holds a migration. Teams write their subclasses in their own packages and must keep being able to. About ten lines in total, most of them in apply.

Problem statement


The payment service sends charges and refunds to the bank. A charge sent twice charges the customer twice, so a Payment is tried once. A refund carries the key of the charge it reverses, and the bank applies it once however often it arrives, so refunds implement the platform team's Idempotent interface, which says how often an idempotent operation may be tried. The platform team sets that number from its configuration and changes it when the bank's limits change.


Finish the two TODOs in src/main/java/practice/Retries.java:


  • send(...): try a payment until the bank accepts it or the payment has used its attempts;
  • Refund.maxAttempts(): how many times a refund may be tried.


When you're done, charges are still sent once, and a failing refund is tried exactly as often as the platform's policy allows at the time, today and after the platform changes it. About five lines in total.
