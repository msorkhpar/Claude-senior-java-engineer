A launch campaign gives a voucher to the first 1,000 people who sign up. The count is an AtomicInteger, and the voucher email goes out from inside the update, so that a customer is emailed only when the count really moves:

Sixteen threads take the launch burst. Afterwards the counter reads exactly 1,000, and the mail log shows 3,520 voucher emails. Every operation in the code is atomic.

An operation is atomic when no other thread can see it half done or act in its middle. A compound action (read, decide, write; or change two values that must agree) is atomic only if one operation does all of it. Every output below is from Java 21 on one machine (availableProcessors() printed 20); timings come from plain loops, not a JMH benchmark.

An Atomic Update Retries Until Its compareAndSet Wins, So Its Function Can Run Many Times

updateAndGet takes no lock; its JDK 21 source is a loop:

It writes only if the value is still the one it read; otherwise it reads again and re-runs the function. So how many times does the function run when 8 threads each call updateAndGet(n -> n + 1) a million times?

The function ran almost three times per update. For n + 1 that only costs CPU; the voucher function sends an email from every losing attempt that was still below the cap. Three runs of the campaign, each followed by a version that decides inside the function and acts after it, on the value it returned:

The extra emails depend on how often threads collided, so a test with one thread, or a quiet day, sends exactly 1,000. The javadoc of getAndUpdate, accumulateAndGet and LongAccumulator says the function "should be side-effect-free, since it may be re-applied when attempted updates fail due to contention among threads". Keep the function a pure computation of the next value, and do the side effect once, after the update, from the value it returned.

Write the loop yourself when the caller needs more than the new value back (did this caller win, which number did it get) or when the decision calls out, to a quota service, say: read, decide, compareAndSet, and on failure go back to the read. Every retry decides again on the new value; a decision kept from the first attempt is a check-then-act again (unit Data races and how to prevent them).

LongAdder Counts Faster Under Contention Because No Single Variable Holds the Total

Every incrementAndGet on an AtomicLong is an atomic add to one memory location, so threads that update it at the same time queue up for that location's cache line. LongAdder spreads contending threads over several cells and adds them up when asked. Ten million increments, split over the threads:

With one thread they cost the same, as the javadoc says ("Under low update contention, the two classes have similar characteristics"). Neither lost an update: after the threads ended, every run's total was exactly 10,000,000.

The price is that no variable holds the total. sum() takes no lock: it reads the cells one after another while they change, and its javadoc says the result is "NOT an atomic snapshot". A queue-depth gauge shows what that means: 4 producers add 1 and then enqueue a job, 4 consumers take a job and then subtract 1. Every subtraction follows its addition, so the depth is never below zero. A monitor read it 20 million times:

Two more runs gave 15 and 110 negative reads. sum() read a consumer's cell after its subtraction and a producer's cell before the matching addition, and returned a value the gauge never held. An alert on "depth below 0" fires; one on "depth above N" can fire late or early.

LongAdder also has no compareAndSet, incrementAndGet or getAndIncrement. It can't hand out the next order number or stop at a cap. Use it for statistics that are read now and then; use AtomicLong when the value takes part in a decision.

compute and merge Are Atomic for One Key, Not for an Action Across Keys

ConcurrentHashMap.compute and merge lock the key's bin while the function runs (unit Thread Safety of Common Data Structures), and the javadoc of compute promises "The supplied function is invoked exactly once per invocation of this method":

In exchange, other updates to that bin wait while the function runs, so the javadoc asks for a computation that is "short and simple" and must not modify the map.

The atomicity covers one call on one key. A show has 200 seats, kept as two keys, and a booking moves one seat from free to sold with two compute calls:

A latch holds the booking at between while another thread adds up the two keys. The fix keeps both numbers in one immutable value under one key, so the only pause point is before its one compute:

Each compute was atomic, and a reader still saw 199 seats. A capacity check that runs in that window admits or refuses on a total that never existed; a scan of the whole map does the same (unit Order of Operations in Concurrent Collections). What must stay consistent goes under one key, so that one compute changes all of it. If the values must live under different keys, every writer and every reader takes the same lock, and the map's own concurrency no longer helps.

Values That Must Agree Need One Lock or One Immutable Holder Replaced by compareAndSet

An account may go below zero only down to its overdraft limit: balance >= -limit. Both fields are AtomicLongs, and both operations check the rule against the other field. pause.here() is the example's hook for holding a thread after its check, on its first attempt only:

From balance 0 and limit 100, a withdrawal of 80 is held after its check while another thread lowers the limit to 50. Each check passes on its own; what does the account end up with?

Replacing set with compareAndSet on each field doesn't help: the withdrawal's CAS on balance succeeds, because the limit changed and the balance didn't. A CAS protects one variable; the rule reads two.

So make them one variable: an immutable Account record holds both and refuses to exist in a state that breaks the rule, and an AtomicReference holds the current record. An update builds the next record from the current one and swaps it in with compareAndSet, retrying from the read:

The withdrawal's swap failed because the record had been replaced; its retry built a record with balance -80 against limit 50, and the constructor refused it. A synchronized method for every read and write of both fields (unit Monitors and synchronized blocks) gives the same guarantee and is simpler when the critical section is short. The holder lets readers take one consistent pair without a lock, and it costs an allocation per update and retries under contention. Unit Visibility issues and proper synchronization techniques covers the single-writer case of this swap, where no compare-and-set is needed.

Summary

  • An atomic class's update is a compare-and-set retried until it wins. The function you pass can run several times per call; side effects belong after the update, decided from its result.
  • `LongAdder` scales a counter by splitting it. It is faster under contention, sum() is not a snapshot, and it has no compare-and-set to make decisions with.
  • `compute` and `merge` are atomic for one key. Two calls, on two keys or on one, are two steps that a reader can fall between; keep what must agree under one key.
  • Values that must agree need one lock or one immutable holder. Atomic fields keep each value whole and let the rule between them break.

Challenges

  1. The voucher fix sends the email after getAndUpdate. If the mail server is down, the voucher is counted and never sent. What would you record, and where, so that a retry sends each voucher exactly once?
  2. Measure the AtomicLong/LongAdder table on your own machine with JMH. At how many threads do they cross, and does that change with work between the increments?
  3. A rate limiter allows 100 requests per second per tenant and is checked on every request. Would you keep the counts in a ConcurrentHashMap<String, LongAdder>, a ConcurrentHashMap<String, AtomicLong> or one compute per request? Which wrong answers would each one let through?

Design Note: Why the Atomic Classes Retry Instead of Lock

A compare-and-set never blocks: a thread that loses tries again, and some thread always wins, so a descheduled thread can't hold the others up the way a lock holder can. A lock gives the opposite trade: the work runs once, and everyone else waits for the holder, however long it is descheduled. Which to use depends first on whether the work may run twice, and then on how long it runs.

A connection pool keeps at least min connections open and never more than max. Operators change the limits by hand and the autoscaler changes them on its own, from different threads, and every change must also pass the platform's Policy (a ceiling per service tier, for example). Last week one service ran with min 16 and max 12 for an hour: an operator raised the minimum while the autoscaler lowered the maximum, and both changes were accepted. Each limit is an AtomicInteger today.


Finish limits(), setMin(...) and setMax(...) in src/main/java/practice/PoolLimits.java. You may change how the limits are stored. The policy check calls the config service and can take seconds, and a change must not wait for another change's policy check. When you're done, the limits can never be seen with min above max, every change that was accepted is in force, and a change that a concurrent change made invalid is refused. About twelve lines in total.
