A monitoring dashboard froze during Monday's peak, and the on-call engineer took a thread dump before restarting it. Two threads were BLOCKED: sensor in Dashboard.markStale and screen in Gauge.value, each waiting for a monitor the other held. Gauge and Dashboard each have one lock, each passed review on its own, and neither nests two synchronized blocks. The post-mortem went through the service class by class with two questions: which threads touch this state, and what guards it? For half the classes nobody could answer.

Most of what makes concurrent code safe is decided before the first lock: whether the state is shared at all, whether what is shared can change, and, for the state that is left, which lock guards it and what runs while it is held. Every output here is from Java 21 on a 20-core machine.

State Confined to One Thread Needs No Lock, Until a Callback Runs Somewhere Else

A local variable is confined to its thread as long as the object it refers to isn't handed to another (unit Terminal operations (forEach, reduce, collect) shows a parallel stream doing exactly that). State that outlives one call gets an owner: a trading service keeps its positions in a plain HashMap that only the ledger thread, a single-thread executor, reads or writes. Other threads don't lock the map; they submit tasks to ledger.

A task on the ledger thread books a trade at the current rate, which the rate service returns as a CompletableFuture. update merges the rate into the positions and prints the name of the thread it runs on; answer is a latch the program releases once the callback is attached:

Pause here: which thread runs update? A cached rate is a future that is already complete; a fetched one is completed later by a thread of the io pool:

A callback attached with a method that isn't Async runs on the thread that completes the future, or, when the future is already complete, right away on the thread that attaches it. (The javadoc promises less: any thread that calls a completion method may run it.) An Async method without an executor runs it on ForkJoinPool.commonPool(). Only the form that names the owner's executor keeps the update on the owner.

The rate service's test double returned completed futures, so every test ran update on the ledger thread and passed. In production a rate that isn't cached arrives on an io thread, which then writes the HashMap while the ledger thread may be writing it too: the unsynchronized map of unit Thread Safety of Common Data Structures, in a class whose design says it needs no lock. Hand every result back to its owner through the owner's executor: thenAcceptAsync(update, ledger). Another thread that needs to read the positions submits the read the same way, supplyAsync(read, ledger).

  1. Coding practice

    Keep the desk's book on the desk's thread

    • A callback attached with a non-async method runs on the thread that completes the future, or at once on the attaching thread when the future is already complete, so state confined to an owner thread must be handed back through the owner's executor.
    • Reads of confined state run on the owner thread too, not only writes.

Problem statement

The quoting desk keeps its rates in a Book that isn't thread-safe. The design gives the book to one thread, the desk's own executor, so that nothing needs a lock: every call into the book runs there. Quotes come from the market-data adapters as CompletableFutures. When an adapter has the rate cached, the future is already complete; otherwise one of the adapter's own threads completes it later.

The desk passed every test, where the adapters are stubs with every rate cached. In production its book has twice lost a rate during a busy minute, and a thread dump caught an adapter thread inside Book.apply.

Finish the two TODOs in src/main/java/practice/FxDesk.java:

  • onQuote(...): put the quote into the book once it has arrived, and return at once;
  • rate(...): answer with the book's rate for a pair.

When you're done, every call into the book runs on the desk's thread, whether the quote was already complete, arrives later from an adapter, or is being read. About three lines in total.

What Passes Between Threads Is Immutable, or Its Sender Never Touches It Again


Confined parts of a program talk through queues, and what travels is a reference. A price feed reuses one tick object to save allocations:



The consumer has fallen behind and takes the three entries after the third put. The second run puts a new record Tick(String sku, long cents) each time:



The queue held three references to one object, and the producer changed it after handing it over. A put happens-before the take that removes the element (unit Synchronization actions and their impact on memory visibility), which covers the writes made before the put, not the ones after. A consumer that keeps up gets something less predictable than three copies of the last tick: it reads fields the producer may be writing at that moment, a data race (unit Data races and how to prevent them) that can pair one tick's SKU with another's price.


Hand an object over in one of two ways. Send an immutable value, a new record per message with its collections copied (unit Proper synchronization to ensure memory visibility), and "never touched again" holds by construction. Or transfer ownership: fill a mutable object, put it, and drop every reference to it, allocating a new one for the next message. Nothing checks the second, so keep it for large buffers you can't afford to copy.


A Latch or a Queue Remembers a Signal That wait() Can Miss


wait() and notifyAll() are correct when every rule of unit Monitors and synchronized blocks is kept: a condition held in a field, checked in a loop, under the monitor that is notified. Skip the field and the order of two threads decides the outcome. At startup the service waits until its cache has loaded, and this time the loader is quick and notifies before the starter begins to wait:



The same order with a CountDownLatch:




notifyAll() wakes the threads that are waiting at that moment and records nothing, so the starter waits for a notification that has already happened. The latch keeps its count: an await() after the count has reached zero returns at once, and its javadoc adds that actions before a countDown() happen-before the actions after a successful return from await() in another thread. A BlockingQueue keeps its elements, a Semaphore its permits (unit Semaphores), a Future its result. Each has the state field, the loop and the notification already written and tested, so application code uses them instead of wait().


Three cache loaders count down one latch, and the tax loader throws first:




Without its timeout the await would return only when interrupted. If the service may start with a cache missing, count down in a finally and record the failure where the starter can see it. If it may not, the failure has to reach the waiter: a Future carries the exception to get().

Write Down Which Lock Guards Each Field, and Let the Code Check It


A lock protects a field only if every access takes it, and the code shows that only to someone who reads every method. Write the policy where the field is declared. The usual convention is @GuardedBy("lock"), from the annotations of Java Concurrency in Practice. The JDK has no such annotation, so this class declares its own:



holdLocked expects its caller to hold lock and says so twice: in the annotation for readers, and in an assert for tests. holdAll calls it without the lock. javac compiles it without a warning. Two runs, differing only in -ea:



Without the check, every single-threaded test passes, and the bug shows only when two group bookings of the same seats run at the same moment: two putIfAbsent calls on a HashMap with no lock between them, and both customers may be told the seat is theirs. With the check, the first test that calls holdAll fails and names the missing lock; Maven Surefire runs tests with -ea unless told not to. Production runs without -ea, where the check costs next to nothing.


Thread.holdsLock knows only monitors. A class guarded by a ReentrantLock asks the lock:



Thread.holdsLock(lock) asks about the ReentrantLock object's monitor, which nobody holds, so that assertion fails on every correct call. isLocked() is true when any thread holds the lock, so an assertion built on it passes in an unlocked caller whenever some other thread holds it. isHeldByCurrentThread() is the check; its own javadoc shows it in an assert. For confined state the assertion names the owner instead: assert Thread.currentThread() == ledgerThread.


The class's Javadoc carries the rest of the policy: whether the class is thread-safe, which thread owns which state, and any lock that callers must take themselves, as the javadoc of Collections.synchronizedList does for iteration.


Static checkers. Some analysers, such as Error Prone's GuardedBy check, read the annotation and report an unguarded access at compile time. No such tool was run for this page.

A Call to Another Object Under Your Lock Adds That Object's Locks to Your Lock Order


Unit Monitors and synchronized blocks breaks a deadlock between two accounts by always locking the lower id first, which works when one method takes both locks and can sort them. Gauge and Dashboard each lock only themselves:



A sensor thread sets the gauge a million times while a screen thread renders the dashboard a million times. Pause here: does it finish? After two seconds the program calls ThreadMXBean.findDeadlockedThreads() and prints, for each thread it returns, the method it is blocked in, the lock it waits for and that lock's owner:



set holds the gauge and, through a listener, asks for the dashboard; render holds the dashboard and asks for the gauge. Each second lock is taken one call away, so neither class shows a nested lock, and the order is set by whoever subscribed at run time.



The fix belongs in the class that calls out: hold the lock for the state, copy what the call needs, and make the call with no lock held. Java Concurrency in Practice calls this an open call:




render still calls value() under the dashboard's lock, but a cycle needs both halves, and the gauge no longer holds its lock while it waits for the dashboard. Each class can vouch only for its own calls, so each makes the open calls it can: render could copy the gauge list under its lock and read the values after releasing it. The lock is now held only for the gauge's state, the short critical section whose throughput unit Monitors and synchronized blocks measures.


With open calls, two set calls on different threads can notify in the opposite order to their writes, so a listener that needs the latest value reads value() rather than its argument.

Summary


  • State confined to one thread needs no lock, until a callback runs it somewhere else. A non-async callback runs on the thread that completes the future, or on the attaching thread if it is already complete; hand results back through the owner's executor.
  • What passes between threads is immutable, or its sender never touches it again. A queue hands over a reference, and its happens-before edge covers only the writes made before the put.
  • A latch or a queue remembers a signal that wait() can miss. notifyAll() records nothing; the library classes keep state, and a latch counts only the countDown() calls that happen.
  • Write down which lock guards each field, and let the code check it. @GuardedBy is a convention javac ignores; an assert of Thread.holdsLock or isHeldByCurrentThread() makes tests catch an unguarded call.
  • A call to another object under your lock adds its locks to your lock order. Make open calls: copy under the lock, call after releasing it; findDeadlockedThreads() names a cycle once it has formed.

These have no single answer.

Design Note: Why Java Leaves the Locking Policy to Comments


Every Java object has a monitor, and any code with a reference can lock it. A field and the lock that guards it are related only by what the author meant, so the compiler can't tell which synchronized block protects which field and can't report the one that's missing. @GuardedBy, assertions and static checkers recover part of that intent after the fact.


The stronger fix is to make the policy structural rather than written: keep the state private in a class whose every method takes the class's own lock, or behind a single owner thread, so that no outside code can reach the state any other way. The price is granularity: one lock or one thread per piece of state serializes work that finer locking could run side by side.
