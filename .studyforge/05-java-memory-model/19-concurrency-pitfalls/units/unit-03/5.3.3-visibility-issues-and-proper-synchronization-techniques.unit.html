At 14:02 the on-call engineer flipped the payment service's kill switch for EU cards. Within a second, nineteen of its twenty workers stopped charging EU cards. The twentieth went on charging them until someone restarted it at 14:40. In staging, where debug logging is on, the switch works every time. When an engineer attached a debugger to a canary and set a breakpoint in the loop, the stuck worker stopped at once. The ticket was closed as "can't reproduce".

The switch started as a plain field and went through two fixes that look right before a third held. Every output comes from Java 21.0.12 (HotSpot, x86_64, 20 CPUs), one JVM per run.

A Visibility Bug Disappears Under -Xint, C1, a Breakpoint or a Log Line: That Is the Diagnosis, Not a Fix

The charge loop read the switch from a plain static field:

main runs the loop on a worker thread, sets paused = true 500 ms later and gives the worker a second to end. We ran the same class six ways, three times each:

Then we attached jdb to the JVM three seconds after it started, with the worker stuck, and set a breakpoint on the charges++ line:

The breakpoint was never hit. With the breakpoint on a line of main instead, the worker was still charging when the program gave up waiting, 31 s after the switch, in three runs of three.

None of the switches that stopped the worker changes what the memory model allows, and no cache hides the write: the hardware keeps caches coherent (unit Shared memory and thread-local memory). Each switch changes which code runs. -Xint keeps every method in the interpreter, which reads the field on every turn. -XX:TieredStopAtLevel=1 keeps C2, the optimizing compiler, out, and C1's code for this loop kept reading. CompileCommand=exclude keeps this one method interpreted. Setting a breakpoint in chargeLoop most likely made HotSpot discard the method's compiled code, and the interpreter then read paused once and left the loop before reaching the breakpoint. The log line puts a call and a lock acquire into every turn of the loop, which kept the JIT from hoisting the read; main never takes that lock, so it is no edge either (unit Synchronization actions and their impact on memory visibility). The debug agent alone didn't change this loop. That leaves C2's code, which most likely read paused once, before the loop: the memory model allows it because no happens-before edge leads from the write to the read (unit Volatile keyword).

Two signs together point to a read the JIT was allowed to hoist: a thread dump shows the thread RUNNABLE in a loop, holding no lock and waiting for nothing, after the condition it waits on has changed; and the hang goes away under -Xint or with that one method excluded from compilation. Narrow it down with CompileCommand=exclude on one method at a time, then fix it with an edge: volatile, a lock both sides take, or an atomic class. A passing run under any of those switches proves nothing about the production JVM.

In production DEBUG is a static final false, so the JIT removes the if, and staging tested a different loop from the one in production.

volatile Covers Reads of the Field, Not the Object It Points To

The first fix put the switch in a settings object and made the reference volatile:

The admin endpoint calls settings.setPaused(true). Two workers wait for it: one keeps the object it read (Settings s = settings; while (!s.isPaused()) charges++;), the other reads the field on every turn (while (!settings.isPaused()) charges++;). A third run uses the rereading worker and replaces the object instead of changing it. Three runs of each gave the same:

settings.setPaused(true) is a volatile read of settings followed by a plain write to paused. What publishes is a volatile write, and this code has none. The worker that holds the object reads only a plain field, so it is the loop from the last section and hangs the same way.

The worker that rereads stopped, but nothing guarantees it. Its volatile read on every turn kept HotSpot from moving the plain read of paused out of the loop. That is how this compiler treats a volatile read, not an edge: no write happens-before the read of paused, so the JLS allows it to return false forever. That is allowed, and was not observed here.

Holding the object is the common case. Any method that takes Settings as a parameter holds it, and so does a local copy taken to read the field once per decision, as unit Volatile keyword advises. So a published object is never changed again; a change is a new object. Assigning a new Settings is a volatile write, and a reader that sees the new reference sees every write made to the object before the assignment. A worker that holds the old object still has to read the field again to get the new one; the last section is about when.

A volatile Array Gives Its Elements No Edge: Use AtomicIntegerArray or a VarHandle

The second fix gave each of the eight card regions its own switch, in an array. Five versions, each worker waiting for element 3:

The admin thread writes the element with the matching call: finalArray[SHARD] = true, volatileArray[SHARD] = true, atomicArray.set(SHARD, 1), ELEMENT.setRelease(handleArray, SHARD, true). Three runs of each gave the same:

volatile belongs to the field that holds the array reference. volatileArray[3] = true reads that field and then writes element 3 with a plain write, exactly like setPaused above. The worker that indexes the field directly stopped for the same reason as the rereading worker, and with the same lack of a guarantee. Passed to a method as a parameter, the array is a plain reference, and the worker hangs as with the final array.

There is no AtomicBooleanArray in the JDK, so switches go into an AtomicIntegerArray as 0 and 1. The package javadoc calls the atomic array classes "notable in providing volatile access semantics for their array elements". A VarHandle from MethodHandles.arrayElementVarHandle keeps the plain boolean[] and gives each access a mode: setVolatile/getVolatile, or setRelease/getAcquire, which is enough for a switch that one thread sets and others read (unit Reordering and optimization by the compiler and runtime compares the modes). Every access must go through the handle; a plain paused[3] = true elsewhere is a plain write again. A third option for arrays is to copy the array, change the copy and assign it to the volatile field, the shape of the next section.

Settings Are One Immutable Snapshot, Replaced Whole and Read Once per Unit of Work

The version that held keeps all settings in one immutable record and replaces it on every change:

Nobody can change a published Settings, so there is no in-place write to miss: copyOf makes copies that the caller's collections can't reach (unit Proper synchronization to ensure memory visibility shows why an unmodifiable view isn't enough). The one volatile write publishes the pause together with the limits, so a reader never sees half of a change (unit Volatile keyword). Readers take no lock. Writers synchronize, because without it two admins pausing two regions at the same time could both build on the same old snapshot, and the second write would drop the first pause. AtomicReference.updateAndGet does the same without a lock, retrying the function if another write got in first (unit Atomicity violations and ensuring atomic operations).

A snapshot reaches a reader only when the reader reads the field again. Two workers charge a batch of six EU charges, one reading the settings once per batch and one once per charge:

send holds the worker on a latch during the second charge while the admin pauses EU:

Both workers are free of data races. How often a worker reads the field sets how long a change takes to reach it: the next charge, the rest of the batch, or never, if the worker reads its settings in its constructor. Read once per unit of work, a charge or a request, and use that one snapshot for every check inside it, so the pause check and the limit check agree.

The price is a full copy on every change. For settings changed a few times a day the copy is negligible. For a large table changed thousands of times a second, a ConcurrentHashMap (unit Thread Safety of Common Data Structures) fits better, and readers give up seeing all keys from one version.

Summary

  • A visibility bug disappears under `-Xint`, C1 only, a breakpoint in the method or a log line. Each changes which code runs, not what the memory model allows; use the pattern to find the read, then fix it with an edge. A run under any of them proves nothing about the production JVM.
  • `volatile` covers reads of the field, not the object behind it. A setter on a published object is a plain write; a reader that holds the object can miss it forever. Replace the object instead of changing it.
  • A volatile array gives its elements no edge. Element writes are plain, and an array passed as a parameter is plain all the way; use AtomicIntegerArray (there is no AtomicBooleanArray), a VarHandle on every access, or a replaced copy.
  • Settings are one immutable snapshot, replaced whole and read once per unit of work. Readers take no lock and never see half a change; writers serialize; a worker sees a change only at its next read, so read per charge or per request, never once per worker.

Challenges

  1. A routing table of 200,000 entries changes 50 times a second and is read on every request. Measure the copy-on-write snapshot against a ConcurrentHashMap for both the readers and the writer, and decide what consistency the readers lose with the map.
  2. Your service reads its settings once per request, but some requests stream for ten minutes. Where do you read them again, and what must stay the same for the length of one stream?
  3. A library's getConfig() returns an object that the library changes in place on every reload. You can't change the library. How do you give your readers a consistent snapshot?
  4. Write a test that would have caught the opening bug before production. What can it check deterministically, and what can no test of it prove?

Design Note: Why volatile Belongs to a Field, Not to an Object

Java has no volatile object and no volatile element type. volatile marks one field, and the ordering it gives belongs to the accesses of that field: in terms of what a compiler may do, no earlier read or write can be moved below a volatile write, and no later one above a volatile read. A "deep" volatile would have to give that treatment to every field of every object reachable from the reference, depending on how the object was reached, on every access, and the compiler could keep almost nothing in a register.

What the language gives instead is one ordering point per hand-off, and it publishes everything written before it to a reader that reads the same field and sees the value. That makes immutability the lock-free way to get a whole object graph across threads: build it, write the reference once, and never write to the graph again. The cost is a copy for every change, and a reader sees the change only when it reads the field again.

Problem statement

Dozens of send threads read the rules for every message, thousands of times a second, and must never wait for a lock. The admin API changes the rules when a domain starts bouncing or a partner asks for a smaller limit.


Support has two complaints. During a busy hour of rule changes, a send thread that had read the rules for a message saw them change while it was still checking that message. And after a block, one send thread went on sending to the blocked domain for half an hour.


Finish the three TODOs of Store in src/main/java/practice/DeliveryRules.java: block, unblock and setMaxSizeKb. Changes come from one admin thread at a time. When you're done, every change applies to the rules read after it, and rules a send thread has already read keep answering as they did when it read them, so a message is never checked against rules that change under it.
