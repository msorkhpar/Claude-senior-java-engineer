The shipping service reloads its rate table every five minutes. A scheduler thread builds a new RateTable, fills it from the rates service and assigns it to a plain field, rates; every request thread reads that field to price a parcel. In review, someone asks for volatile. The author answers that a reference write is atomic, so a request sees either the old table or the new one, and that two years of load tests never priced a parcel at zero.

Both facts are true, and the field is still a bug. Handing an object to another thread takes a happens-before edge (unit Definition of happens-before relationships) from the writes that build it to the reads that use it, unless the object is built so that it needs none.

A Reference Written Without an Edge Can Arrive Before the Writes That Built the Object

The JLS makes every read and write of a reference atomic (JLS 17.7): a reader gets the old reference or the new one, never half of each. That says nothing about the object behind it. The scheduler thread writes the table's fields and then the reference, and with no edge between those writes and the request thread's reads, the JLS lets the request thread see the reference without the fields. It may read them at their default values, null, 0 or false, which every field holds before a constructor writes it. It may also keep reading the old reference for as long as it runs, because the JIT may read a plain field once (unit Volatile keyword).

We tried to catch the half-built case. One class, with one final field and one plain one:

In each of five rounds, the main thread creates 20 million rates and stores each reference into an array slot with a plain write. A reader thread reads each slot with an opaque read (VarHandle.getOpaque), which the JIT must perform every time but which orders nothing, waits if the writer hasn't reached the slot yet, and checks both fields:

Of 100 million racy publications, the reader reached more than ten million slots before the writer and spun until the reference appeared, and it never saw a field at its default. A half-built object is allowed by the JLS and was not observed here. A test that passes says nothing about the next JIT or the next CPU.

Hardware differs. These runs were on x86-64 with Java 21. x86 processors are documented to keep one store from passing another, which leaves the reordering to the JIT; processors with a weaker memory model, such as ARM, leave the race more room. We didn't run on ARM, so the result there is unknown.

What a half-built table would cost: a request that reads the table's rates before they arrive answers "no rate for FR" for a country that has one.

Safe Publication Is an Edge From the Object's Construction to the Read of Its Reference

Every safe way to hand over an object has the same shape. The writer builds the object, then does a release action: a volatile write, an unlock, a put into a concurrent collection. The reader does the matching acquire (a volatile read, a lock, a get or take) and only then reads the object's fields. The construction comes before the release in the writer's program order, the release happens-before the acquire, and the acquire comes before the field reads, so by transitivity the reader sees the object as it was built. These are the idioms, from a program in which each one handed a rate table to another thread:

For the opening's reload, a volatile field costs a request one volatile read and never makes it wait for the scheduler. AtomicReference does the same and adds compareAndSet for writers that race each other. The lock works too, but every request then takes it and waits whenever a reload holds it. A concurrent map fits tables kept per region, and a queue fits an object handed to one consumer. Unit Synchronization actions and their impact on memory visibility quotes each class's javadoc promise.

The reader must take the same path: a request that reads guarded without the lock gets no edge, even though the writer locked (unit Synchronization and memory consistency). And the edge covers the writes made before the release: a change to the table after it is published needs an edge of its own (unit Visibility issues and proper synchronization techniques).

A Static Initializer Publishes to Every Thread, and Fails for Every Thread

A class is initialized once, under a lock that every thread using the class synchronizes on (JLS 12.4.2). A thread that finds the initializer running in another thread waits for it, so whatever the initializer wrote during initialization is visible to every user of the class with no volatile at all. Here the initializer holds while it calls the rates service, a request arrives meanwhile, and a second class's initializer fails:

The request waited, then saw the whole map. While it waited, getState() said RUNNABLE, and a thread dump (jcmd <pid> Thread.print) of the same wait showed RUNNABLE with the line - waiting on the Class initialization monitor for .... A startup stuck in an initializer shows up only in those frames.

A class whose initializer threw is marked as failed and is never initialized again: the first caller gets ExceptionInInitializerError, and every later use in that class loader gets NoClassDefFoundError (on Java 21 its cause names the first exception). If the rates service times out once during startup, pricing fails until the process restarts. Keep static initializers to work that can't fail, and load anything remote into a volatile field that a retry can set again. The lazy holder idiom, a nested class whose only member is the static field, runs the initializer at the first use of that class (JLS 12.4.1) and fails the same way.

final Fields Are Guaranteed Through a Race, and Nothing Else in the Object Is

final has a guarantee beyond the edges of unit Definition of happens-before relationships (JLS 17.5). An object is completely initialized when its constructor finishes, and a thread that sees a reference to it only after that "is guaranteed to see the correctly initialized values for that object's final fields", even when the reference arrived through a data race. The guarantee extends to the objects and arrays reached through a final field, which the reader sees at least as up to date as the field: a final Map filled in the constructor arrives filled.

In Rate, a reader that got the reference through the plain slot is guaranteed zone, not centsPerKg. The run saw both, so only the JLS separates them. String relies on it: JLS 17.5 gives it as the example of an object that its final fields keep immutable without synchronization, so a string handed over through a race reads the same in every thread.

The guarantee is about the object's own fields, not the field that holds the reference. The opening's rates can't be final, because the scheduler reassigns it; it needs one of the idioms above. And it covers only what the constructor wrote before it finished, which leaves two ways to lose it: a constructor that hands out this before it finishes, and a final field that points at something changed afterwards.

Spot the Problem: Registered on the Last Line

A metrics library samples every gauge once when it is registered, as a baseline. Each gauge registers itself on the last line of the base class's constructor, and every field is final:

The queue holds two orders. What does the registry print?

A subclass constructor runs its superclass constructor before it assigns its own fields (JLS 12.5), so Gauge's last line is not QueueDepth's. The registry got this while queue was still null and read a final field at its default. The exception ended the constructor, yet the registry kept the gauge, an object whose construction never finished. All of that happened on one thread. A registry that samples on its own thread is worse off: it saw the reference before the constructor finished, and JLS 17.5 promises such a thread nothing about any field.

Java 21's compiler checks for this. javac -Xlint:this-escape warns "when a constructor invokes a method that could be overriden in an external subclass" (its help text). With Gauge public:

On the file above, where Gauge is package-private, it printed nothing: no subclass in another package can extend it, so the lint doesn't look. An escape within one package goes unreported.

The fix is to finish building before anyone can see the object. The constructor only assigns (Gauge's now takes just the name), and a factory registers what the constructor returned:

this escapes in less visible ways too, with the same fix. A constructor that starts a thread gives it an edge for the writes before start() only (unit Definition of happens-before relationships), not for the assignments after it. A lambda or an inner-class listener that uses a field captures this, so subscribing it from a constructor publishes the object. So does adding this to a static collection.

Immutable Objects Need No Edge; Effectively Immutable Ones Need One Safe Publication


KindWhat it isTo share it
immutableevery field final, this doesn't escape, nothing reachable changes after constructionany reference, even a racy one
effectively immutablemay have plain fields, but nobody changes it after publishing itone safe publication, then no locks
mutablechanges after publicationa safe publication, and a lock or a thread-safe class for every later access (unit Visibility issues and proper synchronization techniques)


The RateTable of the idioms fills a HashMap and is never touched again: effectively immutable. Behind a volatile field it is correct, and requests read it without a lock. To survive a racy reference too, it must become immutable, and a record is not enough on its own:




A record's fields are final, but Zone's list is the loader's list, and the loader's add came after the constructor. JLS 17.5 covers the list as it was when the constructor finished, so a request that got the zone through a race may see two countries, three, or an ArrayList in the middle of growing. Collections.unmodifiableList is a read-only view of the same list, not a copy. List.copyOf copies inside the constructor, so the copy is reached through a final field and nobody can change it. A map of lists needs every inner list copied as well: copying only the outer map leaves the inner lists shared.

  1. 

    Concept check
    

    Check yourself: publishing objects safely
    

      

    • An effectively immutable object is correct after one safe publication with no locks on reads, but not through a racy reference.
      • 

    • A thread that sees an object after its constructor finished is guaranteed its final fields, and what they reach as of that moment, even through a race; plain fields of the same object get no guarantee.
      • 

    • A reference written with no happens-before edge may reach a reader before the writes that built the object, though the reference write itself is atomic; a run that never shows it proves nothing.
      • 

    • Safe publication is a release by the writer after building the object and the matching acquire by the reader: a volatile or AtomicReference field, one lock on both sides, a concurrent collection, a static initializer; it covers the writes made before the release.
      • 

    • A static initializer publishes to every thread that uses the class, and one that throws leaves the class failed: NoClassDefFoundError on every later use until restart.
      • 

    • A thread started in a constructor gets an edge for the writes before start() only, so it may read the fields assigned after it, final ones included, at their defaults.

Summary


  • An atomic reference write is not a safe handoff. Without an edge, a reader may get the reference and see the object's fields at their defaults. The JLS allows it; 100 million racy publications on x86 didn't show it, so a test can't stand in for the edge.
  • Safe publication is a release by the writer after construction and the matching acquire by the reader: a volatile or AtomicReference field, one lock on both sides, a concurrent collection, a static initializer. A static initializer that throws fails every later use of its class.
  • final fields are guaranteed through a race, with what they reach as of the end of the constructor. Plain fields of the same object are not.
  • A constructor that lets this escape gives up that guarantee, and even on one thread shows a subclass's final fields at their defaults. Build first, then register or start.
  • Immutable objects can be shared through any reference; effectively immutable ones need one safe publication. A record holding a caller's list is neither until it copies the list.

Design Note: Why final Got Its Own Guarantee


Before Java 5 the memory model gave final fields no special treatment. The JSR-133 FAQ's example is String, which then kept an offset into a shared character array: a thread could see a substring's offset first as its default, 0, and later as 4, so "/tmp" could read first as "/usr". JSR-133 fixed it by freezing final fields when the constructor ends, which lets an immutable class skip synchronization entirely.


The freeze is tied to the constructor. Nothing the constructor lets out early and nothing changed later through a final reference is covered, so an immutable class needs both: no escape, and copies of whatever it was handed.
