A Tool That Makes Two Threads Collide on Every Trial

The outcomes below need two threads to touch the same fields within nanoseconds of each other. Litmus makes that happen on every trial: both threads wait for each other at a spin barrier, then each runs its actor against a fresh Cell and records what it read in r1 or r2.

Each example below ran in its own JVM with 10,000,000 trials. How often production hits an outcome depends on how often two threads collide.

A Thread Keeps Its Own Order; Another Thread May See Its Accesses Reordered

Within one thread, the compiler and the processor keep only the order that thread can observe. Stripped to its accesses, the pool is this test, called store buffering: each thread writes its own field, then reads the other's.

Before you look: which of the four outcomes can't happen if each thread runs its two lines in order?

r1=0 r2=0 needs both reads to run before both writes, and no interleaving of two in-order threads does that. It came up in 23% of the trials.

The JLS allows it. Within a thread, the rule is intra-thread semantics (JLS 17.4): the thread must behave as its program order says, as far as the thread itself can tell. c.x = 1 and r1 = c.y touch different fields, so doing the read first changes nothing thread 1 can observe, and the compiler, the JIT and the processor may all do it. JLS Example 17.4-1 makes the same point with a read followed by a write. Another thread can tell, and the JMM makes promises to other threads through happens-before and the order of synchronization actions (unit Definition of happens-before relationships): a program free of data races behaves as if sequentially consistent (unit Overview of the Java Memory Model), and this one has two races.

In the pool, both threads read the old value, both proceed, and the request queries a closed connection. A single-threaded test can't show it.

The Processor's Store Buffer Lets a Read Overtake an Earlier Write, with No JIT at All

The reordering doesn't need a compiler. Under -Xint nothing is compiled, and the interpreter runs the bytecode in order:

No compiler moved anything, and both reads still missed both writes. A core doesn't wait for a store to reach the cache: it puts the store in its own store buffer and goes on to the next instruction, and the buffer drains to the cache a little later. A load that comes next can run while the store is still in the buffer, so to every other core the read happened first. The core's own loads check its buffer before the cache, which is why the thread itself always reads what it just wrote.

The caches stay coherent throughout. What hides the write is a queue in front of the cache, not a stale copy in a thread's "working memory" (unit Shared memory and thread-local memory).

On x86 the buffer drains in program order and loads aren't reordered with other loads, so other cores see one core's stores in the order it made them; the next section's interpreted run agrees. That is why switching off the JIT doesn't fix the pool: the swap it suffers is made by the hardware.

Other processors differ. ARM and POWER allow more reorderings in hardware than x86 does, so a race that x86 never shows can appear there.

The JIT Reorders Too, So x86 Shows a Reordering Its Hardware Doesn't Make

The compiler may reorder plain accesses as freely as the processor. HotSpot compiles hot code first with C1, then with the optimizing C2. The test is message passing: thread 1 writes the data (x), then a ready flag (y); thread 2 reads the flag, then the data. A reader that sees the flag should see the data.

r1=1 r2=0: the flag was set and the data was not. Interpreted, and with C1 only, it never happened:

A separate run moved the writer into a method of its own, writeDataThenFlag (ex/run-1.txt). The default JIT gave 6,552 such trials, C2 alone (-XX:-TieredCompilation) 14,220, C1 alone 0, and 0 once -XX:CompileCommand=exclude kept that one method interpreted. The reordering came from the C2-compiled writer, which intra-thread semantics allows: the two stores go to different fields.

Here, a reader that trusts the flag uses data that isn't there in about one collision in 1,500, but only once C2 has compiled the writer. A test run cold, or under -Xint, passes. Another JIT or another platform may reorder elsewhere, so a pass on x86 proves little. Reading a field once before a loop instead of on every iteration is the same freedom (unit Volatile keyword). A bug that disappears under -Xint suggests the compiler, though the interpreter's different timing can hide a race too (unit Visibility issues and proper synchronization techniques).

volatile on Every Access That Needs Ordering Rules Out Both Reorderings

Make the fields volatile and neither forbidden outcome appears. In sb-volatile both fields are volatile (vx, vy); in mp-volatile only the flag is (c.x = 1; c.vy = 1; against c.r1 = c.vy; c.r2 = c.x;):

Volatile reads and writes are synchronization actions, and JLS 17.4.4 puts all of them in one total order that agrees with each thread's program order. A volatile read sees the last write to its field before it in that order (JLS 17.4.7). In store buffering, whichever volatile write comes second in that order is followed, in its own thread, by a read that comes later still, and that read sees the other write. In message passing, the data write comes before the volatile flag write in program order, and the flag write happens-before the read that sees it, so the data read sees 1.

Spot the Problem: One Volatile Flag Out of Two

A review of the pool makes inUse volatile and leaves closing plain, since message passing needed only one volatile field. In the test, thread 1 is the request (vx for inUse) and thread 2 the shutdown (y for closing). Does this fix the pool?

Thread 2's plain write and its read are still free to swap, and the JMM doesn't stop thread 1's plain read from moving ahead of its volatile write either. Message passing needs one ordered edge, from a write to the read that sees it. Store buffering needs each thread's write ordered before its own read, so both fields must be volatile, or both checks made under one lock (unit Synchronization and memory consistency).

A Racy Reference May Expose an Object Before Its Constructor's Writes Land

Thread 1 builds an object and stores it in a plain field; thread 2 reads the field and, if the reference is there, both fields:

r1=1 r2=0 would be a reference to an object whose constructor's writes the reader did not see. The first of three runs:

The other two runs also gave 0: none in 30,000,000 trials. The JLS still allows it: the constructor's writes and the store of the reference are plain writes to different variables, the same freedom the JIT used on x and y above, and only final fields come with a guarantee for a reader that gets the reference through a race (JLS 17.5, unit Proper synchronization to ensure memory visibility). A zero on one machine and one JVM is not a property of the code: a weaker processor or another JIT may produce it. Double-checked locking without volatile (unit Synchronization and memory consistency) bets on it never happening. Publish through a volatile field, a lock or final fields.

Acquire/Release Orders a Handoff, Not a Write Followed by a Read

VarHandle gives one access to a plain field a stronger mode. Release/acquire is enough to hand data over, not to keep a thread's read behind its own earlier write:

The javadoc defines the modes in steps: an acquire read and the accesses after it are ordered after a matching release write and the accesses before it; volatile accesses are, in addition, totally ordered with each other. Message passing held. Neither stops an acquire read from overtaking a release write that comes before it in the same thread, which is the store buffer's reordering, so store buffering failed 610,780 times. VarHandle.fullFence() orders every access before it with every access after it and, like volatile, gave 0.

Use release/acquire for one-way handoffs, such as a producer publishing a filled buffer, when measurement shows volatile costs too much. Use volatile, or a lock, when each thread writes and then reads what the other wrote.

Summary

  • A thread keeps its own order; another thread may see its accesses reordered. Two threads that each write a flag and then read the other's can both read the old value.
  • The processor's store buffer lets a read overtake an earlier write. It happens with no JIT at all; the thread itself still reads its own write.
  • The JIT reorders too. On x86 it made a ready flag visible before the data, which the hardware alone never did.
  • volatile on every access that needs ordering rules out both reorderings. One volatile field is enough to hand data over, not for a write-then-read handshake.
  • A racy reference may expose an object before its constructor's writes land. Not observed here; allowed by the JLS, so publish safely.
  • Acquire/release orders a handoff, not a write followed by a read. Store buffering needs volatile or a full fence.

Design Note: Why the JMM Doesn't Promise Sequential Consistency to Every Program

Java could have promised that every program runs as some interleaving of its threads, races included. Every plain store would then need at least what the fullFence() run added, an ordering against the loads after it, and the JIT could no longer reorder, merge or keep in a register any field access another thread might see. Most fields are touched by one thread at a time, so all code would pay for the few that are shared.

The JMM makes the opposite trade. Plain accesses get no ordering promise to other threads, and the program marks the few that need one with volatile, a lock, final or a VarHandle mode. The cost is what this page measured: a missing mark is not a compile error and often not a test failure. On one x86 machine it showed up in 23% of collisions for one test, one in 1,500 for another, and never for the third.

Problem statement


Your team reviews lock-free code by writing each suspicious interaction down as a tiny program: a few threads, each a list of reads and writes of shared variables. LitmusModel lists every combination of values those reads can end with. Before it models what hardware and compilers do, it needs the baseline: the results the threads can produce when nothing is reordered, which is what the Java memory model promises a program without data races.


LitmusModel.State already performs one operation at a time and keeps memory and registers. Finish explore(state, results) in src/main/java/practice/LitmusModel.java: from state, add the registers of every finished execution to results. About eight lines in total.


When you're done, a reviewer can ask whether two threads that each set their own flag and then check the other's can ever both find the other's flag unset, and get an answer they can trust.

Problem statement


This practice continues the previous one: the starter is its solution, with a second machine added. The baseline model can't explain what the team saw on an x86 server running in the interpreter: two threads that each wrote a flag and then read the other's both read 0, while a reader that saw a ready flag always saw the data written before it.


outcomesWithStoreBuffers models that server. Each thread's writes go into a buffer of its own and reach shared memory later, one at a time; at every step the checker tries both a thread's next operation and moving one buffered write to memory. A new operation, fence(), waits until the thread's own buffer is empty. Finish the three TODO methods of Buffered in src/main/java/practice/LitmusModel.java:


  • load(t, variable): the value thread t reads now;
  • canPerformNext(t): whether thread t's next operation may run now;
  • drainOne(t): a copy in which one of t's buffered writes has reached memory.


When you're done, the checker allows both of the server's outcomes above and no outcome the server could not produce. About ten lines in total.
