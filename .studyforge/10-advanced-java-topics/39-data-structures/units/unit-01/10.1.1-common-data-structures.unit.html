An order book keeps 100,000 resting orders in a LinkedList, because the usual Big-O table gives LinkedList O(1) inserts and new orders go in the middle through add(index, order). Latency climbs with the size of the book. Sampling the inserting thread's stack 1,000 times at 100,000 orders found it in LinkedList.node(int) 997 times: the walk to the index, not the insert.

The table counts steps and leaves out what each step costs on real hardware, and what the JDK's classes do at their edges. Growth rates themselves are unit Big O Notation (analyzing algorithm complexity), and the concurrent collections are unit 6.5.

LinkedList Loses to ArrayList Unless You Already Hold the Position

Four operations, each on an ArrayList and a LinkedList of Integer at three sizes: get(i) at random indexes, add(size/2, x) followed by remove(size/2), a for-each over the whole list, and a ListIterator walk that inserts after every 10th element, followed by a second walk that removes them again (that column is per inserted element, both walks included):

At 100,000 elements ArrayList inserted and removed in the middle 30 times faster.

add(index, x) on a LinkedList is two steps. The link itself is O(1), but first node(index) walks from whichever end is closer, following one pointer per element, and each node is a separate object the CPU has to fetch. ArrayList also does O(n) work, shifting the tail of its array with one System.arraycopy over contiguous memory; at 100,000 elements an add and a remove in the middle took about 4 µs together. The for-each column shows the same effect with no index at all: LinkedList took two to eight times as long per element, even though its nodes were allocated one after another.

LinkedList wins one column: inserting through an iterator at a position the code already holds. From 10,000 elements on its cost per insert stayed flat while ArrayList's grew with n. Use LinkedList for a long list edited during a walk, and ArrayList for one read by index or iterated. The order book finds each position by index, so it is the second kind: in this run an insert and a remove in the middle took ~118 µs on the LinkedList and ~4 µs on an ArrayList.

Memory. Each LinkedList element is a node object with two links besides the element; an ArrayList holds one reference per slot plus spare capacity. Unit Heap and Stack Memory Management measures object sizes.

ArrayDeque Is the Stack and the Queue; Stack Is a Synchronized Vector

java.util.Stack predates the collections framework. It extends Vector: pop and peek are synchronized, push goes through Vector's synchronized addElement, and it inherits the whole List API:

Both pop c first, but a Stack iterates bottom-first, in Vector order, while an ArrayDeque used with push iterates from the top. Code that lists "the last three actions" by iterating a Stack shows the oldest three. Anyone holding the Stack can also insert under the bottom or read by index.

The lock costs time even with one thread. Pushing 1,000 elements and popping them again:

Stack was ten times slower than ArrayDeque. Most of the difference points to the monitor: ArrayList and Vector, whose code is close to the same, took 2.6 and 38.4 ns for the same add and remove at the end. An uncontended synchronized call still acquires and releases the monitor; biased locking, which once made that nearly free, was disabled in JDK 15 (JEP 374) and removed in JDK 18. The lock doesn't make the stack thread-safe either: if (!stack.isEmpty()) stack.pop() is two calls, and another thread can pop between them (unit 6.5 covers the concurrent deques).

Which End a Deque Method Uses

ArrayDeque is both a stack and a queue, and the method names decide which. push, pop, peek and poll all work on the head; add and offer work on the tail. Mixing the families turns the stack into a queue:

On an empty deque pop() throws, and poll() and peek() return null. ArrayDeque refuses null elements, because null is how poll says "empty"; Stack accepts them.

  1. Coding practice

    Make Undo take back the right edit

    • On a Deque, push, pop, peek and poll use the head and add and offer the tail, so add with pop is a queue; pop on an empty deque throws while poll returns null, and ArrayDeque refuses null.
    • java.util.Stack extends Vector: it iterates bottom-first, exposes the List API, and pays for synchronized calls even with one thread, while ArrayDeque with push iterates from the top.

Colliding HashMap Keys Stay Fast Only When They Are Comparable


An API gateway parses each request's JSON fields into a HashMap. "Aa" and "BB" have the same String.hashCode(), so every string made of 13 such blocks has the same hash too: 8,192 distinct names, one hash code. An attacker can send all of them in one request. We look each name up, once with String keys and once with the name wrapped in a record:




With the same names and hash codes, the record keys were 160 times slower per lookup. The first build of the map, which the gateway does for every request, took 278 ms of CPU for about 210 KB of field names.


Since Java 8, a bin of colliding keys turns into a red-black tree. The tree is ordered by hash first; among keys with equal hashes, HashMap uses compareTo only when the key's class implements Comparable of itself, as String does. A record wrapping a String isn't Comparable, so the tree has nothing to descend by and a lookup may search both subtrees: on average half the bin for a key that is there, all of it for one that isn't, as in the linked list it replaced. Counting equals calls per get, with two key classes whose hashCode() returns 42 and whose only difference is that the second implements Comparable<ComparableKey>:



PlainKey compared half the bin per lookup; ComparableKey's count grew by about three per tenfold n: linear against logarithmic. The last row is a record with a working hashCode, for scale. A compareTo that returns 0 for two unequal keys gives the tree nothing to go on. At 1,000 keys, a key class whose compareTo compares hash codes, and one that implements raw Comparable, both needed 501.5 equals calls per get, the same as PlainKey. Ordering by the fields equals compares is what helps.


Reading HashMap's private table by reflection (with --add-opens java.base/java.util=ALL-UNNAMED; unit Accessing Fields, Methods, and Constructors covers why that flag is needed) while adding colliding keys to a new map:



A bin already holding 8 entries is converted on the next insert, but only in a table of at least 64 buckets; a smaller table is doubled instead. So the 9th and 10th keys resized the table and the 11th converted the bin. The fix for the gateway is to keep String keys or make the wrapper implements Comparable<FieldName>, and to cap the number of fields a request may carry.

A PriorityQueue Is Ordered Only at Its Head


A scheduler keeps jobs in a PriorityQueue, and its status page prints the queue. Eight priorities, added one at a time:




The queue is a binary heap in an array: each element is no larger than its two children, at indexes 2i+1 and 2i+2. toString, the iterator and stream() walk that array as it is (the heap layout is from the JDK source; the javadoc promises only the head), so a "next three jobs" panel built from stream().limit(3) shows 11 where 7 is due. Only peek and poll see the order, because poll moves the next-smallest element to the root each time; that costs O(log n) per element. For the k smallest without emptying the queue, poll from a copy or sort a snapshot; the PriorityQueue javadoc suggests Arrays.sort(pq.toArray()).


The last line is jobs t1 to t6 with priorities 2, 1, 2, 1, 2, 1. Priority 2 came out t1, t5, t3, not in the order added. The javadoc says ties are broken arbitrarily. A queue that must be first-come-first-served within a priority needs a sequence number in the comparator.

TreeMap Answers "Which Key Is Nearest?", Compares with compareTo, and Returns Live Views


A price list keyed by the date each price takes effect: what was the price on 10 April? A HashMap can only answer for the exact dates it holds. A TreeMap keeps its keys sorted and answers questions about neighbours:




floorEntry(d) is "the price in effect on d": the greatest key at or below d. floor and ceiling include an equal key and lower and higher don't, so on the change date itself lowerEntry returns the old price. Before the first key, floorEntry returns null, and code that calls getValue() on it fails with a NullPointerException. The two-argument subMap(from, to) includes from and excludes to, like List.subList; the four-argument form says which ends it wants.


subMap, headMap and tailMap return views, not copies:



A key put into the map after the view was taken shows up in the view, and a key outside the view's range can't be put through it. Copy the view (new TreeMap<>(view)) to keep a snapshot.


A TreeMap or TreeSet compares keys with compareTo (or its comparator), not with equals. BigDecimal 1.0 and 1.00 are not equal, because their scales differ, yet compareTo returns 0, so the TreeSet kept one of them and the HashSet both. The TreeMap javadoc calls this an ordering inconsistent with equals: the map still works, by its comparator's rules, and stops obeying the Map contract.

Summary


  • LinkedList loses to ArrayList unless you already hold the position. add(index, x) walks to the index first; only ListIterator.add during a walk is cheaper than ArrayList's array copy.
  • ArrayDeque is the stack and the queue; Stack is a synchronized Vector. Stack iterates bottom-first and was ten times slower uncontended; on a deque, add plus pop is a queue.
  • Colliding HashMap keys stay fast only when they are Comparable. Its tree bins order equal hashes by compareTo; without it a lookup searches through the bin, 160 times slower in our run.
  • A PriorityQueue is ordered only at its head. Its iterator, toString and stream follow the heap array, and ties come out in no particular order.
  • TreeMap answers nearest-key questions with compareTo, and its range methods return live views. floor/ceiling include the key, subMap(a, b) excludes b, and keys equal by compareTo are one key.

Design Note: Why Stack and LinkedList Are Still There


Stack and Vector date from Java 1.0, when the JDK's collection classes (Vector, Hashtable) were synchronized. Java 1.2 added the unsynchronized framework and Java 6 added Deque and ArrayDeque, whose javadoc says it is "likely to be faster than Stack when used as a stack, and faster than LinkedList when used as a queue." Neither old class was deprecated: removing a public class from the JDK breaks every program that names it, and code written against Vector's API in 1997 still compiles. The cost is that the JDK's simplest name for a stack is the one to avoid, and LinkedList, which also implements Deque, looks like a natural queue. In the push-and-pop run ArrayDeque was nearly twice as fast as LinkedList, and it allocates no node per element.
