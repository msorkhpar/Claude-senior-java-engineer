The payments team upgraded its shared retry library from version 1 to version 2. The build was green, javac printed nothing, and in production every retry now waits a full second: the team's backoff of 100, 200, 400 ms no longer runs. Version 2 had added a parameter to the method the team overrode.

The annotations in java.lang are instructions to javac. @Override and @Deprecated add a check; @SuppressWarnings and @SafeVarargs switch one off. Every output is from Java 21. @FunctionalInterface is in unit Using lambda expressions with functional interfaces, and how long an annotation survives is unit Annotation Retention Policies (SOURCE, CLASS, RUNTIME).

@Override Turns a Method That Stopped Overriding into a Compile Error

Version 1 of Retry declares protected long delayMillis(int attempt), version 2 delayMillis(int attempt, Exception cause). Both return 1000, and a final plan(n) lists the delay for each of n attempts. The team's subclass:

Compiled and run against each version:

Against version 2, delayMillis(int) matches no method of Retry, so it is a new method of Backoff, an overload that nothing calls, and javac has nothing to report. With @Override on it, the same upgrade fails the build on the line that has to change:

A method overrides by its signature, with or without the annotation. @Override adds a claim, "this overrides something", and javac checks it against the supertypes each time the subclass compiles, so it also catches a change someone else makes to the supertype later. The check runs only at compile time: the annotated Backoff, compiled against version 1 and run with version 2's Retry.class on the class path, printed delays: 1000 1000 1000 1000 too. A plugin built against one version of a library and deployed into a host that ships another gets no check at all.

A misspelt name does the same to the methods every class overrides. Here equals is right and hashCode is written hashcode:

new AccountId("acc-1042") and new AccountId(" ACC-1042 ") both go into a HashSet:

HashSet calls hashCode(), which is still Object's identity hash, so the two equal IDs almost always have different hash codes, and HashSet never calls equals. @Override public int hashcode() fails with the same error. A Use of a forRemoval Element Warns by Default; Plain Deprecation Is Only a Note

A payment library deprecates two methods, one of them for removal:

Checkout calls charge(1999) on line 4 and refund(500) on line 5. Before reading on: which of the two does a plain javac report, and does a build with -Werror pass?

javac reports each use of a forRemoval element as a [removal] warning; -Xlint:-removal turns them into a note. Uses of plainly deprecated elements are folded into one note per file, and listed only with -Xlint:deprecation. A note isn't a warning, so -Werror doesn't count it. A team that builds with -Werror and no -Xlint can call charge for years without a failed build. The release that sets forRemoval = true fails it at every call, which is what the library author wants.

The two levels are also suppressed separately. In Refunds, one method carries @SuppressWarnings("deprecation") and another is itself @Deprecated; both call charge and refund. A test double in TestGateway overrides refund:

"deprecation" silenced charge and not refund, which takes @SuppressWarnings("removal"). A deprecated caller is exempt from deprecation warnings but not from removal warnings (JLS §9.6.4.6), and overriding a for-removal method counts as a use. Unit Java 17 (LTS) shows the JDK's own [removal] warnings on the Security Manager, and a --release flag that hides them.

@SuppressWarnings Covers Its Whole Declaration, Including Warnings Added Later

A service reads its ports from parsed YAML, a tree of maps, lists and scalars. The author cast the http list once, decided the schema made it safe, and suppressed the warning on the method. A later release added the admin line:

javac Ports.java and javac -Xlint:unchecked Ports.java both print nothing. The run:

The YAML had the port quoted, so admin holds the string "9090". Storing a raw List in a Map<String, List<Integer>> is an unchecked conversion, and the map now claims integers it doesn't hold. That heap pollution fails at line 20, where javac inserted a cast to Integer into a line that has none. The method's annotation covered the new line, because a suppression applies to everything inside the declaration that carries it, code written after the annotation included.

@SuppressWarnings goes on declarations, not statements, so the narrowest scope is a local variable declared for the purpose:

Now a plain javac prints Note: Ports.java uses unchecked or unsafe operations., and -Xlint:unchecked names the new line, line 13 of the changed file:

The suppressed cast is still unchecked: (List<Integer>) checks that the object is a List and nothing about its elements. Code that converts untyped input checks each element instead, and then needs no suppression.

javac silently ignores a key it doesn't know. On a method with an unchecked cast, @SuppressWarnings("uncheked") and @SuppressWarnings("all") both left -Xlint:all reporting [unchecked] unchecked cast: "all" is not a javac 21 key, whatever an IDE does with it.

    Make bad rate-limit configuration fail at load

    • A cast to a parameterized type checks only the class, so code that converts untyped input checks each element and needs no suppression; otherwise the ClassCastException comes later, at a read with no cast.

@SafeVarargs Removes the Warning at the Cause, and javac Doesn't Check the Promise


A label printer builds batches with a varargs factory, and a retry path wraps one label in a batch through a generic helper:




Inside single, T is erased, so the array javac builds for Batch.of(item) is an Object[] (unit Method parameters and return types shows why). Batch keeps it, items() returns it as a T[], and the cast javac inserted into print's loop fails. The trace names print and main, not single, where the wrong array was made.


With the annotation replaced by a comment, -Xlint:all points at the cause:



With it, a plain javac prints nothing, and -Xlint:all only this:



@SafeVarargs is the author's statement that the method only reads the elements of its array and doesn't let the array escape. javac takes it on trust and stops warning every caller, line 13 included. of keeps the array and items() hands it out, so the statement is false. The [varargs] lint doesn't check it either: it flags any use that passes or returns the array itself, and element reads, length and a for-each loop draw nothing. The fix, a List<T> field filled with List.of(items) and returned by items(), prints label C-33 and draws the same [varargs] warning. Unit Method parameters and return types lists where the annotation is allowed: constructors and methods that can't be overridden.

Summary


  • @Override turns a method that stopped overriding into a compile error. Without it, a supertype change or a misspelt name leaves a new method that nothing calls; the check runs only when the subclass compiles.
  • A use of a forRemoval element warns by default; plain deprecation is a note. -Werror ignores the note, "deprecation" doesn't suppress [removal], and a deprecated caller is still warned about removal.
  • @SuppressWarnings covers its whole declaration. On a method it hides the next unchecked line too; on a local variable it hides one cast. javac ignores unknown keys, "all" included.
  • @SafeVarargs removes the warning at the cause, unchecked. A method that lets its varargs array escape as a T[] pollutes the heap, and the ClassCastException lands in code with no cast.

Challenges


  1. Your build passes -Werror. Which -Xlint keys would you add, and what does each one cost on a codebase that has never seen them?
  2. A host application loads plugins built against older versions of its API. What would catch a plugin method that no longer overrides anything, since the plugin's own @Override can't?
  3. You maintain a library and want to remove a method in two releases. What do you ship in each release, and which of your users' builds fail at which step?
  4. Find every @SuppressWarnings on a method or class in a codebase you know. How many would still be needed on a local variable?


Design Note: Why javac Trusts @SafeVarargs


Whether a generic varargs method is safe depends on what it does with the array, and the array can leave through a field, a return value, or a call into code javac isn't compiling. Java 7 chose a promise over an analysis: the author states it once, only on a method no subclass can override, and every caller stops warning. The [varargs] lint is what remains of the check, and it can't tell a copy from a leak.


A false promise fails at the first read with the wrong type, in code that did nothing wrong, and the warning that would have pointed at the cause is the one the annotation removed.
