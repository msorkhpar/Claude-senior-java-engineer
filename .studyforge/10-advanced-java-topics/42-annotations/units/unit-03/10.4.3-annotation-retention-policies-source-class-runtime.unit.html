A payments team writes its own @Transactional and a small interceptor that opens a transaction around every method carrying it. The build is clean, even with -Xlint:all, and the tests of the transfer logic pass. In production a transfer fails between the debit and the credit, and the debit stays. The interceptor's log has no BEGIN for any call: it never found the annotation.

An annotation's retention policy, @Retention(RetentionPolicy.X) on its declaration, decides whether it reaches the class file and whether reflection sees it (unit Custom Annotation Creation covers the rest of a declaration). Every output below is from Java 21 (Temurin 21.0.12).

SOURCE Stops at the Compiler, CLASS Stops in the Class File, Only RUNTIME Reaches Reflection

Three annotations that differ only in their retention, on one method:

javap -v -p -cp out Payments shows where the other two went (the method's part of its output):

javac wrote AuditedRuntime into a RuntimeVisibleAnnotations attribute, the one reflection reads. AuditedClass went into RuntimeInvisibleAnnotations, value and all, which reflection doesn't read. AuditedSource isn't in the class file: the name appears nowhere in javap -v's output, constant pool included.

The other two have their own readers. SOURCE annotations are for the compiler and for annotation processors: @Override (unit Built-in Annotations (@Override, @Deprecated, @SuppressWarnings)) is SOURCE, and a processor run over this file (unit Annotation Processing and Code Generation builds one) reports all three annotations on refund. CLASS annotations are for tools that read class files, as javap just did.

The costly misreading is that CLASS means "compile time only". A CLASS annotation ships in every class file that carries it, with its values: value="refunds" above. A note such as @Review("fraud check skipped for partner 12") with CLASS retention can be read by anyone who runs javap -v on the jar; only SOURCE retention keeps it out.

An Annotation Without @Retention Is CLASS, and Reflection Returns null for It

The opening's @Transactional, with the interceptor reduced to its check:

javac -Xlint:all printed nothing for this file. The interceptor can't tell an invisible annotation from no annotation, so nothing fails. javap -v shows the annotation in the class file, under RuntimeInvisibleAnnotations.

The Retention javadoc gives the rule: with no @Retention on the declaration, the policy is CLASS. Asking the annotation type for its @Retention returns null, not CLASS, so code that checks a policy has to treat null as CLASS itself. Adding @Retention(RUNTIME) fixes it:

A test that calls transfer() directly passes with either declaration. Only a test that goes through the interceptor and checks that a transaction was opened tells them apart.

javac Applies Retention When It Compiles the Annotated Class, and Reflection Checks It Again

Suppose the fix goes into a shared library: Audited changes from CLASS to RUNTIME and the library is released, but the service whose Orders class carries @Audited isn't rebuilt. Audited.java is the two lines import java.lang.annotation.*; and @Retention(RetentionPolicy.CLASS) @interface Audited { }, with RUNTIME in the second step. We compile all three files, then change and recompile Audited alone, then recompile Orders, then set Audited back to CLASS and recompile it alone. Check prints the annotation on Orders.cancel after each step:

javac chose the attribute for @Audited when it compiled Orders, from the retention Audited had at that moment. Recompiling Audited doesn't touch Orders.class, which still says invisible. The last step shows that reflection checks the type too: Orders.class now has @Audited under RuntimeVisibleAnnotations, but the loaded Audited is CLASS, so reflection returns null. An annotation reaches reflection only when the class file's attribute and the annotation type's current retention both say RUNTIME.

So raising a retention to RUNTIME takes effect only after every user is recompiled. Lowering it hides the annotation from reflection at once, but its values stay in old class files until they are recompiled.

A RUNTIME Annotation Whose Class Is Missing at Run Time Disappears Without an Error

An annotation's jar is often on the compile class path and missing from the deployment: a provided dependency the server was supposed to supply, or a plug-in class loader that can't see the API. Here a new Audited, RUNTIME and with a value, is on Orders and on cancel. Scan reads the annotations the way a framework's class scanner does. Then Audited.class is deleted and Scan runs again:

Reflection returned empty arrays and cancel ran, with no exception and no warning. Orders.class still holds Audited(value="cancellations") under RuntimeVisibleAnnotations; reflection drops an annotation whose type it can't load. If the annotation meant "audit this", auditing is off, and the first sign is an audit table with no rows.

Naming the missing type does fail: getAnnotation(Audited.class) throws java.lang.NoClassDefFoundError: Audited at that line. And when the annotation type is present but a class named in one of its elements isn't, the annotation comes back and fails only when that element is read:

With GatewayTimeout.class deleted:

The AnnotatedElement javadoc specifies this TypeNotPresentException, and an EnumConstantNotPresentException for an enum constant that no longer exists. A start-up check that names each annotation type the service relies on, reads its elements, and asserts that the annotation is present where it is expected turns a missing jar into a failed start, and catches a retention that is too short as well.

Summary

  • SOURCE stops at the compiler, CLASS in the class file, RUNTIME reaches reflection. A CLASS annotation ships with its values; only SOURCE keeps a note out of the jar.
  • No `@Retention` means CLASS. getAnnotation returns null, javac doesn't warn, and an interceptor silently does nothing.
  • Retention is applied when the annotated class is compiled and checked again when it is read. Raising it to RUNTIME needs every user recompiled.
  • A missing annotation class makes the annotation vanish; the class still loads. Naming the type throws NoClassDefFoundError; a missing class inside an element throws TypeNotPresentException when that element is read.

Challenges

  1. Your service relies on five annotation types from three libraries. Write the start-up check that fails when any of them can't be read. Which failures on this page does it catch, and which still need a test through the interceptor?
  2. A build step leaves provided jars out of the container image. How would you find, from the class files alone, every annotation type your classes carry that the image doesn't contain?
  3. A library wants its annotation's values out of its users' class files without breaking users compiled against the RUNTIME version. What do those users' class files and reflection show at each step of the change?

Design Note: Why a Missing Annotation Is Ignored

The language treats an annotation as information attached to a program element, with no effect at run time of its own (JLS 9.7). The JVM loads a class without loading its annotation types, and reflection skips the ones it can't load. That lets one class carry RUNTIME annotations for frameworks that one deployment includes and another leaves out, each needing its jar only where it is read.

This costs you when an annotation does change behaviour, through an interceptor or a scanner. Then its absence changes behaviour too, and nothing reports it. A retention that is too short fails the same way. Neither the compiler nor the JVM can tell that you meant the annotation to matter, so the check has to come from the code that depends on it: a test through the interceptor, or a start-up check that names the types it needs.
