The order service finds its commands at startup: it scans the class path for classes marked @Command("refund"), @Command("audit") and so on, and creates each one through its no-arg constructor. A refactoring made Audit's constructor private. The build passed, every test that didn't create an Audit passed, and the service failed in production on the first audit request.

An annotation processor moves that work into the compile. javac runs it; it writes the registry as Java source and can refuse the bad class before anything ships. Declaring annotations is unit Custom Annotation Creation and retention is unit Annotation Retention Policies (SOURCE, CLASS, RUNTIME): a processor reads source, so RetentionPolicy.SOURCE is enough for @Command. Reading annotations at run time through reflection is units Class and Object Introspection to Reflection Performance Considerations.

Processing Runs in Rounds, and a Generated File Is Processed in the Next One

A second processor in the build, CrudProcessor, generates a delete command for every entity marked @Crud. For Customer it writes:

That class carries @Command, but it doesn't exist when IndexProcessor reads the sources. Here the index processor keeps every @Command it sees in a field, found, and logs each call with a call counter and the simple names of the round's root elements and @Command classes:

Round 1 hands the processors the sources. Every file created in a round is an input of the next round, so DeleteCustomer arrives in round 2, where its @Command is seen. Rounds go on until one creates nothing, and then a last round runs with no inputs and processingOver() true.

The Processor javadoc adds that a processor called in one round is called in every later round, including the last, even with no annotations for it, and that javac creates the processor object once per compile, not once per round. That is why found carries the commands from round to round.

The fix keeps collecting in every round and writes once, when processingOver() is true:

CommandIndex has no annotations, so no processor needs to see it, and javac still compiled it. With -Werror the same compile failed on that warning, so a build that sets it must write the file earlier, from a round it can tell is the last to bring @Command classes. A generated file whose annotations a processor must see has to be written before the last round.

The Filer javadoc counts the initial inputs as created by a "zeroth round", so they can't be created again. Nor can a processor edit a class in place: Element has only getters. (Lombok adds methods to the classes being compiled by working on javac's internal syntax trees, outside this API.) The Filer javadoc's alternative is to generate a subclass of the user's class, or a superclass that the user's class names in its own extends.

Summary

  • A processor is code javac runs during the compile. It reads declarations, not objects, and what it adds are new files that compile with the sources. Name it with -processor or a processor path: javac 25 no longer runs one found only on the class path.
  • Report errors through the `Messager` with the element. javac then points at the user's line. Without the element there is no location, and an error in generated code points at a file nobody wrote.
  • Processing runs in rounds. A generated file is processed in the next round, and one processor object sees every round, the last with processingOver() true.
  • The `Filer` creates each file once and never replaces an input. An aggregate file written per round fails with FilerException once a later round brings more; collect in a field and write once.

Challenges

  1. The check found a private constructor. List what else new X() in generated code needs from X (not abstract, not an inner class, type arguments), and which of these a Messager check reports more clearly than the compile of the generated file.
  2. Your build compiles only the files that changed. The aggregate index then sees only those files' @Command classes. What do the Filer's "originating elements" give an incremental build, and what must still be compiled in full?
  3. Compare a build with IndexProcessor to a startup scan with reflection, for a service with 400 commands: measure the compile time added and the startup time saved on your machine.

Design Note: Why a Processor Can Only Add Files

JSR 269 gives a processor a read-only model of the program and a Filer that refuses to touch the inputs. The API offers no way to change a class the developer wrote, and generated code sits in files that can be opened, read and diffed.

The cost falls on the design of the user's code: code that wants generated behaviour must call a generated class (CommandIndex.create) or extend one. Lombok changes the class itself, which ties it to javac's internals.
