Two top-ups for wallet 7, one of 10 and one of 20, reach two instances of the payments service in the same millisecond. Each instance turns off auto-commit (unit JDBC (Java Database Connectivity)), reads the balance, adds its amount in Java, writes the result and commits. Both return 200 and log committed. The wallet started at 100 and now shows 120, and nothing failed.

A transaction commits or rolls back its statements together. It does not, by itself, stop another transaction from changing the same rows in between. Every run here uses H2 2.2.224, in-memory.

Read, Compute in Java, Write Back Loses an Update Under READ COMMITTED

A and B both read 100. A writes 110 and commits. What does READ COMMITTED, H2's default, do when B writes 120?

It lets B write. READ COMMITTED only promises that B reads committed data, and 100 was committed when B read it. The UPDATE sets a constant computed in Java, and the database can't tell that it came from a stale read. A's 10 is gone with no error.

A synchronized block around the read and the write (unit Monitors and synchronized blocks) excludes threads of one JVM, and the two top-ups ran on two instances. The compound action belongs with the owner of the state (unit Applying DRY in concurrent programming), and here the owner is the database. When the new value is a function of the old one, one statement does it:

A's UPDATE locked the row until A ended. B's UPDATE waited, then read the committed 110 and added 20.

SELECT ... FOR UPDATE Makes the Second Reader Wait for the First Commit

Often the new value needs Java: a daily limit, a fee table, a currency rule. Then the read has to be the statement that locks:

The lock belongs to the read. Code that reads with a plain SELECT and locks just before writing has already computed from the stale value.

The lock lasts until commit() or rollback(). An early return on "insufficient funds" that skips both leaves the row locked while the connection stays open. Every other top-up of that wallet then waits, and with H2's default the wait ended after about 2 seconds in the lock timeout shown in the page's last section.

A Version Column Turns a Lost Update into an Update Count of 0

A lock shouldn't be held while a person edits a form for five minutes: every other writer of the row waits that long. A version column lets the write itself check that nothing changed since the read:

A tops up 10, and A's beforeWrite runs B's whole top-up of 20, once, between A's read and A's write:

Nothing is thrown: the update count is the only signal, and code that ignores what executeUpdate() returns loses A's top-up as before. The retry must read again, because version 0 matches nothing on every attempt. Every writer must increment the version, or the next check passes against a changed row. JPA's @Version generates this statement and turns count 0 into an exception (unit ORM (Object-Relational Mapping) Frameworks).

The write can still wait. Here A has run its version-checked UPDATE and not committed when B's arrives; then A commits:

B waited for A's row lock, and then its version check failed against A's commit.

An Isolation Level Is What Your Database Does, and on H2 None Stops Write Skew

The SQL standard defines the three lower levels by the anomalies each must prevent, and SERIALIZABLE as equivalent to some serial order of the transactions. This program runs five interleavings of two transactions, t[0] as A and t[1] as B, after setTransactionIsolation on both. The phantom check is typical:

The other four: B reads a row A changed but hasn't committed (dirty); B reads a row twice around A's commit (non-repeatable); the lost update of the first section; and write skew. Two wallets of one family must keep 100 between them. Each transaction reads the total, 200, sees that taking 90 leaves 110, and takes 90 from its own wallet.

H2's REPEATABLE READ is a snapshot. B sees the database as of its first read, so the inserted row never appears. The standard allows a phantom at this level, and H2 prevents it.

The second writer of a changed row is refused. At REPEATABLE READ and SERIALIZABLE, B's UPDATE of a row that A changed and committed after B's snapshot fails with SQLState 40001, and the message says Deadlock detected though nothing waited. B got the same 40001 at REPEATABLE READ with balance = balance + 20, and with SELECT ... FOR UPDATE, once its snapshot had started. Code at these levels treats 40001 as "run the transaction again", like the deadlock in the page's last section.

SERIALIZABLE let write skew through. The family's wallets hold 20. No serial order of the two transactions produces that: whichever ran second would have seen 110 and refused. So H2's SERIALIZABLE is not serializable in the standard's sense. Each transaction wrote a different row, so there was no write conflict for H2 to refuse. At READ COMMITTED, reading both wallets with FOR UPDATE made B wait, then see 110 and refuse.

Databases differ. Only H2 ran here. Other databases implement these levels with other locking and snapshot rules, so run the same five interleavings against the database you ship on before you rely on a level.

A Failed Statement Undoes Only Itself; a Savepoint Undoes the Group

A nightly import writes each order and its lines in one transaction, into orders(id) and line(order_id, sku NOT NULL). Order 1's second line has no SKU:

On H2 the failed INSERT undid only itself. The transaction stayed open, and the commit kept order 1 with one of its two lines: an order the warehouse will ship short. rollback(savepoint) undid every statement since the savepoint, order 2's header and its good line included, and left the transaction open for order 3. A savepoint ends with its transaction: after the commit, rolling back to it fails with 90063.

A savepoint set once, before the loop, would undo every order since the start, the good ones too. It goes at the start of each group of statements that must stand or fall together.

On H2, a Lock Timeout Fails One Statement; a Deadlock Rolls Back the Whole Transaction

Both happen when a transaction can't get a lock, and H2 answers them differently. First a lock timeout: B's session runs SET LOCK_TIMEOUT 500, so it waits at most 500 ms. A holds wallet 7 with FOR UPDATE. B credits wallet 8, tries to debit wallet 7, and then commits:

The message says "table", but only one row was locked. The timeout failed B's statement and nothing else: B's credit was still in the transaction, and the commit wrote it without its debit.

Now a deadlock. A moves 10 from wallet 7 to wallet 8, B moves 5 from wallet 8 to wallet 7, and each has made its debit when it asks for the other's row. creditA runs A's credit to wallet 8, then A's commit, on its own thread, and returns once A waits. B's catch does what many retry helpers do, and retries the statement that failed:

H2 found the cycle at once and rolled back B's whole transaction, debit included, which let A finish. B's retried credit ran in a new transaction, and the commit wrote it alone: the two wallets hold 205, and 5 was created. H2 chose B in every run here; don't build on which side it picks.

A transaction that got 40001 no longer exists, so the retry rolls back and runs it again from its first statement. A's debit of wallet 7 has run before this loop:

Every retry rolls back and starts again from the first statement, and only for failures a rerun can fix. A CHECK violation from the same input fails again on every attempt. After a lock timeout the transaction is still open on H2, so the caller rolls it back before deciding to retry. Taking a transfer's rows in one order, lower id first, keeps two transfers from crossing (unit Monitors and synchronized blocks does the same for Java locks). The retry is still needed for REPEATABLE READ's 40001 and for code that ignores the order.

Databases differ here too. What a lock timeout or a deadlock undoes is the database's choice; only H2 ran here. Check yours before relying on the open transaction after a timeout.

Summary

  • Read, compute in Java, write back loses an update under READ COMMITTED. The UPDATE writes a constant computed from a stale read, and a JVM lock can't see the other instance. One statement (balance = balance + ?) or a lock on the read fixes it.
  • `SELECT ... FOR UPDATE` makes the second reader wait for the first commit, then read the new value. The lock is held until commit() or rollback(), on every path.
  • A version column turns a lost update into an update count of 0. Check the count, increment the version on every write, and read again before retrying.
  • An isolation level is what your database does. On H2, REPEATABLE READ is a snapshot; at it and at SERIALIZABLE a second writer gets 40001 "Deadlock detected"; SERIALIZABLE let write skew through.
  • A failed statement undoes only itself on H2; a savepoint undoes the group. One savepoint per group of statements that must stand or fall together.
  • On H2, a lock timeout fails one statement; a deadlock rolls back the whole transaction. A retry rolls back and reruns the whole transaction, and only for failures a rerun can fix.

Design Note: Why the Victim Loses Its Whole Transaction

When two transactions wait for each other, one must give up a lock it holds, and a row lock protects a change the transaction made. H2 undoes all of the victim's changes rather than guess which of its earlier statements the rest depend on, and says so in the SQLState. It reports a write conflict under a snapshot with the same 40001, and the remedy is the same: the transaction's reads are stale.

A transaction therefore has to be a unit the code can run again from the start: no e-mail sent, no message published and no in-memory counter changed before the commit, because the retry does it a second time. Code that retries just the failed statement creates money after a deadlock, and code that commits after a timeout writes half a transfer. Roll back, and run the whole transaction again.

Problem statement


In the shop's back office, editors tag products by hand while a nightly job adds seasonal tags. Nobody holds a lock while editing: an editor may sit on a product page for minutes. Since the job started running during office hours, editors report tags that "didn't stick": they saved, saw the tag, and an hour later it was gone. Every product row already has a version column that nothing uses yet.


Finish the two TODOs in src/main/java/practice/ProductTags.java:


  • addTag(...): add one tag and save it, trying at most ATTEMPTS times;
  • save(...): write the new tags, unless someone else saved the product since it was read.


Read products with load(...). The other writers keep the version column the way your save does. When you're done, no writer's tag is lost, whoever saves first. About fifteen lines in total.


The tests run each editor on its own connection to an in-memory H2 database, and use the Pause to let another writer save between an editor's read and its save.

Problem statement


Wallet transfers run all day; at midnight an interest job adds a little to every wallet, one transaction per batch, in its own order. Since the job moved earlier, a few transfers a night fail with SQLState 40001. Customers retry by hand, and support would like that to stop. A first attempt at an automatic retry made the nightly totals stop adding up, and a transfer to a wallet that is already near its limit now hammers the database three times before failing.


Finish transfer(...) in src/main/java/practice/Transfers.java, using debit and credit. The table's CHECK keeps every balance between 0 and 1000. When you're done, a transfer that collides with the interest job still completes with the right balances, and a transfer the database refuses for its own rules fails at once and changes nothing. About twelve lines.


The tests run on an in-memory H2 database and use the Pause after the debit to make the transfer cross the interest job, twice: once with the job's transaction begun first, once with the transfer's. H2 rolls back one side of each crossing; the test's job reruns itself when it is the one, and a test fails with a message saying so if H2 never picks the transfer.
