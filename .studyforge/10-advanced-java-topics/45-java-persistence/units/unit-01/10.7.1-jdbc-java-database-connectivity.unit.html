The nightly sensor import pastes each reading's values into a new SQL string. The payment job failed last night on a memo that was too long for its column: the account that payment debited stayed debited, and no payment row says where the money went. The same morning the support screen that lists open orders started throwing The object is already closed. Each failure breaks one JDBC rule about what a statement, a result set and a connection hold.

Every run on this page uses H2 2.2.224, in-memory (jdbc:h2:mem:...), on Java 21.

A PreparedStatement Is Parsed Once and Bound Per Row; a Batch Sends the Rows in One Call

Bound values let the database parse a statement once and run it many times. We insert 20,000 sensor readings three ways: with the values pasted into the SQL text, with one PreparedStatement executed per row, and with the same statement batched:

Each version ran 20 times on a fresh database; we dropped the first five rounds as warm-up:

The text version is slowest because every row is a new SQL string, so the database parses 20,000 statements. A PreparedStatement is parsed once, and each execution only binds new values. The same separation of text and values is what stops SQL injection (units Use Cases and Benefits and Common Vulnerabilities).

Batching changed nothing here: H2 runs inside our JVM, so each execution is a method call. Against a database across a network each executeUpdate waits for a round trip, and a batch can send the queued rows together; this run can't measure that.

Drivers differ. Whether a batch really travels in one round trip is up to the driver, and some send it row by row unless a connection setting asks otherwise.

executeBatch() returns one update count per queued statement, and a count of 0 is not an error:

The second UPDATE matched no row. Code that ignores the counts doesn't notice.

A ResultSet Lives Only as Long as Its Statement

The open-orders screen calls this method and iterates what it returns:

A ResultSet belongs to the statement that produced it, wherever the driver keeps the rows. The Statement javadoc says that closing a statement closes its current result set, and the try-with-resources closed the statement on return, before the caller called next(). The ResultSet javadoc adds that executing the statement again closes it too, so a nested loop that runs its inner query on the outer loop's statement loses the outer rows:

The fix is to read the rows inside the method and return a List of records. A try-with-resources that opens a connection, a statement and a result set closes them in reverse order of declaration, as a wrapper that prints each close() shows:

A method that is lent a connection closes only what it opened. With a connection pool, close() on a borrowed connection hands it back to the pool rather than closing it; no pool library was run for this page.

Auto-Commit Is On, So Each Statement Commits by Itself

The payment code debits the account and records the payment with two statements:

The account holds 1000.00, the payment is 250.00, and the memo rent for March, flat 4B has 23 characters for a VARCHAR(20) column. Before you look: what is the balance after the exception?

Under auto-commit each statement is its own transaction, committed when it completes. The debit was committed before the insert failed, and the exception undid nothing. The fix turns auto-commit off for the unit of work, commits at the end, rolls back on any failure, and gives the connection back in the mode it came in:

Under auto-commit, a batch of four payment rows whose third memo is too long:

H2 ran the rest of the batch after the failed row and committed the three good ones; -3 is Statement.EXECUTE_FAILED. The executeBatch javadoc lets a driver stop at the first failure instead, so the portable way to get all or nothing is a transaction around the batch.

Spot the Problem: Restoring Auto-Commit in finally Commits the Half

A shorter version passed review: it turns auto-commit off, and its finally turns it back on. The catch only logs.

The setAutoCommit javadoc says that changing the mode during a transaction commits it. The debit was still pending when the insert failed, and the finally committed it. Rollback has to come before anything that ends the transaction, which is why the fix above rolls back in the catch, for unchecked exceptions too. Concurrent transactions are unit Transactions and Database Concurrency Control.

A Getter Converts; Ask getObject for the Java Type You Mean

A shift starts at TIMESTAMP '2024-03-31 02:30:00', and its break length is NULL. The JVM runs in Europe/Berlin, where clocks jumped from 02:00 to 03:00 that night:

A TIMESTAMP column has no zone. getTimestamp builds a java.sql.Timestamp, an instant, by reading the value in the JVM's default zone, and 02:30 doesn't exist in Berlin that night, so it came back as 03:30. The same program with -Duser.timezone=UTC printed id 1: getTimestamp 2024-03-31T02:30 | getObject 2024-03-31T02:30 | ...: the bug hits only values inside a DST gap of the JVM's zone. getObject(2, LocalDateTime.class) maps the column to the java.time type with the same meaning, a date and time with no zone (unit 7.3), and setObject(i, localDateTime) writes one back.

getInt returns 0 for SQL NULL, the same as row 2's real 0. Call wasNull() right after it, or use getObject(3, Integer.class), which returns null.

Summary

  • A `PreparedStatement` is parsed once and bound per row, which is also what keeps values out of the SQL; a batch saves round trips, which an in-process database doesn't have. An update count of 0 is a result, not an error.
  • A `ResultSet` lives only as long as its statement: closing or re-executing the statement closes it, so read rows into objects before the statement closes.
  • Auto-commit is on by default, so a failure between two statements leaves the first committed. Group them in a transaction, roll back in the catch, then restore the mode.
  • Ask the inserting statement for a generated key, with RETURN_GENERATED_KEYS or key columns at prepare time; MAX(id) can return another session's row.
  • Getters convert: getTimestamp goes through the JVM's zone and getInt turns NULL into 0; getObject(i, LocalDateTime.class) and getObject(i, Integer.class) don't.

Challenges

  1. The import must load 2 million rows. Choose a batch size and a commit size, and say what a failure on row 1,500,001 leaves behind with each choice.
  2. A report query returns 300,000 rows. Returning a List keeps them all in memory, returning the ResultSet keeps the statement open. Design a method that streams them and still closes the statement, and say who owns the connection while it runs.
  3. Your team's schema stores times as TIMESTAMP and the servers run in three zones. Find every place that uses getTimestamp or setTimestamp, and decide whether to change the code or the column type to TIMESTAMP WITH TIME ZONE.

Design Note: The Caller Owns the Transaction

Every method of the module's JdbcOperations opens its own connection with getConnection(), so each call is its own transaction and no caller can make two of them succeed or fail together. The pay and payInTransaction methods on this page take the connection as a parameter instead: the caller decides where the unit of work begins and ends, and each method closes only what it opened. The cost is that every method in the chain must accept the connection and must not commit, close or change its auto-commit mode unless it set it. Unit ORM (Object-Relational Mapping) Frameworks covers what an ORM adds on top of these calls.
