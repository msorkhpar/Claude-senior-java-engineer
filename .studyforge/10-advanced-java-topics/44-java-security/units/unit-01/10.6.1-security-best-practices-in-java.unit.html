An incident review of an account service lists four findings. A support log holds a line with a user's password in it. Two users received the same password-reset link. An attachment named %2e%2e%2freport.pdf passed the name check. A heap dump attached to a vendor's support ticket holds a password that the code wipes after every login.

Each finding has a rule, one per section below. Injection, path traversal, XML entities and deserialization are unit Common Vulnerabilities; encryption and password hashing are unit Cryptography and Encryption in Java. The SecurityManager is no part of the answer: JEP 411 deprecated it for removal in Java 17, and on Java 21 System.setSecurityManager throws UnsupportedOperationException unless the JVM starts with -Djava.security.manager=allow.

Validate the Value the Next Layer Will Use, Against an Allow-List

The upload endpoint checks attachment names with a deny-list: refuse anything containing ../, / or \. The storage service behind it decodes the name with URLDecoder (form decoding, which also turns + into a space) and normalises it with NFKC. An allow-list instead matches the whole input against a pattern for a good name:

Six names, each check's verdict, and what the storage layer receives:

String.contains compares characters as they are, and neither %2e%2e%2f nor the full-width ．．／ (U+FF0E, U+FF0E, U+FF0F) contains the characters the deny-list looks for. Both became ../ one layer later, after the check had passed them. A deny-list has to name every spelling of every bad input, and each decoder or normaliser downstream adds more.

The allow-list refused the encoded and full-width names, because %, ． and ／ are not in its character class, so a spelling nobody thought of is refused. Decoding and normalising first make the check judge the string the storage layer will use, so the full-width ｒｅｐｏｒｔ.pdf is accepted and stored as report.pdf, not under a second spelling of the same name.

NFKC doesn't help with the last row. The Cyrillic р (U+0440) is a different letter from the Latin p, and normalisation leaves it alone; only the allow-list's ASCII range refuses it. A field that must accept other scripts needs a rule about which ones, or two names that look the same can belong to two people.

URLDecoder.decode throws IllegalArgumentException on a stray %, as in 100%.pdf; treat that as a refusal too.

A Token from Random Is a Function of Its Seed; Use SecureRandom

The reset service made each token like this:

Two requests in the same millisecond, then 10,000 tokens from each generator, issued as fast as a loop runs:

The javadoc of java.util.Random specifies a 48-bit seed advanced by a linear congruential step, and requires that two instances with the same seed return the same sequence. The seed here is the clock, so requests in the same millisecond share a token, and one second of possible request times is only 1,000 seeds. Seeding from nanoTime(), or leaving the seed out, removes the collisions but not the formula: the javadoc says instances of Random are not cryptographically secure, and Math.random() uses one.

SecureRandom on Linux defaults to NativePRNG, which reads the operating system's generator. A SHA1PRNG is different when seeded before its first use: the javadoc says setSeed supplements the existing seed, but a SHA1PRNG that hasn't produced anything yet has none to supplement:

Create one new SecureRandom() (its javadoc says it is safe for concurrent threads), don't seed it, and take 16 bytes or more per token.

Wiping a char[] Removes Your Copy of a Secret; a String Copy Stays Until GC

Console.readPassword() returns a char[] so that the caller can overwrite it, which a String doesn't allow. This program dumps its own heap at each step of a login. dump(label, liveOnly) calls HotSpotDiagnosticMXBean.dumpHeap, which with liveOnly set runs a full GC first and writes only reachable objects. A second JVM then counts the copies of the placeholder password hunter2-example in each dump, so the search adds no copies of its own:

Arrays.fill removed the array's copy at once (dump 3). The second login wiped its array too, but new String(p2) had copied the characters into the String's own byte array, which no public API can overwrite. Unreachable, it stayed in the heap, and in a whole-heap dump, until a full GC reclaimed it (dumps 4 to 6).

An API on the way that takes a String, such as DriverManager.getConnection(url, user, password), makes a copy you can't wipe. The program wipes inline; real code wipes in a finally, so a failed login wipes too, and wipes every array it copied the secret into.

What the run can't show. A heap dump lists objects. Whether a reclaimed object's bytes stay in the process's memory until the space is reused depends on the collector; a collector that moves objects, as G1 does, may leave an earlier copy of the array where it used to be. Swap, core files and the operating system's buffers are out of Java's reach. Wiping shortens the time the characters sit in a live object; it doesn't remove every copy.

A Record's toString Prints Every Component, Password Included

Nobody wrote log.info(password). The login handler logged the request:

A record's generated toString prints every component by name and value, and a record that contains it prints it too, because the generated toString of Session calls the one of LoginRequest.

Two fixes, run in the same program: override toString in the record, or give the secret a type whose toString hides it.

The override protects one record; every other record holding the password as a String needs its own. The Secret type makes every toString that reaches it print ***. A char[] component doesn't print its characters, because arrays inherit Object.toString, but the generated equals then compares the arrays by identity, as the last line shows.

Summary

  • Validate the value the next layer will use, against an allow-list. A deny-list checks one spelling; %2e%2e%2f and full-width ．．／ passed it and became ../ downstream. Decode, normalise with NFKC, then match the whole string; normalisation doesn't touch look-alike letters from other scripts.
  • A token from `Random` is a function of its seed. Seeded from the clock, 10,000 tokens came out as 5 distinct values. Use one unseeded SecureRandom; a SHA1PRNG seeded before use repeats too.
  • Wiping a `char[]` removes your copy; a `String` copy stays until GC. A heap dump showed the password after the array was wiped, because an API took a String.
  • A record's `toString` prints every component. Log calls, exception messages and enclosing records all print the password; override toString, or wrap the secret in a type that prints ***.

Challenges

  1. Your API gateway URL-decodes paths, and your service decodes them again. Which string should your validation see, and what does a double-encoded %252e turn into at each layer?
  2. A username field must accept Latin, Greek and Cyrillic names. Which rule stops аdmin (with a Cyrillic а) from passing for admin, and what does it cost legitimate users?
  3. Find every place in a service where a password exists as a String, starting from the HTTP request body. Which of them can you remove, and which belong to libraries you can't change?

Design Note: Hide the Secret in Its Type, Not at Each Call Site

A rule such as "never log the password" depends on every developer, at every log call, knowing which objects contain one. The record run shows how it fails: the code logged a request and a session. A Secret type makes printing safe wherever the value travels.

Every reader of the value then calls value(), and the type changes only toString: any code that calls value(), a serializer that reads record components included, still sees the text, and the value is still a String that a heap dump can show.

Problem statement


Members of a community site choose a public handle at sign-up. Last week someone registered ｓｕｐｐｏｒｔ, in full-width letters. On a profile page it looks like the staff account, and the mention service, which looks handles up after NFKC normalisation, now delivers some @support mentions to it. A second account, ѕupport, starts with a Cyrillic letter.


HandleRegistry.register already refuses reserved and taken handles. Finish the two TODOs in src/main/java/practice/HandleRegistry.java:


  • canonical(raw): the form of the handle that the registry checks, stores and compares;
  • allowed(handle): whether the handle keeps to the rules below.


A handle is 3 to 20 characters long, each one a lowercase letter of the Latin script (accents are fine: zoë_m, renée), a digit 0–9, or _. When you're done, any two spellings the mention service treats as one handle are one handle here too, and a handle that only looks like a Latin one is refused. About three lines in total.

Problem statement


Operators unlock the deployment vault by typing a passphrase at a console, which hands it over as a char[], sometimes with a trailing '\n'. After an incident, the security team took a heap dump of the deploy tool and found the passphrase in it twice, long after the unlock had finished.


The vault's client library takes the passphrase without the newline, reads it during open, and keeps no reference to it. Write unlock(typed) in src/main/java/practice/VaultUnlock.java: it opens the vault and returns the session id, or lets the vault's IllegalArgumentException for a wrong passphrase reach the caller. passphraseLength(typed) is there to help.


When unlock has returned or thrown, every char[] that held the passphrase, the operator's included, holds only '\0'. About seven lines in total.
