A pricing service runs with a 1 GB heap. It keeps a 400 MB cache of price lists and allocates a few kilobytes per request, and its p99 latency has spikes of tens of milliseconds. One colleague wants ZGC because "it has no pauses", another wants Parallel because "it has the best throughput", and a third adds System.gc() after every cache reload. None of them has read the GC log.

Every run here is Java 21 (Temurin 21.0.12) on one machine with 20 CPUs. Absolute pause times vary with hardware, heap and version; compare the runs with each other. Where objects live and what OutOfMemoryError looks like is unit Heap and Stack Memory Management.

A Young Collection Costs What Survives, Not What Was Allocated

This program allocates 8 GB of 1 KB arrays. Each array stays in a ring of window slots, so it lives until window more arrays have been allocated:

With a window of 1,000, about 1 MB is alive at any moment; with 200,000, about 200 MB. How do the pauses compare? We ran each window with java -Xms1g -Xmx1g -Xlog:gc:file=gc.log GcLoad <window> 8000 on G1, the default collector, and summed each log's Pause lines with a short script. The first run of each:

Over three runs: 14 pauses and 12–13 ms in total for the small window, 90–99 pauses and 508–1251 ms for the large one. Two young collections from the first log:

G1 splits the heap into regions. A young collection copies the live objects out of the young regions and reuses those regions whole. It never visits the 612 MB of dead arrays, so its cost follows the 2 MB that survive. That is the bet a generational collector makes: most objects die young, so collecting the young part often is cheap. With the 200,000 window almost every young object is still alive at the collection, so each one is copied, then promoted (moved to old regions), and later found dead there by a concurrent marking cycle, after which mixed collections clean the old regions.

"Alive" means reachable from a root: a local variable of a running method, a static field, a thread. Nothing counts references, so two objects that refer only to each other are garbage:

The costly objects live a little while, such as a batch held across a few requests. They are copied in the young generation and then marked in the old one.

Lines from each first run, decorations cut, collector's name in front:

ZGC's pauses are tiny, and the application still waited. Single-generation ZGC marks the whole heap, including the 400 MB cache, in every cycle. The request data filled the heap faster than a cycle finished, so the allocating thread stopped in Allocation Stall until the cycle freed memory: about 20 ms at a time, 30 times per run, longer than G1's longest pause. A latency dashboard sees those as pauses whatever the log calls them. Generational ZGC collects the young objects on their own, kept up with the same program, and never stalled.

Parallel was the slowest and used the most CPU. With 450 MB live in a 1 GB heap, its sizing policy predicted that a young collection's survivors would not fit in the old generation, and ran a full collection instead: in every run 62 of its 65 pauses are Pause Full (Ergonomics), each marking the whole cache with 15 GC threads. With -Xmx2g, in one run, the same program had 44 young pauses, no full one, 240 ms of pauses in total and 2.9 s of CPU.

Serial had the longest pauses and the least CPU. One thread does all the work, with the application stopped. In every run its two longest pauses (80–122 ms) are the first two young collections, which copy the freshly built cache into the old generation.

Versions differ. On Java 21 ZGC is single-generation unless -XX:+ZGenerational is given. JDK 23 made generational the default (JEP 474) and JDK 24 removed the single-generation mode (JEP 490): on Java 25 the flag prints Ignoring option ZGenerational; support was removed in 24.0.

System.gc() Is a Request, and JVM Flags Decide What It Does

After each reload, the third colleague's code calls System.gc() "to clean up". This program holds 300 MB, creates a WeakReference to an object nothing else holds, and times the call:

With -Xlog:gc, under five flag sets (each followed by the GC lines the call caused, then the program's line):

The javadoc says the call "suggests" a collection, with no guarantee of what it reclaims. On G1 and Parallel the best effort is a full, stop-the-world collection of the whole heap, so every reload adds a pause for all request threads (18–40 ms over two runs of each), and it reclaims nothing the collector would not have reclaimed on its own later. With -XX:+DisableExplicitGC, which some deployments set for that reason, the call does nothing at all and the weak reference stays uncleared. A test that relies on System.gc() to clear a reference fails on a machine that sets this flag. With ExplicitGCInvokesConcurrent or ZGC the pause is short, but the calling thread still waits for the whole cycle.

A WeakHashMap Entry Goes Only When Nothing Else Reaches Its Key

A WeakHashMap holds its keys through weak references and its values strongly. A weak reference is cleared by the first collection that traces its object and finds it reachable only through weak references. The program builds three maps with three kinds of key:

Only the plain map lost its entry. A string literal is interned and stays reachable while the class that uses it is loaded, so it never becomes weakly reachable. In the third map the value refers to its key, and the map holds the value strongly, so the key is reachable from the map itself. That map leaks like a HashMap.

The plain entry also did not go at the collection. The collector cleared the weak reference, then the JDK's reference-handler thread put it on the map's queue, and the map removes entries for queued references on its next call. So size() still said 1 right after System.gc() returned: the removal races with the caller on any machine, and code that checks for it has to wait. Unit Observer Pattern (loose coupling for event handling) shows the opposite failure: a listener held only weakly is lost at the first collection.

  1. Coding practice

    Stop the tracer from keeping finished requests

    • A WeakHashMap entry goes only when nothing else reaches its key; a value that refers to its key, or an interned literal key, keeps the entry.

Problem statement

The checkout service traces every request: SpanTable keeps a span per request object, and the web layer calls event(request, ...) while it handles it. Since the tracer went in, the heap grows by a request body for every request served, and a heap dump shows finished requests still reachable from the tracer. An exporter also keeps finished spans for a while, to send them in batches, and needs their labels then.

SpanTable already records events and labels spans. Finish the two TODOs in src/main/java/practice/SpanTable.java:

  • open(request): a new span labelled "<method> <path>", for example "POST /orders".

When you're done, the tracer holds a span for as long as the web layer holds its request, and not after; a span the exporter still holds gives its label without keeping its request in memory. About four lines in total.

A Soft Cache Survives Collections While There Is Room, and Empties When an Allocation Doesn't Fit


The javadoc leaves clearing a SoftReference to the collector. It asks only that every soft reference be cleared before an OutOfMemoryError, and that recently created or used ones be cleared last. Ten 4 MB entries in a soft cache, with a 64 MB heap:




The same in all three runs with -Xmx64m; with -XX:+UseSerialGC it took 20 MB, and then also 0 of 10. A full System.gc() with room to spare kept every entry. Once 12 MB more had been allocated, none of the ten was left.


HotSpot decides by age and room: a soft reference survives roughly -XX:SoftRefLRUPolicyMSPerMB (default 1000) milliseconds per MB of free heap since its last get(). With that flag set to 0, the same System.gc() left 4 and 3 of 10 in two runs. As the heap fills, the allowance shrinks towards nothing, and a collection that still can't make room clears every soft reference.


So a soft cache empties at once under memory pressure, when recomputing every entry hurts most. A map with a size bound (an LRU map with a maximum size) evicts the entries you choose, when you choose.


Collectors differ. On generational ZGC the same program printed between 0 and 7 of 10 after System.gc() in six runs.


A Cleaner Runs After a Collection Finds Its Object, So close() Is the Release You Can Count On


finalize() is deprecated for removal. Its replacement, java.lang.ref.Cleaner, runs an action on its own thread once the registered object becomes phantom reachable: no strong, soft or weak reference reaches it any more. A buffer that releases native memory registers a release action and calls it from close(); a second buffer's action is a lambda that reads its own field:




Run with an argument, so that no collection happens, and with -Xlog:gc:



b-2 was released by close(), at once; clean() runs the action at most once, so a collection later does not release it again. The forgotten b-1 was released only after a collection found it. In the second run, with no collection before the JVM exited, it was never released. A forgotten buffer that has reached the old generation waits for an old-generation collection, holding its native memory until then.


c-1 is never released. The lambda reads this.name, so it holds the buffer, and the Cleaner holds the lambda, so the buffer stays reachable from the Cleaner for the life of the JVM. The action must hold only what it needs to release, as Release does with the name.

Problem statement


An image service decodes into buffers outside the Java heap. NativeBuffer takes its memory from an Allocator and must give the address back with free. Most code closes its buffers with try-with-resources, but a few code paths forget, and the service's native memory climbs until the container is killed. Freeing an address twice is worse: it corrupts the allocator.


Finish the two TODOs in src/main/java/practice/NativeBuffer.java:


  • register(cleaner): what frees the buffer's memory if nobody closes it;
  • close(): free the memory now.


When you're done, every buffer's address is freed exactly once: at close() if it is closed, and otherwise after a garbage collection finds the buffer unreachable. About four lines in total.


The tests give each buffer its own Cleaner, ask the JVM for collections with System.gc(), and wait up to ten seconds for a forgotten buffer to be freed.

    Concept check
    

    Check yourself: garbage collection
    

      

    • Each collector puts the cost of the same workload somewhere else: G1 in short pauses, Serial and Parallel in longer ones (Parallel in full collections when the heap is tight), single-generation ZGC in allocation stalls that no Pause line shows.
      • 

    • Soft references survive collections while the heap has room (HotSpot keeps recently used ones longer) and are all cleared when a collection can't free enough, so a soft cache empties at once.
      • 

    • System.gc() asks for a collection: on G1 and Parallel it is a full stop-the-world collection, and with -XX:+DisableExplicitGC it does nothing.
      • 

    • A young collection copies only what is still alive, so short-lived garbage is cheap and objects that outlive a few collections cost copying, promotion and old-generation marking.

Summary


  • A young collection costs what survives. Short-lived garbage is nearly free; objects that live through a few collections are copied, promoted and marked again.
  • Each collector puts the cost somewhere. G1 in pauses of a few milliseconds, Serial and Parallel in longer ones, single-generation ZGC in allocation stalls when the heap fills faster than it collects; the log and the CPU time show which.
  • System.gc() is a request. On G1 and Parallel it is a full stop-the-world collection; with -XX:+DisableExplicitGC it does nothing.
  • A WeakHashMap entry goes only when nothing else reaches its key, and only after the reference is queued, not at the collection.
  • A soft cache survives collections while there is room, and empties when an allocation doesn't fit. HotSpot keeps recently used soft references longer when the heap has room, and clears them all when a collection can't free enough.
  • A Cleaner runs only after a collection finds its object, and never if its action holds the object. close() is the release.

Design Note: Why Java Never Promises When an Object Is Collected


Java collects by reachability and leaves the timing to the collector. That freedom is what lets G1 skip the dead young objects, ZGC move objects while the application runs, and Parallel spend fifteen threads on a full collection. Each collector meets its own goal because nothing in the language says when an unreachable object goes.


The cost falls on everything that wants to act on collection. finalize() ran late or never, and was deprecated. A Cleaner, a WeakHashMap and a soft cache inherit the same uncertainty: they act after some later collection, on another thread, and System.gc() can't force it because it is only a request. Code that must release something at a known time does it explicitly, with close().
