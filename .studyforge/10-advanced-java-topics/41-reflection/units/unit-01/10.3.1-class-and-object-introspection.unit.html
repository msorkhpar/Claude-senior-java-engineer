getMethods and getDeclaredMethods Answer Different Questions, and Neither Lists Everything

Circle extends an abstract Shape:

Before reading on: which of the two calls lists getColor, and which lists validate?

(The names are sorted for printing; the next section explains why that is needed.) getMethods() answers "what can any caller invoke on a Circle": public methods only, inherited ones included, down to Object's. getDeclaredMethods() answers "what does Circle's own class file declare": every access level, nothing inherited. So validate() is missing from the first list and getColor() from the second, and the protected area() appears only in the second, because Circle overrides it.

A tool that must see every method a type's classes declare, whatever its access, walks the chain itself: call getDeclaredMethods() on the class, then on getSuperclass(), until that returns null. It sees overridden methods twice, once in each class that declares them, and it misses interface default methods unless it also visits getInterfaces(). The same split holds for fields (getFields / getDeclaredFields) and constructors, except that a class inherits no constructors.

Neither follows the source. The javadoc of both methods says the elements "are not sorted and are not in any particular order". Twenty launches of each command, header line only:

With the archive on, the order was the same on every launch, which is what makes the dependency easy to ship: the export passes every test on one JVM setup, then a different JDK build, container image or flag reorders the columns, and a consumer that reads by position books Jane Doe as the invoice id. Without the archive it changed between two launches of the same command. JUnit 4 met this with test methods and fixes the order itself since 4.11; its MethodSorters.JVM option warns that "the order from the JVM may vary from run to run".

Why it moves. HotSpot sorts a class's methods by the memory address of each name in the JVM's symbol table, and the shared archive changes where names live. That is an implementation detail and may change; the javadoc promises nothing.

When order matters, take it from something that defines one: sort by name, read an annotation that carries a position, or, for records, use the components (two sections down).

The Compiler Adds Methods You Never Wrote: Bridges and Lambda Bodies

Here is OrderHandler from the opening, with a lambda field it uses to skip test orders:

Its getDeclaredMethods():

After erasure, Handler.handle takes an Object, and a handle(OrderPlaced) does not override it in the class file. So javac adds a bridge method handle(Object) that casts its argument to OrderPlaced and calls the real one, and it copies the method's annotations onto the bridge. The lambda's body became a private static method, lambda$new$0. Both are marked synthetic: isSynthetic() is true, and isBridge() picks out the bridge. Both handle methods are declared by OrderHandler itself, and getMethods() lists the same two: the interface's abstract handle is dropped there, because a method declared by a class wins over one with the same signature declared by an interface. The annotations go only onto the bridge; Handler.handle still has none.

A scan that turns methods into routes, columns or subscriptions skips isBridge() methods, and usually every isSynthetic() one.

Read a Record Through Its Components and a Sealed Type Through Its Permitted Subclasses

A payment is one of a sealed family, and one case is itself sealed:

An exporter that treats "no-argument instance methods" as a record's values, next to the record's own description:

A record's toString, hashCode and equals are real methods in its class file, so the method scan exports toString and hashCode columns. getRecordComponents() returns exactly the components, and its javadoc promises them "in the same order that they are declared in the record header", the only member list with a promised order. Each RecordComponent gives the name, the type, the generic type and getAccessor(), the method to call for the value.

getPermittedSubclasses() lists only the direct subtypes: Wallet appears as a case, and reaching ApplePay takes a second call. Its javadoc leaves the order unspecified, and it returns null for a type that is not sealed, so a recursive walk stops on null rather than on an empty array. A permitted subclass that the class loader cannot load is "silently ignored", so a missing jar shrinks the list without an error.

Type Arguments Survive in Declarations, Not in Objects

A settings class has a field List<Integer> ports = new ArrayList<>() and a method Map<String, List<Integer>> portsByHost(). What each reflective view reports:

The object is an ArrayList, and an ArrayList<String> has the very same Class: type arguments are erased from objects. Declarations keep them. For every field, method and class whose declaration uses type arguments, the compiler writes the generic signature into the class file. getGenericType(), getGenericReturnType() and getGenericSuperclass() return it, as a ParameterizedType when the type has arguments, and its getActualTypeArguments() gives Integer, a plain Class.

The last line is how libraries capture a type that has no field to hang on. TypeRef<T> is an abstract class whose method returns ((ParameterizedType) getClass().getGenericSuperclass()).getActualTypeArguments()[0]. The anonymous subclass new TypeRef<List<String>>() {} records List<String> in its own superclass signature, and that call reads it back. Called on an ordinary object's class, getGenericSuperclass() reads that class's declaration: for every ArrayList, whatever it was created with, it is java.util.AbstractList<E>.

Summary

  • `getMethods()` is public and inherited; `getDeclaredMethods()` is this class, every access level. Seeing every class's methods takes a walk up getSuperclass().
  • Members come back in no particular order. The order shifts with JVM setup; take order from a sort, an annotation or record components.
  • The compiler adds bridge and synthetic methods, and bridges carry the annotations. A scan that doesn't skip isBridge() registers an implementation of a generic interface method twice, once for the erased parameter type.
  • Records and sealed types describe themselves. getRecordComponents() is in header order; getPermittedSubclasses() is direct subtypes only, unordered, null when not sealed.
  • Type arguments live in declarations. getGenericType() and its relatives have them; an object's getClass() never does.

Challenges

  1. A dependency-injection container finds constructors with getDeclaredConstructors(). A class has two that are both eligible. What does the container do today, and what makes it pick the other one next year?
  2. Your serializer walks fields with getDeclaredFields() up the hierarchy. A subclass declares a field with the same name as a private field of its superclass. What should the JSON contain?
  3. Wallet gains a third case in a jar that one service doesn't ship. What does a tool built on getPermittedSubclasses() report there, and how would you notice?

Design Note: Why Signatures Keep Type Arguments and Objects Don't

Generics arrived in Java 5 with erasure, so that a List<String> and a pre-generics raw List are the same class at run time and old binaries keep working. The type arguments went into the Signature attribute of each class, field and method, for the compiler compiling against that class, and reflection exposes the same attribute. Nothing per object records them, which costs every framework that binds data: it can only learn a type argument from a declaration.

SettingsBinder already finds the field, clears the list and converts each item. Finish elementType(...) in src/main/java/practice/SettingsBinder.java: the type every item of that field's list must have.


Settings classes declare their lists as List<Something>, or as a named class of their own such as class PortList extends ArrayList<Integer>, and a list may be empty before binding. When you're done, every item ends up as the declared element type in all of these cases. About four lines in total.
