Creating an object or calling a method from a name moves checks the compiler would have made to run time. A name in a string is checked only when a class loader is asked for it. If startup doesn't ask, the first request that needs the class does: here a batch job twelve hours after the deploy, when rolling back means another deploy.

Resolve the name at startup and check its type:

ReportJob exists but isn't an Exporter, and asSubclass checks that against the class object. The cast (Class<? extends Exporter>) Class.forName(name, false, loader) compiles with an unchecked warning and checks nothing, because generics are erased: ReportJob would pass startup and fail with a ClassCastException at the line that takes its first instance as an Exporter, before any Exporter method is called. The message of asSubclass names only the class, so wrap it with the config key that named it.

Class.forName(name) Runs the Static Initialiser; the Three-Argument Form Waits for First Use

The startup check now touches every configured plug-in. Which of their code runs? Three exporters in the default package have a static block each. PdfExporter and CsvExporter print a line, and XlsxExporter reads a setting it requires:

The program reaches each one differently, then calls forName("XlsxExporter") twice:

Class.forName(name) is forName(name, true, callerLoader): it loads the class and initialises it, which runs its static field initialisers and static blocks. A class literal and forName with false only load it, and the initialiser runs at the first instance, static method call or access to a static field that isn't a compile-time constant.

A failed initialiser is not retried. The class stays unusable, and every later use in that JVM throws NoClassDefFoundError: Could not initialize class; on Java 21 its cause names the first failure, as above. With one-argument forName, an exporter nobody uses tonight stops the service from starting. With false the check confirms the name and the type, and leaves the exporter's own setup for when it is used.

Class.newInstance Lets the Constructor's Checked Exception Escape Undeclared

Class.newInstance() is shorter than getDeclaredConstructor().newInstance(), but deprecated since Java 9 because of what it does when a constructor throws. A loader creates each plug-in and skips the ones that fail:

The first plug-in's constructor is SftpExporter() throws IOException, and it throws:

Constructor.newInstance wraps whatever the constructor throws in an InvocationTargetException, which is a ReflectiveOperationException, so the catch runs and the loop goes on. Class.newInstance declares only InstantiationException and IllegalAccessException, and rethrows the constructor's exception as it is. The IOException came out of a method that doesn't declare it, passed the catch and ended main, which declares nothing either. One plug-in that can't reach its server stopped every other one from loading.

The caller can't catch it as an IOException, because the compiler sees none in the try; only a broad catch (Exception e) sees it:

javac -Xlint:deprecation flags each use (warning: [deprecation] newInstance() in Class has been deprecated). Replace it with getDeclaredConstructor().newInstance(), and take getCause() of the InvocationTargetException where the constructor's own exception matters.

A Method Handle Has a Type, and invokeExact Holds the Call Site to It

Method.invoke (unit Accessing Fields, Methods, and Constructors) takes Object and Object..., so a wrong argument shows only at the call: apply(long) called with "2500" throws IllegalArgumentException: argument type mismatch. A MethodHandle is looked up with its full type, return type included, and each call is checked against it. Discount.apply(long) returns 90 % of its argument:

All four invokeExact calls compiled. invokeExact is signature-polymorphic: javac takes the call site's type from the static types of the arguments and the cast on the result, and checks nothing. At run time that type must equal the handle's, with no widening, boxing or upcasting. Without the cast the call site's return type is Object, or void in a bare statement, and it fails the same way. invoke converts as if through asType, which also casts an Object receiver down to Discount.

The lookup is checked as well. Asking for an apply that returns int fails there, before any call:

A handle moves the failure to the lookup, which can run at startup, and to a call site with the wrong type, which fails on its first call. When the receiver is only known as Object, adapt the handle once with asType(MethodType.methodType(long.class, Object.class, long.class)) and keep calling invokeExact. Unit Reflection Performance Considerations measures what each style costs.

Summary

  • A class named in configuration fails at its first use. Resolve every name at startup and check its type with asSubclass; an unchecked cast of the Class checks nothing.
  • `Class.forName(name)` runs the static initialiser. forName(name, false, loader) loads without running it. A failed initialiser is never retried, and later uses throw NoClassDefFoundError.
  • `Class.newInstance` lets a constructor's checked exception escape undeclared. getDeclaredConstructor().newInstance() wraps it in InvocationTargetException.
  • A method handle has a type. The lookup checks it, and invokeExact throws WrongMethodTypeException when the call site's type differs; invoke adapts.

Challenges

  1. Your service reads 40 plug-in names from a table that operators edit while it runs. Where do you resolve them, and what happens to a row that fails?
  2. A plug-in's static initialiser opens a connection pool. When the database is down at startup, who should see the failure: the startup check, the first request, or a health endpoint?
  3. Rewrite a Method.invoke-based dispatcher with one cached handle per method. Which errors move from the first request to startup, and which can't?

Design Note: Why the Compiler Doesn't Check invokeExact

A method handle's type is a value that exists only after the lookup has run, so javac has nothing to check a call against. It records the call site's type instead, and the JDK makes invokeExact compare that type with the handle's at run time and refuse any difference. An exact match needs no conversion at the call; invoke is for callers that want one. The cost is that a missing cast compiles and fails on its first call, with a message that names two method types rather than the mistake in the line.
