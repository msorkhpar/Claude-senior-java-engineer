The billing service hangs on about one start in thirty. The last log line is "warming caches", the CPU is idle, and the orchestrator kills the instance when its health check times out. On another start it came up, and for an hour it sent invoices with 0 % VAT. Nobody changed the code between those starts. Two classes, Rates and Tariff, read each other's static fields while they initialise, and which class was touched first, and by how many threads at once, decided each outcome.

Every output below is from Java 21 (Temurin 21.0.12) on Linux x64.

A Class Is Loaded When Code First Needs It, and Initialised Only When Code First Uses It

An export service has three renderers. This run exports CSV only:

Which of the renderer classes does the JVM load, and whose static block runs? -Xlog:class+load prints a line for each class the JVM loads. Of about 450 lines, 440 are JDK classes mapped from the class-data-sharing archive (source: shared objects file) and a few more come from the JDK's own modules (source: jrt:/...); with those filtered out:

XlsxRenderer was never loaded: archive() never ran, and checking it needed nothing from XlsxRenderer. PdfRenderer was loaded before main printed anything, yet its static block never ran. Before main runs, the verifier checks Export's bytecode; to prove that a PdfRenderer or a CsvRenderer may be stored in a Renderer variable, it loads all three (the JVM specification allows verification to load classes, JVMS §5.4.1). Loading reads the class file and creates the Class object. Initialisation, which runs the static field initialisers and static blocks, waits for the first new, call of a static method the class declares, or read or write of a static field that isn't a compile-time constant (JLS §12.4.1). A superclass is initialised before its subclass, so Renderer printed first.

An interface type changes what the verifier loads. With Renderer as an interface, the same run loads Renderer before main and CsvRenderer only after "main starts", when new runs. PdfRenderer is never loaded. Don't rely on either: which classes the verifier loads is an implementation detail.

A static block is therefore not start-up code: a class whose initialiser opens a connection pool runs it on the first request that uses the class, in that request's thread, and fails that request if it throws. Unit Dynamic Object Creation and Method Invocation shows Class.forName(name) forcing initialisation, and a failed initialiser turning every later use into NoClassDefFoundError.

Each Loader Asks Its Parent First, So the JDK's Classes Always Come from the JDK's Loaders

Three loaders are built in. getClassLoader() names the one that defined a class:

null is the bootstrap loader, which defines java.base. The platform loader defines other JDK modules such as java.sql, and the application loader defines the class path. Asked for a class, ClassLoader.loadClass first returns one this loader has already loaded, then asks its parent, and only when the parent fails calls its own findClass. A request from the application loader for java.lang.String therefore travels to the bootstrap loader, and a String.class on the class path is never read.

A Class Is Its Name Plus the Loader That Defined It

The report server loads each customer's exporter plugin from its own directory with a URLClassLoader. A plugin implements the host's Exporter interface, and its build copies the API jar into the plugin, so the plugin directory holds PdfExporter.class and a copy of Exporter.class. The plugin directory is not on the host's class path:

The host tries two parents for the plugin's loader:

PdfExporter implements Exporter, and the cast still fails. With the platform loader as parent, nobody above the plugin loader knows Exporter, so the plugin loader defines its own copy, and PdfExporter implements that one. The JVM identifies a class at run time by its name and its defining loader (JVMS §5.3), so the host's Exporter and the plugin's are two unrelated types that print the same. Unit Singleton Pattern (ensuring a single instance) shows the same split giving a singleton two instances.

With the application loader as parent, defining PdfExporter needs its superinterface, so the plugin loader is asked for Exporter, passes the request up, and the application loader answers with the host's class. The copy in the plugin directory is never read. The plugin loader is the initiating loader of that Exporter, the application loader its defining loader, and getClassLoader() reports the defining one.

Static Initialisers Run in Textual Order, and a Cycle Lets Code Read a Field Before It Is Set

These are the two classes from the billing service:

Billing reads Rates.DEFAULT_TARIFF first when given rates, and Tariff.STANDARD first when given tariff:

Before any initialiser runs, the JVM sets every static field to its default: 0, false or null. Initialising Rates runs its field initialisers top to bottom. The first one needs Tariff, so Tariff is initialised in the middle of Rates, and its constructor reads Rates.VAT_PERCENT. Rates is already being initialised by this same thread, and the JVM doesn't wait for itself: it lets the read through (JLS §12.4.2), and the read returns the field's default, 0. Started from the other end, Tariff.STANDARD is still null when Rates copies it. Each order leaves one wrong value in a final field for the life of the process, and nothing throws during initialisation.

Swapping the two lines in Rates fixes the first order and not the second (the rates run then prints 20; the tariff run still leaves DEFAULT_TARIFF null). A compile-time constant does fix both: with static final int VAT_PERCENT = 20; both orders print 20 and the default tariff is set, because javac copies the value into Tariff (bipush 20) and reading it initialises nothing. A rate read from configuration can't be a constant, so the lasting fix is to break the cycle: one of the two classes must not read the other while it initialises.

Two Threads That Initialise a Cycle from Both Ends Wait for Each Other Forever

A class is initialised once, under a per-class lock: a second thread that needs a class another thread is initialising waits for it (JLS §12.4.2). Unit Proper synchronization to ensure memory visibility relies on that lock for safe publication. In the billing service, a request thread touches Rates while the cache warmer touches Tariff. To make the timing repeatable, each class gets a static block, above its field initialisers, that waits on a two-party CyclicBarrier until both threads have started; then:

After join(2000) on each thread:

http-1 holds Rates's initialisation lock and waits for Tariff's; cache-warmer holds Tariff's and waits for Rates's. On Java 21 both threads report RUNNABLE, not BLOCKED, and ThreadMXBean.findDeadlockedThreads() (unit Best practices for safe concurrent programming) returns null, because it tracks only monitors and java.util.concurrent locks. A thread dump (jcmd <pid> Thread.print, trimmed) shows it:

Without the barrier, the hang needs both threads inside their initialisers at once, which is why the service hung on some starts and not others. Every later thread that touches either class joins the wait. Breaking the cycle fixes both failures.

Each Thread Has Its Own Stack and Program Counter; the Heap and Method Area Are Shared

The JVM specification names six runtime data areas (JVMS §2.5). Three belong to a thread, and they show in a stack walk. This program recurses twice, then walks its own stack, and prints the top frame of a second thread that is in Thread.sleep:

Each call has its own frame with its own n, and each frame records the bytecode index of the call it is waiting on: 12 (the forEach call) in the top countdown frame, 19 (the recursive call) in the two below it. The frame that is executing holds the same kind of index, and that is the thread's program counter. The sleeping thread's top frame is a native method: Java code sees the frame but no bytecode index, and the native frames beneath it can't be walked.

Summary

  • A class is loaded when code first needs it, and initialised only when code first uses it. The verifier can load a class that never runs; a static block runs on the first request that uses the class, in that request's thread.
  • Each loader asks its parent first. java.* always comes from the JDK, and the loader you ask may not be the one that defines the class.
  • A class is its name plus its defining loader. A plugin that defines its own copy of the host's interface can't be cast to it.
  • Static initialisers run in textual order, and a cycle reads a field before it is set. The result is a default value in a final field, different for each first use.
  • Two threads initialising a cycle from both ends hang. The threads show as RUNNABLE and the deadlock check misses them; a thread dump names the class initialisation monitor.
  • Stacks and program counters are per thread; the heap and method area are shared.

Challenges

  1. Your service needs a class's static initialiser to fail at start-up, not on the first request. Which ways of forcing initialisation are there, and which ones survive a refactoring that moves the class?
  2. A plugin host loads child-first so each plugin can bring its own JSON library. Which packages do you send to the parent, and what breaks if a plugin returns a JSON object to the host?
  3. Find a static-initialisation cycle in a code base you know. Which first use gives a default value, and could two threads reach it from both ends?

Design Note: Why Delegation Goes to the Parent First

Asking the parent first means that a name resolves to the same class for every loader below the one that defines it. The host and every plugin see one String and, with the application loader as parent, one Exporter, so objects cross the boundary without casts failing. A loader below the platform loader can't define a java.* class at all, so none can put its own String in front of the JDK's.

The cost is that a child can't override anything its parent has. An application server that lets each application use its own version of a library inverts the order for most classes, and then has to list, by hand, every package that must still come from the parent. Each package missing from that list is a class the server and the application each define, and the first object passed between them fails a cast, as the plugin's Exporter did.

Problem statement


The report server runs exporters that customers write themselves. Each plugin arrives as a jar built with everything it was compiled against: the server's plugin API and the libraries the customer tested with, which are often older or newer than the server's own copies.


Two attempts have shipped so far. The first gave every plugin its own URLClassLoader with no link to the server, and the server could no longer use a single plugin: every one failed with ClassCastException on the line that hands it to the scheduler. The second made the server's loader the parent, and a customer's ledger export began formatting numbers the way the server's version of their formatting library does, not the way the version in their jar does.


PluginLoader already knows what the jar holds (inBundle), which classes are the server's API (isApi), and how to define a class from the jar (defineFromBundle). Finish the TODO in src/main/java/practice/PluginLoader.java: loadClass(...), which decides what each class name the plugin uses resolves to.


When you're done, the server can use every plugin through the API types it knows, each plugin runs on the library versions in its own jar, and anything the jar doesn't carry, the JDK included, comes from the server. About eight lines in total.


The tests build a plugin jar in memory from compiled classes, so its classes have the same names as classes the server already has.

Problem statement


The subscription shop has two ways in. Most visitors open the price list first; some go straight to the sign-up form. After a restart last week, the first visitor went straight to sign-up, and every customer who signed up until the next restart was billed without VAT. In the staging environment, where the price list is usually opened first, the sign-up form failed instead: new customers had no tariff at all.


Tariff and its STANDARD tariff are fine as they are. Finish the two TODOs in src/main/java/practice/Pricing.java, both in Rates:


  • vatPercent(): the VAT configured for this deployment (configuredVat() reads it);
  • defaultTariff(): the tariff a new customer starts on, which is the standard tariff.


When you're done, the standard tariff charges the configured VAT and every new customer starts on it, whichever of the two the shop uses first after a start. About three lines in total.


Each test starts the shop afresh: it loads its own copy of the Pricing classes, so their static fields are set up again, in the order that test uses them.
