The order service runs in a container with a 1 GB memory limit and no JVM flags. Some mornings its requests time out while the health check still answers, and on Fridays the pod restarts with OOMKilled. You have a shell next to the process and the JDK's own tools: jcmd, the Flight Recorder and the java launcher. Each of them prints a number that is easy to misread.

Every run here is Java 21 (Temurin 21.0.12) on one Linux machine. In the outputs, <pid> and <nid> replace process and thread ids, and ... marks lines left out. GC logs are unit Garbage Collection Algorithms, JIT logs unit JIT (Just-In-Time) Compilation.

GC.heap_info Counts Garbage as Used; Live Data Is What a Full Collection Leaves

jcmd <pid> <command> attaches to a running JVM started by the same user and runs a diagnostic command inside it; jcmd alone lists the JVMs it can see. This program keeps 64 MB, throws 300 MB away, then idles:

We start it with java -Xms1g -Xmx1g -Xlog:gc:file=gc.log Catalog. Pause here: how much of the heap does it report as used?

211 MB, three times what the program holds: "used" counts every byte in the regions the collector has handed out, including the 142 young regions full of arrays nobody references. A class histogram, first with -all, then without, and the GC log:

The plain histogram counts only live objects. To find them it ran a stop-the-world full collection, and jmap -histo:live, run on the same program, logged the same line. It took 5 ms on 211 MB; on a heap of tens of gigabytes it can stop the service for seconds. -all collects nothing and counts garbage too.

So a high "used" figure is not a leak. A leak is the number after a full collection (211M->65M here) climbing from one collection to the next.

A Thread Dump Names a Deadlock Cycle, Not a Thread Stuck Behind a Holder That Waits

Unit Best practices for safe concurrent programming finds a deadlock from inside with ThreadMXBean.findDeadlockedThreads(). From outside, jcmd <pid> Thread.print (the dump jstack prints) shows every thread's stack and the locks in it. Two warehouse threads take the same two monitors in opposite orders:

With hang false, the dump ends with a deadlock section:

With hang true, reprice holds the price list while it waits on a CountDownLatch that nobody counts down. restock is just as stuck, but the dump has no deadlock section, because there is no cycle: reprice waits for a latch, not a lock. Find the holder by matching the address restock waits for to a - locked line:

In production the latch is a database call or an HTTP request without a timeout, and fifty request threads are BLOCKED on <0x...70e0>. Follow each BLOCKED thread's address to its - locked line, then read what the holder waits for. Match the address, not the class: two price lists are two locks.

A thread keeps its monitors while it parks, sleeps or reads a socket. Only Object.wait() gives up one, the monitor it waits on, and the dump still lists that one as - locked, below a - waiting on line with the same address. That line is not a lock the thread holds; its other - locked lines are. A hand-rolled spin lock shows no owner at all (unit Benefits of KISS for concurrency).

    Tell the on-call engineer which thread everyone waits for

    • A thread BLOCKED on a monitor names the object's address; the thread whose stack lists that address as locked is the one it waits for, and two objects of one class are two locks.
    • A thread keeps its monitors while it parks, sleeps or reads; only Object.wait() gives up the one it waits on, though the dump still lists it as locked below a waiting-on line.

Problem statement

The payments service hangs a few times a month, and each time the on-call engineer scrolls through a jcmd <pid> Thread.print of four hundred threads, looking for the one that everybody else is waiting for. The dump has no deadlock section, because there is no cycle. We want a tool that reads the dump and answers that question directly.

DumpReader already splits a dump into threads and joins the answers into a report. Finish the two TODOs in src/main/java/practice/DumpReader.java:

  • waitingFor(thread): the monitor the thread is blocked trying to enter, or null;
  • held(thread): the monitors the thread holds while the dump is taken.

When you're done, whoBlocksWhom(dump) maps each thread that is blocked on a synchronized lock to the threads that really hold that lock, and to no one else. Threads that sleep, park or wait for a notify are not blocked by anybody. About fifteen lines in total, including any helper you add to read a lock line.

The tests feed it thread blocks cut from a real Java 21 dump of a payments program, so print one with jcmd from a small program of your own if you want to see every kind of line first.

A JFR Allocation Sample Stands for All the Bytes Since the Previous One


The JDK Flight Recorder (JFR) records events inside the JVM to a file that the jfr tool reads. Start it with the program (-XX:StartFlightRecording) or on a running one (jcmd <pid> JFR.start, then JFR.dump). This invoice renderer runs for two seconds, beside a customerName lookup with a small cache, and prints what its thread allocated (ThreadMXBean.getCurrentThreadAllocatedBytes; the number in brackets only keeps the result in use):




The view groups by the top frame, which is the JDK's own allocation helper. One event shows the rest of the stack:



The sampled array holds part of one invoice, at most a few kilobytes, yet its weight is 655.9 kB. JFR doesn't record every allocation: the default settings take about 150 samples a second, and a sample's weight is what its thread allocated since its previous sample. This program sums the weights by the first frame outside the JDK, with the jdk.jfr.consumer API:




304 samples stand for 36,153 MB, and the thread's own counter says 36,187 MB. The sampler takes a fixed number of samples per second, so a count of samples follows time spent, not bytes. Here the += copies the whole string on every line, and the fix is a StringBuilder.


The split between methods is rougher than the total. In a worker alternating two methods, one allocating 5,287 MB in large StringBuilder arrays and one 865 MB in small strings, JFR charged the second 199 to 293 MB across five recordings. Read per-method figures as a ranking.

JFR Lock Events Name the Lock, the Waiter and the Previous Owner, Above a Threshold


Four threads post to one ledger for two seconds, each post holding its monitor for 1 ms:




1,995 posts of 1 ms in 2 s: four threads did the work of one. Together they waited about six seconds, in single waits of up to 953 ms for a lock never held longer than 1 ms, so here the monitor did not hand the lock over in arrival order. Each event names the lock's class, the thread that waited, the thread that held it before, and the line that asked.


By default JFR records a monitor wait only from 20 ms up; with -XX:StartFlightRecording:jdk.JavaMonitorEnter#threshold=0ms,... the same program recorded 36 waits instead of 15. And a ReentrantLock is not a monitor: the same ledger with one recorded no jdk.JavaMonitorEnter events, and its waits were jdk.ThreadPark events with parkedClass = java.util.concurrent.locks.ReentrantLock$NonfairSync.


Without -Xmx the Heap Is a Quarter of the Memory the JVM Sees


The JVM sizes the heap from the memory it believes the machine has. In a container that is the container's limit (UseContainerSupport is on by default). -XX:MaxRAM sets the number by hand, which is how these runs stand in for containers of each size. A script ran java <flags> -XX:+PrintFlagsFinal -version for each line and kept four flags:



With no flags in a 1 GB container the order service gets a 256 MB heap, because MaxRAMPercentage defaults to 25. Between about 250 and 500 MB the heap stays at a floor of 126 MB; below that, MinRAMPercentage (50) applies. -XX:MaxRAMPercentage=75 gives 768 MB and follows the limit when the container is resized; -Xmx overrides both. The initial heap is 1/64 of the memory, at least 8 MB, and -Xms sets it.


The collector is chosen at startup too: with one CPU the JVM picked Serial instead of G1.


MaxRAM doesn't stand in for everything. It changes the heap sizing, but not the collector choice: with -XX:MaxRAM=1g the JVM still picked G1. A container's limit does change it. We ran Java 21 under docker run --memory=... --cpus=... and read -XX:+PrintFlagsFinal:



Below about 1.8 GB, or with one CPU, the default is Serial. Name the collector yourself in a small container.


The Process Is Bigger Than the Heap


-Xmx limits the heap only. Thread stacks, class metadata, compiled code, the collector's own structures and direct buffers live outside it, and Native Memory Tracking (NMT) counts them. A gateway with a 256 MB heap, 200 waiting threads and 128 MB of ByteBuffer.allocateDirect, started with -Xms256m -Xmx256m -XX:NativeMemoryTracking=summary:



The process committed 500 MB for a 256 MB heap; the direct buffers are the 128 MB under Other. "Reserved" is address space and costs nothing. "Committed" is memory the process may touch; the kernel charges each page to the container once it is touched, so plan the limit for it. Put this gateway in a 512 MB container with MaxRAMPercentage=75: once the heap grows to 384 MB, the rest needs 244 MB more, and the kernel kills the process (OOMKilled). There is no OutOfMemoryError and no heap dump, because the JVM never ran out of heap. Size the heap as the limit minus what NMT shows for the rest.

Summary


  • GC.heap_info counts garbage as used. Live data is what a full collection leaves, and a plain GC.class_histogram forces that collection; -all doesn't.
  • A thread dump names a deadlock cycle, not every stuck thread. Follow a BLOCKED thread's address to its - locked line and read what the holder waits for.
  • A JFR allocation sample stands for all the bytes since the previous one. Sum weight, and look past the JDK's frames to your own.
  • JFR lock events name the lock, the waiter and the previous owner, for monitor waits of 20 ms or more by default; ReentrantLock waits are jdk.ThreadPark.
  • Without -Xmx the heap is 25 % of the memory the JVM sees, which in a container is its limit; MaxRAMPercentage changes the share.
  • The process is bigger than the heap. The container limit must hold the heap plus what NMT shows for stacks, code, the collector and direct buffers.

Challenges


  1. Your service's heap after each full collection grows by 30 MB a day. Which jcmd commands, run a day apart, tell you which class grows, and what does running them cost the service?
  2. A recording has no jdk.JavaMonitorEnter events, yet throughput stops growing beyond four threads. What else in the recording can tell you why, and which setting do you change first?
  3. A team runs 40 pods with -Xmx at 90 % of the limit. Using NMT on one pod, work out the limit they need, and what they gain or lose by switching to MaxRAMPercentage.


Design Note: Why the Recorder Samples


A profiler that recorded every allocation would slow the program it measures, so JFR samples: about 150 allocations a second, each weighted by the bytes it stands for, and lock waits only past a threshold. That keeps a recording cheap enough to leave running in production. The price is that every number is an estimate, and anything below the threshold or between samples is missing. A total built from weights comes close (36,153 MB against 36,187 MB above); a count of samples doesn't. jcmd makes the opposite trade: its answers are exact, but some of them, such as a plain class histogram, stop the program to get them.
