After a load test of 1,000 requests, the dashboard's request counter still shows 0. The line that counts is hits = hits++;, and two reviewers read it as "add one". javac compiled it without a warning, even with -Xlint:all.

javac produces bytecode, instructions for a stack machine. The JVM loads and verifies it (unit JVM Architecture (Class Loader, Execution Engine, Runtime Data Areas)), interprets it, and compiles hot methods to machine code (unit JIT (Just-In-Time) Compilation). javap -c prints it.

Bytecode Works on an Operand Stack, So i = i++ Stores the Old Value Back

Before reading on, predict what these three methods return for 5:

javac Increments.java && javap -c Increments shows why:

Each method call has an array of local variables (the parameter i is local 0 in a static method) and an operand stack. iload_0 pushes a copy of local 0, istore_0 pops the top into local 0, and iadd, isub and the other binary arithmetic instructions pop two values and push the result. iinc 0, 1 works differently: it adds 1 to local 0 in place and leaves the stack alone.

In post, iload_0 pushes 5, iinc makes the local 6, and istore_0 writes the 5 from the stack back over it. The JLS defines it this way: the value of i++ is the variable's value before the increment, and the assignment stores that value after the increment has happened. ++i increments first, then loads, so pre stores 6. In both, the left operand is loaded first (5), two increments make the local 7, the right operand loads 7, and isub subtracts the top of the stack from the value under it: 5 − 7 = −2.

So hits = hits++ stores the old value back on each of the 1,000 iterations, and the counter stays at 0. As a loop's update, for (...; i < n; i = i++) runs forever. Write hits++ on its own, and don't read a variable again in the expression that increments it.

invokedynamic Leaves the Choice of Code to the First Run

String concatenation (unit String concatenation) and lambdas (unit Introduction to lambda expressions) both compile to invokedynamic. This program times the first three calls of one of each:

Each method centres on one invokedynamic:

#0 and #1 index the class's BootstrapMethods table (javap -v, first two entries, descriptors replaced by ...):

The class file holds no concatenation code and no IntSupplier class. It holds a description (the recipe \u0001:\u0001, the method lambda$fixed$0) and the JDK method that builds the code. The first time an invokedynamic runs, the JVM calls that bootstrap method, which generates the code and returns a call site. The JVM links the instruction to it, and every later execution goes straight to the linked code. Each Runnable in main is linked before timed starts its clock, so the 8.6 ms of the first label call is StringConcatFactory building its code: with -Xlog:class+load, that call alone loaded 15 generated LambdaForm$MH classes.

javac can still emit the old form. With -XDstringConcat=inline (an internal javac option) or --release 8, label compiles to a StringBuilder chain:

The first concatenation is now cheap. The first fixed() call still pays for its own bootstrap, which spins one hidden class. Over five runs of each on one busy machine, the two first calls together took 8.9–15.7 ms with invokedynamic and 0.5–2.1 ms with inline. From the second call on, both were in microseconds.

The cost is paid once per call site, at startup: a service with thousands of distinct concatenations and lambdas spends part of its start in bootstraps. The code that concatenates belongs to the JDK that runs the class (see the Design Note); a class compiled for Java 8 keeps its StringBuilder chain on every JDK. The lambda body lambda$fixed$0 is a synthetic method (unit Class and Object Introspection), and the linked target is a MethodHandle (unit Dynamic Object Creation and Method Invocation).

A switch on Strings Is a hashCode lookupswitch Followed by equals

"Aa" and "BB" have the same hashCode(), 2112, and so does "C#". Which case does each reach?

Every string reached the right case. The bytecode is two switches:

The JVM can only switch on an int. javac switches on the hash first, with a lookupswitch because the hashes are sparse. Each hash leads to an equals for every label with that hash: 2112 tries "BB", then "Aa". A match stores the case's position in the source (0 for "Aa", 1 for "BB", 2 for "eu"; local 2 starts at −1), and a tableswitch on that dense index jumps to the case body. The hash only narrows the search and equals decides, which is why "C#" falls to default. The NullPointerException comes from the hashCode() call on javac's copy of the selector, <local1>. The program passes new String(r) so that no selector is the same object as a label: equals, not identity, decides.

A hand-written dispatch keyed by hashCode() alone sends "BB" to "Aa"'s handler. If you bucket by hash, compare with equals inside the bucket, as javac does.

`case null` compiles differently. A Java 21 switch on a String with a case null label compiles to invokedynamic SwitchBootstraps.typeSwitch followed by a tableswitch, with no hashCode() call in the method, and route(null) returns the case null value.

finally Is Copied Onto Every Exit, and a return There Replaces the athrow

There is no finally instruction. Unit The finally block for cleanup operations showed how finally behaves; javac builds it from copies and an exception table:

parseOrSwallow is listed from offset 13; its first lines are the same as parse's.

calls++ appears twice in parse. The normal path (0–14) saves the result in local 1, runs its copy of the finally code, and returns the saved value. The exception table sends any throwable raised between offsets 0 and 5 to offset 15, a handler of type any: it saves the exception in local 2, runs the second copy, and rethrows it with athrow. The range stops at 5, so an exception thrown by a copy of the finally code isn't caught by the same handler and doesn't run it twice.

In parseOrSwallow the handler ends with iconst_m1, ireturn. The exception sits in local 2 and no instruction reads it again. That is how a return in finally swallows an exception: javac copied the return onto the exception path, and a path that returns has no athrow.

Copying also multiplies code. Counting the audit calls in javap -c for these two methods:

status has five copies: one per return and one in the any handler. In nested, each finally is copied onto the two returns and into its own handler. A long finally in a method with many exits makes the method several times longer, and that counts against HotSpot's inlining limits (MaxInlineSize 35 bytes, FreqInlineSize 325 on this JDK; unit JIT (Just-In-Time) Compilation). Move a long cleanup into a method of its own, and each copy becomes one call.

Summary

  • Bytecode runs on an operand stack. i++ pushes the old value before iinc changes the local, so i = i++ stores the old value back, and a counter written that way never moves.
  • `invokedynamic` defers the code to its first execution. The bootstrap method (StringConcatFactory, LambdaMetafactory) runs once per call site, costing milliseconds at startup, and the JDK that runs the class, not the compiler, decides the concatenation code.
  • A `switch` on a `String` switches on `hashCode()`, then confirms with `equals`. Colliding strings still reach their own case, and a null selector throws from hashCode() unless there is a case null.
  • `finally` is copied onto every exit, and a `return` in it replaces the rethrow. The exception is stored in a local that nothing reads again, and the copies grow the method.

Design Note: Why the Bytecode Names a Bootstrap Instead of the Code

Before Java 9, javac decided how + concatenated, and every class it compiled carried that decision until it was recompiled. A better strategy in a new JDK reached no existing library. With invokedynamic, javac records only what is concatenated and leaves the how to a method in the running JDK, so a JDK upgrade changes the concatenation code of every class at once. Lambdas got the same freedom: their classes are spun at run time instead of shipped in the jar.

The cost is the one measured above: work javac used to do once at build time now happens, by default, at every start, once per call site. javap -c no longer shows everything a method does either. For a concatenation or a lambda, the code that runs exists only after the first call.
