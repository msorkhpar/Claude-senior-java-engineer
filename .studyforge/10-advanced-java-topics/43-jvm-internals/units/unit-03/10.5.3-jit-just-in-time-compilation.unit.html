After each deploy, the quote service answers its first requests several times slower than the rest. On some days latency steps up again for a moment when a tenant's fee plug-in is loaded, although no code on the hot path changed. And a microbenchmark in the same repository reports that the hash at the heart of the quote cache costs 0.01 ns per call, less than one CPU cycle.

All three come from the JIT compiler: when it compiles, what it assumes while compiling, and what it is allowed to leave out. Every output below is from Java 21 (Temurin 21.0.12) on Linux x64, on one 20-thread laptop CPU that was also running other work, so only the ratios between timings mean anything.

A Method Starts in the Interpreter and Is Compiled in Tiers Once Its Counters Say It Is Hot

The JVM first runs a method's bytecode (unit Bytecode Execution and Interpretation) in the interpreter, which counts the method's calls and its loop iterations. When those counts cross a threshold, it queues the method for compilation on a background thread and keeps interpreting until the machine code is ready. This program calls score ten million times per round, for five rounds:

java -XX:+PrintCompilation Warmup, trimmed to this class's methods:

The columns are milliseconds since the JVM started, a compile id, attributes and the tier. Tiers 1 to 3 are C1, the fast compiler; tier 4 is C2, the optimising one. score went from the interpreter to tier 3, which is C1 code that keeps counting and records which branches and types it sees, then to tier 4, which C2 compiled from that profile. The getter factor() went straight to tier 1, plain C1 code without profiling: HotSpot treats a method that only returns a field as trivial. Tier 2, C1 with counters only, stands in for tier 3 when C2 falls behind. It never showed up for this class in ten runs; with a single C2 thread (-XX:CICompilerCount=2), it did for some of the JDK's own methods, such as StringUTF16::getChar.

"made not entrant" does not mean something failed. Compile 7, the tier-3 score, was made not entrant a millisecond after compile 8 installed tier 4: new calls stop entering the old code and go to the new one. The log prints the same words when compiled code is thrown away because an assumption broke. What tells them apart is whether a newer compile of the same method was already taking calls, as compile 8 was here.

round is called only five times, but its loop runs ten million times inside the first call. A % line is an on-stack replacement (OSR) compile: machine code for the loop starting at bytecode 4, which the running call jumps into mid-loop. Without it, round 1's loop would stay interpreted to the end.

Until the Compiled Code Is Installed, the Same Loop Runs Tens of Times Slower

The same program with the JIT off (-Xint), with C1 only (-XX:TieredStopAtLevel=1), and with the defaults, three JVMs each (the script joins each JVM's five lines into one):

Interpreted, a round takes about 185 ms. C2's code takes 3.3 to 4.8 ms, 38 to 56 times less, and C1's 6.3 ms. A request path that runs a few thousand methods pays the interpreter's price on each of them until each one crosses its threshold. That is the slow start after a deploy, and why services send warm-up traffic before taking real traffic.

Round 2 of the default runs is no faster than round 1, and slower in two of three. In the log, compile 11, C2's loop code, was made not entrant at 24 ms, when round 1 left its loop. -Xlog:deoptimization=debug names the reason (from another JVM, so the time differs):

Bytecode 7 is the loop's exit test. In every iteration profiled before C2 compiled the loop, the test had failed, so C2 compiled no code for leaving the loop, only a trap back to the interpreter. Round 2 started in the tier-3 code (compile 10), got a new loop compile (130) at 46 ms, and the tier-4 round that new calls enter (compile 131) arrived only at 49 ms.

Compiled Code Rests on Assumptions, and a Class Loaded Later Can Make It Not Entrant

C2 compiles for the program it has seen so far. When Fee.apply has one implementation among the loaded classes, C2 calls it directly and inlines it, and records a dependency: if a class that overrides apply is loaded, this code is wrong. A Benchmark Measures Nothing When the JIT Can Drop the Work or Fold Its Input

The hash from the opening, and three loops that time it:

Each loop runs in its own JVM, for ten rounds of ten million calls, and prints the median of rounds 6 to 10. The returned sums are added up and printed. Before reading on: which of the three costs what mix costs?

Only consumed. The interpreter does all the work in all three loops, at about 18 ns per call. C2 inlined mix into each loop. In discarded nothing used its result, so it deleted the computation and then the empty loop (unit Reflection Performance Considerations shows the same for a reflective call). constantInput uses every result, and still costs nothing: mix(42) has the same value on every iteration, so C2 folded it to a constant while compiling. A related freedom lets the JIT read a plain field once outside a spin loop (unit Volatile keyword).

A measurement can be trusted only when the JIT can't predict the work: every result reaches something it can't see through (the returned sum, printed at the end), and every input varies the way production inputs do. JMH, the OpenJDK project's benchmark harness, consumes results and runs fresh JVMs and warm-up rounds for you, but the inputs are still yours to choose. It wasn't available for this page, so the loops do it by hand. When a number looks too good, -Xint shows how much work there was.

Summary

  • A method starts interpreted and is compiled in tiers once its counters say it is hot. Tier 3 profiles, tier 4 is C2's code built from that profile, and "made not entrant" on a lower tier is usually a replacement.
  • Until compiled code is installed, the same loop runs 38 to 56 times slower here. Warm-up is slow for each method separately, and an OSR compile thrown away at a loop's exit can make the second round slower than the first.
  • Compiled code rests on assumptions about the loaded classes and the types seen. Loading a subclass that overrides a method, or calling with a new class, makes the code not entrant and costs a step in latency until C2 compiles again.
  • A benchmark measures nothing when the JIT can drop the work or fold its input. Consume every result, vary the input, and compare with -Xint when a number looks too good.

Challenges

  1. Your service takes traffic 10 seconds after start. Using -XX:+PrintCompilation, how would you find out whether its hot paths reach tier 4 before then, and what would you send as warm-up traffic?
  2. A rules engine loads tenants' rule classes on demand under traffic. Run LateClass with ten subclasses loaded one per round. Does every load cost a step, or only the first?
  3. Write a benchmark for String.hashCode on strings of varying length. What does the JDK's caching of a string's hash do to your measurement, and how do you keep it honest?

Design Note: Why HotSpot Compiles for the Program It Has Seen

C2 compiles a method for the classes loaded and the types seen so far, instead of for every program that could still happen. That lets it call one implementation directly, inline it, leave out the code for a branch that was never taken, and compute a value once that never changed. A compiler that had to be right for every future class could inline a virtual call only behind a type check on every call, and would compile every branch the profile never saw.

The price is that compiled code can become wrong, so the JVM keeps the means to throw it away: dependencies on the class hierarchy, traps where it guessed, and the interpreter to fall back to. Performance then depends on history: the same method is fast or slow depending on what ran before it.

Problem statement


The search service's latency jumps for a few seconds several times a day, and the team now runs it with -XX:+PrintCompilation. Each jump comes with a burst of made not entrant lines, and nobody can tell by eye which of them matter. The on-call engineer wants a small tool that, for one method, answers two questions from the log alone.


CompileLog already reads the log: it skips every line that isn't a compile line and turns the rest into Line records, in log order. Finish the two TODOs in src/main/java/practice/CompileLog.java:


  • currentTier(method): the tier of the code that a call to the method made now would enter, or 0 for the interpreter;
  • deoptimizations(method): how many times the JIT threw away the method's code because it could no longer be used. The method's ordinary progress through the tiers is not an incident and doesn't count.


Both answers are about the code that calls enter. About fifteen lines in total.


The tests feed logs of other services' methods, with other ids and timestamps.

Problem statement


The team settles performance arguments with MicroBench, a small helper of its own, because JMH isn't on the build's class path. Last week it reported that the new coupon check costs 0.02 ns per call, and that the old one, which nobody had touched, had become three times slower after someone raised the number of warm-up rounds. Nobody believes either number.


Write measure(...) in src/main/java/practice/MicroBench.java. It gets the work, the inputs to call it with, and the number of warm-up rounds; it runs the work over every input in each warm-up round and then in one timed round. The report it returns gives:


  • nanosPerCall: the time per call of the timed round;
  • checksum: the sum of every value the work returned.


When you're done, the numbers describe the work as it would run in production, whatever the JIT is allowed to do with the loop. About seven lines.


The tests pass a clock of their own, so no test depends on how fast the machine is.
