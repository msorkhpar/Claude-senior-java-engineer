# 10.6.3. Cryptography and Encryption in Java

A review of a customer-records service lists four findings. A column is encrypted with
`Cipher.getInstance("AES")`. A migration job drew one random IV at start-up and used it for every
row. The password table holds plain SHA-256 digests, and many rows share a digest. The webhook
verifier compares tags with `Arrays.equals`. All four passed their tests: each decrypts what it
encrypted or matches what it stored.

The first section sets up the fix the findings are measured against, AES-GCM; each later section
takes one finding. Everything runs on the JCA API and the JDK's own providers, no library. Where
keys and tokens come from and why secrets travel as `char[]` is unit 10.6.1; injection, path
traversal and deserialization are unit 10.6.2. Every key on this page is generated by the run that
uses it, and every output is from Java 21.

## AES-GCM Refuses a Changed Ciphertext; Encryption Without a Tag Doesn't

`AES/GCM/NoPadding` takes a key and an IV (12 bytes is the recommended length), and returns the ciphertext with a 16-byte
authentication tag after it. The IV isn't secret, but decryption needs it, so we store it in front:

```java
static final SecureRandom RANDOM = new SecureRandom();

/** Returns IV (12 bytes) + ciphertext + tag (16 bytes). */
static byte[] seal(SecretKey key, byte[] plaintext) throws Exception {
    byte[] iv = new byte[12];
    RANDOM.nextBytes(iv);                                   // a fresh IV for every message
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    byte[] sealed = cipher.doFinal(plaintext);              // ciphertext + 16-byte tag
    byte[] box = Arrays.copyOf(iv, 12 + sealed.length);     // the IV travels in front
    System.arraycopy(sealed, 0, box, 12, sealed.length);
    return box;
}

static byte[] open(SecretKey key, byte[] box) throws Exception {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(128, box, 0, 12));
    return cipher.doFinal(box, 12, box.length - 12);        // checks the tag before returning
}
```

The key comes from `KeyGenerator.getInstance("AES")` with `init(256)`. We seal
`transfer 100 to acct-0042` twice, open the first box, then flip one bit of the ciphertext's byte 9
(box byte 21, the `1` of `100`) and open it again. The last line makes the same flip under `AES/CTR/NoPadding`, which
is GCM's encryption without the tag:

```text
plaintext bytes: 25, box bytes: 53
box 1 IV: d06aae8500e30550200be4b5
box 2 IV: 37803c84d050aa44b4842a34
same message, same box: false
open(box 1): transfer 100 to acct-0042
open(tampered): javax.crypto.AEADBadTagException: Tag mismatch
CTR, same flip: transfer 000 to acct-0042
```

12 bytes of IV, 25 of ciphertext, 16 of tag. Sealing the same message twice gives different boxes
because the IV differs.

The CTR line shows why the tag matters. CTR, and GCM underneath, encrypt by XOR-ing the text with
a keystream, so flipping a ciphertext bit flips the same bit of the plaintext. Whoever knows the
message layout can change `100` to `000` without the key, and the receiver decrypts a clean,
wrong transfer. GCM computes the tag from the key, the IV, the ciphertext and any associated data
passed to `updateAAD`. Decryption recomputes it and throws `AEADBadTagException` if any of them
changed, a box opened with a different key included.

Decrypting the tampered box in parts, SunJCE's `cipher.update(...)` returned 0 bytes; the plaintext comes only from `doFinal`, after the tag
matched. Code that catches `AEADBadTagException` and carries on with a default value undoes all
of this: treat it as an attack or a corrupt record, never as an empty one.

## A GCM IV Used Twice Under One Key Gives Away the XOR of the Two Plaintexts

The migration job drew its IV from `SecureRandom`, once, and sealed every row with it. Two rows,
the same key, the same IV, a new `Cipher` for each:

```java
static byte[] encrypt(SecretKey key, byte[] iv, String text) throws Exception {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");   // a new Cipher each call
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    return cipher.doFinal(text.getBytes(StandardCharsets.UTF_8));
}
```

```java
String p1 = "salary=4200;name=Jane Doe";
String p2 = "salary=9100;name=John Roe";
byte[] c1 = encrypt(key, iv, p1);
byte[] c2 = encrypt(key, iv, p2);
```

The program XORs the first 25 bytes of each, the ciphertext without the tag:

```text
c1 xor c2: 000000000000000d030000000000000000000e060b00160000
p1 xor p2: 000000000000000d030000000000000000000e060b00160000
equal: true
with a fresh IV for p2, equal: false
```

The keystream depends only on the key and the IV, so the same pair gives the same keystream, and
XOR-ing the two ciphertexts cancels it. What remains is the XOR of the plaintexts, computed without
the key: `00` wherever the rows agree (`salary=`, `00;name=J`, `oe`), and the difference
everywhere else. Anyone who knows one row can XOR it back in and read the other. The AES key stays hidden,
but the `Cipher` javadoc adds that repeated GCM IVs are "subject to forgery attacks": the tag
stops protecting either message. What matters is that an IV is never repeated under the key.

SunJCE checks for a repeat only within one `Cipher` object. The first line below is a `Cipher`
initialised with no IV at all:

```text
provider-chosen IV length: 12
same Cipher, same key and IV again: java.security.InvalidAlgorithmParameterException: Cannot reuse iv for GCM encryption
new Cipher, same key and IV: accepted
```

SunJCE remembers the last key and IV a `Cipher` encrypted with and refuses them again. A new
`Cipher` remembers nothing, and the migration job made one per row. Use a new random 12-byte IV per
encryption, as `seal` does, or pass no IV and read the provider's with `getIV()`. Random 96-bit IVs make a repeat unlikely,
not impossible, so a key that encrypts a very large number of messages still needs rotating.

## Cipher.getInstance("AES") Is ECB, and ECB Encrypts Equal Blocks to Equal Blocks

The first finding named no mode. Three 16-byte records, the first and the third equal, encrypted
with ECB, with plain `"AES"`, and with GCM, all under one generated key:

```java
String records = "status=REJECTED;" + "status=APPROVED;" + "status=REJECTED;";
```

```text
AES/ECB/PKCS5Padding:
  block 0: 645d4a3ec757449ff4f7e465f82372ff
  block 1: c803c6ff6cf8744433fc9316ac058b38
  block 2: 645d4a3ec757449ff4f7e465f82372ff
"AES" (no mode named):
  block 0: 645d4a3ec757449ff4f7e465f82372ff
  block 1: c803c6ff6cf8744433fc9316ac058b38
  block 2: 645d4a3ec757449ff4f7e465f82372ff
  getIV(): null
AES/GCM/NoPadding:
  block 0: 7fd15093d9b022be8f657954a59bc18b
  block 1: 58b7e5edbcf5c722bd4b2e7406fb6a3e
  block 2: ddc68f25fb368dbeb9640ff12b218882
```

ECB encrypts each 16-byte block independently under the key, so block 2 equals block 0. A reader
without the key sees which records are equal, and once one record's meaning is known (one
rejection, say), every copy of it is readable. Plain `"AES"` gave the same bytes: the `Cipher`
javadoc leaves mode and padding to the provider when the transformation names none, and SunJCE
picks ECB with PKCS5 padding, with no IV and no tag. GCM XORs each block with a keystream block
derived from the key, the IV and a counter, so equal plaintext blocks meet different keystream
blocks and the repeat is gone.

Always name all three parts of the transformation, `AES/GCM/NoPadding`. The `Cipher` javadoc
requires every Java platform to support it with a 128-bit key; JDK 21 also took the 256-bit keys
used here.

## A Password Hash Needs a Salt per User and a Slow Function: PBKDF2, Not SHA-256

SHA-256 is one-way, which is why the password table used it. Two users who chose the same
password, under SHA-256 and under PBKDF2 with a random 16-byte salt each:

```java
static byte[] pbkdf2(char[] password, byte[] salt, int iterations) throws Exception {
    PBEKeySpec spec = new PBEKeySpec(password, salt, iterations, 256);   // 256-bit output
    try {
        return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
    } finally {
        spec.clearPassword();                                            // the spec keeps its own copy
    }
}
```

```text
SHA-256, alice: b3b91917af45ed005a70a09232ce0aa2...
SHA-256, bob:   b3b91917af45ed005a70a09232ce0aa2...
PBKDF2, alice:  a605eca6095a5fb3fd9ced9b01ad64c4...  salt cba0d898360f482e7f779b0e544c6b4d
PBKDF2, bob:    a8172371fa93ee8a41993e3e59cae74b...  salt a34146a04354806b3673b150bf8c9db8
verify alice: true
verify alice, wrong password: false
```

An attacker with the table doesn't reverse a digest: they hash guesses and look each result up.
Without a salt, one guess is checked against every row at once, rows with the same digest have the
same password, and a table of digests of common passwords computed years ago still works. A salt
per user makes equal passwords look different, so no precomputed table matches, and forces a
separate search per user. The salt is
not secret; it's stored beside the hash, and `verify` recomputes with it and compares.

A salt doesn't make a single guess any slower. The iteration count does: for a 256-bit output,
PBKDF2 runs HMAC-SHA256 that many times. Time per hash in this program, single thread, after a
warm-up, on one machine (the SHA-256 loop includes `getInstance` and string building). The table is
the first of three runs:

```text
SHA-256:                        0.34 us per hash
PBKDF2,  10,000 iterations:       1.93 ms per hash (5,719x SHA-256)
PBKDF2, 600,000 iterations:     112.17 ms per hash (332,787x SHA-256)
```

The other two runs gave 0.22–0.36 µs, 1.70–2.28 ms and 99.8–111.8 ms (`us` above is µs). The
cost grows in proportion to the count, for the attacker's guesses and for your login alike, so
choose the highest count your login latency allows, measured on your servers. Store the count with
each hash: when you raise it, old hashes must still verify with the count they were made with, and
are re-hashed at the next successful login. `clearPassword()` wipes only the spec's clone; the
caller still clears its own `char[]` (unit 10.6.1 shows what a wiped array buys).

> **Other functions.** bcrypt, scrypt and Argon2 are designed for the same job, and scrypt and
> Argon2 also make each guess cost memory. The JDK 21 providers ship none of them, only PBKDF2
> with HMAC-SHA1 and the SHA-2 family.

## Compare Tags and Hashes with MessageDigest.isEqual; Arrays.equals Stops at the First Difference

The webhook verifier recomputes the HMAC-SHA256 tag of the body and compares it with the one the
caller sent. Both comparisons, on six received tags:

```text
received tag     Arrays.equals  MessageDigest.isEqual
the same tag     true           true
byte 0 differs   false          false
byte 31 differs  false          false
first 16 bytes   false          false
empty            false          false
null             false          false
```

The answers match; the difference is the running time. The implementation note in the
`MessageDigest.isEqual` javadoc says: "All bytes in `digesta` are examined to determine equality.
The calculation time depends only on the length of `digesta`. It does not depend on the length
of `digestb` or the contents of `digesta` and `digestb`." The `Arrays.equals` javadoc makes no
promise about time. Its JDK 21 source returns as soon as the lengths differ or a difference is
found: `ArraysSupport.mismatch` checks byte 0 on its own, then compares the rest in chunks of 8
bytes or more.

A comparison whose time depends on where the first difference is tells a caller how much of a
forged tag is right. With enough requests and averaging, a byte-by-byte loop leaks a tag one byte
at a time; the JDK 21 `Arrays.equals` leaks byte 0 and then whole chunks, and a later JDK may
compare differently. Whether network noise hides the difference depends on the deployment;
`isEqual` removes it. `String.equals` makes no time promise either, so for hex or Base64 tags
compare the decoded bytes with `isEqual`, and pass the value you computed as `digesta`, so the time
depends on your tag's length and not the caller's.

## Summary

- **AES-GCM refuses a changed ciphertext.** One flipped bit gave `AEADBadTagException`; the same
  flip under CTR turned `100` into `000` with no error. Store the 12-byte IV in front of the box.
- **A GCM IV used twice under one key gives away the XOR of the plaintexts**, and lets tags be
  forged. The JDK refuses a repeat only on the same `Cipher` object; draw a new IV per encryption.
- **`Cipher.getInstance("AES")` is ECB**, and ECB showed equal records as equal ciphertext
  blocks. Name the mode: `AES/GCM/NoPadding`.
- **Passwords need a salt per user and a slow function.** Unsalted SHA-256 gave two users the
  same digest at a fraction of a microsecond per guess; PBKDF2 at 600,000 iterations took 100 to
  112 ms per hash. Store salt and count with each hash.
- **Compare tags with `MessageDigest.isEqual`.** It gives the same answers as `Arrays.equals`, but
  its time doesn't depend on where the bytes differ.

## Challenges

1. Your service encrypts 50,000 messages a second under one key with random 12-byte IVs. When
   should the key rotate, and what has to be stored with each message so old ones still decrypt?
2. A record's ciphertext is stored with its customer id beside it. An attacker with write access
   swaps the ciphertexts of two customers; both decrypt fine. Which `Cipher` call binds a
   ciphertext to its row, and what does decryption need afterwards?
3. Measure PBKDF2 at three iteration counts on the machine that serves logins. What count keeps a
   login under 250 ms at your peak login rate, and how many cores does that take?

## Design Note: Store the Parameters with the Ciphertext

Every fix on this page writes more next to the secret data: the IV in front of the ciphertext,
the tag behind it, the salt and the iteration count beside the password hash. None of them is
secret, and leaving any of them out either breaks decryption or leaves no clean way to change the
choice later. A column format with no room for an IV per row invites one shared IV; a password
table without a count column has to guess which count each old hash was made with before it can
raise the count.

That means versioning the stored format. A stored value that starts with a version byte, or a hash stored
as `algorithm:iterations:salt:hash`, can move to a new algorithm or a higher count one record at a
time, as each is read or as each user logs in. Without it, every change is a migration of all the
data at once, under a key or a count you already know is too weak.
